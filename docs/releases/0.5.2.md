## ハイライト

kairo 0.5.2 は、止まったプロセスからの立ち直りと、ディスクの故障への備えを強くします。

- 上限で待っていた実の作用のステップは、プロセスが落ちても「要確認」にならず、別のプロセスで送り直されます。
- いなくなったと確かめられたプロセスの仕事は、借用の期限（既定 30 秒）を待たずに引き継ぎます。
- 関数が決定的でなくリプレイが記録から外れたときは、外への作用を起こす前に止めます。
- kairod は、実行とプランを SQL のデータベースに保存できます。複製はデータベースに任せるので、ディスクが 1 つ壊れても確定した実行を失わない構成を取れます。
- ワークフローの経過（何を呼び、何回試行し、どう終わり、途中でプロセスが止まったか）を記録から読めるようになり、ブラウザで見るビューアを足しました。

### 止まったときの立ち直り

- **上限で待っていたステップを要確認にしない（ADR 0085、#114）：** 実の作用のステップの意図を、上限と受け入れ（埋め込みの同時実行・アクション・宛先の上限、kairod のテナントの順番・RPM/TPM・ワーカーのクレジット）を通ってから記録するようにしました。待っているだけのステップには意図がないので、プロセスが落ちても、別のプロセスでそのまま送り直されます。要確認になるのは、実際に実行器へ渡したステップだけです。デモで、kill 1 回で 18〜20 件が要確認になっていた（実際に動いていたのは 2 件）問題です。すぐに通れるステップは、今までどおり 1 回の書き込みで済みます。
- **いなくなったプロセスの仕事を早く引き継ぐ（ADR 0086、#105）：** 埋め込みのランタイムのプロセスは、終わると外れる「生きている印」を持ちます。SQLite のファイルでは、データベースの横の OS のロック、PostgreSQL では、セッション単位の勧告ロックです。ほかのプロセスは、その印が外れたと確かめられたら、借用の期限を待たずに仕事を引き継ぎます。確かめる周期は `ownerCheckMs` / `owner_check_ms` / `OwnerCheck` で、既定は借用の長さの 6 分の 1 です。自分の印を失ったプロセスは止まります。
- **閉じるときに固まらない（#116）：** TS で、引き継いだワークフローが要確認の呼び出しを待っているあいだに `close()` を呼ぶと、返らないことがありました。閉じる途中で、新しい駆動を始めてしまっていたためです。

### 決定的でないワークフローを止める（ADR 0084、#106）

コードで書くワークフローの関数が決定的でなく、リプレイのときに記録にない作用のある呼び出し（非保護でないアクション、子のワークフロー）を作ろうとしたら、その前に止めます。記録された作用のある呼び出しにまだ届いていないかを確かめます。Go は `Parallel` の枝ごとに、TS と Python は関数がそれ以上進めなくなった時点で判定します。外れていたら、何も作らず、`ErrDiverged` / `DivergedError` で知らせ、`run.stuck` を出します。ワークフローは失敗にせず、コードを直して配り直せば、そのまま続きます。

### kairod の SQL の保存先（ADR 0087、#109）

配布している `kairod` は、環境変数 `KAIRO_STORE`（`postgres://`、`mysql:`、`tidb:`、`oracle://`、`sqlite:`）を指定すると、耐久性のあるティアのログ・スナップショット・ブロブと、登録したプランとノードの定義を、そのデータベースに保存します。シャード数も一緒に保存します。同期の複製を持つデータベースを使えば、ディスクが 1 つ壊れても確定した実行を失いません。構成と、守られること・守られないことは `docs/kairod-store.md` にあります。

### ワークフローの経過を見る（ADR 0088）

- **経過の読み取り：** Go・TypeScript・Python の SDK に `progress(id)`（Go は `Progress(ctx, id)`）を足しました。ワークフローの木（呼び出し、待ち、子のワークフロー）と、各実行に記録されたイベント（開始、試行の成功・失敗、タイマー、シグナル、決着、取り消しなど）を返します。失敗した試行の種類が `process_lost` なら、実行していたプロセスが止まって中断したものです。記録にないことは推定せず、読んでも状態は変わりません。埋め込みのランタイムの SQLite と PostgreSQL で使えます。
- **ビューア：** TypeScript の SDK に `kairo-view` を同梱しました。`npx kairo-view .kairo/app.db`（PostgreSQL は `--postgres <URL>`）で、データベースのワークフローを、呼び出しと試行を時刻の上に並べて表示します。開いている間は表示が更新されます。画面から、シグナルの送信、要確認の呼び出しの決着、ワークフローの取り消しができます。自分のプロセスの中からは `serveViewer(k)` で開けます。
  - ループバックだけで待ち受け、起動ごとに作る鍵のない要求は受け付けません。表示される URL を知っている人は、実行の入力と結果を読み、操作できます。共有したり、ポートを外に出したりしないでください。
  - コマンドで起動したビューアは、アクションの定義を持ちません。そのため、未完了の呼び出しが残っているワークフローの取り消しと、呼び出しの決着は断ります（409）。これらは、ワークフローを動かしているプロセスの中から `serveViewer` で開いて行います。
  - 別のプロセスからの取り消しは、ビューアに限らず、ワークフローが「取り消し」でなく「失敗」で終わることがあります（#128）。

### SDK

- **TypeScript：** WASM のコアを、`node:wasi` を使わずに動かすようにしました。読み込むたびに出ていた `ExperimentalWarning` が出なくなります（#108）。
- **Python：** WASM のコアのコンパイル結果を、同じプロセスの中で使い回し、キャッシュのディレクトリにも保存します。新しいプロセスで `Core` を開く時間が、手元の計測で約 370ms から約 50ms になりました（#107）。

## アップグレードのときの注意

- **ADR 0084：** 版を上げずに関数を書き換え、作用のある呼び出しの前に別の作用のある呼び出しを足すと、走っている実行は `run.stuck` で止まるようになります。これまでは、別の呼び出しとして動いていました。関数を書き換えるときは、版を分けてください（ADR 0060）。
- **ADR 0086：**
  - SQLite のファイルを使うプロセスは、データベースの横に `<データベース>.owners/` というディレクトリを作り、プロセスごとのロックのファイルを置きます。
  - PostgreSQL を使うプロセスは、接続のプールから 1 本を、印のために持ち続けます。
  - 0.5.1 以前のプロセスは印を持たないので、混ざって動いているあいだ、それらの仕事はこれまでどおり借用の期限で引き継ぎます。
- **ADR 0087：**
  - 配布する `kairod` のバイナリは、`store/kairod` から作るようになりました。データベースのドライバを含む分だけ大きくなります。
  - ソースから `go build ./cmd/kairod` で作る kairod は、今までどおりファイルだけに書きます。
  - kairod の本体は、パッケージ `github.com/r-hashi01/kairo/kairod` に移りました。
- **Python：** キャッシュは `KAIRO_WASM_CACHE` で置き場所を決めます。既定は `$XDG_CACHE_HOME/kairo-sdk`（なければ `~/.cache/kairo-sdk`）で、`off` にすると使いません。サーバーレスの関数では、関数と一緒に配るディレクトリを指定し、ビルドのときに埋めておくと、コールドスタートでもコンパイルが要りません（`docs/serverless.md`）。

ADR 0085 と #116 の修正は、振る舞いを直すもので、設定の変更は要りません。
