## ハイライト

kairo 0.5.0 は、障害や rolling upgrade をまたぐ code workflow の回復を強化し、
embedded runtime と kairod-backed SDK の API を近づけ、admission・制限・運用計測を
拡充します。v0.4.1 後の repository 全体 review で見つかった correctness、durability、
trust boundary の問題も修正しています。

### Workflow の寿命と回復

- workflow の完了と取消は、最初に耐久化された settlement を採用します。live と再起動後で
  同じ結果を返します。
- child workflow は parent tree に属します。未到達の child は単独で再開せず、未完了の
  descendant は parent より先に settle し、外から始める workflow も未完了の parent へ
  原子的に attach できます。
- 一時的な Store failure は workflow を恒久的な失敗にせず、現在の drive を止めて同じ
  recovery path から再開します。
- embedded workflow の終了済み tree は、設定した期間の idempotency と child result を
  保ちながら bounded retention されます。
- embedded の TypeScript・Python SDK でも、結果不明で `blocked` になった real call は、Go と
  同じく review を待ちます。wait mode では決着まで待ち、suspend mode では `Suspended` を
  返します。`resolve` / `resolveFailed` で決着すると workflow が続きます。
- 取消の途中に始まった workflow replay は、その取消に従います。取消より先に完了や失敗を
  記録しません（Go、TypeScript、Python SDK）。
- TypeScript の wait mode の `run()` / `result()` は、止まった process が drive lease を持つ
  workflow を待つ間 process を保ち、lease の期限後の sweep で再開します。`close` を呼ばない
  script も、何も待っていなければ従来どおり終了できます。

### kairod-backed code workflow

- Go、TypeScript、Python SDK は、未確認の start を同じ RunID で再試行し、取消と deadline を
  揃え、rolling upgrade のための graceful worker drain を capability negotiation します。
- `Resolve`、`Children`、`List`、parent tree、suspend mode の workflow drive を kairod 経由で
  利用できます。
- signal-ahead は、logical signal ID と only-if-waiting を持つ耐久・原子的な receipt として、
  process をまたいで扱われます。
- 非同期 HTTP action の callback と attempt ごとの expiry を kairod が所有できます。SDK 側に
  callback endpoint を常駐させる必要はありません。
- `Children` と `List` は millisecond 内に複数の実行を作っても、RunID ではなく保存先が
  割り当てた作成順で安定して返します。旧記録は従来の順序を保つ legacy group になります。

### Admission、制限、運用

- durable start admission は、storage pressure に合わせて bounded・tenant-fair に調整されます。
- call は runtime destination を選べます。request、実 weight、weight-per-minute、provider の
  `Retry-After` を含む制限を利用でき、embedded process 間でも Store を通じて共有できます。
- start confirmation、workflow claim、WAL latency、blocked work、worker disconnect、graceful
  drain を、耐久化しない bounded metrics として出力できます。
- SQLite-backed process は、SQLite を正本のまま保ち、bounded・best-effort な local
  notification で peer を起こせます。
- process-level の workflow claim scan を実測し、現状では専用 index を増やさず現在の設計を
  維持する判断材料を記録しました。

### Correctness、durability、trust boundary

- shared destination の task は自分の action にだけ配送され、worker credit は protocol 境界で
  検証・上限化されます。
- daemon-owned callback の retry idempotency は終了 marker に残り、再起動後も保たれます。
  取消済み `Engine.Wait` の登録も直ちに除去されます。
- malformed worker message と serialize できない result は session を決定的に失敗させ、
  CSPRNG failure は握りつぶさず呼び出し元へ返します。
- WAL、blob、snapshot の directory durability failure を伝播し、plan/node registry は原子的な
  catalog として crash-safe・collision-free に保存されます。
- file store の初期化（各 directory と `SHARDS`）を crash-durable にしました。
- `Engine.Wait` は、blob を参照する出力を inline している途中の run について、参照ではなく
  inline 済みの出力を返します。その直後に削除される blob への参照を渡しません。
- `engine.New` は初期化が途中で失敗したとき、開いた sink を閉じます。ある tier の sink が
  一部の shard でしか用意できない場合、その tier はどの shard でも使いません。
- TypeScript の `SQLiteStore` は、他の process が持つ write lock を最大 5 秒待ちます（Go・
  Python と同じ）。待たずに `database is locked` で失敗しません。
- kairod の control API は、上限を超える request body を JSON の解析前に 413 で拒否します
  （共通の JSON 32 MiB、node 登録 1 MiB、signal と workflow finish 8 MiB）。
- Go SDK の非同期 HTTP action は、宣言した timeout と shutdown に従って止まり、callback の
  配送も残りの期限（最大 60 秒）に限られます。
- worker の既定 listener は owner-only の Unix socket です。TCP listener は token を要求し、
  明示した development option の場合だけ unauthenticated TCP を許します。
- SDK の action/callback body と built-in HTTP executor の成功 response・retained SSE output は、
  既定 16 MiB、設定可能範囲 1 byte〜512 MiB に制限されます。超過や途中切断を成功として
  扱いません。
- shutdown と listener lifecycle を concurrent call に対して安全にし、通常の CI で各 SDK の
  compile・package を検証します。

### SDK diagnostics

- embedded Go、TypeScript、Python SDK は、action を実行せず、wait を進めず、耐久状態を
  変更せずに、保存済み terminal call record から code workflow を replay できます。
- record-only replay は到達した call trace を返し、missing、unfinished、blocked、trimmed の
  call で止まります。parent replay では child workflow を1つの recorded call として扱います。

## Upgrade notes

- Go build は Go 1.27.4 を使います。
- worker を TCP で接続する配備は、kairod と全 worker に同じ `KAIRO_WORKER_TOKEN` を設定して
  ください。認証なし TCP を続けるには development 用の明示 option が必要です。
- action/callback/HTTP response の既定上限は 16 MiB です。既存配備がそれより大きい payload を
  必要とする場合は、各 runtime の option で 512 MiB 以下の値を明示してください。
- embedded SQL Store は `created_order` column と prefix ごとの counter table を自動追加します。
  rolling upgrade 中に旧 SDK が書いた実行は legacy group になります。正確な新しい作成順を
  全 writer に適用するには、同じ database を書く SDK をすべて 0.5.0 へ更新してください。
- kairod は data directory に作成序数の予約値を保存します。data directory は従来どおり全体を
  1つの単位として backup・restore してください。
- 新しい worker/HTTP capability は negotiation され、kairod が acknowledge するまで SDK は
  optional capability を使いません。
- record-only replay は、tree が保持されている embedded code workflow が対象です。kairod と
  graph run には適用しません。
- embedded の TypeScript・Python workflow で、`ctx.call` が投げる `blocked` の `CallError` を
  捕捉していたコードは、それを受け取らなくなります。real call が `blocked` になると、
  workflow はその場で review を待つ（suspend mode では suspend する）ので、`resolve` /
  `resolveFailed` で決着させてください。kairod 経由の動きは変わりません。
- `Config.Sinks` で sink を用意する Go の埋め込み利用は、ある tier の sink を全 shard で
  用意するか、どの shard でも用意しないかのどちらかにしてください。一部の shard だけで
  用意した tier は使われません。
- release preparation PR は tag や package を作りません。公開時は ADR 0057 に従い、nested Go
  module tag を先に push し、`v0.5.0` を最後に単独で push します。
