# kairod の保存先を SQL のデータベースにする（ディスクの故障に耐える構成）

kairod は、既定ではデータディレクトリ（`-data`）のファイルに書きます。ファイルには複製がないので、そのディスクが壊れると、確定した実行も失われます。

配布している `kairod`（`store/kairod` から作るもの）は、環境変数 `KAIRO_STORE` を指定すると、耐久性のあるティアのログ・スナップショット・ブロブと、登録したプランとノードの定義を、SQL のデータベースに保存します。複製は、そのデータベースの複製に任せます（ADR 0087）。kairo は、自前の複製を持ちません。

## 使い方

```sh
KAIRO_STORE='postgres://kairo:...@db.internal/kairo?sslmode=verify-full' \
  kairod -data ./kairo-data -tier file
```

- `KAIRO_STORE` の書き出しで、データベースの種類を選びます。

  | 書き出し | データベース | 続き |
  |---|---|---|
  | `postgres://`、`postgresql://` | PostgreSQL | pgx の DSN |
  | `mysql:` | MySQL | go-sql-driver の DSN |
  | `tidb:` | TiDB | go-sql-driver の DSN |
  | `oracle://` | Oracle | go-ora の URL |
  | `sqlite:` | SQLite | ファイルのパス（複製はない。試すとき用） |

- DSN は、コマンドの引数ではなく環境変数で渡します。資格情報が、ほかの利用者から見えるプロセスの一覧に出ないようにするためです。エラーにも DSN は出しません。
- 接続は、検証付きの TLS だけを受け付けます（ADR 0020）。試すときだけ、`-store-allow-insecure` で外せます。
- `-store-namespace`（既定 `kairod`）で、1 つのデータベースに複数の kairod のデータを分けて置けます。
- データディレクトリは、これまでどおり要ります。ワーカーのソケットなどを置きます。ただし、実行とプランはデータベースから読むので、別のマシンで新しいデータディレクトリから始めても、実行を引き継げます。
- シャード数は、データベースに一緒に保存します。最初の kairod の数を、あとの kairod も使います。`-shards` で違う数を指定すると、起動を止めます（実行はハッシュでシャードに割り当てるので、数が変わると実行を見失うため）。
- ファイルだけに書く `cmd/kairod` は、`KAIRO_STORE` を受け付けません。

## 何が守られるか

ティア `file` の実行が「確定」するのは、データベースのコミットが返ったときです。

- **同期の複製**（例：PostgreSQL のストリーミングレプリケーションで `synchronous_commit` を `on` 以上にし、`synchronous_standby_names` を設定する）：コミットは、スタンバイが受け取ってから返ります。主のディスクが壊れても、確定した実行は失われません。スタンバイを主に切り替えて、kairod をそこにつなぎ直します。
- **非同期の複製**：コミットは、スタンバイを待たずに返ります。切り替えのときに、最後に確定した実行を失うことがあります。
- **書き手の排他**：同じ名前空間に 2 つの kairod が書くことはありません。あとから開いた kairod が書き手になり、前の kairod の書き込みは拒まれます（ADR 0020 のフェンシング）。切り替えのあとに、古い kairod が書き続けることはありません。

## 守られないこと

- ファイルだけの構成（`KAIRO_STORE` なし）は、これまでどおりディスクの故障に耐えません。
- ティア `none` と `memory` の実行は、データベースに書かないので、守られません。
- 観測（`-obs`）と計測（`-metrics`）の出力は、データベースに書きません。

## 費用

- SQL の保存先の書き込みは、ファイルより遅くなります。同期の複製では、確定までの時間に、スタンバイまでの往復が加わります。
- 配布している `kairod` は、データベースのドライバを含む分だけ大きくなります。
