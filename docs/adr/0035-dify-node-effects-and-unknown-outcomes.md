# 0035. Dify のノードに作用の型を割り当て、結果が不明な実の命令は、明示した設置に限って「失敗」として扱えるようにする

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR3 / 不変条件 5, 10 / ADR 0003, 0004, 0028, 0030

## 背景

kairo は作用に型を付ける（ADR 0003）。

- 実（real）の命令は、意図を耐久化してから出す（ADR 0004）。
- 結果が不明になったら（タイムアウト、切断、再起動）、成功とも失敗とも扱わず、要確認で止める（不変条件 5）。

Dify は作用を区別しない。

- `retry_config` が有効なら、どのノードも失敗のたびに再実行する。
- タイムアウトなどの結果が不明なものも、ただの失敗として扱い、エラー処理（ADR 0030）に進む。
- 利用者は「要確認で止まる」実行を見たことがない。

そのため、Dify のノードを kairo で動かすには、次の 2 点を決める必要がある。

1. ノードの種類ごとの作用の型
2. 結果が不明な実の命令の扱い

## 決定

### ノードの種類ごとの作用の型（DSL の変換器が割り当てる）

| 作用の型 | Dify のノード |
|---|---|
| 保護（kairo の中で評価） | if-else（`kairo.switch`）、variable-aggregator、assigner（`kairo.assign`）、list-operator、start / end / answer の組み立て |
| 非保護（再実行してよい） | llm、question-classifier、parameter-extractor、knowledge-retrieval、document-extractor、template-transform、code |
| 実（外部に作用する） | http-request、tool、agent、ワークフローを入れ子に呼ぶ tool、knowledge-index |
| 待機 | human-input（signal を待つ） |

- code（sandbox）は、外部に作用しない前提で非保護にする。ネットワークに出るコードを書かれうるが、Dify の sandbox は既定で外部への通信を制限している。
- template-transform は Jinja2 を sandbox で実行するので、保護ではなく非保護（ワーカーで実行）にする。
- tool は、プラグインの宣言を見て非保護にできる余地がある（読み取り専用の検索など）。v1 では一律に実とし、後で宣言を使う。

### 結果が不明な実の命令の扱い（`on_unknown`）

- step の定義に `on_unknown` を足す。値は `review`（既定。今と同じ）と `fail`。
- `fail` の設置では、結果が不明になったら**確定した失敗**として扱い、エラー処理（ADR 0030）に進む。
  - **成功としては扱わない。** 不変条件 5 の「成功扱いしない」は守る。
  - **再試行もしない。** `IdempotentRetry` の宣言がなければ、今までどおり盲目的に再実行しない。
  - 失敗の `error_type` は `outcome_unknown` にし、外部で作用が起きた可能性を残す。
- Dify の DSL の変換器は、実のノードに `on_unknown: fail` を付ける。Dify と同じく、実行は止まらずに失敗として進む。
- 不変条件 5 の文言を変える。「結果が不明な実の命令を成功扱いしない。`IdempotentRetry` の宣言がなければ、要確認で止めるか、`on_unknown: fail` を明示した設置に限って失敗として扱う。どちらの場合も再実行しない」。

### Dify の retry との違い

- Dify は、`retry_config` があれば結果が不明な失敗も再実行する。kairo は、実のノードでは確定した失敗だけを再実行する。結果が不明なときは再実行せず、上のとおり失敗にする。
- これは、外部への作用の重複を避けるための、**意図した違い**とする。
- 差分ハーネス（ADR 0028）では、モックが「結果が不明」を返す fixture を、既知の差として扱う。

## 結果

- Dify の利用者から見て、実行が「要確認」で止まることはない（Dify と同じ）。外部への作用が二重に起きる経路は、Dify より少ない。
- kairo 自身の定義は、何も指定しなければ今と同じく要確認で止まる。
- 悪くなること:
  - 不変条件 5 が、明示した設置について緩む。`on_unknown: fail` を付けた設置は、外部に作用が起きたかもしれない状態で失敗の分岐に進む。補償は、利用者のフロー（fail-branch）の責任になる。
  - ワーカーは、確定した失敗と結果が不明な失敗を区別して返す必要がある。Python ワーカーでは、HTTP のタイムアウトや切断を「不明」にする。
- テスト:
  - `on_unknown: fail` の実のステップが、タイムアウトで失敗になり、再実行されない。`on_error` の分岐に進む。
  - 既定（`review`）では、今までどおり要確認で止まる。
  - `IdempotentRetry` の宣言があれば、今までどおり再実行する。
  - `TestRealCommandWaitsForDurableIntent` など、不変条件 4, 5 のテストはそのまま通る。

## 検討した代替案

- Dify のノードをすべて非保護にする: 外部への作用（HTTP の POST、tool による書き込み）が、再起動のたびに黙って再実行される。kairo を使う意味がなくなる。
- 要確認で止める（kairo の既定のまま）: Dify の利用者には、止まった実行を解決する画面も運用もない。互換の前提が崩れる。
- Dify と同じく、結果が不明なものも再実行する: 外部への作用の重複を、kairo が自分から起こすことになる。

## 実装で詰めた詳細（2026-10-05 追記、ADR 0017）

- **`on_unknown`。** step の定義に足した。値は `review`（既定）か `fail`。
  - `fail` の設置で、結果が不明な実の命令は、再実行も要確認もせずに、確定した失敗として扱う（`giveUp`）。`on_error` があればそれに進み、なければ map の要素か実行を失敗にする。
  - 再起動のときに「意図は耐久化したが結果が分からない」実の命令も、同じ扱いになる。
  - `error_type` は `outcome_unknown`。
- **確定した失敗は、今までどおり。** `retry` の回数だけ再実行する。
- **不変条件 5 の文言を変えた。** AGENTS.md の不変条件 5 を、この ADR の決定に合わせて書き換えた。
- **割り当ての表は変換器で使う。** ノードの種類ごとの作用の型の表は、Dify の DSL の変換器（`compat/dify`）を作るときに使う。kairo 本体の変更は、`on_unknown` だけ。
- **テスト:** `TestOnUnknownFail`、`TestOnUnknownFailAfterRestart`。不変条件 4, 5 の既存のテストは、そのまま通る。
