# 0065. 外から始めるワークフローを、未完了の親の木へ原子的に加える

- 状態: 承認（2026-11-06）
- 日付: 2026-11-06
- 関連: ADR 0041（実行 1 回あたりのコスト）、0049（コードで書く API）、0054（親子の記録と木ごとの削除）、0059（投げっぱなしの開始と駆動の借用）、0062（子の到達と親子の寿命）/ GitHub Issue #4

## 背景

コードで書くワークフローの呼び出しと子のワークフローは、作ったワークフローの ID を保存先の `parent` 列に記録する。親が未完了の間は、終わった子も `KeepFinished` の期間を過ぎて消されず、親が終わった後に木ごと消える（ADR 0054）。親の終了と取り消しは、未完了の子孫を先に取り消す（ADR 0062）。

一方、`Run` / `Submit` でワークフローの外から始めた実行は、常に木の根になる。外部の処理が、すでに動いているワークフローに属する仕事を受け取る場合、この制約が問題になる。

KairoCode では、1 つの turn をワークフローとして動かし、その中で Claude Code が発行した MCP の tool call を、MCP の受け口から別の kairo ワークフローとして `Submit` する。tool call は turn に属するが、ワークフロー関数から直接始めたものではないため根になる。tool call が終わってから `KeepFinished` の期間が過ぎても turn が承認などを待っていると、tool call の記録だけが先に消える。turn のリプレイで結果が要ると、同じ作用を二重に動かさないため、利用側の別の表で補う必要がある。

単に `parent` を option として保存するだけでは正しくない。親の終了処理と子の作成が競合し、終了処理が子を列挙した直後に新しい子を作れると、終わった親の下で新しい作用が動く。親の存在と未完了を確かめること、親子関係を保存することを、保存先の同じトランザクションで直列化する必要がある。

また、外から作った子は、親のワークフロー関数の呼び出し位置を持たない。ADR 0062 の「親のリプレイが同じ子へ到達したときだけ回復する」を、外部から同じ子をもう一度投入することに対応させる必要がある。

## 決定

### 1. `Run` / `Submit` に、埋め込みランタイム用の親 option を足す

外から始めるコードワークフローに、親のワークフロー ID を指定できるようにする。

- Go: `kairo.Parent(parentID)`（`RunOption`）
- TypeScript: `k.run(..., { parent })` / `k.submit(..., { parent })`
- Python: `await k.run(..., parent=...)` / `await k.submit(..., parent=...)`

親を指定して新しく作ったワークフローは、その ID を実行行の `parent` に持つ。`List` には根として現れず、`Children(parentID)` には現れる。保存期間、親の完了・失敗・取り消し、子の回復には ADR 0054 と 0062 の規則をそのまま適用する。

この option は、親子を保存する埋め込みランタイムだけで使える。kairod は実行間の親子をまだ保存しないため、親を指定した `Run` / `Submit` は Go では `ErrNeedsEmbedded`、TypeScript と Python では同等のエラーにする。親を指定しない既存の API は変えない。

### 2. 親は、同じ保存先にある未完了のワークフローでなければならない

新しい子を作るとき、親について次をすべて要求する。

- 同じ埋め込みの保存先に存在する。
- コードで書くワークフローの実行である。
- `completed`、`failed`、`cancelled` のどれでもない。
- 子自身と同じ ID ではない。

満たさなければ、子は作らない。Go は `ErrParentUnavailable`、TypeScript と Python は `ParentUnavailableError` を返す。このエラーは、存在しない親、ワークフローでない親、終わった親、既存 ID の親の不一致を区別せず「指定した木へ安全に加えられない」ことを表す。メッセージには理由を残す。

子の ID は従来どおり冪等キーであり、最初に作った行の親は変えない。

- 既存の実行へ同じ親を指定した場合は、その実行を再開するか、記録済みの結果を返す。
- 親のない既存の根へ後から親を指定した場合と、別の親を指定した場合は `ParentUnavailableError` にする。後付けで木を移動しない。
- option を省略して既存 ID を再投入した場合は、保存済みの親を実際の親として使う。これにより、従来の再投入でも親子の寿命を外さない。

### 3. 親の確認と子の新規作成を、同じ保存先トランザクションで行う

埋め込みランタイムの実行開始に「この親が未完了なら開始する」という guard を足す。保存先は、新しい子の行を入れる前に親の行をロックして、決定 2 の条件を確認する。

- SQLite とメモリの保存先は、既存の書き込みトランザクション / mutex の中で確認する。
- PostgreSQL は親の行を `FOR UPDATE` でロックしてから子を入れる。
- 親の終端イベントも親の行を同じくロックするので、子の開始と親の終了に 1 つの順序が付く。
  - 子の開始が先なら、親の終了処理はその子を列挙し、必要なら取り消してから親を終える。
  - 親の終了が先なら、子の開始は guard に失敗し、行も借用も作らない。

新しい表・列・event は足さない。`parent` 列と既存の実行開始、駆動の借用を使う。Go の `Store`、TypeScript / Python の store が返す変更には、親 guard を表す値を足し、組み込みの保存先と store の共通テストでこの原子性を契約にする。

既存の子を再投入するときは、その行に保存された親を読み、指定した親との一致と、親がまだ未完了であることを確認してから駆動する。確認の直後に親の終了が始まっても、その子の行はすでに親の木に含まれているため、ADR 0062 の終端処理が子を取り消してから親を終える。新しい親子関係を作る競合だけを、開始トランザクションで防ぐ。

### 4. 外からの再投入を、ADR 0062 の「到達」とする

親を付けた外部の子は、プロセスが止まった後、期限切れの駆動の借用だけでは単独に回復しない。親の関数にはその子を呼ぶ位置がないため、外部の受け口が同じ子 ID を `Run` / `Submit` した時点を、その子への新しい到達とする。

- 同じ ID と保存済みの親で再投入すると、終わった呼び出しは記録から返し、未完了の子はそこから再開する。
- 外部から再投入されない子を、親のリプレイだけで勝手に再開しない。
- 親が先に終わる、失敗する、または取り消される場合は、ほかの子と同じく外部の子も先に取り消す。

外部の配送側は、少なくとも once の再配送に同じ子 ID を使う。これは新しい対応表を kairo に常駐させる約束ではなく、既存の冪等キーによる再投入である。

### 5. 費用

親を指定しない `Run` / `Submit` の経路には、読み取りも書き込みも足さない。

親を指定して新しい子を作るときだけ、親の行の読み取りとロックが 1 回増える。これは、実行の状態を正しい木へ耐久化し、親の終了後に作用させないための仕事である。既存の子を外から再投入するときは、保存済みの親と状態を確認する読み取りが増える。どちらも、その外部の子を開始または再開するときだけ払い、ポーリング、実行ごとの goroutine、常駐する対応表は足さない（ADR 0041）。

## 結果

- 外部の tool call を turn の木へ入れ、turn が待っている間は `KeepFinished` を過ぎても tool call の記録を残せる。
- turn が終われば、外から付けた実行も同じ木として取り消され、期間の後に一緒に消える。
- 終わった親の下へ、競合で新しい作用を持つ子を作れない。
- プロセス停止後に、親のコードが知らない外部の子を勝手に再開しない。外部から同じ ID を再投入したときだけ再開する。
- kairod の保存形式と API、コア、状態の符号化、ログ、WASM ABI は変えない。

## 実装の詳細（2026-11-06）

- 外から親を付けたことは、ワークフローの既存の入力 JSON に `external_parent: true` として 3 SDK 共通で保存した。新しい列や event は足していない。期限切れの駆動の借用を回収するときはこの印を読み、借用を終えるだけにする。同じ ID の `Run` / `Submit` は保存済みの親を読み、明示した再到達として駆動する。
- 保存先の変更に `GuardParent` / `guardParent` / `guard_parent` を足した。新しい外部の子を入れるトランザクションは、親行をロックし、存在する未完了のコードワークフローであることを確認する。
- 実装中の競合テストで、親の子孫走査と終端 event のトランザクションの間にも子が入れる窓を確認した。そのため終端側にも `GuardTreeSettled` / `guardTreeSettled` / `guard_tree_settled` を足した。終端トランザクションは親行のロックを持ったまま未完了の子孫がないことを再確認する。子が先に入っていれば終端を記録せず、SDK が子孫を終端してからやり直す。終端が先なら、その後の `GuardParent` は終了済みの親を拒否する。
- メモリ、SQLite、PostgreSQL の保存先で同じ guard を実装した。SQLite は書き込みトランザクション、PostgreSQL は `FOR UPDATE` を順序の根拠にする。
- Go の共通テストと TypeScript・Python の保持テストへ、保持と木ごとの削除、無効な親、親の変更拒否、親からの取り消し、親終端との競合、期限切れの駆動借用と外部からの再投入を追加した。

次を Go の `kairotest` と TypeScript・Python の同じ振る舞いの一式へ足す。

- signal を待つ親へ、外から子を付けて完了させる。`KeepFinished` を過ぎて掃除しても親子が残り、親を終えて期間が過ぎると木ごと消える。`List` では子が根に現れず、`Children` では親の下に現れる。
- 存在しない親、ワークフローでない親、終わった親を指定すると、子の行と駆動の借用を作らず `ParentUnavailableError` になる。
- 親の完了と外部の子の新規作成を競合させる。子が先なら親は子を終端させてから終わり、親が先なら子は作られない。終わった親の下に未完了の子を残さない。
- 同じ子 ID と同じ親は冪等に再開できる。親のない既存の根、または別の親を指定すると関係を変えずに失敗する。
- 外部の子を途中で動かしてプロセスを止める。期限切れだけでは子の作用を再開せず、外部から同じ ID を再投入すると、完了済みの呼び出しを二重に動かさず続く。
- 親を取り消すと、外部から付けた子とその子孫も終端してから戻る。
- SQLite と PostgreSQL、ならびに Go / TypeScript / Python が共有する同じ表で、親の guard と既存の親の読み取りが同じ意味になる。

## 検討した代替案

- **親を先に `Get` してから、通常の `Submit` で子を作る:** 2 つの処理の間に親が終わり、親の終端処理が見なかった子を後から作れる。
- **ID の接頭辞を親として扱う:** ADR 0054 と同じく、利用者の ID に区切り文字が入る。保存期間と取り消しの問い合わせも、明示した `parent` 列を使っている。
- **保存期間だけ親に従わせ、取り消しと回復は独立させる:** 1 つの `parent` に 2 つの意味ができる。親が終わった後に外部の子が作用でき、ADR 0062 の「終わった木は作用しない」を破る。
- **終わった実行をすべて永久に残す:** 外部の記録は守れるが、DB の大きさを期間で抑える ADR 0054 の目的を失う。
- **外部の子を、期限切れの借用だけで自動回復する:** 親のコードがもう不要と判断した子を、親より先に再開する ADR 0062 以前の問題を戻す。外部の配送側が同じ冪等キーで再投入する。
- **既存の根へ後から親を設定する:** 親が終端処理を済ませた後に木へ移せる。どの保存期間・取り消しに従っていたかも途中で変わるため、親は最初の作成時だけ決める。
- **この ADR で kairod にも親子を保存する:** kairod の状態・ログ・HTTP API と shard の終端処理を変える別の判断になる。まず `parent` 列とトランザクションをすでに持つ埋め込みランタイムへ適用する。
