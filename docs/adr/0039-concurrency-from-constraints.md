# 0039. 同時実行数は固定値で決めず、外部の制約、手元の資源、下流の容量から決める

- 状態: 承認（2026-10-05）
- 日付: 2026-10-05
- 関連: ADR 0008（割り当てを広げる）, 0026, 0038

## 背景

今の kairo の同時実行数は、どれも起動のときの固定値である。

- 組み込みの実行器（`Engine.RegisterExecutor`、`engine/exec.go:38`）は、固定の数の goroutine を立て、各 goroutine が仕事を 1 つずつ処理する。`kairod` の `-http-concurrency` は既定 2048。
- ワーカープロトコルのクレジット（同時に受け取る仕事の数）は、ワーカーの起動の引数で決まる（Python のワーカーは `concurrency`、Dify のワーカーは `KAIRO_WORKER_CONCURRENCY`）。

性質は、Celery の `-c 4` と同じである。数字は資源から決まったものではなく、運用者の推測である。

- 小さすぎれば、資源が空いていても処理量が頭打ちになる（ADR 0038 の背景）。
- 大きすぎれば、外部の上限やメモリを超えて失敗する。

一方で、外部の上限の考え方は、すでに `sched.DestLimits` にある（宛先ごとの RPM、TPM、テナントごとの同時実行数）。

処理量を本当に決めているのは、次の 3 種類の制約である。

1. **外部:** 宛先（LLM の提供元、外部の API）の RPM、TPM、同時接続数。宣言されていない上限もある。
2. **手元の資源:** プロセスのメモリ、ファイル記述子とソケット、CPU。
3. **下流:** 結果を受け取る側（Dify の DB への書き込み、SSE の publish、イベントの出口の購読者）の容量。

## 決定

同時に進める仕事の数は、運用者が固定値で決めるのをやめる。上の 3 種類の制約から、kairo とワーカーが決める。固定の数字が残るのは、OS や資源の上限から計算した「安全のための天井」だけにする。

### 1. 外部の制約: 宛先ごとの同時実行数を、観測から決める

- 宣言できる上限は、今と同じく `DestLimits` で宣言する（RPM、TPM、テナントごとの同時実行数）。
- それに加えて、ディスパッチャ（`sched.Dispatcher`）が宛先ごとに「同時に出してよい数」を持ち、結果から調整する。
  - 方式: 遅延の勾配で決める方式に、AIMD を組み合わせる。
  - 結果が「上限に当たった」（429、提供元の rate limit の誤り）か、タイムアウトなら、その宛先の同時実行数を減らす（乗算で減らす）。
  - 遅延が悪化していなければ、少しずつ増やす（加算で増やす）。
  - 初期値は小さく始め、宣言された上限を超えない。
- 「上限に当たった」は、実行器が誤りの種類で知らせる。`task.Result.ErrType` に `rate_limited` を足す。HTTP の実行器と Python の SDK は、429 や提供元の rate limit の例外をこれに対応させる。
- 状態はディスパッチャの単一の goroutine が持つ（ADR 0008 のとおり）。調整には `ev.At` と同じく時計を引数で受け取り、テストでは偽の時計で決定的に確かめる。

### 2. 手元の資源: ワーカーのクレジットを、資源の予算で返す

- 仕事を 2 種類に分ける。どちらになるかは、ノードの仕様（`ir.NodeSpec`）に宣言する（新しいフィールド `Resource: io | cpu`。宣言がなければ `io`）。
  - **io:** 外部を待つ仕事（LLM、HTTP、tool）。CPU はほとんど使わない。メモリとソケットを使う。
  - **cpu:** 手元で計算する仕事（code、テンプレート、下流の処理）。
- ワーカー（Go の実行器、Python の SDK）は、クレジットを固定値でなく、予算の空きで返す。
  - io の仕事: メモリの予算（同時に抱える入出力のバイト数の合計の見積もり）と、ソケットの予算（`ulimit -n` から計算）が許す限り受け取る。
  - cpu の仕事: CPU の数（または割り当てられた CPU の量）まで受け取る。
  - 予算は、プロセスが知る資源の上限から既定値を決める（コンテナのメモリの上限、`ulimit -n`、CPU の数）。運用者が変えられるのは予算で、仕事の数ではない。
- 組み込みの実行器の「固定の数の goroutine」はやめる。ディスパッチャから受け取った仕事ごとに goroutine を立て、予算の範囲で同時に動かす。
  - 実行ごとに goroutine を持たない（不変条件 6）のは変わらない。goroutine は「動いている仕事」ごとで、その数は予算で抑える。
- Python のワーカー（Dify）では、io の仕事は gevent で抱え、cpu の仕事はプロセスの数で並べる。

### 3. 下流の容量: 背圧をかける

- イベントの出口（ADR 0034）の購読者の遅れが一定を超えたら、ディスパッチャは新しい仕事の配布を遅らせる。アドミッション（新しい実行の受け付け）も止める。購読者が追いつけば、元に戻す。
  - 今は、遅れが `FeedLimit` を超えると購読を切る。その手前で、配布を遅らせる段階を入れる。
- Dify のワーカーの下流（DB と SSE）が詰まったら、ワーカーはイベントの ack を遅らせる。これが背圧になる。

### 4. 見えるようにする

- 宛先ごとの今の同時実行数、上限に当たった回数、予算の使用量を `Stats` に出す。
- 運用者が見て判断するのは、これらの観測値と予算であって、仕事の数ではない。

## 結果

- 処理量が、設定の数字ではなく、外部の上限と手元の資源で決まる。資源を増やせば（ワーカーを増やす、メモリを増やす）、処理量も増える。
- 提供元の上限に当たり続けることがなくなる。上限が変わっても、観測から追従する。
- 悪くなること:
  - 同時実行数が時間とともに変わるので、遅延の分布が固定の設定よりも読みにくい。そのため、観測値を `Stats` に出す。
  - 調整の方式には、調整の速さや減らす割合といった定数が残る。これは同時実行数そのものではなく、反応の速さを決める定数として扱い、既定値を計測で決める。
  - io と cpu の分類を誤ると、予算が効かない（cpu の仕事を io として大量に受け取るなど）。宣言のない作用を「実」として扱う（不変条件 10）のと同じく、宣言がないときの既定を安全な側に倒すかどうかは、実装のときに計測して決める。
- テスト:
  - 宛先ごとの調整: 偽の時計と偽の宛先（一定の数を超えると 429 を返す）で、同時実行数がその数の付近に収束すること。
  - 予算: メモリとソケットの予算を超えて仕事を受け取らないこと。
  - 背圧: 購読者が遅れたら配布が遅れ、追いついたら戻ること。
  - 性能の予算（`scripts/bench.sh`）が悪化しないこと。ディスパッチャはホットパス。

## 検討した代替案

- **固定値のまま、既定値を大きくする。** 外部の上限を超えたときに失敗が増える。資源の少ない環境では、メモリを使い切る。
- **運用者が宛先ごとに同時実行数を設定する。** 宣言できる上限（`DestLimits`）は今もある。宣言のない上限や、変わる上限に追従できない。
- **キューの長さだけを見て、ワーカーの台数を自動で増減する（オートスケール）。** ① のプロセス管理（Docker / Kubernetes）の役で、この ADR とは別の層。この ADR の観測値（`Stats`）は、その判断の材料になる。

## 実装の前に変えたこと（2026-10-05、利用者の承認）

決定のとおりに入れて測ったところ、次の問題が出た。そこで、次の 3 点を変えた。

- **測って出た問題（宛先ごとの同時実行数を「小さく始めて、成功するたびに増やす」場合）:**
  - 多くの仕事が同時に動き出さないと先に進まない仕事が止まった。初期値の 8 で詰まり、どの仕事も終わらない（sched のテスト）。
  - `TestHandoffLatency` の p99 が、同じ負荷の下で 0.53ms から 2.6ms に悪化し、予算（1ms）を超えた。

1. **宛先の同時実行数は、宛先から拒否されるまで絞らない。**
   - 上限を宣言していない宛先は、初めて「上限に当たった」と返ってくるまで、同時実行数を制限しない。
   - 初めて返ってきたら、その時点で出している数の半分まで下げる。以降は 1 節のとおり（拒否なら半分、拒否がなく遅延が悪化していなければ少しずつ増やす）。
   - 拒否されるまで、ホットパスの遅延は今と変わらない。
2. **「上限に当たった」は、誤りの種類（`ErrType`）ではなく、別のフラグで知らせる。**
   - `task.Result.RateLimited`、ワーカープロトコルの `rate_limited`。
   - `ErrType` を書き換えると、Dify の記録に残るノードの本来の誤りの種類が変わり、graphon との一致が崩れるため。
3. **既定では、DB（保存先）の容量を処理量の天井にする。**
   - 処理量の上限を決めるのは、設定の数字ではなく、結果を保存する側の書き込みの容量であるべき、という方針。
   - Dify のワーカーが同時に下流（DB と SSE）を作る実行の数の既定を、Dify の DB の接続プールの大きさ（`SQLALCHEMY_POOL_SIZE` + `SQLALCHEMY_MAX_OVERFLOW`）にする。それを超える実行のイベントは、ワーカーの中で待つ。
   - 待っている間、そのイベントは ack されない。イベントの出口の購読の遅れとして kairo に伝わり、3 節の背圧（仕事の配布と、新しい実行の受け付けを遅らせる）が働く。
   - kairo 自身の保存先（WAL、group commit）も同じで、書き込みが詰まれば耐久化が遅れ、実の命令の解放と `Submit` の応答が遅れる（ADR 0023 のとおり）。
   - ノードの実行（LLM など）には、固定の上限を置かない。手元の資源（2 節）と宛先の拒否（1 節）だけで絞る。

## 実装で詰めた詳細（2026-10-05 追記、ADR 0017）

- **宛先の同時実行数（`sched/dispatcher.go`）。**
  - `Dispatcher.Finish(t, Outcome{Tokens, RateLimited})` を足した。`Done` は `Finish` の短縮。
  - 宛先は、出している数（`inflight`）と上限（`limit`）を持つ。初めて `RateLimited` が返るまでの上限は、宣言（`DestLimits.Concurrency`、0 は無制限）のまま。
  - 初めて返ったら「出している数の半分」にする。以降は、拒否なら半分（1 往復に 1 回まで）、拒否がなく遅延（往復時間の平滑値）が最小の 2 倍以内なら、1 往復に 1 つ増やす。
  - 往復時間は、配った時刻から `Finish` までを、ディスパッチャの時計で測る。
- **「上限に当たった」の知らせ方。**
  - `task.Result.RateLimited`、ワーカープロトコルの `rate_limited`、Python の SDK の `Result.rate_limited`。
  - HTTP の実行器は 429 で立てる。`GraphonNodeRunner` は、graphon の誤りの種類が提供元の rate limit のとき（`InvokeRateLimitError` など）に立てる。
- **手元の資源から決める既定値。**
  - `NodeSpec.Resource`（`io` / `cpu`、空は `io`）を足した。Dify の変換器は、code、template-transform、document-extractor を `cpu` にする（`dify.ConverterVersion` を 4 にした）。
  - `Engine.RegisterExecutor` の同時実行数が 0 以下なら、`cpu` の仕事は CPU の数、`io` の仕事はファイル記述子の上限の半分にする（`engine/resources.go`）。`kairod -http-concurrency` の既定は 0（資源から決める）にした。
  - Python の SDK の `Worker` の同時実行数を省くと、`cpu` は CPU の数、`io` はファイル記述子の上限の半分とメモリの 1/4（1 つの仕事を 2 MiB と見積もる）の小さい方にする。
  - Dify のワーカーは、`io` と `cpu` のノードを別の接続で受け取り、それぞれを資源から決めた数だけ同時に動かす。`KAIRO_WORKER_CONCURRENCY` は上限の指定（0 は資源のまま）。
- **DB を天井にする。**
  - Dify のワーカーが同時に下流を作る実行の数は、DB の接続プールの大きさ（`SQLALCHEMY_POOL_SIZE` + `SQLALCHEMY_MAX_OVERFLOW`）まで（`FeedWorker` のセマフォ）。待つ実行のイベントは ack されない。
  - エンジンは、イベントの出口で ack されていないエントリが `Config.FeedHold` を超えたら、`Dispatcher.Hold(true)` と `Admission.Hold(true)` で、新しい仕事の配布と新しい実行の開始を止める。その半分を下回ったら戻す。（のちに、止めるのは新しい実行の開始だけに変えた。下の「レビューで直したこと」の 1。）
    - `FeedHold` の既定は `FeedLimit` の半分。負の値なら背圧をかけない。
    - `kairo-dify` の既定は 10000 件（実行 1 回あたり約 20 件として、約 500 実行分）。
  - 止めている間の新しい実行は、アドミッションの待ち行列に入る（`Submit` は待つ）。
- **見えるようにする。** `Stats.Dests`（宛先ごとの `inflight`、`limit`、`refused`）を足した。
- **テスト:**
  - `TestConcurrencyFollowsTheDestination`（同時に 6 を超えると拒否する宛先に対して、落ち着いた後の 8 割以上が 6 以内）
  - `TestConcurrencyUnlimitedWithoutRefusals`
  - `TestFeedBackpressure`
  - `TestFeedLag` は、切断そのものを確かめるため、背圧を切って動かす（`FeedHold: -1`）。

### レビューで直したこと（2026-10-06）

`invariant-reviewer` の指摘を受けて、次の 7 点を直した。

1. **背圧で止めるのは、新しい実行の受け付けだけにした。**
   - 当初は仕事の配布も止めていた。しかし Dify のワーカーは、実行が終わるか一時停止するまで ack しない（ADR 0038）。そのため、配布を止めると進行中の実行が終われず、ack も進まず、止まったまま戻らなかった。
   - 進行中の実行を進めることが、ack を進める唯一の道である。`Dispatcher.Hold` は削除した。
   - 3 節「ディスパッチャは新しい仕事の配布を遅らせる」からの変更として、ここに記録する。
   - 利用者の確認を得た（2026-10-06）。購読者（Dify のワーカー）がすべて止まっているときは、新しい実行を受け付けない。`Submit` は待ち、kairo-dify は 30 秒で 503 を返す。遅れた購読者を切って記録を失うより、受け付けを止める方を選ぶ。
2. **背圧の判定と適用の競合をなくした。**
   - 判定（`held`）は `feedHub.mu` の中で更新する。適用（`reconcile`）は別のロックの下で、最新の判定を読み直してから行う。呼び出しの順序がどうであれ、最後の状態が反映される。
   - エントリを削るすべての経路（`Ack`、`Next`、`Subscribe`、`Unsubscribe`、到着）の後で適用する。
   - 解除の条件を「`FeedHold` の半分以下」にした（`FeedHold: 1` で解除されない問題）。
   - 数えるのは、ログの位置を持つエントリだけ。加えたときと削ったときに増減させる。
3. **組み込みの実行器の固定の goroutine をやめた（2 節のとおり）。**
   - 配られた仕事ごとに goroutine を立てる。同時に動く数は、エンジン全体で資源（`io` / `cpu`）ごとに共有する予算で抑える。
   - `io` の予算は、ファイル記述子の上限の半分と、メモリの 1/4（1 つの仕事を 64 KiB と見積もる）の小さい方。メモリは cgroup、`/proc/meminfo`、sysctl の順に調べる。
4. **宛先の同時実行数の調整を直した。**
   - 遅延をまだ測っていない間に続けて拒否されても、半分にするのは 1 回だけにした（拒否された仕事自身の往復時間を窓にする）。
   - 遅延の比較の相手を、最小値から長期の平均（重み 1/64）にした。最小値はばらつきの大きい LLM では小さい値に引き戻され続け、増やす条件が成り立たなくなるため。
   - タイムアウト（誤りの種類か内容に timeout、timed out、deadline exceeded を含む）でも減らすようにした（1 節のとおり）。
   - 時計を与えて `observe` を直接確かめる、決定的なテストを足した。
5. **宛先の `inflight` の数え漏れをなくした。** 配った仕事は、`Finish` か `requeue` で必ず 1 つ減らす（同じキーを新しい仕事が再利用していても）。
6. **統計（`Stats.Dests`）の作り直しを、100ms に 1 回までにした。** ホットパスの費用を抑えるため。
7. **kairo-dify の区画（ADR 0038）を直した。**
   - チャンクは、受け持ちがいなければ溜めない。送ったら印を付け、後の受け持ちには送らない。
   - 送り済みのチャンクが 1024 を超えて溜まったら、詰めて取り除く。
   - ack は ID の索引で引き、割り当ての世代は常に照合する。
