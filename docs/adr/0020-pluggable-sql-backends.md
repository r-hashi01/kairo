# 0020. 指定があれば SQL データベース（PostgreSQL、MySQL、TiDB、Oracle、SQLite）に保存できるようにする

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: ADR 0005, 0014, 0016, 0018（モジュール構成の一部を置き換え）, 0019

## 背景

ADR 0018 で SQLite 版を試し、既存の保存先インターフェース（`wal.Sink`、`wal.Retirer`、`blob.Store`）のまま SQL データベースに載せられること、性能も足りることを確かめた。利用者の方針は次のとおり。

- 既定はファイル形式とする。
- 指定があれば、利用者の環境にあるデータベースに保存できるようにする。対象は PostgreSQL、MySQL、TiDB、Oracle。

ネットワーク越しのデータベースは、ローカルの SQLite にはない次の性質を持つ。

- **複数のプロセスから同じログに書けてしまう。** 二重起動やフェイルオーバーの直後に、同じシャードのログに 2 つのエンジンが追記すると、LSN が混ざって壊れる。
- **製品ごとに制約がある。** 1 行や 1 トランザクションの大きさに上限がある（MySQL の `max_allowed_packet`、TiDB のエントリとトランザクションのサイズ上限など）。プレースホルダ、UPSERT の書き方、BLOB の型も製品ごとに違う。
- **障害範囲は外に出る。** コミットの応答は、データベース側の耐久化（と、設定によっては複製）の後に返る。要件の「障害範囲の外からの確認」には、ローカルファイルより適う。

## 決定

### 構成

- 共通の SQL 実装を、別モジュール `store/sqlstore` に置く。依存は `database/sql` だけ。
  - `wal.Sink` ＋ `wal.Retirer` と `blob.Store` を実装する。
  - 製品ごとの違いは `Dialect`（SQL 文、型名、プレースホルダ、UPSERT、上限値）に閉じ込める。
- 製品ごとに薄いモジュールを置く。各モジュールは「Dialect とドライバの登録」だけを持つ。依存するのは、利用者が選んだ製品のドライバだけになる。

  | モジュール | ドライバ |
  |---|---|
  | `store/postgres` | `github.com/jackc/pgx/v5`（stdlib アダプタ） |
  | `store/mysql` | `github.com/go-sql-driver/mysql`（TiDB も、このモジュールの TiDB 用 Dialect で扱う） |
  | `store/oracle` | `github.com/sijms/go-ora/v2`（pure Go。Instant Client 不要） |
  | `store/sqlite` | 0018 の実装を `sqlstore` の上に載せ替える |

- 本体モジュール（`kairo`）は、どれも import しない（ADR 0014）。既定はファイル形式のまま。

### 表の形（全製品共通の論理形）

- `kairo_log(log_id, lsn, rec)`
  - 主キーは `(log_id, lsn)`。
  - `log_id` は `<namespace>/shard-NNN/<tier>`。1 つのデータベースを、複数のエンジンとシャードで共有できる。
- `kairo_log_meta(log_id, next_lsn, owner_epoch)`
  - 番号の続き（`Next`）と、書き手の世代を持つ。
- `kairo_blob(key, part, data)`
  - 主キーは `(key, part)`。大きな値は `part` ごとに分割して書く。1 行の上限は Dialect ごとに決める（既定 1 MiB）。
  - 置き換えは「同じ key の行を消して書き直す」を 1 トランザクションで行い、原子性を保つ。
- 表は、`Open` 時に `CREATE TABLE IF NOT EXISTS` 相当で作る。作る権限がない環境向けに、DDL を出力する関数も用意する。
- 表名の接頭辞は、オプションで変えられる。

### 書き手の排他（フェンシング）

- `Open` のとき、そのログの `owner_epoch` を 1 増やし、その値を自分の世代として持つ。
- 以後の `Append` と `Retire` は、同じトランザクションの中で `owner_epoch` が自分の世代のままであることを確かめる（条件付き UPDATE）。違っていたら、その Sink は壊れた状態にして、以後の追記を拒否する。
  - こうすると、後から開いたエンジンだけが書ける。古いエンジンは、次の書き込みで止まる。
- エンジンの起動中に別のエンジンに奪われたら、そのシャードのログは失敗状態になり、実の命令は以後解放されない（既存の `l.failed` の扱い）。

### 退役

- `DELETE ... WHERE log_id = ? AND lsn < ?` を、Dialect が決める件数ごとに分割して実行する。TiDB などのトランザクションの上限に当たらないようにするため。
- 領域の回収は製品に任せる（PostgreSQL の autovacuum など）。

### テスト

- 共通テスト（`wal/waltest`、`blob/blobtest`）に、次を足す。
  - フェンシング: 同じログを 2 回開くと、先に開いた方が書けなくなる。
  - 大きな blob の分割と、その置き換え。
- 各製品で、共通テストとエンジンの統合テスト（ログ圧縮、リカバリ）を流す。
  - 製品は Docker で立てる。`store/compose.yaml` に、PostgreSQL、MySQL、TiDB、Oracle Database Free を定義する。
  - 接続先は環境変数で渡す（`KAIRO_TEST_POSTGRES_DSN` など）。未設定ならその製品のテストは飛ばすので、`scripts/check.sh` は Docker なしでも通る。
  - `scripts/check-backends.sh` で、コンテナの起動から全製品のテストまでを行う。CI では、別のジョブとして毎回流す。
- 計測: 0018 と同じ比較（ack p99、スループット、CPU）を、各製品で行い、結果を記録する。ネットワーク越しなので、合否の基準は設けず、目安を示すにとどめる。

### セキュリティ

- **SQL インジェクション**
  - 値はすべてプレースホルダで渡す。SQL 文は Dialect が持つ固定の文字列だけとし、値を文字列連結で埋め込まない。
  - 識別子で可変なのは表名の接頭辞だけ。`^[a-z][a-z0-9_]{0,30}$` に合わない値は `Open` で拒否する。
  - これを守らせるテストを置く。
    - 実行する SQL 文が、起動時に組み立てた固定の集合に含まれることを確かめる。
    - 悪意のある `log_id` や blob のキー（`'; DROP TABLE` など）でも、共通テストが通ることを確かめる。
- **接続情報（パスワードなど）**
  - 推奨は、利用者が作った `*sql.DB` か `driver.Connector` を渡す形とする。資格情報の取得、ローテーション、IAM 認証（RDS や Cloud SQL など）は利用者の仕組みに任せられる。
  - DSN の文字列も受け付けるが、ログ、エラー、可観測性ストリームには一切出さない。
- **通信の暗号化**
  - ネットワーク越しの製品では、TLS（サーバー証明書の検証つき）を必須とする。
  - 平文や検証なしの接続は、`AllowInsecureTransport` を明示したときだけ許す。localhost も例外にしない。
- **最小権限**
  - 実行時の DB ユーザーに要るのは、kairo の表に対する SELECT / INSERT / UPDATE / DELETE だけ。
  - 表の作成（DDL）は別の権限で行えるよう、自動作成を切る設定と、DDL を出力する関数を用意する。
- **障害時の挙動**
  - すべての DB 呼び出しに、タイムアウト（文単位）を付ける。
  - タイムアウトしたトランザクションは、コミットされたかどうか分からない。そのため、その Sink は壊れた状態とし（0016 と同じ扱い）、実の命令は解放しない。
- **データベース上のデータの扱い**
  - ログとスナップショットには、ワークフローの入出力（プロンプト、個人情報を含みうる）が平文で入る。
  - 暗号化と改ざん検知は、全保存先に共通する仕組みとして ADR 0021 で扱う。
  - DB 側の暗号化（TDE など）やバックアップの保護は、利用者の運用に任せる。
- **テナントや環境の分離**
  - `namespace` で同じ表を共有できるが、これは同じ信頼範囲の中での共有に限る。
  - 信頼範囲の違う環境（本番と検証、別の顧客など）は、DB ユーザーかスキーマを分ける。ドキュメントにもそう書く。
- **依存（サプライチェーン）**
  - ドライバは製品ごとのモジュールに隔離する。使わない製品のドライバは、利用者の依存に入らない。
  - CI で `govulncheck` を全モジュールに流す。依存の版は `go.sum` で固定する。

### 進める順番

1. `store/sqlstore` と、SQLite の載せ替え
2. PostgreSQL
3. MySQL と TiDB
4. Oracle

1 つ終わるごとに、共通テストを通してから次に進む。

## 結果

- 利用者は、手元のデータベースを指定するだけで、ログとスナップショットをそこに置ける。何も指定しなければ、いまと同じファイル形式で動く。
- エンジン側の変更は要らない。耐久化の順序制御（0016）は全保存先で共通（0019 の判断と整合する）。
- 2 つのエンジンが同じログに書く事故を、データベース側で止められる。ファイル版にはこの仕組みがない（ファイル版は、データディレクトリを共有しない前提）。
- リポジトリの Go モジュールが 6 つになる。CI のジョブに、データベースのコンテナが加わる。
- Oracle Database Free のイメージは大きく（数 GB）、起動にも時間がかかる。ローカルでは任意、CI では別ジョブにする。
- ネットワーク越しの ack 遅延は、ラウンドトリップとデータベース側の耐久化に左右される。要件の p99 ≤ 5ms を満たすかは環境次第になる。

## 検討した代替案

- 製品ごとに、ゼロから個別に実装する: SQL の違いはわずかで、重複が大きい。
- 1 つのモジュールに全ドライバを入れる: MySQL しか使わない利用者にも、Oracle などのドライバ依存が載る。
- ORM やクエリビルダを使う
  - 使う SQL は十数文で、表は 3 つの固定のもの。ORM の主な利点（モデルの対応付け、関連、クエリの組み立て）が効かない。要件も「汎用 DB として振る舞わない」としている。
  - 正しさの要は SQL を直接書いた方が確かめやすい。条件付き UPDATE の影響行数によるフェンシング、追記とメタ情報の更新を 1 トランザクションにすること、製品ごとに書き方の違う件数指定の削除などである。
  - ORM のリフレクションなどの層が、ホットパス（すべての遷移の後ろで動くログ追記）に乗る。
  - ORM の依存が、共通部分を通じて全製品の利用者に載る。
  - ORM のセキュリティ上の利点（パラメータ化）は、上の「SQL インジェクション」の決定とテストで同じだけ得られる。
- フェンシングなし（データディレクトリと同じく「共有しない前提」とする）: ネットワーク越しのデータベースは複数のエンジンから簡単に共有できてしまう。壊れたときの被害（LSN の混在）が大きい。

## 実装で詰めた詳細（2026-10-01 追記、ADR 0017）

### API

- `sqlstore` が提供するもの:
  - `NewBackend(db, Dialect, Options)`（`engine.Config` 用の `Sinks` と `Store`）
  - `OpenSink`、`OpenStore`、`Sinks`、`Migrate`、`DDL`
  - `ReadLog`（所有権を取らずにログを読む。点検や道具向け）
- 製品モジュールが提供するもの: `Dialect`（MySQL のモジュールは `MySQL` と `TiDB`）と `Open(dsn, Options)`。
- `*sql.DB` を自分で作って渡すこともできる。その場合、通信の検査は利用者の責任になる（`Open` を通したときだけ検査する）。
- `sqltest.Run` で、どの製品にも同じ一式を流せる。中身は、共通テスト（フェンシング、任意の名前、大きなオブジェクトの分割と置き換え、空の値）と、エンジンのログ圧縮・リカバリの統合テスト。

### フェンシングの方式

- 当初は「条件付き UPDATE の影響行数」で判定するつもりだった。しかし MySQL は、値の変わらない UPDATE を 0 行と数える。
- そこで、`SELECT owner_epoch ... FOR UPDATE` でメタ行をロックして読み、自分の世代と比べる方式にした。各製品で挙動が揃う。SQLite は書き手が 1 つなので `FOR UPDATE` を付けない。後から書いたトランザクションは、SQLite 自身が `SQLITE_BUSY` などで失敗させる。
- 世代の取得（`Open`）だけは、値を変える UPDATE なので、影響行数で「行がない」を判定してよい。

### 通信の検査（`Open`）

| 製品 | 受け付ける接続 | ほかに強制すること |
|---|---|---|
| PostgreSQL | `sslmode=verify-full` だけ（`verify-ca` はホスト名を検証しない、`prefer` は平文に切り替わりうる、の理由で不可） | — |
| MySQL / TiDB | `tls=true` か、登録済みの TLS 設定で検証ありのもの（`skip-verify`、`preferred` は不可） | `multiStatements` と `interpolateParams` を強制的にオフにする。値は常にサーバー側でバインドする |
| Oracle | `SSL=true` かつ `SSL VERIFY` が有効 | — |

- DSN のパースに失敗したときのエラーには、DSN を含めない（テストで、パスワードが含まれないことを確かめる）。

### 製品ごとの違い

- **Oracle**
  - `CREATE TABLE IF NOT EXISTS` は 23ai 以降にしかないので、普通の `CREATE TABLE` を出し、ORA-00955 を無視する。これで 19c 以降に対応する。
  - 複数行の INSERT も 23ai 以降なので、1 行ずつ INSERT する。
  - 空の BLOB は NULL になるので、読むときに空として扱う。
- **TiDB**: エントリとトランザクションの上限に合わせて、分割の単位を 512 KiB、退役の 1 回あたりの件数を 2,000 にした。
- **PostgreSQL**: 退役は `ctid` で件数を区切る。
- **MySQL / TiDB**: 退役は `LIMIT` で件数を区切る。

### テスト環境

- `store/compose.yaml` と `scripts/check-backends.sh`。使い捨ての CA と証明書を `store/.certs` に生成する。
- PostgreSQL と MySQL は、証明書を検証する TLS で接続してテストする。MySQL は `require-secure-transport` で、平文の接続をサーバー側でも拒否する。
- TiDB と Oracle は、テスト用のコンテナに TLS を用意していない。テストでは `AllowInsecureTransport` を明示して接続する。
- CI: `backends` ジョブ（全製品）と `vulncheck` ジョブ（全モジュールに `govulncheck`）を足した。
- 依存の脆弱性: `govulncheck` で見つかった `golang.org/x/text`（PostgreSQL のドライバ経由）を v0.42.0 に上げた。

### 一時的な失敗と接続数（計測で見つかった問題への対応）

- Oracle の計測中に、接続プールが同時に多くの接続を開き、`ORA-12516`（空きのハンドラがない）で拒否された。
  - その結果、シャードのログが失敗状態になり、実の命令と完了通知が解放されず、実行が止まり続けた。安全側には倒れていたが、運用では困る。
- 対応 1: トランザクションを始める前の失敗は、何も書いていないことが確かなので `wal.ErrTransient` とする。
  - コミッタは、そのバッチを間隔を空けて（10ms から倍々に、最大 1 秒）再試行する。シャードは止まらず、ack が遅れるだけになる。
  - 書き込みを始めた後の失敗は、これまでどおり結果不明として、その Sink を壊れた状態にする。
- 対応 2: 製品の `Open` が返すプールに、既定で上限を設ける（`MaxOpenConns` 既定 16、アイドル 5 分で回収。`sqlstore.Pool`）。自分で `*sql.DB` を作る場合も、`sqlstore.Pool` を通すことを推奨する。
- 対応 3: 失敗状態のログの数を、`engine.Stats.FailedLogs` に出す。
- Oracle の複数行 INSERT は、19c でも使える `INSERT ALL ... SELECT 1 FROM DUAL` で行う（`Dialect.InsertRows`）。1 行ずつの INSERT に比べて、ack p50 が 737ms から 114ms に、スループットが約 1,000 から約 3,500 実行/秒に改善した。

### 計測結果

- 条件: Apple M4 Max、Docker Desktop（macOS 上の仮想マシン）、負荷平均 5〜11。`KAIRO_COMPARE=1 scripts/check-backends.sh`。
  - ack: コミッタ経由で 4,000 記録を書く。
  - スループット: file ティアの 5 ノード実行 2,000 件、同時 256、4 シャード。
- 製品ごとに単独で、2〜3 回測った範囲を示す。全製品のコンテナを同時に動かすと仮想マシンのディスクを取り合い、さらに数倍遅くなった。

| 製品 | ack p50 | ack p99 | 実行/秒 | CPU / 実行 |
|---|---|---|---|---|
| SQLite（ローカル） | 9〜10 ms | 12〜14 ms | 約 6,000 | 113〜134 µs |
| PostgreSQL 17 | 11〜20 ms | 15〜27 ms | 10,000〜16,000 | 117〜227 µs |
| MySQL 8.4 | 139〜149 ms | 152〜162 ms | 7,100〜9,800 | 220〜250 µs |
| TiDB 8.5（単一ノード） | 約 62 ms | 約 72 ms | 約 6,900 | 約 180 µs |
| Oracle Free 23 | 114〜148 ms | 132〜165 ms | 1,100〜3,500 | 225〜234 µs |

- macOS の Docker では fsync が非常に高くつく。MySQL は既定で 1 コミットにつき 2 回同期する（`sync_binlog=1` と `innodb_flush_log_at_trx_commit=1`）。これらの値は本番の環境を代表しない。
- 判断に使うなら、Linux の実機か、利用者の実際のデータベースで測り直す。
