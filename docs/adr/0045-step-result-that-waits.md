# 0045. ステップの結果として「期限まで待ってから、この出力で終わる」を返せるようにする

- 状態: 承認
- 日付: 2026-10-06
- 関連: 不変条件 2・3・6、ADR 0009（ワーカーのプロトコル）、0034（トレース）、0041（実行 1 回あたりのコスト）、0042（n8n との統合）

## 背景

n8n の Wait ノード（と、待つ動きをするほかのノード）は、待つ時刻をノード自身が実行中に決める。時刻は式で書けて、前のノードの出力によって変わる。

engine v2 では、実行器（`V1StepExecutor`）がこれを「待ちの宣言」として返す。

- 宣言の中身は、再開する時刻（`resumeAt`）と、期限が来たときにステップが出す出力（`outputsAtDeadline`）。
- データプレーンは、そのステップを「待機中」（`waiting`）にして、ノードのコードは動かさずに待つ。期限が来たら、宣言の出力でステップを完了させ、後続に進む。
- 期限の見回りは、定期的なポーリング（`wait-sweeper`）で行う。
- 再開の要求で抜ける待ち（期限のないもの）は、engine v2 もまだ扱っていない。実行器がエラーにする（`UnsupportedWaitError`）。

kairo の `wait` ノードは、時間が定義に固定されているか、信号を待つかのどちらかである。待つ時刻をステップが実行中に決める形は、今の IR とイベントでは表せない。そのため、kairo-n8n は Wait ノードを含むワークフローを動かせない（ADR 0042 の段階 5 で残した項目）。

## 決定

ステップの結果に、「期限まで待ってから、この出力で終わる」を足す。コアは、その時刻にタイマーを置き、期限が来たらステップを宣言の出力で完了させる。

- **ワーカーのプロトコル（`protocol.Result`、`task.Result`）:** 結果に `wait` を足す。`{"wait": {"until": <unix ミリ秒>, "output": <期限で出す出力>}}`。`output` と `error` とは同時に使えない。
  - TypeScript の部品（`sdk/ts`）の `Result` にも同じものを足す。
- **イベント（`core`）:** `EvStepWait` を足す（Act、Attempt、`Deadline` = 期限、`Data` = 期限で出す出力）。エンジンは、`wait` の付いた結果をこのイベントにしてコアに渡す。
  - ログには、ほかのイベントと同じ順で書く（不変条件 3）。
- **コアの扱い:**
  - `EvStepWait` を受けたステップは「待機中」になる。期限で出す出力をその活性化（Act）に持ち、`CmdTimer` で期限にタイマーを置く。
  - タイマーが来たら（`EvTimer`）、ステップを、持っていた出力で成功として終える。そこから先は、`EvStepOK` を受けたときと同じ（後続の辺、出力の口）。
  - 期限が過去なら、すぐに終える（タイマーを置かない）。
  - 待機中の実行は、ほかの待ちと同じく退避できる（静止している）。取り消されたら、タイマーを外して取り消しで終える。
  - 状態の符号化に、Act の新しいフィールド（期限と出力）が要る。`codecVersion` を上げ、古いスナップショットは今までどおり読めるようにする。
- **トレース（ADR 0034）:** 待機に入ったとき `TrNodeWait`（期限を載せる）を出す。期限で終わったときは、ふつうの `TrNodeEnd`（成功）を出す。
- **作用の型:** 待ちの宣言は、確定した結果である。実の作用のステップ（`n8n.node` など）でも、結果不明（Unknown）とは扱わない。再実行はしない。
- **kairo-n8n と kairo-worker（ADR 0042）:**
  - kairo-worker は、実行器が返した待ちの宣言を、`wait`（`until` = `resumeAt`、`output` = `outputsAtDeadline`）にして返す。
  - 期限のない待ち（再開の要求だけで抜けるもの）は、engine v2 と同じくエラーにする。
  - kairo-n8n は、`TrNodeWait` でステップの行を `waiting` にし、期限（`waitTill`）を書く。実行の状態も、engine v2 と同じく `waiting` にする。期限で終わったら、ステップの行を `completed` にし、実行の状態を `running` に戻す。

## 結果

- n8n の Wait ノード（期限のあるもの）を、kairo-n8n で動かせるようになる。待つ時刻をステップが決める形は、n8n に限らず使える。
- **費用（ADR 0041）:** 待たないステップには何も増えない。待つステップには、タイマー 1 つと、イベント 1 つ（ログ 1 件）が増える。期限の見回りはタイミングホイールで行い、ポーリングしない（不変条件 6）。engine v2 のポーリングより軽い。
- **新しく守ること:**
  - `EvStepWait` を適用したら、ログに書く。リプレイで同じ待機とタイマーになること（`checkReplay`）。
  - 待機中の Act の出力は、期限までは後続に見せない。
- **形式の変更:**
  - ログ: 新しいイベントの種類を足す。古いログは今までどおり読める。
  - スナップショット: `codecVersion` を上げる。古い形式も読めるようにする。
  - ワーカーのプロトコル: `Result` にフィールドを足す。古いワーカーは送らないだけで、壊れない。
- **テスト（足す）:**
  - `core`: 待機に入り、期限で後続に進むこと。期限が過去ならすぐ終わること。取り消し。退避と復元の後でも期限で終わること。いずれも `checkReplay` を通す。
  - `engine`: 再起動をまたいでも、期限でステップが終わること。
  - `protocol` と `sdk/ts`: `wait` 付きの結果が届くこと。
  - `compat/n8n`: Wait ノードを含むグラフで、ステップの行が `waiting` から `completed` になること。実機の n8n で、engine v2 と記録を比べる。

## 検討した代替案

- **IR の `wait` に、実行中に決まる期限（前のノードの出力への参照）を足す。** 変換器が、待つかもしれないノードの後ろに `wait` を差し込むことになる。しかし、どのノードが待つかは、変換の時点ではわからない（Wait ノードのほか、送信して返事を待つノードなど）。すべてのノードの後ろに差し込めば、待たない実行もグラフのノードと遷移の分だけ費用を払う（ADR 0041 に反する）。
- **ワーカーの中で待つ（ステップが終わらないまま、ワーカーが時間まで寝る）。** 待つ間ずっとワーカーの枠を占め、再起動で待ちが失われる。待機中の実行の費用が、状態のバイト数でなくなる。
- **kairo-n8n の側で、待ちを外から作る（期限まで実行を止め、後で信号を送る）。** 実行ごとのタイマーか見回りが kairo の外に要り、待機の記録が kairo のログと二重になる。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

- **状態の並びは変えず、`codecVersion` は決定どおり 4 に上げた。** 期限で出す出力は、その Act の `Results[0]` に持つ（`Results` は map の Act だけが使い、ステップの Act では空いている）。待機中であることは、空いていたフラグ `fStepWait` で表す。期限は既存の `Timer`・`TimerAt` に入る。どれも今の符号化に含まれるので、並びは同じで、古い版（1〜3）のスナップショットもそのまま読める。版を上げるのは、古いバイナリに戻したときに、待機中の実行を黙って止めたままにせず、復号のエラーとして見えるようにするため（レビューの指摘）。ログを古いバイナリで読み直した場合は、`EvStepWait` が無視され、ステップは再実行される（実の作用なら要確認になる）。古い版への戻しは約束していない。
- **ログの形式も変えなかった。** 期限は、既存の `Event.Deadline`（拡張部分に入る）で運ぶ。イベントの種類 `EvStepWait` は、既存の種類の後ろに足したので、古いログの番号は変わらない。
- **再起動:** 待機中の Act はタイマーを持つので、`recover` の既存の処理（タイマーを置き直す）で期限に再び置かれる。取り消しも、既存の `fail`（すべてのタイマーを外す）で済む。ステップの打ち切りのタイマーは、待機に入るときに外す（待ちはステップの打ち切りの時間に数えない。実行全体の期限は効く）。
- **トレース:** `Trace` に `Until`（期限）を足した。実行器が返したメタデータ（ADR 0034）は、`TrNodeWait` に載せる。期限で出る `TrNodeEnd` はタイマーから出るので、メタを持たない（レビューの指摘）。トレースはメモリの中の構造体で、ログには書かない（リプレイで作り直す）ので、形式の互換は要らない。kairo-dify は、待ちを返すワーカーがないので変えていない。
- **kairo-n8n:**
  - 期限（`waitTill`）は記録の表に書かない。engine v2 の API（`StepDetail`）にも出てこないため。
  - 実行の状態は、engine v2 と同じ規則で計算し直す（待機中のステップがあり、動いているステップがなければ `waiting`、それ以外は `running`）。計算し直すのは、待機に入ったとき、待機中のステップがある間のステップの始まりと終わり、待機していたステップが終わったときだけ（待たない実行には何も増えない）。
  - 再起動: どのステップが待機中かは、kairo-n8n のメモリに持つ。再起動の後に実行の情報を作り直すときは、記録（ステップの行）から復元する（`runInfo.restore`）。記録を読むのは、実行の記録がもう `queued` でないとき（再起動の前にトレースを読んでいた実行）だけで、新しい実行には何も増えない。テスト: `TestDaemonRestoresWaitingSteps`（待機中にメモリを捨て、期限の後に実行が `running` に戻ること）。
- **kairo-worker:** 実行器の待ちの宣言を、`wait`（`until` = `resumeAt` を Unix ミリ秒にしたもの、`output` = `outputsAtDeadline`）にして返す。期限のない待ちは、engine v2 と同じくエラーにする。n8n の Wait ノードは、65 秒未満の待ちをノードの中で寝て済ませるので、待ちの宣言になるのは 65 秒以上のときだけ。
- **テスト:**
  - `core`（`stepwait_test.go`）: 期限で後続に進むこと、期限が過去ならすぐ終わること、取り消し、スナップショットと再起動の後に同じ期限でタイマーが置き直されること。いずれも `checkReplay` を通す。
  - `engine`: 退避と再起動をまたいで、期限でステップが終わること（`TestStepWaitAcrossRestart`）。
  - `protocol`: Go のワーカーが返した待ちが届くこと（`TestWorkerResultWaits`）。`sdk/ts`: 結果の本文に `wait` が載ること。`until` は整数のミリ秒に切り捨てる（Go の側は int64 なので、小数だと結果ごと読めない。レビューの指摘）。
  - `compat/n8n`: ステップの行と実行が `waiting` になり、期限で `completed` に進むこと。待機中にライフサイクルイベントが出ないこと（`TestDaemonStepWaits`）。
- **実機（n8n）:** 70 秒待つ Wait ノードのワークフローを、kairo-n8n と engine v2 で動かした。待機中（実行 `waiting`、Wait のステップ `waiting`）も、終わった後（すべて `completed`、出力も同じ）も、記録は一致した。
- **性能:** `scripts/bench.sh` の予算は範囲内（遷移 1097ns、5 ノードの実行あたりの CPU 77µs、受け渡しの p99 374µs）。1 回目の計測では受け渡しの p99 が予算を超えた（2276µs、load average 23）。時間をおかずに測り直すと範囲内だった。
