# 0021. 保存するログとスナップショットを、任意で暗号化し改ざんを検知する

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: ADR 0003, 0004, 0005, 0016, 0020

## 背景

ログ、スナップショット、ブロブには、ワークフローの入出力がそのまま入る。プロンプト、モデルの出力、ツールへの入力などで、個人情報や機密を含みうる。現状は、どの保存先でも平文である。

さらに重大な問題がある。保存先に書き込める者（DB の管理者、バックアップを扱う者、データディレクトリに触れる者）は、ログに偽のイベントを差し込める。あるいは、記録を並べ替えたり、削ったりできる。リカバリはログを正しいものとして再生するので、次のことが起こりうる。

- 偽の記録から状態を組み立て、「実」の命令（送信、決済）を発行する。
- 「要確認」で止まっていた手順を、勝手に「成功」として再開する。

現在の CRC は、偶然の破損を検出するだけで、意図的な改ざんは防げない。

## 決定

- 保存先をラップする暗号化の層を、本体に置く（標準ライブラリだけで書ける）。
  - `wal.Encrypted(sink, keys)` と `blob.Encrypted(store, keys)`
  - ファイル形式、SQL の各製品、メモリのどれにも同じように被せられる。既定は無効で、`engine.Config` で鍵を渡したときに有効になる。
- 方式は AES-256-GCM（AEAD）。
  - **ログの記録**: 関連データ（AAD）として `log_id` と LSN を入れる。別の位置への移動、別のログへの持ち込み、並べ替えを検知する。
  - **スナップショットとブロブ**: AAD としてキーを入れる。
  - 削除の検知について:
    - 途中の記録が消えると、復号の時点で LSN が飛ぶ。これはリカバリが連続性を確かめることで検知する。
    - 末尾をまとめて消された場合（巻き戻し）は、暗号だけでは防げない。結果の節に書く。
- 鍵の扱い:
  - 鍵は ID つきで複数持てる。書き込みは現在の鍵で行い、読み込みは記録に付いた鍵 ID で選ぶ。これで、データを書き直さずに鍵をローテーションできる。
  - 鍵の取得は `KeyProvider` インターフェースで受ける。KMS、Vault、環境変数などは利用者が実装するか、別モジュールで提供する。本体は鍵を保存しない。
- 改ざんを検知したら（復号の失敗、LSN の不連続）、そのシャードは起動に失敗させる。黙って読み飛ばしたり、続けたりしない。実の命令が偽の状態を根拠に出ないことを優先する。
- 可観測性ストリームとライブストリームは、この層の対象外とする。出力先の扱いは利用者の責務。ただし、ドキュメントで注意を促す。

## 結果

- 保存先の管理者やバックアップから、内容を読まれない。偽の記録で実の命令を出させることもできない。
- 防げないこと（明記する）:
  - **末尾の巻き戻し。** 古い時点のログとスナップショットに丸ごと戻されること。対策は、外部に最後の LSN を記録するなどで、別途検討する。
  - **可用性の妨害。** データを消して止めること。
  - **鍵そのものの漏えい。**
- コスト:
  - 記録ごとに nonce と認証タグの 28 バイト程度が増える。
  - 暗号化と復号の CPU がかかる。group commit の 1 バッチ単位でまとめても、記録ごとの AAD は残る。
  - 有効にしたときの性能は、`scripts/bench.sh` で測って記録する。
- テスト:
  - 共通テストを、暗号化の層を被せた状態でも流す。
  - 改ざんのテスト: ビットの反転、記録の入れ替え、別のログへの移植、途中の削除。いずれでも起動に失敗することを確かめる。
  - 鍵のローテーションをまたいで読めることを確かめる。

## 検討した代替案

- 保存先側の暗号化（DB の TDE、ディスクの暗号化）だけに任せる: 盗まれた媒体からは守れるが、DB の管理者やアプリの経路からの読み取り、改ざんは防げない。
- CRC を HMAC に置き換え、改ざんの検知だけ行う: 内容の秘匿ができない。AEAD なら両方まかなえる。
- 製品ごとの暗号化機能を使う（pgcrypto など）: 製品ごとに挙動と鍵の扱いが違い、ファイル形式には使えない。
- 既定で有効にする: 鍵を管理する仕組みが必要になり、試すときの手間が増える。既定は無効のまま、本番の構成例では有効にする方針をドキュメントに書く。

## 実装で詰めた詳細（2026-10-01 追記、ADR 0017）

- **パッケージと API**
  - 暗号処理は `seal`（`Keys`、`Static`、`Batch`、`Opener`、`Name`）に置いた。
  - 保存先を包む層は `wal.Encrypted` と `blob.Encrypted`。
  - `engine.Config.Keys` を渡すと、全シャード×ティアのログ（log id は `shard-NNN/<tier>`）、スナップショット、ブロブに被さる。
- **nonce の扱い**
  - ランダムな 96 ビットの nonce は、同じ鍵で安全に使えるのが約 2^32 回までで、このログの書き込み量ではすぐ届く。
  - そこで、封をする単位（ログの 1 バッチ、1 オブジェクト）ごとに 128 ビットのランダムなソルトを引き、HKDF-SHA256 で使い捨てのサブ鍵を導出する。サブ鍵の中では、項目の通し番号を nonce にする。
  - 封筒の形式: `0x01 | 鍵 ID | ソルト | 番号 | 暗号文+タグ`。
- **オブジェクト名を隠す**
  - 保存するときの名前は、`Keys.NameKey()` で鍵付けしたハッシュにする。
  - 素のままだと、実行 ID と、内容アドレス型のブロブの平文のハッシュが、保存先から見える。
  - 名前用の鍵は回転しない（変えると既存のオブジェクトに届かなくなる）。
- **古いスナップショットへの差し戻しの検知**（暗号化の有無に関わらず有効）
  - リカバリで、スナップショットの LSN が、ログにある最新のチェックポイントの LSN より小さければ起動を拒否する（`seal.ErrTampered`）。
  - スナップショットの書き込みは前にしか進まないので、正常な動作ではこれは起こらない。
  - AEAD の対象はオブジェクト名だけなので、同じ実行の古いスナップショットに戻されても暗号では見抜けない。これをこの検査で補う。
- **テスト**
  - `seal_test`、`wal/encrypted_test`（暗号化した上での共通テスト、ビット反転、別ログへの移植、途中の削除）、`blob/encrypted_test`（名前の秘匿、入れ替えの検知）。
  - エンジン: `TestEncryptedEngine`（データディレクトリに平文の入力も実行 ID も残らない。違う鍵では起動しない。正しい鍵で再開する）、`TestTamperedLogRefusesToStart`、`TestStaleSnapshotRefusesToStart`（暗号化あり／なし）。
