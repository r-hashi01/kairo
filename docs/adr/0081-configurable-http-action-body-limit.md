# 0081. HTTP アクションの本文上限は配備ごとに設定し、安全な既定値と絶対上限を持つ

- 状態: 承認
- 日付: 2026-11-17

## 背景

HTTP アクションとコールバックは、署名対象の JSON 本文を受け取る。公開された受け口では、送信者を認証する前に本文を読み、署名を検証しなければならない。本文を無制限に保持すると、認証されていない一つの要求だけでも利用可能なメモリを使い切れる。呼び出す側も、接続先が返す応答を無制限に保持すると同じ問題を持つ。

Go の HTTP アクションの受け口には 16 MiB の固定上限があるが、この値を選んだ計測、想定する本文の分布、またはメモリ予算は記録されていない。他の SDK の受け口と呼び出す側には同じ上限がなく、言語と通信方向によって、拒否する本文とメモリ使用量が異なる。

必要な本文の大きさと利用可能なメモリは配備によって異なる。小さい JSON だけを渡す配備と、長い LLM の入力または結果をインラインで渡す配備に同じ固定値を強制すると、前者には不要な危険を、後者には不要な不互換を生む。一方、上限を任意に解除できる設定では、公開された認証前の受け口を有界にする目的を満たさない。

メッセージ基盤でも、本文上限は利用する基盤と配備の設定に属する。RabbitMQ は既定を 16 MiB とし、配備で変更できる絶対上限を 512 MiB としている。Celery はすべての broker に共通する本文上限を決めず、broker ごとの制約と設定を使う。これらは kairo の値を自動的に決める根拠ではないが、安全な既定値と配備ごとの変更を分ける先例になる。

## 決定

### 決定項 1（すべての HTTP アクション本文を有界にする）

HTTP アクションとコールバックの要求・応答は、送信側と受信側の両方で本文のバイト数を制限する。上限は JSON の復号後の値ではなく、HTTP で転送する符号化済み本文のバイト数に適用する。

受信側は、上限を超える要求を署名の検証、JSON の復号、利用者の handler の実行より前に拒む。呼び出す側は、上限を超えた応答と途中で切れた応答を、切り詰めた成功として扱わない。実の作用について結果を確定できない場合は、既存の結果不明の規則へ渡す。

### 決定項 2（既定を 16 MiB、絶対上限を 512 MiB とする）

本文上限の既定値を 16 MiB とする。この値は最適な本文サイズの主張ではなく、既存の Go の受け口との互換性を保ち、一般的なメッセージ基盤にも採用例がある安全な初期値として使う。

配備は、要求と応答に共通する本文上限を、正のバイト数で明示して変更できる。設定できる値は 512 MiB 以下に限る。512 MiB は安全な推奨値ではなく、設定によって有界性そのものを失わせないための絶対上限である。大きい値を選ぶ配備は、同時要求数と、本文の保持、結合、文字列化、JSON 復号で生じる一時メモリを自分のメモリ予算に含める。

### 決定項 3（通信の両端が自分の上限を強制する）

本文上限は通信時に合意せず、各配備が自分の送信と受信へ強制する。両端の設定が異なる場合、実効上限は小さい側になる。送信側の上限を超える本文は送信前に失敗し、受信側の上限を超える要求は受信側が拒む。

この設定は、上限の大きい相手が上限の小さい相手へ成功を強制できる能力にはしない。上限の不一致や、応答が上限を超えたことによって作用の結果が確定しない場合も、成功には倒さない。

### 決定項 4（既定値は利用実績から別の判断として見直す）

16 MiB の既定値は、利用者から報告された実際の本文サイズ、拒否された利用例、メモリ障害、および大きな本文を参照へ移す運用の実績を根拠に見直せる。既定値または絶対上限を変えるときは、互換性とメモリへの影響を記録した新しい判断でこの決定を置き換える。

本文または本文サイズを、見直しのために kairo が外部へ自動送信しない。利用者が明示的に共有する Issue、障害報告、公開された利用例を判断材料にする。

### この ADR で決定しないこと

- 公開 API の設定名、環境変数、CLI option、内部の読み取り方式は、各 SDK と daemon の公開仕様および実装へ委ねる。
- 大きい値を選ぶ配備の同時要求数、リバースプロキシの上限、プロセス全体のメモリ制限は、配備の資源設定へ委ねる。
- インライン本文を blob または object storage の参照へ置き換える形式は、HTTP アクションの既存形式とは別の判断へ委ねる。
- HTTP アクション以外の control API、ワーカープロトコル、保存先の値の上限は、この ADR の適用範囲に含めない。

## 結果

- 良い影響: 認証前の要求と信頼できない応答が、一つの本文だけで無制限のメモリを消費できなくなる。
- 良い影響: 小さい本文だけを扱う配備は上限を下げ、既定値を超える正当な本文を扱う配備は、メモリ予算を確認したうえで上限を上げられる。
- 悪い影響: 配備間で上限が異なると、小さい側で要求が拒否されるか、結果不明になる。運用者は通信する両端の設定を合わせる必要がある。
- 悪い影響: 上限を大きくしても本文の保持と JSON 復号に必要な複数倍のメモリは減らない。512 MiB に近い設定は、小さい配備ではプロセス停止を起こし得る。
- 中立な影響: 16 MiB 以下の既存の要求と応答の意味は変わらない。既定値の配備では、Go の既存の受け口と同じ境界になる。
- 新しく守る制約: 本文上限は正かつ 512 MiB 以下とする。上限超過または途中切断した応答を成功として扱わない。設定を省略した配備は 16 MiB を使う。

## 検討した代替案

- 上限を設けない: 認証されていない要求と信頼できない応答が、メモリ使用量を一つの本文だけで増やせるため採らない。
- 16 MiB を変更不能な共通仕様にする: 16 MiB を最適値とする計測がなく、配備ごとの本文と資源の差を扱えないため採らない。
- 配備が任意の値または無制限を設定できるようにする: 誤設定によって有界性が失われ、公開された受け口の安全な既定を保てないため採らない。
- 利用可能なメモリから上限を自動計算する: 同時要求数、リバースプロキシ、同じ process の他の仕事、JSON の形による復号コストを本文の受け口だけでは確定できないため採らない。
- 通信の開始時に上限を合意する: 単発の HTTP 呼び出しに合意用の往復と状態を加え、受信側が自分の上限を守るだけで得られる安全性を増やさないため採らない。

## 関連する ADR

- ADR 0008 の決定「16 KiB を超える出力はブロブにする」: 状態へ保持する値には別の境界があり、この ADR の HTTP 転送上限とは目的と適用箇所が異なる。
- ADR 0039 の決定項 2（手元の資源: ワーカーのクレジットを、資源の予算で返す）: 本文上限を大きくする配備が、同時に保持する仕事をメモリ予算へ含める根拠。
- ADR 0052 の決定「呼び出し（ランタイム → アクション）」および「コールバック（アクション → ランタイム）」: この ADR が本文上限を追加する HTTP 通信の契約。
- ADR 0070 の決定項 4（結果を耐久化してから callback を確認する）: daemon が受ける callback も上限付き本文にする既存判断。
