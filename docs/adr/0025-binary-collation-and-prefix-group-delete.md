# 0025. 名前は大文字小文字を区別してバイト順で比較し、MySQL / TiDB には VARBINARY で手当てする

- 状態: 承認（2026-10-02）
- 日付: 2026-10-01
- 関連: ADR 0020, 0024（SQL 側の方法を置き換え）

## 背景

ADR 0024 の SQL 側を詰めていて、2 つのことが分かった。

1. **不具合: MySQL で、名前の大文字・小文字が区別されない（実際に再現した）。**
   - MySQL 8 の既定の照合順序（`utf8mb4_0900_ai_ci`）は、大文字小文字もアクセントも区別しない。
   - 共通テストで `snap/Case` を読むと、`snap/case` の中身が返った（MySQL 8.4）。
   - TiDB は既定が `utf8mb4_bin` なので再現しない。ただし、新しい照合順序の仕組みを有効にして既定を変えた環境では起こりうる。
   - そのため `snap/ABC` と `snap/abc` が同じ行として扱われる。実行 ID が大文字小文字だけ違う 2 つの実行が、互いのスナップショットやブロブを読んだり上書きしたりできてしまう。ログの ID も同様。
   - PostgreSQL は等しいかどうかは区別するが、ロケール依存の照合順序のままだと、範囲での比較の順序がバイト順にならない。
2. **0024 の「`grp` 列を足して `DELETE WHERE grp = ?`」は、製品ごとの差が大きい。**
   - 既存の表への列の追加と、索引の作成の構文が製品ごとに違う（MySQL と Oracle は `ADD COLUMN IF NOT EXISTS` や `CREATE INDEX IF NOT EXISTS` を持たない）。
   - 索引がないと、削除のたびに表全体を走査する。

## 決定

- 名前（実行 ID、ログ ID、オブジェクト名）は、kairo 全体で大文字小文字を区別し、バイト列として比較する。
  - 実行 ID や冪等キーは外部から来るので、大文字小文字が混ざりうる。エンジン（Go の map、シャードの割り当て）、ファイル形式、メモリの保存先は、もともとこの規則で動いている。
- DB の既定のままではこの規則にならない製品にだけ、Dialect で手当てする（`IDType`）。

  | 製品 | 既定のままで | 手当て |
  |---|---|---|
  | MySQL / TiDB | 大文字小文字やアクセントを区別しない（MySQL の既定。TiDB も新しい照合順序の仕組みを有効にすると同じ） | 名前の列を `VARBINARY(512)` にする。バイト列なので照合順序の影響を受けず、サーバーや DB の既定の設定にも左右されない。値は UTF-8 のまま入るので、DB を直接見ても読める |
  | PostgreSQL | 区別する。ただし並び順はロケール依存 | 下の範囲での削除のために `VARCHAR(512) COLLATE "C"` にする |
  | Oracle | 区別する（既定の `NLS_COMP=BINARY`。前提としてドキュメントに書く） | なし |
  | SQLite | 区別する（既定の BINARY） | なし |

- ブロブのグループ `run/<id>` の削除は、名前の前方一致の範囲で行う。
  - `DELETE ... WHERE k >= ? AND k < ?`。値は `<namespace>/run/<id>/` と、その末尾の `/` を `0`（次のバイト）に変えたもの。
  - 名前の比較がバイト順なので、この範囲は、その接頭辞を持つ名前とちょうど一致し、主キーの索引が使える。
  - 表の形は変わらない（列を足さない）。ADR 0024 の SQL 側の方法（`grp` 列）を、これで置き換える。
- 既存の表は、自動では作り直さない。
  - 型の違う表には、`sqlstore.DDL` の説明に従って、列の型を変える `ALTER` を流すよう、ドキュメントに書く。
  - v0 にはまだ利用者のデータベースがないので、今回の変更で移行の対象はない。
- 共通テストに、大文字小文字だけが違う名前が別物として扱われることを足す（`snap/Case` と `snap/case`）。全製品に流す。

## 結果

- 大文字小文字だけが違う ID の実行同士が、互いのデータに触れなくなる（MySQL で現に起きている不具合の修正）。全保存先とエンジンで、名前の比較規則が一致する。
- ブロブのグループの削除が、追加の列も索引も使わずに、主キーの範囲で済む。
- MySQL / TiDB では、名前の列がバイト列の型になる。DB を直接見るときは、クライアントによっては 16 進で表示される（`CAST(k AS CHAR)` で読める）。
- テスト:
  - 共通テストの任意の名前の項目に、`snap/Case` と `snap/case` を足す。
  - `DeleteGroup` の共通テストで、隣り合う ID（`run/a` に対する `run/a0`、`run/ab`、`run/A`）の境界を確かめる。

## 検討した代替案

- MySQL に合わせて、全体を大文字小文字を区別しない方式にする
  - エンジンの入口で ID を正規化し、全保存先を揃える必要がある。
  - それでも、MySQL の照合順序の規則（アクセントを区別しない、末尾の空白を無視するなど。サーバーの設定次第）は Go の側で再現できない。MySQL だけが同じ名前とみなす差が残る。
  - 外部から来る ID の大文字小文字が意味を持つ場合にも合わない。
- MySQL で `utf8mb4_bin` の照合順序を列に指定する: 区別はできるが、照合順序の仕組みには依存したまま。`VARBINARY` なら、その依存自体がなくなる。
- ID の文字を小文字の英数字などに制限する、または内部ではハッシュにする: どの照合順序でも同じ結果になる。しかし、利用者の ID に制約がかかる。ハッシュにすると、DB を直接見ても ID が読めなくなる。
- ADR 0024 のとおり、`grp` 列と索引を足す: 製品ごとの DDL の違いと、既存の表の移行が要る。
- `LIKE 'prefix%'` で消す: `%` と `_` のエスケープが要る。照合順序によっては索引が使われない。
