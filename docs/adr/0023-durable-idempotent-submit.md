# 0023. Submit は開始が耐久化してから返し、RunID を冪等キーとして扱う

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: FR5, FR6 / ADR 0004, 0016

## 背景

いまの `Engine.Submit` は、アドミッションを通した時点で実行 ID を返す。開始記録がログに書かれ耐久化するのは、その後である。そのため、次の 2 つの場合に、呼び出し側が「受け付けられた」と思った実行が黙って消える。

- アドミッション待ちのキューにある実行（メモリにしかない）
- 開始直後、ログが耐久化する前にクラッシュした実行

一方で、呼び出し側が失敗だと思って `Submit` を再試行すると、同じ仕事が二重に始まりうる。再試行を安全にする手段がない。

## 決定

### 返る時点

- `Submit(ctx, req)` は、実行の開始記録と最初のイベントが耐久化してから返る。
  - 耐久性ティアが none の実行は、ログがないので、シャードが開始を受け取った時点で返る。
  - 開始の ack は、出力コミットの仕組み（ADR 0004 の `hold`）に「開始の確認」を足して実現する。
- アドミッション待ちの間も、`Submit` は戻らずに待つ。
  - `ctx` が切れたら、待ちキューから取り除いて `ErrNotAccepted` を返す。この場合、実行は始まっていない。
  - キューが満杯なら、これまでどおり `ErrOverloaded` を返す。
- 開始は済んだが、耐久化の確認を待つ間に `ctx` が切れた場合は、`ErrUnconfirmed` を返す。実行は続いているかもしれない。呼び出し側は、同じ RunID で再試行して確かめる。

### 冪等性

- `RunID` を冪等キーとして扱う。同じ RunID の `Submit` は、次のように振る舞う。
  - 実行中なら、新しい実行を作らず、既存の実行の開始が耐久化するのを待って成功を返す。
  - 最近終わった実行（終了済みキャッシュ。既定 100,000 件、`Config.RecentRuns`）なら、新しい実行を作らず成功を返す。
  - それ以外（キャッシュから外れた、または再起動でキャッシュが消えた）なら、新しい実行として始める（ADR 0016 の RunID 再利用の扱い）。
- `RunID` を省略すると、エンジンが ID を振る。この場合、再試行は冪等にならない。
- 確実に再試行したい呼び出し側は、自分で RunID を決める。HTTP API では `Idempotency-Key` ヘッダを RunID として使う。
- 応答（`SubmitResult`）で、新しく始めたのか、既存の実行だったのかを区別できるようにする。

### API

- `Submit(ctx, req) (SubmitResult, error)` に変える（v0 なので、互換のための旧シグネチャは残さない）。
- HTTP の `POST /v1/runs` は、開始が耐久化してから 201（既存の実行なら 200）を返す。待ちが長いときに備えて、`timeout` パラメータを受ける。

## 結果

- `Submit` が成功を返した実行は、クラッシュしても再起動で必ず再開する（耐久性ティアが none のものを除く）。
- 再試行は、RunID を決めておけば、キャッシュの範囲内で冪等になる。
  - 限界: 冪等性の範囲は、終了済みキャッシュに残っている間に限る。プロセスが再起動するとキャッシュは消えるので、再起動をまたいだ「終了済みの実行」の重複は防げない。防ぐには、終了の記録を永続化する仕組み（期限つき）が要る。必要なら別の ADR で扱う。
- `Submit` の遅延に、group commit 1 回分（ファイルティアで数 ms、ネットワーク越しの DB では、その往復と同期）が加わる。
- テスト:
  - 開始の耐久化の前にプロセスを止めると、`Submit` は返らない（または `ErrUnconfirmed` を返す）。返った実行は、再起動後に必ずある。
  - 待ちキューにいる間に `ctx` が切れると、`ErrNotAccepted` になり、実行は始まらない。
  - 同じ RunID の再試行は、実行中でも終了直後でも、新しい実行を作らない。

## 検討した代替案

- アドミッション待ちのキュー自体をログに書き、再起動で戻す: 待ちキューはシャードに属さない。シャードのログに入れると、待ちの順序とテナント間の公平性を、ログから組み立て直す必要が出る。`Submit` を待たせて、受け付けを開始の耐久化と一致させる方が単純。
- `Submit` は今のまま速く返し、別に `Confirm` を用意する: 呼び出し側が確認を忘れやすい。既定を安全側にする。
- 終了の記録を永続化して、常に冪等にする: 期限と回収の仕組みが要る。まず範囲を限った形で入れ、必要になったら足す。

## 実装で詰めた詳細（2026-10-02 追記、ADR 0017）

- 開始の確認は、出力コミットの保留（`hStarted`）として実装した。
  - 保留する LSN は、開始記録の LSN ではなく、最初のイベントを適用した後の `lastLSN` にした。最初のイベントの処理中に積まれた保留（実の命令など）より小さい LSN で積むと、保留の列の LSN 順が崩れるため。
- 保留が全部解けたときに、退避を必ず再判定するようにした（`ack`）。
  - 開始の確認を保留している間に退避が見送られ、その後再判定されない不具合が出た。チェックポイントのときにも同じ型の不具合を個別に直していたので、一般化した。
- アドミッションの待ちは、`sched.Ticket.Cancel` で取り消せる。
- HTTP の応答:
  - 新しく開始: 201
  - 既存の実行: 200
  - 過負荷: 429
  - 受け付けていない: 503（`Retry-After`）
  - 未確認: 504（`run_id` つき）
- テスト: `TestSubmitWaitsForDurableStart`、`TestSubmitIsIdempotent`、`TestSubmitNotAcceptedWhileQueued`、`TestAdmissionCancel`。
