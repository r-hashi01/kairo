# 0043. 出力の口が複数あるステップと、切り出しながら回すループを IR に足す

- 状態: 承認
- 日付: 2026-10-06
- 関連: ADR 0029（グラフの実行モデル）、0031（分岐のハンドル）、0032（ループ）、0033（変数）、0042（n8n との統合）

## 背景

ADR 0042 の段階 1 で、n8n の engine v2 のグラフを kairo の計画に移すと、2 つが表せないことがわかった。

1. **出力の口が複数あり、同時に複数が生きるノード。**
   - n8n のノードの出力は、口（スロット）の並び `[slot0, slot1, ...]` である。口ごとに、`null` なら「通らない」、配列なら（空でも）「通る」。
   - 辺は「どの口から出るか」（`outputIndex`）と「どの口に入るか」（`inputIndex`）を持つ。Switch の「当てはまる口すべてに流す」のように、同時に複数の口が生きることがある。
   - kairo の分岐は、ステップの出力の 1 つのフィールド（`Branch`）の値で、行き先を 1 つ選ぶ形しかない（ADR 0029、0031）。
   - 入力の側も、入ってくる辺ごとに「どの口に入るか」がある。死んだ辺の口には `null` が入る。
2. **SplitInBatches のループ（engine v2 の `batch` ステップ）。**
   - 回ごとに、入口の項目を `batchSize` 件ずつ切り出して本体に流す（loop の口）。本体の出力（戻りの辺）は、回をまたいで貯める。
   - 切り出すものがなくなったら、貯めたものを done の口から出す。本体が何も返さなかった（戻りの辺が死んだ）ら、そこで終わり、ループの後ろは通らない。
   - kairo の loop（ADR 0032）と `kairo.assign` の append（ADR 0033）で、回ること・貯めること・終わることは表せる。しかし、「何回目の分を切り出す」を表す組み込みの部品がない。

どちらも、IR の構成要素を増やす変更である（AGENTS.md の「ADR が要る変更」）。

## 決定

### 1. 出力の口（ports）

- ノード仕様（`ir.NodeSpec`）に `Ports` を足す。
  - `Ports` を持つステップの出力は、口の並び（JSON の配列）とする。
  - 口 i が生きている ⇔ 出力の i 番目が `null` でない（範囲の外は死んでいる）。
- 辺（`EdgeDef`）に `port`（出る口の番号）を足す。
  - `Ports` を持つステップから出る辺は、`port` を必ず書く。`handle` とは一緒に使わない。
  - 辺の状態（ADR 0029 の 3 値）は、元のステップが終わったときに決める。
    - 成功し、その口が生きていれば「通過」。
    - 死んでいれば「スキップ」。
  - 複数の口が同時に生きてよい。その場合、それぞれの先が動く。
- 入る口は、辺ではなく、先のステップの入力の参照で表す。
  - 先のステップの入力は、`入力名 -> 参照` のまま（ADR 0029）。
  - 参照の path で、元の出力の i 番目を指せるようにする（`<node>.<i>`）。
  - 元がスキップされた場合と、その口が `null` の場合、参照の値は `null` になる。
  - n8n の変換では、入力を `in0`、`in1`、... とし、それぞれの参照を元の口にする。
- 判定は、コアの中の純粋な処理である（不変条件 1）。同じ出力からは、同じ辺の状態になる（不変条件 2）。
  - ログの形は変えない。ステップの出力はすでに記録している。
  - 状態の形も変えない。辺の状態はすでに持っている。
- `Branch`（1 つ選ぶ）は残す。Dify のノードと kairo 自身の分岐は、これまでどおり。

### 2. 切り出しながら回すループ

- 組み込みの保護アクション `kairo.slice` を足す（ADR 0015、0031 の `kairo.switch` と同じ扱い）。
  - 入力: `items`（配列）、`size`（1 以上の整数）、`round`（0 から数える回）
  - 出力: `{"items": items[round*size : (round+1)*size], "more": 切り出したものが空でないか}`
  - 純粋な関数で、コアの中で評価する。出力はログに残さず、リプレイで計算し直す。
- n8n の `batch` ステップは、kairo の loop にこう移す（`compat/n8n` の変換器が組み立てる）。
  - loop の変数:
    - `items`: 入口の項目（loop に入るときに 1 回だけ決める）
    - `arrivals`: 貯めた本体の出力（`array[any]`、空から始める）
  - 本体の始めに `kairo.slice`（`round` は loop の回）を置く。
    - `more` が false なら、その回で終わる（ADR 0032 の break）。
    - true なら、切り出した項目を本体の最初のノードに流す。
  - 戻りの辺の元のノードの出力は、`kairo.assign` の extend で `arrivals` に足す。
  - 戻りの辺が死んだら（本体が何も返さなかったら）、その回で終わる。この場合、loop の done の口は死ぬ（ループの後ろはスキップ）。
  - loop の出力は口の並び（1 の ports）にする。
    - 口 0（done）は、`more` が false で終わったときに `arrivals`、そうでなければ `null`。
    - 口 1（loop）は、ループの外には出さない。
- n8n の `iteration`（何回目か）は、loop の回にあたる。kairo-n8n は、`kairo.slice` のトレースから、`batch` ノードの回ごとのイベントを組み立てる。
  - 回ごとの出力は `[null, 切り出したもの]`、最後の回は `[arrivals, null]` になる。
- 入れ子のループ、ループへの入口が 2 本以上、本体の途中から外へ出る形は、engine v2 と同じく断る。

## 結果

- n8n の engine v2 のグラフ（v1 ノード・分岐・合流・SplitInBatches のループ）を、形を変えずに kairo で実行できる。
- `Ports` は n8n のためだけのものではない。出力の口が複数ある実行の形（同時に複数の後続を動かす分岐）を、ほかの統合でも使える。
- 増えるもの:
  - コアの辺の決め方に、口の判定が 1 つ増える。分岐の判定と同じ場所で、同じ重さである。
  - `kairo.slice` は、ループの 1 回につき 1 回、コアの中で計算する。切り出す配列の大きさに比例する。
- 守らせるテスト:
  - `core_test.go`: 複数の口が同時に生きる分岐と、死んだ口の参照が `null` になること。`checkReplay` で決定性も確かめる。
  - `kairo.slice` の単体テスト（境い目、空、`size` より少ない最後の回）。
  - SplitInBatches のループを loop に移した計画で、engine v2 の結合テストと同じ結果になること（`m1-acceptance` の題材: 1 件ずつ回す、本体が何も返さない、本体の中の分岐と合流、ループの連結）。
- IR の形式が変わる（辺の `port`、仕様の `Ports`、参照の配列の位置）。既存の計画は今までどおり読める。ログと状態の形は変えないので、`codecVersion` は上げない。

## 検討した代替案

- **n8n のノードの出力を、口ごとの真偽値のフィールドにして、`Branch` を口の数だけ並べる。** 1 つのステップに分岐を複数持たせる形になり、ADR 0029 の分岐の決まりを、結局作り直すことになる。
- **口ごとに、kairo 自身の `cond` ノードを後ろに置く。** 余計なノードが辺の数だけ増える。n8n のグラフと形がずれ、イベントの対応付けも複雑になる。
- **`batch` を n8n 側のワーカーのステップにする（切り出しをワーカーで計算する）。** 回ごとにワーカーへの往復が増える。項目の全体を、毎回ワーカーに送ることになる（ADR 0041 の原則 1）。engine v2 も、`batch` はエンジンの中で処理している。
- **`kairo.batch` として、n8n の意味（貯めること・done の口）までまとめた組み込みにする。** 貯めることは `kairo.assign`、終わることは loop の break で表せる。組み込みは「切り出す」だけにして、意味を小さく保つ。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

- **口を持つのは、ステップだけでなく、graph・map・loop も含める（`Def.Ports`）。** SplitInBatches の loop の done の口を表すためである。ノード仕様の `Ports` を持つステップは、書かなくても口を持つ。分岐（ハンドル）と口は、1 つのステップで一緒に使えない。
- **口の判定は、出力の i 番目を参照の取り出し（`extract`）で読む。** そのため、配列だけでなく、キーが `"0"`、`"1"` のオブジェクトも口の並びとして扱える。loop の出力（変数のオブジェクト）を口にするのは、この形による。
- **`kairo.slice` は、決定の「何回目の分を切り出す」ではなく、「残りから次の分を切り出す」形にした。** 入力は `items`（残り）、`size`（入力か params）、`done`。口は `[done, 次の分, その後の残り]` である。
  - 残りが空なら `[done, null, null]` になる。`done` が null なら `[]` を入れ、done の口は生きる。
  - そうでなければ `[null, 次の分, 残り]` になる。
  - こうすると、ループの何回目かを参照しなくてよい（loop の回は、今の IR では map の `$index` のように参照できない）。残りはループ変数に置き、`kairo.assign` で書き換える。
  - 口の 0 と 1 は、n8n の `batch` ノードの出力（`[done, loop]`）とそのまま同じ形になる。kairo-n8n は、`kairo.slice` のトレースを `batch` ノードのイベントにそのまま使える。
- **SplitInBatches の loop の組み立て方（テスト `TestSliceLoop` の形）。**
  - ループ変数: `rest`（入口の項目）、`arrivals`（`[]`）、`go`（1）、`"0"`（done の口、初期値 null）
  - 本体の始めの `kairo.slice`（`items: rest`、`done: arrivals`）について:
    - 口 1 の先で、`rest` を口 2 で書き換え、`go` を 0 にする。
    - 口 0 の先で、`"0"` を口 0（`arrivals`）にし、`go` を 0 にする。
  - 戻りの辺の元のノードの口の先で、`arrivals` に extend し、`go` を 1 にする。
  - `go` が 0 なら抜ける（loop の break）。
    - 切り出すものがなくなったら、`"0"` に貯めたものが入り、done の口が生きる。
    - 本体が何も返さなかったら、`"0"` は null のままで、ループの後ろはスキップになる。
  - loop は `loop_output: "vars"` で、`ports: true`。後ろへの辺は口 0。
- **参照で配列の位置をたどれるようにした。**
  - 参照の取り出し（`extract`）は、もともと配列の位置をたどれた。条件と `kairo.assign` が使う `resolveFound` は、オブジェクトのキーしかたどれなかったので、配列の位置もたどれるようにした。
  - Dify の変数の参照は、配列の位置を数字でたどらないので、Dify の挙動は変わらない。
- **大きな出力をブロブに移すときは、配列の null の口を `fields` に残す（`engine/exec.go`）。** そのため、口の判定にブロブを読まなくてよい。生きている口の参照は、ブロブの中の位置への参照になり、仕事の入力を作るときに中身に置き換わる。ブロブの中の位置をたどる処理も、配列の位置に対応させた。
- ログと状態の形は変えていない。`codecVersion` は上げない。
- テスト: `core/ports_test.go`（複数の口が同時に生きる、範囲外の口と配列でない出力は死ぬ、コンパイルのエラー、SplitInBatches の loop の 3 通りの件数と本体が何も返さない場合）。いずれも `checkReplay` で、リプレイの決定性と符号化の往復を確かめる。
- 性能: `bench.sh` を、変更前（HEAD）と同じ時間帯に比べた。load average が約 40 で揺れが大きく、悪くなっていない、までが言える。受け渡しの遅延の p99 は、変更前が 1501 µs、変更後が 277 µs、同じ時間帯に `TestHandoffLatency` を 5 回ずつ流すと、どちらも 130〜320 µs だった。

### レビューで直したことと、利用者と決めたこと（2026-10-06）

- **ブロブに移した出力の口。** 口として扱える長さ（`MaxPort + 1` まで）の配列だけ、長さ（`fields` の `$ports`）と死んだ口を記録する。コアは、ブロブの出力の口を、この記録で判定する（`portLive`）。記録のないブロブ（配列でない出力、長すぎる配列）の口は、すべて死んでいる。口を持つノードへの参照では、死んだ口は null になる。テストは `TestPortsOfABlob`。
- **参照で配列の位置をたどれるのは、口を持つノードを参照するとき（最初の段）だけにした。** Dify の参照と条件の挙動は変えない（graphon の変数プールは、配列の位置をたどらない）。
- **決定からの 2 つのずれを、利用者が認めた。**
  - `kairo.slice` を「残りから次の分を切り出す」形にした（上の「実装で詰めた詳細」）。
  - loop の done の口を、変数のオブジェクトのキー `"0"` で表すことにした。
- **制約: `kairo.slice` は、ブロブに移したリストを切り出せない。** コアはブロブを読めない（不変条件 1）。kairo-n8n では、当面、出力をブロブに移さない（閾値を十分大きくする）。engine v2 も、出力を DB の行にそのまま入れている。
