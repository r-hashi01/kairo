# 0001. 状態遷移は I/O のない純粋関数とし、時刻はイベントで渡す

- 状態: 提案（v0 実装済み）
- 日付: 2026-09-30
- 関連: FR2 / 不変条件 1, 2, 3

## 背景

要件は「(状態, イベント) → (新しい状態, 命令)」の純粋関数と、同じイベント列から同じ状態が得られること（リプレイ可能性）を求めている。リカバリ、スナップショット、テストはすべてこの性質に依存する。

## 決定

- `core.Apply(plan, state, event, out)` を唯一の遷移関数とする。状態はその場で書き換える（割り当てを避けるため）が、観測できる振る舞いは純粋関数と同じ。
- 時刻は `Event.At`（シャードが付与し、ログに残る）からだけ得る。ID は `NextAct` / `NextScope` / `NextTimer` の連番。
- Go の map を走査して出力を作るときはキーをソートする（`sortedActs`）。JSON の組み立ても決定的にする。
- 適用されなかったイベントは `ErrIgnored` を返し、状態を変えない。エンジンはそれをログに書かない。
- 保護ステップ（`kairo.pass` / `kairo.append`）はコアの中で計算する。出力はイベントではないのでログに残らず、リプレイ時に再計算される。

## 結果

- リプレイ、スナップショットの往復、並べ替え耐性をテストで検証できる（`checkReplay`、`TestParallelJoinAnyOrder`）。
- 1遷移あたり約 1µs（予算 20µs）。
- コアに I/O を入れる変更はできない。`TestCoreIsPure`（import の許可リストと `time.Now` / `go` 文の静的検査）と hook `guard-edit.sh` が止める。

## 検討した代替案

- ワークフローをコードとして実行し、途中経過を記録する方式（Temporal 型のリプレイ）: 決定性の責任が利用者のコードに移り、ランタイムの固定コストも大きくなる。
- 実行ごとの goroutine が状態を持つ方式: 待機中のコストが状態のバイト数にならない（→ 0002）。
