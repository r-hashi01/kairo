# 0083. 列挙する実行は保存先が割り当てる作成序数で並べる

- 状態: 承認（2026-11-20）
- 日付: 2026-11-18

## 背景

コードワークフローの直接の子を返す `Children` と、根のコードワークフローを返す `List` は、どちらも実行を作成順に返す公開 API である。しかし保存している作成時刻の精度は millisecond であり、同じ millisecond に複数の実行を作れる。

作成時刻が同じ実行について、埋め込みランタイムの3 SDKは作成時刻の次に利用者指定の RunID を比較し、kairod の `Children` は RunID だけを比較する。コードから作る呼び出しの RunID には作用名と入力のhashが含まれるため、逐次に作った2件でも、入力によって表示順が逆になる。kairod の `List` も作成時刻が同じ場合は RunID を比較するため、同じ問題を持つ。

更新時刻は作成順の代わりにならない。先に作った実行が後から終わることがあり、未完了の実行は更新時刻を変え続ける。親の実行記録にも、子を作った位置は保存されていない。また、根の一覧と外から親へ付けた実行には、親コード上の位置そのものがない。

3 SDKが同じdatabaseを共有する場合、作成順はprocessの時計やmemoryでは決められない。kairodでも、RunIDによって別shardへ分かれる実行に、再起動とログ退役を越えて同じ順序を与える必要がある。そのため、どの時点を「先に作った」とするか、順序をどこへ保存するか、旧記録をどう扱うかを決める。

## 決定

### 決定項 1（保存先が初回作成を直列化した順に序数を割り当てる）

`Children` または `List` の対象になり得る新しい実行には、その保存先が正の作成序数を1回だけ割り当てる。対象は、親を持つ実行と、workflow名を持つ根のコードワークフローである。通常のgraph rootは対象にしない。

作成序数は、保存先が新しいRunIDを初めて受け付ける直列化点の順序を表す。同時に来た作成には、databaseのtransactionまたはkairodの所有する順序が先後を与える。呼び出したprocessの時計、処理を終えた順序、RunIDのbyte順は使わない。

同じRunIDの冪等な再投入は、最初の作成序数を保つ。失敗した作成による欠番は許す。保存先が保持している序数付き実行の間では、序数を重複または再利用せず、新しい値をそれらすべてより大きくする。

序数のscopeは、kairodではdata directory、埋め込みランタイムではdatabaseのtable prefixとする。別scopeの序数には比較可能性を与えない。3 SDKで整数を正確に共有できるよう、値は1以上かつJavaScriptのsafe integer以下とし、使い切った保存先は序数を再利用せず、新しい対象実行の作成を明示的に拒否する。

### 決定項 2（ChildrenとListの順序とcursorに作成序数を使う）

`Children` は直接の子を作成序数の昇順で返す。`List` は根のコードワークフローを作成序数の昇順で返し、`after` cursorもcursor実行の作成序数より後を選ぶ。

`since` と `until` は引き続き作成時刻を対象にする。作成時刻は表示と時間範囲のfilterに残すが、同順位の判定にも全体の並びにも使わない。更新時刻とRunIDも順序には使わない。

この変更では作成序数を `RunInfo` の公開fieldに加えない。現在必要な性質は、`Children` と `List` が正しい順で返し、`List` のpaginationがその順を保つことで満たせる。複数の保存先または複数の問い合わせ結果を利用者が自分で統合する公開APIが必要になった場合は、scope、表現、保持期間を別のADRで決める。

### 決定項 3（序数を実行の耐久メタデータとして保存する）

作成序数は、親、workflow名、作成時刻と同じく、実行の初回作成から保持終了まで変わらない耐久メタデータにする。kairodではactive、evicted、終了済みのどの段階でも復元できるよう、start、checkpoint、終了マーカーの任意fieldとして保存する。埋め込みランタイムではrun rowに保存し、複数processからの割り当てを保存先内で原子的にする。

作成序数を持たない旧記録はlegacy groupとして、序数を持つ新しい記録より前に並べる。legacy groupの中は、従来どおり作成時刻とRunIDのbyte順で並べる。存在しなかった真の順序は推測せず、upgrade前から保持している結果の順序を変えない。新しいreaderは旧記録を読み続ける。

通常のgraph rootは作成序数を持たず、既存recordのbyte列と開始経路を変えない。親を持つ実行とコードワークフローの根は、既存の開始記録または作成transactionに序数を含める。eventごとの書き込み、一覧専用の永続index、background pollingは足さない。

### 決定項 4（序数割り当ての費用は対象実行の作成時だけに払う）

作成序数の割り当ては、対象実行の作成を耐久化する仕事の一部とする。対象実行1件につき、固定長のメタデータと保存先の序数割り当てを1回だけ増やす。更新、完了、`Children`、`List`のたびに序数を更新しない。

複数processで共有するdatabaseでは、保存先固有のsequence操作を使ってよい。ただし、実行とは別に一覧内容を複製する表や、通常のeventごとに更新する索引は作らない。実装時には、作成throughputと既存の実行あたりの費用を同じ環境で比較する。

### この ADR で決定しないこと

- column名、record flag、sequenceの確保方法、index、移行手順、個別の検証手順は、参照に示す実装Issueとコードで決める。
- 別のdata directoryまたはdatabaseにある実行を1つの順序へ統合しない。
- legacy groupに、保存されていない真の作成順を後付けしない。
- 通常のgraph rootを列挙する管理APIや、そのための作成序数は決めない。
- 作成序数を公開するAPIは足さない。必要性が具体化した場合は別のADRで決める。

## 結果

- 良い影響: 同じmillisecondに逐次作成した子と根でも、`Children` と `List` はRunIDや入力hashに左右されず、保存先が受け付けた順に返す。`List` のpage境界も同じ順序を使う。
- 悪い影響: 対象実行ごとに作成序数の保存と割り当てが増える。database schemaとkairodのstart、checkpoint、終了マーカーの形式が拡張される。同じdatabaseを共有する旧SDKが新しい実行を作る間は、すべての新規実行に正確な序数が付く保証を持てない。
- 中立な影響: 作成時刻と更新時刻の値、時間範囲filter、保持期間、親子の寿命は変わらない。同時作成の先後は利用者processの開始時刻ではなく、保存先の直列化順として定義される。
- 新しく守る制約: 冪等な再投入で序数を変えない。保持中の序数を重複または再利用しない。legacy groupを新しい序数付き記録より前に保つ。通常のgraph rootに序数の費用を加えない。

## 検討した代替案

- 作成時刻の精度を上げる: process間の時計にはずれがあり、同じ値も取り得る。時刻だけでは原子的な先後にならない。
- 更新時刻でtieを解く: 作成順ではなく、作用や待ちが進んだ順になる。実行中にも並びが変わり、paginationを安定させない。
- RunIDを時系列形式に変える: 利用者指定IDと既存の冪等IDを変え、親コードが作るhash由来IDとの互換性を失う。
- 親のリプレイ履歴から子の位置を復元する: 根の`List`、外から付けた子、並行して作る子には位置がない。列挙のたびにコードをリプレイすることもできない。
- 親ごとの序数だけを持つ: `Children`は直せるが、根の`List`に同じ欠陥が残り、2種類の順序規則が必要になる。
- 作成順の専用一覧表を持つ: 実行の耐久メタデータと別の真実になり、作成、削除、回復との原子性が必要になる。実行自身に序数を持てば足りる。
- 旧記録を移行時に推測して書き換える: kairodのappend-only logを破り、推測したRunID順を真の作成順として固定する。legacyとして明示するほうが正確である。

## 関連する ADR

- ADR 0041 の決定項 1（原則）: 序数の費用を、その順序が必要な実行の作成時だけに限定する。
- ADR 0059 の決定項 5（実行の一覧と目印）: 埋め込みランタイムの`List`が約束する作成順を、保存先の序数で定義する。
- ADR 0067 の決定項 1（親IDを実行の耐久メタデータとして保存する）: 作成序数を同じ寿命のメタデータとして保存する。
- ADR 0067 の決定項 4（`Children`をHTTPと3 SDKへ足す）: RunIDのbyte順という部分を本ADRの作成序数順で置き換える。
- ADR 0068 の決定項 1（一覧に要る情報を、コードワークフローの実行メタデータとして保存する）: 作成序数を一覧に必要な不変メタデータへ加える。
- ADR 0068 の決定項 2（engineが各shardのsnapshotを集め、要求時にだけ並べる）: `(created_at, RunID)`順とcursor比較を本ADRの作成序数へ置き換える。
