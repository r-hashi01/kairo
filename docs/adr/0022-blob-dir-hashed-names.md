# 0022. blob.Dir は、オブジェクト名をハッシュしたファイル名で保存する

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: ADR 0011, 0020, 0021

## 背景

ADR 0020 で足した共通テスト（任意の名前）で、既定のファイル形式の `blob.Dir` に不具合が見つかった。

- オブジェクト名の末尾 2 バイトをサブディレクトリ名に使っている。マルチバイト文字の途中で切れると不正なファイル名になり、保存に失敗する（例: `snap/日本語`）。
- 名前を、`:` と `/` を置き換えただけで、ほぼそのままファイル名にしている。
  - ファイル名の長さの上限（255 バイト）を超える名前は保存できない。
  - OS によってはパスとして解釈されうる文字（`\` など）がそのまま入る。
  - エンジンが使う名前は `snap/<run id>` と `sha256:<hex>` だが、`blob.Store` は公開の API で、run id は利用者が指定できる。

## 決定

- ファイル名を、オブジェクト名の SHA-256 の 16 進表記（64 文字）にする。置き場所は `<root>/<先頭 2 文字>/<64 文字>` とする。
- 以前の形式で保存されたオブジェクトも読めるようにする。
  - `Get` は新しい名前で見つからなければ、以前の形式の名前でも探す。
  - `Delete` は両方の名前を消す。
  - `Put` は新しい名前で書き、以前の形式の名前に古いものがあれば消す。
  - 以前の形式の名前が不正になる（上の不具合に当たる）場合は、そちらは探さない。
- 移行のための一括の書き換えはしない。古いオブジェクトは、書き直されるか消されるときに新しい形式に移る。

## 結果

- どんな名前でも保存できる。ファイル名から名前が直接は分からなくなる。ただし、ハッシュなので、推測した名前の照合は防げない。それを防ぐには ADR 0021 の暗号化を使う。
- 以前の形式のオブジェクトが残っている間は、見つからないときの `Get` が 2 回探す。
- テスト:
  - `blob.Dir` の共通テストで `ArbitraryNames` を有効にする。
  - 以前の形式で書いたオブジェクトを、新しい実装で読み、書き換え、消せることを確かめる。

## 検討した代替案

- 名前を 16 進や base64 に符号化してファイル名にする: 長い名前がファイル名の上限を超える。
- 名前に使える文字を制限する: `blob.Store` の他の実装（メモリ、SQL）は任意の名前を扱えるので、ファイル形式だけ制限すると実装ごとに挙動が違ってしまう。
- 以前の形式を読まない: 既存のデータディレクトリにあるスナップショットが読めなくなり、実行が失われる。

## 実装で詰めた詳細（2026-10-01 追記、ADR 0017）

- 以前の形式の名前を探さない条件を、次のように決めた（`Dir.legacyPath`）。
  - UTF-8 として不正
  - 255 バイトを超える
  - `.` または `..` になる
  - `\` か NUL を含む
- `Put` は、新しい名前への書き込みを耐久化してから、以前の形式のコピーを消す。間でクラッシュしても、両方が残るだけで、新しい方が優先される。
- テスト:
  - `TestDirConformance`（`ArbitraryNames` を有効にした）
  - `TestDirReadsPreviousFormat`（以前の形式を読める。書き直すと移る。削除で両方消える。ファイル名に名前が出ない）
