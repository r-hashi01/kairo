# 0072. kairod で開始を確認できない実行は、同じ RunID で確認し直し、ワークフローの失敗にしない

- 状態: 承認（2026-11-09）
- 日付: 2026-11-09
- 関連: 不変条件 2・5 / ADR 0023（耐久化した開始と冪等な RunID）、0041（実行ごとのコスト）、0063（一時的な保存先エラーからの再駆動）、0069（kairod の駆動権）/ GitHub Issue #12

## 背景

`POST /v1/runs` は、開始が耐久化してから成功を返す。開始はシャードへ渡ったが、既定30秒のうちに耐久化の確認が返らないと、kairod は HTTP 504 と `run_id` を返す（ADR 0023 の `ErrUnconfirmed`）。実行は、その後に耐久化して続くことも、kairod が落ちて消えることもある。

コードで書くワークフローが `Call`、`Child`、`Sleep`、`WaitFor` の子runを開始するとき、この504を通常の関数エラーとして扱うと、親ワークフローが失敗を記録し得る。2026-11-09のqualificationでは、負荷中に子runの開始ackが30秒を越え、実際には後から開始・完了した子がある一方、SDKの現在の駆動には `start not confirmed` が返った。

これは実のアクションの結果不明とは違う。子runのIDは、親ID・プラン・入力・呼び出し番号から決まる。同じIDの開始を確認し直しても、ADR 0023の冪等性により別の実行は増えない。逆に、504を親の業務上の失敗に変えると、一時的なfsync遅延を永久的な結果へ変えてしまう。

ADR 0063は、kairod経由のHTTP一時障害へ自動で再駆動の印を付けることを対象外にした。この判断はその範囲を広げるため、別に承認する。

## 決定

### 1. 開始の未確認を、業務上の失敗と分ける

3つのSDKは、冪等なRunIDを指定した開始について、次を「開始の未確認」として扱う。

- `POST /v1/runs` の HTTP 504。応答に同じ `run_id` があることを確認する。
- requestを送った後、成功応答を読めず、受理されたかを判定できない通信エラー。

400、404、409、429など、意味が確定したHTTP応答は含めない。開始前の定義登録、認証、入力の誤りも含めない。

### 2. 同じRunIDで開始を確認し直す

- SDKは同じplan・input・parent・RunIDで `POST /v1/runs` をやり直す。新しいIDを振らない。
- 成功（新規201または既存200）が返れば、通常どおり続ける。最初の開始が後から耐久化していれば既存として見つかり、消えていれば同じIDで開始される。
- 再確認は、呼び出し元のcontext / AbortSignal / taskの期限まで行う。失敗のたびに短い上限付きbackoffを置き、回復していないkairodへbusy loopしない。専用の常駐goroutine、ポーリング用のrun、耐久記録は足さない。この費用は未確認が起きたときだけ払う。
- 呼び出し元が停止して確認を続けられなくなった場合、現在のワークフロー駆動は成功も失敗も記録しない。kairodの駆動権を譲り、同じワークフローの次の駆動が同じ子RunIDを確認し直す。サスペンドモードでは既存の `ErrSuspended` / `Suspended`、待ちモードでは既存の停止エラーとして返す。

### 3. 実のアクションの結果不明とは混ぜない

この再確認でやり直すのは、runの冪等な開始だけである。workerへ渡した実のアクションが切断された場合は、これまでどおり結果不明として `blocked` にする。`IdempotentRetry` のない実のアクションを再実行しない。

### 4. APIと保存形式は増やさない

HTTP 504の本文にある `run_id`、既存のRunID冪等性、既存の駆動権を使う。コアのイベント、WAL、スナップショット、worker protocol、runの保存形式は変えない。

## 結果

- fsyncやDBの一時的な遅延で開始ackが30秒を越えても、それだけで親ワークフローを永久に失敗させない。
- 成功を返す条件は緩めない。開始が耐久化したと確認できるまで、SDKはその子runを成功した開始として扱わない。
- 同じRunIDしか送らないため、再確認によって子runや作用が増えない。
- kairodまたは保存先が長く回復しないと、呼び出しはcontextの期限まで長く待つ。運用側は504と再確認回数を観測し、過負荷を直す必要がある。
- 3 SDKで次を同じ意味のテストにする。
  - 最初の開始応答を504にし、同じRunIDの再送で既存のrunを見つける。親は完了し、子は1つだけ。
  - 応答を失った開始を同じIDで確認し直す。
  - contextを切るまで未確認を続けても、親の失敗を記録しない。別の駆動で完了する。
  - worker切断中のnon-idempotent real actionは、引き続き `blocked` であり再実行されない。

## 実装

2026-11-09にGo・Python・TypeScript SDKへ実装した。開始requestのbodyは各試行で同一で、backoffは50msから始めて最大1秒とする。Goはcontext、Pythonはtask cancellation、TypeScriptはAbortSignalで再確認を打ち切る。DrainとCloseも開始確認を打ち切り、その呼び出しが戻るまで待つ。Pythonで取消後に残り得る同期HTTP threadはrequest timeout（既定90秒）で上限を持つ。3 SDKの回帰試験は、最初の504後も同じRunIDが送られること、取消後に再試行しないこと、同じRunIDを後の駆動で完了できることを確認する。

## 検討した代替案

- **HTTP timeoutを30秒より長くする:** 遅い条件を後ろへずらすだけで、応答を失う可能性は消えない。過負荷時にHTTP接続とメモリを長く保持する。
- **504を通常のワークフロー失敗として記録する:** 一時的な耐久化遅延を永久的な業務結果へ変える。後から子runが完了すると、記録された親の失敗とも食い違う。
- **504で直ちに新しいIDを振る:** 同じ子を二重に開始し、実の作用を重複させ得る。
- **すべてのHTTPエラーを再試行する:** 認証、入力、親の不在など恒久的な誤りまで隠す。冪等な開始の未確認だけに限る。
- **実のアクションの結果不明も同じように再試行する:** RunIDの冪等な開始と、外界へ作用したか不明な試行は別である。不変条件5に反する。
