# 0044. 実行の終わりを、希望したワーカーに知らせる

- 状態: 承認
- 日付: 2026-10-06
- 関連: ADR 0009（ワーカーのプロトコル）、0026（取り消し）、0041（実行 1 回あたりのコスト）、0042（n8n との統合）

## 背景

ワーカーのプロトコル（ADR 0009）は、ステップ単位のやり取りだけを持つ。メッセージは Hello・Task・Result・Credit・Chunk・Cancel の 6 種類。ワーカーには、実行がいつ終わったかがわからない。これまでのワーカーは、ステップをまたいで何も持たなかったので、困らなかった。

n8n との統合（ADR 0042 の段階 5）で、kairo-worker は式のサンドボックスを 1 実行に 1 つ持つようにした（利用者と決めた。v1 と同じ単位）。ワーカーが、初めて実行ごとの状態を持つようになった。

- 実行の終わりがわからないので、手放し方を推測に頼っている。今は、最近使った実行の分を最大 64 まで持ち、超えたら一番古いものを手放す。
- そのため、終わった実行のサンドボックスが、ほかの実行に場所を譲るまでメモリに残る。上限は勘で決めた値で、小さければ使い回しが効かず、大きければメモリを無駄に使う。
- 今後ワーカーが実行ごとに何かを持つたびに、同じ推測が要る。

実行の終わりを知っているのは kairo だけである。

## 決定

kairo から、実行の終わりをワーカーに知らせるメッセージ `RunEnd` を足す。希望したワーカーの接続にだけ、その接続に仕事を渡した実行についてだけ送る。

- **メッセージ:** `RunEnd {"run_id": "..."}`（型 7、runtime → worker）。実行が終わり、その終わりが耐久化した後に送る（`Engine.Wait` が戻るのと同じ時点）。
  - 実行の結果（成功・失敗・取り消し）は載せない。ワーカーが要るのは「この実行の仕事はもう来ない」ことだけである。
  - 同じ実行の Task より後に届く。Cancel との順番は保証しない（2026-10-06、利用者と決めた）。Cancel は取り消しの処理が別の goroutine から書くので、取り消しで終わった実行では、RunEnd が先に届くことがある。ワーカーは Cancel を仕事の番号で引くので、順番が逆でも壊れない。まだ Result を返していない仕事があっても、ワーカーはその Result を返す（ADR 0026 と同じ）。
- **希望の申し出:** ワーカーは Hello に `"run_end": true` を付ける。付けないワーカーには送らない。古いワーカーは知らない型を読み飛ばすので、付けなくても壊れない。
- **kairo の側（`protocol`、`engine`）:**
  - `engine.Engine` に、実行が終わったときに呼ぶ関数を 1 つ登録する口を足す（`OnRunEnd(func(runID string))`）。`e.finish` から呼ぶ。シャードのループからも呼ばれるので、登録する関数は待ってはいけない。
  - `protocol.Server` は、希望した接続について、仕事を渡した実行の ID を覚える（サーバー全体で、実行 ID → 接続の表）。実行が終わったら、その表を引いて、該当する接続の書き込み側に `RunEnd` を積み、表から消す。書き込みは接続の書き込み用 goroutine が行う（シャードのループで待たない）。
  - 接続が切れたら、その接続を表から消す。
- **費用（ADR 0041）:** 希望しない接続と、その実行には、何も増えない。希望した接続では、実行ごとに表の 1 項目と、終わりのフレーム 1 つ。これは、ワーカーが実行のために持った資源を手放す仕事、つまりノードの実行の一部である。タイマーもポーリングも使わない。
- **ワーカーの側:**
  - TypeScript の部品（`sdk/ts`）: `Worker` に `onRunEnd(runId)` を渡せるようにする。渡したら、Hello に `run_end` を付ける。
  - kairo-worker: `RunEnd` を受けたら、その実行のサンドボックスを手放す（その実行のステップが動いていれば、終わってから）。最近使った実行を最大 64 まで持つ仕組みは残すが、役目は安全弁になる。
  - Python の部品は、今回は変えない（実行ごとの状態を持たないため）。

## 結果

- 実行ごとの状態を持つワーカーが、終わりと同時に資源を手放せる。kairo-worker のサンドボックスが、終わった実行のために残らなくなる。
- 新しく守ること:
  - `RunEnd` は、その接続に渡した同じ実行の Task より前に届いてはいけない。
  - `OnRunEnd` に登録する関数は、待ってはいけない（シャードのループから呼ばれる）。
- 届かないことがある。ワーカーは、届かなくても壊れないように作る（安全弁を残す）。
  - kairo が再起動すると、どの接続に仕事を渡したかの表は消える。再起動の前に渡した実行の終わりは、知らせない。
  - 接続が切れて、つなぎ直したときも同じ。
- テスト（足す）:
  - `protocol`: 希望した接続にだけ、仕事を渡した実行についてだけ、Task の後に 1 回届くこと。希望しない接続には届かないこと。接続が切れたら表から消えること。
  - `sdk/ts`: `onRunEnd` が呼ばれること（偽のランタイムとの単体テスト）。
  - `compat/n8n` の結合テスト（`interop_test.go`）: TypeScript のワーカーが、本物のサーバーから `RunEnd` を受けること。
  - 実機（n8n）で、サンドボックスの数が実行の数に応じて増え続けないこと。

## 検討した代替案

- **ワーカーの側の推測だけで済ませる（今の形）。** 終わった実行の資源が残り、上限を勘で決めることになる。実行ごとの状態を持つワーカーが増えるたびに、同じ推測が要る。
- **すべての接続に、すべての実行の終わりを送る。** 実行ごとの費用が、ワーカーの数に比例して全実行にかかる。希望しないワーカーにも払わせることになる（ADR 0041 に反する）。
- **kairo-n8n から知らせる。** kairo-n8n は実行の終わりを知っている（トレース）。しかし、ワーカーとの間には、ワーカーから問い合わせる口（step-data）しかない。知らせるには、実行ごとの購読か、別の常設の経路が要る。
- **最後のステップに印を付ける。** どのステップが最後かは、実行が終わるまでわからない（分岐、ループ、失敗）。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

- **エンジン:** `Engine.OnRunEnd` は、登録した関数を `e.finish` の最後に呼ぶ。`Wait` の待ち手と、ライブ中継の終わりを知らせた後になる。登録は何度でもでき、どれも呼ぶ。
- **サーバー:** `Serve` の最初の呼び出しで 1 回だけ登録する（UNIX ソケットと TCP の両方で待ち受けても 1 回）。
  - 仕事を渡した実行を覚えるのも、`RunEnd` を書くのも、接続の書き込み用 goroutine で行う。仕事は、フレームを書く前に覚える。そのため、同じ実行の Task より先に `RunEnd` が出ることはない。
  - 終わりの知らせ（`runEnded`）は、表を引いて、該当する接続の待ち行列に積み、書き込み用 goroutine を起こすだけにした（容量 1 のチャネルに送るが、待たない）。
- **テスト:**
  - `protocol` の `TestRunEnd`: 申し出た接続にだけ、実行ごとに 1 回、その実行の仕事の後に届くこと。申し出ない接続には届かないこと。接続が切れたら表から消えること。
  - `sdk/ts` の単体テスト: Hello に `run_end` が付き、`onRunEnd` が呼ばれること。
  - `compat/n8n` の `TestTypeScriptWorker`: TypeScript のワーカーが、本物のサーバーから受けること。
- **実機（n8n）:** 同時 8 本で 300 回流し、`RunEnd` は 300 回すべて届いた。kairo-worker が持つサンドボックスの数は、ずっと 0〜7 で、同時に動いている実行の数を超えなかった。
- **性能:**
  - `scripts/bench.sh` の予算は、すべて範囲内だった（遷移 1180ns、5 ノードの実行あたりの CPU 75µs、受け渡しの p99 185µs）。
  - 実機（プール 16、load average 19〜35）では、c=1 で 47 rps（p50 21ms）、c=8 で 144 rps（p50 54ms）、c=32 で 162 rps（p50 184ms）だった。c=32 は、終わりを知らせる前の 100 rps から伸びた。終わった実行のサンドボックスが場所をふさがなくなり、新しい実行が 1 つずつ取り直さずに済んだためと見ている（推定）。
- **レビューで直したこと（2026-10-06）:**
  - **終わった実行の仕事を送らない。** 取り消しや失敗で終わった実行の仕事が、ディスパッチャの取り消しが追いつく前に書き込み用 goroutine に渡ることがある。そのまま送ると、その実行の `RunEnd` はもう過ぎているので届かず、表にも残り続ける。
    - 希望した接続では、仕事を送る前に、実行がもう終わっていないかを確かめる（`Server.sending`、`Engine.Finished`）。終わっていれば送らず、取り消された仕事として片付ける。
    - 確認と表への登録は、同じロック（`rmu`）の中で行う。確認の後に終わった実行は、`runEnded` が表で見つけるので、取りこぼさない。
  - **希望する接続がなければ、何もしない。** 希望した接続の数を数えておき（atomic）、0 なら `runEnded` はロックを取らずに戻る。エンジンの側も、登録した関数の一覧を atomic に持ち、実行の終わりにロックを取らない。
  - テスト: `TestRunEnd` に、終わった実行の仕事は送らないことを足した。
