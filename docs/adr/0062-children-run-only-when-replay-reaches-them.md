# 0062. 子の実行は親のリプレイが到達したときだけ再開し、親が終わる前に未完了の子孫を取り消す

- 状態: 承認
- 日付: 2026-11-04
- 関連: 不変条件 2・4・5・6 / ADR 0026（実行中のタスクの取り消し）、0041（実行 1 回あたりのコスト）、0049（コードで書く API）、0054（親子の記録と木ごとの削除）、0058（Go の SDK）、0059（駆動の借用）、0060（ワークフローの版）/ GitHub Issue #2

## 背景

コードで書くワークフローは、再開のたびに関数を最初から動かす。終わった呼び出しと子のワークフローは、同じ ID の記録から結果を返し、まだ終わっていないものは続ける（ADR 0049）。埋め込みのランタイムでは、呼び出しと子のワークフローの行に、それを作ったワークフローの ID を `parent` として記録する（ADR 0054）。

ワークフローの版を変えずに関数を変えることは ADR 0060 で禁止しているが、実際には、古い関数が始めた子へ新しいリプレイが到達しない場合がある。たとえば、利用側の記録された guard が入力のずれを見つけ、古い子を呼ぶ前に関数を終える場合である。

今のランタイムは、親がリプレイで子へ到達するかどうかと関係なく、子の実行をそれぞれ回復する。

- 子の呼び出しに期限切れの手順の借用があれば、`tick` が結果不明として回復し、再試行できる作用なら動かす。
- 子の呼び出しに期限の来た timer があれば、`tick` が発火させる。
- 子のワークフローを動かしていた関数は、親のリプレイとは別のきっかけでも再び動きうる。

そのため、親の新しいリプレイが子を必要としないと判断する前に、古い子の作用が動くことがある。親がその後に完了または失敗しても、到達しなかった子を取り消す処理はなく、子は待ち続けたり作用を続けたりする。親の記録と、それを待つ人には仕事が終わったように見えるのに、その木の中の仕事が後から外へ作用する。

親が終わった後に子を列挙して取り消すだけでは、この問題を防げない。子は親のリプレイより先に回復でき、親の終端記録と子の取り消しの間でプロセスが落ちれば、取り消しも失われる。親のリプレイへの到達可能性と、子の回復を結び付ける必要がある。

この問題は `parent` を保存している埋め込みのランタイム（Go・TypeScript・Python）にまず適用する。kairod は実行間の `parent` をまだ保存しないため、同じ規則を適用できない。kairod に親子の記録を足す変更で、この ADR の規則も適用する。

## 決定

### 1. 親のある実行は、親のリプレイが同じ呼び出しへ到達したときだけ再開する

`parent` のある実行（アクションの呼び出し、wait、sleep、子のワークフロー）は、プロセスが止まった後、期限切れの借用や timer だけを理由に単独では再開しない。

- `tick` が、`parent` のある実行の期限切れの手順の借用または期限の来た timer を見つけたら、子へ回復イベントを直接適用しない。その木の、まだ終わっていないワークフローの駆動を起こす。
- ワークフローの関数がリプレイされ、同じ ID の呼び出しまたは子のワークフローへ到達したとき、その実行に残る期限切れの借用と期限の来た timer を処理してから結果を待つ。
- その地点へ到達しなければ、古い子の作用は再開しない。
- `parent` のないグラフの実行は、これまでどおり `tick` が直接回復する。

待ちモードでは、根のワークフローの駆動の借用を起こす。サスペンドモードでは、今まで child の timer や結果が直接の親を起こしたのと同じく、期限の来た child を見つけた時点で親のワークフローを再駆動する。親のリプレイが child へ到達して初めて、その timer を発火させる。

到達したことを保存先へ新しく記録しない。関数が同じ呼び出しの ID を作り、既存の実行を開くこと自体を到達の印にする。プロセスが途中で止まれば、次の駆動で同じ判断をやり直す。

### 2. ワークフローは、未完了の子孫を片付けてから成功または失敗を記録する

ワークフローの関数が成功または失敗で戻ったら、SDK はすぐに `done` を送らず、次の終端処理を行う。

1. その駆動の context を止め、関数が残した並列の枝が新しい呼び出しを始めないようにする。これはプロセスの駆動を止めるだけで、親の実行を取り消したことにはしない。
2. `parent` をたどって子孫を集める。終わっていない実行（running、waiting、blocked）を、深いものから取り消す。
3. 各子孫の耐久化した終端結果を確かめる。競合して先に完了または失敗した子は、その結果のままにする。
4. 未完了の子孫がないことをもう一度確かめてから、親へ成功または失敗の `done` を送り、ADR 0061 のとおり記録された結果を返す。

終端処理の途中で保存先のエラーが起きた、またはプロセスが止まった場合は、親の成功・失敗を記録しない。親は unfinished のまま残り、次の駆動が関数のリプレイと終端処理をやり直す。子の取り消しは冪等なので、途中まで済んでいても同じ結果になる。

通常の関数では、到達した呼び出しは結果を待ってから関数が戻るので、子孫はすでに終わっている。追加の仕事は `parent` の索引で直接の子を確かめる読み取りである。再帰するのは子がある場合だけにする。

TypeScript の `Promise.all` のように、1 つの枝の失敗を返した後も別の枝が動きうる場合も、この終端処理で別の枝を止め、その呼び出しを取り消してから親の失敗を記録する。Go の `Parallel` のように全枝を待つ実装でも、同じ終端処理を通す。

### 3. 明示した取り消しも、子孫の終端を確認してから返す

SDK の `Cancel` は、対象のワークフローと未完了の子孫を木として取り消す。

- まず見つかっている子孫を深いものから取り消し、親を取り消す。親の取り消しは、そこで動いている関数の context を止める。
- 親の取り消しと競合して作られた子がないか、もう一度木を調べ、未完了の子孫を取り消す。
- 親とすべての子孫の耐久化した終端状態を確認してから `Cancel` を返す。親については ADR 0061 の `ErrRunSettled` / `RunSettledError` の規則を保つ。

途中でプロセスが落ち、親だけが終端状態になった場合も、決定 1 の回復時の確認で修復する。`tick` が `parent` のある実行を進めようとしたとき、祖先のどれかが終わっていれば、その子を回復または発火させずに取り消す。これを子孫へ繰り返す。そのため、終わった親の下の作用が、回復をきっかけに新しく動くことはない。

すでに実行器へ渡ったタスクの取り消しは、ADR 0026 と同じく best effort である。タスクが取り消しを無視して外で作用することまでは防げないが、その試行を再実行せず、後から届いた結果で記録を変えない。

### 4. 実の作用を持つ子も、通常の取り消しと同じ意味にする

結果待ちの実の手順を含む子孫も、通常の `Cancel` と同じく `cancelled` にする。

- 成功または失敗として扱わない。
- 同じ試行も新しい試行も、取り消し後には実行しない。
- 実行器への取り消しは best effort で、外で作用したかどうかを断定しない。
- 遅れて届いた結果は、終わった実行への結果として無視する。

結果不明の実の手順を `blocked` に変えることは、この ADR では行わない。現在の明示した `Cancel` は、作用の有無を成功・失敗のどちらにも決めず、実行全体を `cancelled` にする（ADR 0026）。自動の子孫取り消しだけを `blocked` にすると、同じ取り消しに 2 つの意味ができる。確認を必須にするなら、通常の `Cancel` の意味そのものを別の ADR で変える。

### 5. ワークフローの子は detached にしない

`Child` / `ctx.workflow` で始めた子と、ワークフローから呼んだアクションは、常に親の寿命に含める。この ADR では detached の指定を足さない。

親より長く動く仕事は、ワークフローの外から、親を付けない根の実行として始める。外から親を指定して始める API を足す場合（GitHub Issue #4）は、親を指定したものにはこの ADR の規則を適用し、親を指定しないものを独立した根として扱う。

### 6. 形式と費用

コアの状態、イベントと命令、保存先の表は変えない。ADR 0054 の `parent` 列と索引、既存の `cancel` イベントを使う。保存先には、1 つの実行について期限切れの借用と期限の来た timer を処理する操作が要るが、新しい永続化形式は作らない。

- 通常のワークフロー終了ごとに、直接の子を確かめる索引読み取りが 1 回増える。これは、親の結果を、その木の仕事が終わった結果として記録するための仕事（ADR 0041）である。
- 子孫の列挙と取り消しは、未完了の子孫があるときだけ、その数に応じて行う。
- 親のある実行の到達確認は、プロセス停止後の回復時にだけ行う。すべての手順の通常の開始には、祖先を読む費用を足さない。
- ポーリング、実行ごとの goroutine、新しい常駐の対応表は足さない。

## 結果

- リプレイが以前の子へ到達しなくなった場合、その子の作用はプロセス停止から単独で再開されず、親の終端処理で取り消される。
- 親の成功または失敗が利用者へ返る時点では、記録上、未完了の子孫は残らない。
- 明示した取り消しも、戻る時点では木の未完了の子孫を残さない。
- 親の終了と子孫の取り消しの間で落ちても、終わった祖先の確認により、子を作用させずに修復する。
- 通常の、同じコードでのリプレイは、親が同じ呼び出しへ到達した時点で初めて子を回復する。終わった呼び出しはこれまでどおり記録から返す。
- kairod 経由には、親子を記録する変更までこの規則を適用できない。この制約を SDK の文書に明記する。

次のテストを、Go の `kairotest` と TypeScript・Python の同じ振る舞いの一式へ足す。

- 親が C1 を終え、C2 の作用を実行中にプロセスが止まる。次の駆動では、記録された guard が C2 へ到達する前に親を失敗させる。C2 の作用を再開せず、C2 とその未完了の子孫を取り消してから親が失敗する。
- 親が成功で別の経路へ進む場合も、到達しなかった子孫を取り消す。
- 子の期限切れの借用と期限の来た timer は、親のリプレイがその子へ到達するまで処理されない。到達すれば従来どおり続く。
- 親の終端直後、子孫の取り消し前にプロセスが止まった形を作る。次の `tick` は子の作用を回復せず、取り消す。
- 明示した `Cancel` は、子のワークフロー、その呼び出し、待ち、blocked の実行を取り消し、すべての終端を確認してから返す。
- 並列の 1 枝が失敗し、別の枝がまだ呼び出しを待っている場合、別の枝を取り消してから親の失敗を記録する。
- 結果待ちの実の手順を持つ子を取り消しても、成功・失敗にせず、再試行せず、遅い結果を無視する。

## 検討した代替案

- **親が終わった後で、子を列挙して取り消す:** 親のリプレイより先に子の回復が作用を動かせる。終端記録の直後に落ちると、取り消しが行われない。
- **利用側の guard が `Children` と `Cancel` を呼ぶ:** どの関数変更で古い子が不要になったかを、利用側が毎回正しく列挙する必要がある。guard より先に子が回復する競合も残る。
- **期限切れのすべての子を、今までどおり独立に回復する:** 親のコードがもう到達しない作用を、記録があるという理由だけで動かす現在の問題を残す。
- **親が終わったら子孫の行を削除する:** 呼び出しの記録、結果不明の実の試行、監査に要る状態を失う。遅れて届く結果との関係も分からなくなる。取り消しとして記録し、木は ADR 0054 の期間まで残す。
- **実の手順を持つ子だけ `blocked` にする:** 通常の `Cancel` と違う意味になり、親の終端も人の確認まで止まりうる。取り消しは作用の成功・失敗を断定せず、再実行もしないので、不変条件 5 は守られる。
- **detached を指定できるようにする:** 親の終了後に誰が結果と失敗を所有するか、保存期間をどの木に従わせるかを新たに決める必要がある。必要な例が出るまでは、独立した根として明示的に始める。
- **すべての子の開始と回復で祖先を読む:** 通常の実行すべてに DB 読み取りを足す。祖先の確認は、プロセス停止後の回復と終端処理に限れば足りる。
