# 0086. 埋め込みのランタイムは、いなくなったと確かめられたプロセスの仕事を、借用の期限を待たずに引き継ぐ

- 状態: 承認（2026-11-27）
- 日付: 2026-11-27

## 背景

埋め込みのランタイム（Go・TypeScript・Python の SDK）では、ステップとワークフローの駆動に借用（lease）を付ける（ADR 0051、ADR 0059 の決定 1（ワークフローを動かす側にも借用を付ける））。借用には持ち主（owner）と期限（until）があり、持ち主のプロセスが期限の前に更新し続ける。ほかのプロセスは、期限が切れた借用だけを引き継ぐ。

- 期限の長さは借用の長さで、既定は 30 秒である（Go の `Options.Lease`、TypeScript の `leaseMs`、Python の `lease_ms`）。
- 待ちモードのプロセスは、借用の長さに 1 回、期限切れの借用を探して引き継ぐ（掃除）。3 つの SDK とも、掃除の周期は借用の長さと同じである。
- 期限を待たずに引き継げるのは、同じ owner の名前で開き直した場合だけである。そのプロセスは、前の自分の借用を、開いたときに止まったものとして扱う。owner の既定はランダムなので、多くの構成では使えない。

そのため、プロセスが閉じずに止まると（クラッシュ、kill、サーバーレスの実行環境の破棄）、その仕事は、借用の期限と次の掃除までのあいだ、どのプロセスも進めない。既定では最大でおよそ 60 秒になる。借用を短くすれば待ちは短くなるが、更新の書き込みと掃除の読み取りが、その分だけ増える。

一方、プロセスが終わったことは、借用の期限を待たなくても確かめられる場合がある。

- PostgreSQL のセッション単位の勧告ロック（advisory lock）は、そのセッション（接続）が終わると外れる。ほかのセッションは、そのロックを取れるかどうかで、持ち主の接続が残っているかを確かめられる。
- 同じマシンのプロセスどうしなら、OS のファイルのロックは、持ち主のプロセスが終わると OS が外す。SQLite は、同じマシンのプロセスどうしで使う保存先である。

ただし、「接続が切れた」ことは「プロセスがいない」ことと同じではない。ネットワークが一時的に切れて、プロセスは生きたまま接続だけを失うことがある。そのときにほかのプロセスが引き継ぐと、同じワークフローを 2 つのプロセスが動かすことになる。

## 決定

### 決定項 1（プロセスは、終わると外れる印を持つ）

埋め込みのランタイムのプロセスは、保存先が対応していれば、自分の owner の「生きている印」を持つ。印は、プロセスが終わると、保存先か OS が外すものに限る。

- PostgreSQL では、owner ごとのセッション単位の勧告ロックを、そのための専用の接続で持つ。
- SQLite では、OS が、プロセスの終わりとともに外すロック（owner ごとのファイルのロックなど）を持つ。
- 印を持てない保存先（メモリなど）と、印に対応していない保存先は、これまでどおり借用の期限だけで引き継ぐ。

### 決定項 2（印が外れたと確かめられた持ち主の借用は、期限の前でも引き継ぐ）

掃除は、期限の切れていない借用のうち、ほかの owner のものについて、その owner の印が外れているかを確かめる。外れていると確かめられた owner の借用は、期限が切れたものと同じに引き継ぐ。

- 「外れている」とするのは、印を自分で取れたなど、確かな証拠があるときだけにする。確かめる操作がエラーになったときや、結果がはっきりしないときは、外れていないものとして扱い、借用の期限を待つ。
- 引き継ぎ方は、期限が切れた借用と同じにする。ADR 0085 の決定項 1（意図は、上限と受け入れをすべて通ったときに記録する）のとおり、意図のある実の作用のステップは要確認になり、意図のないステップは送り直す。

### 決定項 3（自分の印を失ったプロセスは、止まったプロセスとして振る舞う）

プロセスが自分の印を失ったとき（専用の接続が切れたなど）は、ほかのプロセスがすでに引き継いでいるかもしれない。そのため、そのプロセスは、止まったプロセスとして振る舞う。

- 新しいステップと駆動を始めない。借用の更新もやめる。
- 動いているステップと駆動は、閉じるときと同じに止める。
- 印を取り直せたら、新しい owner として仕事を始め直してよい。前の owner の借用は、ほかのプロセスと同じ規則で引き継ぐ。

これで、印が外れたと見なされたプロセスが、そのあとも同じ仕事を進め続けることはない。印を失ってから止まるまでのわずかな間に、ほかのプロセスが引き継いで同じワークフローを動かすことはありうる。その間の実の作用は、借用と意図の規則（不変条件 4・5）で守られ、二重には起きない。

### 決定項 4（確かめる頻度と費用）

印を確かめるのは、ほかの owner の生きている借用があるときだけにする。確かめる周期は、借用の長さとは別に決められるようにする。既定は、借用の長さより短くする。

- 費用は、プロセスごとの専用の接続（PostgreSQL）か、ロックのファイル（SQLite）と、ほかの owner ごとの確かめの操作である。実行の数には比例しない（ADR 0041 の決定項 1（原則））。
- ほかの owner の生きている借用がないときは、何もしない。

### この ADR で決定しないこと

- 印のロックの鍵の決め方、ロックのファイルの置き場所、確かめる周期の既定の値。各 SDK の実装と、その PR で決める。
- kairod。kairod は 1 つのデータディレクトリを 1 つのプロセスが持ち、ほかのプロセスとの引き継ぎがないので、対象にしない。
- MySQL・Oracle などのそのほかの保存先。埋め込みのランタイムの保存先になったときに、別に決める。
- 同じ owner の名前で開き直したときの扱い。これまでどおりとする。

## 結果

- 良い影響
  - プロセスが閉じずに止まっても、その印が外れたと確かめられれば、ほかのプロセスが借用の期限を待たずに仕事を引き継ぐ。PostgreSQL でプロセスが落ちた場合や、同じマシンの SQLite の場合に、引き継ぎまでの時間が、確かめる周期程度に縮む。
  - 借用を短くしなくてよいので、更新の書き込みは増えない。
- 悪い影響
  - PostgreSQL では、プロセスごとに接続が 1 本増える。
  - 掃除が、ほかの owner の印を確かめる分だけ、読み取りと操作が増える。
  - 印の接続が一時的に切れると、生きているプロセスでも止まったものとして扱われ、仕事がほかへ移る。移る途中の実の作用のステップは、要確認になることがある。
  - マシンごと止まった場合（電源断、ネットワークの断絶）は、PostgreSQL が接続の終わりに気づくまで印が外れない。そのあいだは、これまでどおり借用の期限を待つ。
- 中立な影響
  - 借用の形式、イベント、記録の形式は変わらない。
  - 印に対応しない保存先の振る舞いは変わらない。
- 新しく守る制約
  - 印が外れたとするのは、確かな証拠があるときだけにする。
  - 自分の印を失ったプロセスは、仕事を続けない。

## 検討した代替案

- **借用の既定を短くする:** 引き継ぎは速くなるが、すべてのプロセスで更新の書き込みと掃除が増える。止まったときにだけ払うべき費用を、常に払うことになる（ADR 0041）。採らなかった。
- **閉じるときに借用を手放すだけにする:** 閉じずに止まった場合には効かない。問題はその場合なので、採らなかった。
- **プロセスの生存を、保存先の表の心拍（定期的な書き込み）で表す:** 借用の更新と同じ費用がかかり、借用を短くするのと変わらない。採らなかった。
- **印が外れたら、すぐに要確認のステップも自動で再試行する:** 外で動いたかもしれないステップを再試行することになり、不変条件 5 を破る。採らなかった。

## 関連する ADR

- ADR 0041 の決定項 1（原則）: 印を確かめる費用を、ほかの owner の借用があるときだけに限る根拠。
- ADR 0051（kairo は常駐するサーバーを前提にしない）: 埋め込みのランタイムと、保存先での借用。
- ADR 0059 の決定項 1（ワークフローを動かす側にも借用を付ける）: 駆動の借用と、掃除による引き継ぎ。引き継ぐ条件に「印が外れた」を足す。
- ADR 0085 の決定項 1（意図は、上限と受け入れをすべて通ったときに記録する）: 引き継いだステップのうち、要確認にするものと送り直すものの分け方。
