# 0074. 耐久開始の受け付けを保存先の処理能力に合わせ、開始前に過負荷を返す

- 状態: 承認（2026-11-09）
- 日付: 2026-11-09

## 背景

耐久性のある run の開始は、開始記録と最初のイベントが保存先へ書かれた後に成功する。開始を shard へ渡した後で呼び出しの期限が切れると、実行が残ったか判断できないため、API は開始未確認を返す。SDK は同じ RunID で確認し直せるが、これは曖昧な結果を業務上の失敗にしないための回復であり、過負荷そのものを減らさない。

同じ環境で run の総数をそろえ、同時数だけを段階的に変えた試験では、全体 108 in-flight までの各ラウンドは完了し、120 in-flight は成功する回と開始確認が 30 秒を越える回に分かれた。この境界には保存先、マシン負荷、shard の inbox、workflow claim、worker の処理が重なるため、単発の成功値を製品の固定上限にはできない。

既存の admission は、開始した run を終了まで active と数え、上限に達するとテナント間ラウンドロビンで待たせる。上限の既定は無制限である。この数は、長く待つ workflow と短い workflow を同じように保持する一方、開始記録が耐久化するまで保存先に掛かっている圧力を直接表さない。待ち行列の既定も大きいため、保存先が詰まったときの主な流量制御が、開始後の 30 秒の期限になり得る。

耐久ログは shard と durability tier ごとに group commit される。したがって、開始確認を待つ数と、その確認に要した保存処理の往復を同じ単位で観測できる。受付前の待ちなら、期限切れや拒否が起きても run はまだ作られておらず、実の作用も始まっていない。

## 決定

### 決定項 1（耐久開始だけを数える admission window を置く）

耐久性のある新しい run は、shard と durability tier ごとの start admission window を通してから shard の状態とログを作る。1 run は、window を通ってから開始の耐久 ack または確定した開始エラーが返るまで 1 枠を占める。耐久ログを持たず即時に開始できる run と、すでに耐久開始を確認済みの run の処理は、この枠で制限しない。

window が埋まっている開始は、run を作る前の待ち行列に置く。行列はテナント間をラウンドロビンで進め、同じ条件の別テナントが待つ間に一つのテナントだけを続けて通さない。既存の run 全体の admission、宛先ごとの RPM・TPM、worker credit は別の制約として残し、互いの数を代用しない。

### 決定項 2（window は保存先の実測に適応させる）

window の大きさを、特定のマシンで成功した同時数から固定しない。各 shard・durability tier は 1 枠から始め、耐久 ack の一つの group-commit round ごとに、待ち行列の増減と開始確認の往復を観測して調整する。

- 開始確認の直近の往復が、その保存先で成功した長期の往復の 2 倍以内なら、window を加算的に広げる。直近と長期の値は、急な変化と通常の揺れを分けるため、異なる重みの移動平均にする。
- 直近の往復が長期の 2 倍を越えたとき、または保存処理が一時失敗したときは、window を半分に狭める。ただし 1 枠は残し、一つの観測済み往復の間に複数回は狭めない。
- 一つの group-commit で複数の開始が確認されても、調整はその round に対して一度だけ行う。group commit の batch を細かく分ける誘因を作らないためである。
- 運用者は保存先やプロセスの資源から安全のための上限を設定できる。その上限を、通常時に必ず使う固定同時数にはしない。

時間は window を調整する観測値であって、正しさの合否条件にはしない。正しさとして守る性質は、開始確認中の数がその時点の window を越えないこと、同じ観測列から同じ window が得られること、テナント間の順序、受付前に拒否された run が存在しないことである。

### 決定項 3（待ち行列を処理 round 数で有界にする）

start admission の待ち行列は、その時点の window の 4 倍までとする。window が縮んで既存の待ちがこの範囲を越えた場合は、待っている開始を取り消さず、新しい開始を範囲内へ戻るまで加えない。これにより、待ちを特定マシンの秒数ではなく、保存先が処理する有界な round 数で表す。

待ち行列が満杯なら、API は run を作らず HTTP 429 と `Retry-After` を返す。受付前に呼び出しの期限が切れた場合は、既存どおり「受け付けていない」応答を返す。どちらも同じ RunID で安全に再試行できる。開始後に耐久 ack を確認できない場合だけを、引き続き開始未確認として区別する。

SDK は 429 を「開始されていないことが確定した過負荷」として扱い、`Retry-After` を下限にした上限付き backoff の後、同じ RunID で再試行する。開始未確認の再確認にも RunID から決まる bounded jitter を加え、同時に失敗した process が同じ時刻に再送しないようにする。いずれも呼び出し元の取消と Drain で止まり、親 workflow の成功も失敗も記録しない。worker に渡した実の action は、この再試行の対象にしない。

### 決定項 4（遅延の寄与を境界ごとに観測する）

開始 admission の判断と qualification では、次の区間を混ぜずに記録する。

1. API 到着から start admission までの待ち
2. admission から shard が開始を扱うまでの inbox 待ち
3. 開始記録の flush から耐久 ack までの WAL / group-commit 待ち
4. workflow claim request から claim 応答までの待ち
5. task の dispatch から worker が受け取るまでの待ちと、worker の実行

start admission は、shard・durability tier ごとの現在の window、開始確認中、待ち、拒否の累計を `Stats` から読めるようにする。区間の時間はライブの観測であり、core の状態、WAL、snapshot、リプレイ結果には入れない。時間の値で CI の合否を決めず、同じ環境の負荷曲線で raw measurement を比較する。

### この ADR で決定しないこと

- window の係数や平常範囲を計算する内部表現、公開設定の名前、観測値の wire 上のフィールド名は実装仕様へ委ねる。
- start admission 以外を含む metrics endpoint、histogram の bucket、外部監視製品との接続は、運用 metrics の Issue に委ねる。
- 最大処理量と推奨設定は、反復する負荷・障害注入・低負荷比較の qualification に委ねる。この ADR は一台の結果からその値を決めない。
- 非同期 URL action の callback 所有と、先取り Signal の保存・receipt は、それぞれ別の提案 ADR の範囲とする。

## 結果

- 良い影響: 保存先が処理できる範囲を越えた開始は run 作成前に待つか、再試行可能な過負荷として返る。30 秒の開始未確認を通常の流量制御として使わなくてよくなる。
- 良い影響: active run の寿命や一台の同時実行成功数ではなく、実際に詰まる耐久開始の往復に追従する。待つ workflow が多くても、それだけで新しい開始を絞らない。
- 良い影響: 受付前の拒否と受付後の未確認を区別し、どちらも親 workflow の永久的な失敗や実の action の再実行へ変えない。
- 悪い影響: 起動直後は window が小さいため、保存先の処理能力を学ぶまで burst の一部が待つ。保存先の特性が急変すると、調整が追いつくまで 429 または開始未確認が起こり得る。
- 悪い影響: shard・durability tier ごとの admission 状態と観測が増え、開始ホットパスに一定の計数コストが加わる。
- 中立な影響: 429 は成功でも開始未確認でもなく、run が存在しないと確定した応答である。利用者は `Retry-After` と同じ RunID を使って再試行する。
- 新しく守る制約: start admission を通っていない run の状態や耐久記録を作らない。開始確認中の数は window を越えない。待ち行列はテナント公平かつ有界にする。window の調整を wall-clock のテスト閾値にはしない。

## 実装

2026-11-09に `sched.StartAdmission` として実装した。window は shard・耐久性 tier ごとに1から始まり、成功したgroup-commit roundで加算、往復の移動平均がbaselineの2倍を越えたときか書き込み失敗時に半減する。一つのLSNで複数の開始が確定しても調整は一度だけである。待ち行列はwindowの4倍で、テナント間ラウンドロビンにする。`-max-starting` は適応を止める固定値ではなく安全上限である。

開始前のキューが満杯ならAPIは `429` と `Retry-After` を返し、runを作らない。Go・Python・TypeScript SDKは、429と開始未確認を区別したまま、同じRunIDをstableな75〜125% jitter付きbackoffで再送する。429では `Retry-After` を待ちの下限にする。取消とDrainはどちらの再送も止める。

`GET /v1/stats` の `Starts` は、各laneのwindow、開始確認中、待ち、拒否累計と、start queue・shard inbox・WAL/group-commitの移動平均を返す。これらはライブの計測だけで、core・WAL・snapshotには含めない。

## 検討した代替案

- active run の固定上限を 108 または 120 付近に置く: 一台の一部のラウンドから得た値で、保存先、shard 数、待ちの長さが変わると意味が変わる。開始確認以外の長時間待機まで同じ枠に保持する。
- HTTP の同時接続数だけを制限する: 一つの workflow drive が子 run を順に開始する経路や、別の API client を同じ保存先の能力として公平に扱えない。接続が切れても、開始確認待ちの run は残り得る。
- 30 秒の timeout を短くして早く 504 を返す: 受付済みか不明な応答を増やすだけで、保存先へ渡す量を減らさない。
- 待ちを無制限にして 429 を返さない: メモリと接続を有界にできず、過負荷時の応答が呼び出し元の期限だけで決まる。
- window を固定設定だけにする: 運用者が安全上限を置く用途には使えるが、保存先や負荷の変化へ追従せず、製品の既定値を一台の計測から決める問題が残る。
- worker の同時実行数を下げる: action の下流を保護する制約であり、action より前にある run の開始記録と group commit の詰まりを直接制御しない。

## 関連する ADR

- ADR 0005 の決定（shard・tier ごとの group commit）: start admission が処理能力を観測する保存境界。
- ADR 0012 の決定（テナント間ラウンドロビンの admission）: start admission でも同じ公平性を守り、既存の run 全体の上限は置き換えない。
- ADR 0023 の決定（耐久化した開始と冪等な RunID）: 受付前の過負荷と、受付後の開始未確認を区別する根拠。
- ADR 0039 の決定項 3（下流の容量: 背圧をかける）: 保存先の容量を新しい run の受付へ伝える既存方針。
- ADR 0056 の決定項「何をどこで確かめるか」: 時間は計測し、数えられる window と公平性をテストする。
- ADR 0063 の決定（一時的な保存先エラーで workflow を失敗にしない）: 過負荷で親 workflow の結果を記録せず、後の駆動へ譲る意味をそろえる。
- ADR 0072 の決定項 1（開始の未確認を、業務上の失敗と分ける）: 429 を開始未確認には含めず、開始前と確定した別の再試行可能状態として扱う。
- ADR 0072 の決定項 3（実のアクションの結果不明とは混ぜない）: start admission の再試行を実の action へ広げない。
