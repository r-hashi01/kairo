# 0085. 実の作用のステップの意図は、上限や受け入れを通って実行器へ渡す直前に記録する

- 状態: 提案
- 日付: 2026-11-26

## 背景

実の作用のステップは、外へ作用する前に「意図」を記録し、その記録の耐久化を待ってから実行器へ渡す（不変条件 4）。結果が分からない実の作用は成功扱いせず、再実行もせず、要確認（blocked）で止める（不変条件 5）。回復のとき、コアは送り出したまま結果のないステップを次のとおり分ける（`core/apply.go` の `recover`）。

- 意図が記録されている実のステップは、外で動いたかもしれないので、結果が分からないものとして要確認にする。
- 意図のない実のステップは、外へ出ていないことが確かなので、もう一度送り出す。

いま、意図を記録する時点は、ステップを送り出した時点である。

- 埋め込みのランタイム（Go・TypeScript・Python の SDK）は、コアが送り出しの命令を出したトランザクションの中で、意図も一緒に記録する。そのあと、プロセスの同時実行の上限、アクションの同時数と開始の速さ、宛先の上限の枠が空くのを待ち、空いてから実行器を呼ぶ。枠を待つあいだも、ステップの借用は取ったまま更新する（ADR 0059 の決定項 3（埋め込みのランタイムに、同時実行と速さの上限を足す））。
- kairod は、シャードが意図を記録し、ログがその位置まで耐久化してから、ステップをディスパッチャへ渡す。ディスパッチャは、テナントの順番、1 分あたりの要求数とトークン数、ワーカーのクレジットに従って、ステップを待たせてからワーカーへ渡す。

そのため、上限や受け入れで待っているだけで、まだ外へ何もしていない実のステップも、意図は耐久化済みになっている。プロセスが落ちると、回復の処理はそれらを「結果が分からない」ものとして要確認にする。デモでは、埋め込みのランタイムの同時実行の上限を小さくしてプロセスを 1 回止めると、18〜20 件のステップが要確認で止まった。実際に動いていたのは、多くても 2 件だった。

二重の作用は起きていないので、不変条件は守られている。しかし、上限で絞るほど、止まるたびに人が 1 件ずつ決着させるステップが増える。上限は、外の相手を守るために絞るものなので、この増え方は上限の使い方とぶつかる。

## 決定

実の作用のステップについて、埋め込みのランタイム（3 つの SDK）と kairod の両方で、次のとおりにする。

### 決定項 1（意図は、上限と受け入れをすべて通ったときに記録する）

実の作用のステップの意図は、そのステップが、そのプロセス（または kairod）にあるすべての上限と受け入れを通り、実行器へ渡せるようになった時点で記録する。上限と受け入れには、同時実行の上限、アクションや宛先の同時数・開始の速さ・重みの上限、kairod のテナントの順番・要求数とトークン数の上限・ワーカーのクレジットを含む。

- 実行器へ渡すのは、これまでどおり、その意図の記録が耐久化してからにする（不変条件 4）。
- 上限や受け入れで待っているステップには、意図がない。プロセスが落ちても、回復の処理はそれを外へ出ていないステップとして、もう一度送り出す。
- 意図を記録してから実行器へ渡すまでのあいだ、そのステップが通った枠は取ったままにする。耐久化を待つあいだに枠を別のステップに渡すと、上限を超えて実行器を呼ぶことになるからである。

### 決定項 2（待たずに通れるステップには、書き込みを増やさない）

埋め込みのランタイムでは、送り出しの時点で上限と受け入れをすぐに通れるステップは、これまでどおり、送り出しと同じトランザクションで意図を記録する。待つことになったステップだけ、通った時点で意図を記録する書き込みが 1 回増える。費用は、上限で待ったときにだけ払う（ADR 0041 の決定項 1（原則））。

kairod では、受け入れをディスパッチャの goroutine が持つので、シャードは送り出しの時点で通れるかを知らない。そのため、実の作用のステップは、ディスパッチャが受け入れてからシャードに意図を記録させ、耐久化を待ってからワーカーへ渡す。耐久化を待つ回数はこれまでと同じ 1 回で、受け入れとシャードのあいだのやりとりが 1 回増える。この費用は、変更の前後で `scripts/bench.sh` を測って確かめる（AGENTS.md のホットパスの手順）。

### 決定項 3（待っているステップの借用は、これまでどおり持つ）

埋め込みのランタイムで枠を待つステップは、これまでどおり借用を取ったまま更新する（ADR 0059 の決定項 3）。ほかのプロセスが同じステップを取らないようにするためである。プロセスが落ちて借用の期限が切れたら、ほかのプロセス（または次の `tick`）が回復し、意図のないステップとしてもう一度送り出す。

### この ADR で決定しないこと

- 回復で送り出し直したステップが、試行の回数を 1 つ使うこと。いまの回復はそうしており、非保護のステップも同じである。変えるなら別の ADR で決める。
- 実行器へ渡したあとのステップ（意図が記録された後）の扱い。これまでどおり、結果が分からなければ要確認にする（不変条件 5）。
- 非保護のステップ。意図を記録しないので、この ADR の対象にならない。
- 枠の取り方、トランザクションの分け方、ディスパッチャとシャードのやりとりの形。各 SDK と kairod の実装と、その PR で決める。

## 結果

- 良い影響
  - プロセスが落ちても、要確認で止まるのは、実際に実行器へ渡したステップだけになる。上限で待っていたステップは、自動でもう一度送り出される。
  - 上限で絞っても、止まったときに人が決着させる量が増えない。
- 悪い影響
  - 埋め込みのランタイムでは、上限で待ったステップごとに、意図を記録する書き込みが 1 回増える。
  - kairod では、実の作用のステップごとに、ディスパッチャとシャードのあいだのやりとりが 1 回増える。また、ディスパッチャが受け入れてから意図が耐久化するまで、そのステップがワーカーのクレジットを取ったままになる。実の作用のステップが多いときの受け渡しの遅延と、スループットへの影響を、bench で確かめる。
- 中立な影響
  - コア、ログ、スナップショット、保存先の形式は変わらない。コアは、意図のない実のステップをもう一度送り出す回復を、すでに持っている。
  - 上限で待たないステップの振る舞いと費用は、埋め込みのランタイムでは変わらない。
- 新しく守る制約
  - 実の作用のステップの意図は、上限と受け入れをすべて通るまで記録しない。
  - 意図を記録してから実行器へ渡すまで、通った枠を手放さない。

## 検討した代替案

- **待っているステップの借用を外し、枠が空いたときに送り出す:** 待つあいだに借用がないので、ほかのプロセスがすぐ拾える。しかし、送り出しの命令をプロセスの外に持てないので、待っているステップを保存先のどこかに置き直す仕組みが要る。意図の時点を変えれば済むので、採らなかった。
- **意図とは別に「実行器へ渡した」印を記録する:** 回復は、その印で要確認かどうかを分けられる。しかし、実の作用のステップごとに耐久化を待つ書き込みが 1 回増える。採らなかった。
- **埋め込みのランタイムだけを直し、kairod は今のままにする:** kairod でも、ディスパッチャで待つステップは同じ理由で要確認になる。同じ性質を 2 つの形で違えたくないので、採らなかった。
- **回復のときに、要確認のステップを自動で再試行する:** 外で動いたかもしれないステップも再試行することになり、不変条件 5 を破る。採らなかった。

## 関連する ADR

- ADR 0004（状態は先に適用し、外に出る作用だけをログの耐久化まで保留する）: 意図の耐久化を待ってから実の命令を出す決定。この ADR は、その意図を記録する時点を、上限と受け入れの後に決める。
- ADR 0041 の決定項 1（原則）: 待ったときにだけ費用を払う根拠。
- ADR 0051（kairo は常駐するサーバーを前提にしない）: 埋め込みのランタイムで、意図を送り出しと同じトランザクションで記録する、という実装の詳細を、待つステップについて変える。
- ADR 0059 の決定項 3（埋め込みのランタイムに、同時実行と速さの上限を足す）: 枠を待つステップの借用の扱いは変えない。待っているステップに意図を持たせないところを足す。
