# 0056. 時間の予算は、テストでも CI でも判定しない: 決まったマシンで測り、変更の前後で比べる

- 状態: 承認
- 日付: 2026-10-08
- 関連: 非機能要件（`docs/runtime.ja.md`）、ADR 0041（実行 1 回あたりのコスト）

## 背景

時間の予算のうち、受け渡しの遅延（p99 ≤ 1ms）だけは、テスト `TestHandoffLatency` が合否を判定している。このテストは `scripts/check.sh` の「不変条件」の段と `go test ./...` に入っているので、CI の必須のジョブ（check）で判定される。さらに CI には、`scripts/bench.sh` で予算をすべて判定するジョブ（bench、`continue-on-error`）がある。

2026-10-08 に、Go のコードを変えていない push で、check と bench が落ちた。GitHub のランナーで計 6 件を診断した（ブランチ `diag/handoff-latency`）。

- ランナーは、どれも 4 vCPU（物理 2 コア × ハイパースレッド 2）である。CPU は AMD EPYC 7763・9V74・9V45 が混ざる。
- 受け渡しの p99 は 0.52〜2.73ms だった。CPU だけの処理（遷移のコスト）も 1.9〜3.3µs とばらつき、遅い CPU（7763）ほど p99 も悪い。同じ CPU（9V74）でも 0.52ms と 1.59ms の差があった。手元の M4 Max（14 コア）では 0.35ms である。
- 遅延の分布はなだらかで、決まった待ち（1ms の山）はない。原因は、テストの負荷（実行 2,000 件 × 1 実行約 70µs）が、物理 2 コアの約半分を埋めることによる待ちである。
- 耐久化の ack の p99 も、1.5ms・2.2ms・41.6ms とディスクによってばらついた。

ここから、次のことが言える。

1. **時間の予算は、正しさではない。** AGENTS.md は不変条件を「破ると壊れるのは性能ではなく正しさ」と定めている。受け渡しが 1.2ms になっても、結果は何も壊れない。
2. **時間の絶対値の判定は、劣化の検出として役に立たない。** 同じコードの p99 が、ランナーによって 5 倍動く。劣化がなくても落ち、劣化があっても速いランナーなら通る。
3. **劣化を見つけるのは、同じマシンでの前後の比較である。** AGENTS.md はすでに、ホットパスを変えたら `scripts/bench.sh` の前後の値を報告することを求めている（Go 1.27 への更新は、この方法で確かめた）。

## 決定

テストと CI が判定するのは、結果が決まるものだけにする。時間の予算は測るだけにして、判定は人が、決まったマシンでの前後の比較で行う。

### 何をどこで確かめるか

| 種類 | 例 | 確かめ方 |
|---|---|---|
| 正しさの不変条件 | 純粋性、リプレイ、意図の耐久化、追記のみ | テスト。`check.sh` と CI で判定する（今のまま） |
| 数えられる構造の性質 | 実行ごとに goroutine を持たない、待機中に起きない、待機中の 1 実行のメモリ | テスト。`check.sh` と CI で判定する（今のまま）。値はマシンの速さに左右されない |
| 時間の予算 | 遷移のコスト、1 実行の CPU、受け渡しの遅延、耐久化の ack | `scripts/bench.sh` で測る。判定しない |

### 変えるもの

- **`TestHandoffLatency`:** 合否の判定をやめ、計測だけにする。
  - 環境変数 `KAIRO_MEASURE=1` のときだけ動き、それ以外は飛ばす（`go test ./...` と `check.sh` では動かない）。
  - `check.sh` の「不変条件」の段から外す。
- **`scripts/bench.sh`:** 値を測って、予算と並べて表示する。
  - 予算を超えた行には `over` と印を付けるが、終了コードは 0 にする。測れなかった（テストが失敗した）ときだけ 1 にする。
  - 出力の先頭に、マシン（CPU の型、コア数）と Go の版を出す。比べるときに、同じマシンかどうかが分かるようにするためである。
- **CI:** bench のジョブを消す。
- **予算そのもの:** 変えない。要件として `docs/runtime.ja.md` に残す。満たしているかどうかは、決まったマシン（今は開発者の手元）で測って確かめる。
- **文書:** AGENTS.md（作業の進め方、落とし穴、ハーネスの節）、`/verify` と `/bench` のスキル、`docs/runtime.ja.md` を、この決定に合わせる。
  - 「テストの閾値を緩めて通してはいけない」は残す。テストの閾値は、正しさと構造の性質のものだけになる。
  - 「ホットパスを変えたら前後の値を報告する」は残す。予算の確かめ方は、これになる。

## 結果

- CI の結果が、ランナーの当たり外れで変わらなくなる。
- **悪くなること:** 時間の劣化を、CI が自動では見つけない。ホットパスの変更で前後を比べる決まり（AGENTS.md）と、`/bench` のスキルに頼る。
- **新しく守ること:**
  - 時間で合否を決めるテストを足さない。足したくなったら、数えられる性質（起きた回数、確保の回数、goroutine の数）で表せないかを先に考える。
  - 予算を満たしているかの報告には、測ったマシンを書く。
- **テスト:** `TestHandoffLatency` は計測になる。`check.sh` から外れたことは、`check.sh` の出力（不変条件の段の一覧）で分かる。

## 検討した代替案

- **CI では判定し、落ちたら流し直す:** 遅い CPU に当たると、何度流しても落ちる（7763 では 3 回とも 1ms を超えた）。流し直しは、本当の劣化も隠す。
- **CI で、同じランナーの上で前後を比べる（ベースラインとの比較）:** 同じ CPU の型でも 3 倍ばらつくので、2 回の計測の差が劣化なのか揺れなのか区別できない。
- **専用のランナー（自前のマシン）で判定する:** 確実だが、マシンの用意と保守が要る。必要になったら、この ADR の上で足せる（`bench.sh` は判定しないので、判定はそのランナーの側に置く）。
- **予算を CI のランナーに合わせて緩める:** 予算は要件で、CI のランナーの都合で変えるものではない。

## 実装で詰めた詳細（2026-10-08 追記、ADR 0017）

- **`TestHandoffLatency`:** `KAIRO_MEASURE` がないと飛ばす（理由をメッセージに出す）。合否の判定を消し、代わりに遅延の分布（0.25ms 刻みで 2ms まで）と `GOMAXPROCS` をログに出す。診断で使った出力を、そのまま残したものである。
  - 判定がなくなったので、`-race` のときに判定を外す分岐（`raceEnabled`）も、このテストでは使わなくなった。
- **`scripts/bench.sh`:**
  - 予算を超えた行の印は `over`（小文字）にした。測れなかった行は `FAIL` にし、そのときだけ終了コードを 1 にする。
  - 先頭の `== machine` の行に、CPU の型、CPU の数、Go の版、負荷を出す。
- **`scripts/check.sh`:** 「不変条件」の段の一覧から `TestHandoffLatency` を外した。
- **CI:** bench のジョブを消した。残るジョブは check、backends、vulncheck である。
- **文書:** AGENTS.md（作業の進め方、落とし穴、ハーネス）、`/verify` と `/bench` のスキル、`docs/runtime.ja.md`、README（性能の節と開発の節）を合わせた。
- **診断のブランチ `diag/handoff-latency`:** 診断を終えたので消した。CI でランナーの情報を出す段は、本線には入れていない（bench のジョブがなくなり、check には要らないため）。
