# 0088. コードで書くワークフローの経過は、記録されたイベントだけから読み取り専用で公開し、手元のビューアで見せる

- 状態: 承認（2026-11-27）
- 日付: 2026-11-27

## 背景

コードで書くワークフローは、アクションの呼び出し、signal の待ち、sleep、子ワークフローを、それぞれ根の実行の子として保存する。埋め込みランタイムの保存先は、実行ごとの行（計画、状態、入力、出力、作成時刻、最後の更新時刻、親）に加えて、各実行に適用したコアのイベントを、追記だけの列として保持する。この表は Go・TypeScript・Python の SDK で同じ形で、SQLite と PostgreSQL でも同じである。

イベントの種類は、開始、ステップの成功、ステップの失敗、timer の発火、signal、意図、回復、決着、取り消し、ステップの待機である。どのイベントも、適用した時刻を持つ。ステップの成功と失敗は試行の番号を持ち、失敗はさらに、再試行できるか、結果が不明か、失敗の種類、メッセージを持つ。実行していたプロセスが止まって借用を引き継いだ場合は、その試行を「プロセスが止まった」という種類の失敗として記録する。

一方、SDK が公開している読み取りは次のものに限られる。

- 子の一覧は、子ごとの計画の名前、状態、入力、結果、作成時刻、最後の更新時刻を返す。試行の回数、失敗した試行、プロセスが止まって中断した試行は分からない。
- 記録だけのリプレイ（ADR 0080）は、関数が到達した呼び出しと、その記録された状態と結果を返す。試行の経過と時刻は返さない。
- 運用指標と observe（ADR 0076）は耐久化しないため、後から、あるいは別のプロセスから読めない。
- 保存先の契約と公開の API には、イベントを読む操作がない。表とイベントの符号化は公開の契約ではない。

試行を始めた時刻は、一般にはイベントとして記録されない。例外は実の作用のステップで、上限と受け入れを通った時点で意図を記録する（ADR 0085）。それ以外のステップでは、残るのは結果を適用した時刻だけである。また、イベントの時刻は、それを適用したプロセスの時計で付けられる。

実例として、Zenn の記事の公開前チェックを行うワークフローで、レビュー 2 本の実行中にプロセスを強制終了し、同じ所有者で再起動した実行を確かめた（2026-11-27）。保存先には、レビューの子それぞれについて、開始、1 回目の試行の「プロセスが止まった」失敗、timer、2 回目の試行の成功が、この順で残っていた。子の一覧では、どちらのレビューも、最初の開始から再開後の完了までの 1 つの区間にしか見えない。

コードで書くワークフローを使う理由の一つは、何をどの順に行い、いまどこまで進んだかを、文章でなく実行の記録で確かめられることである。いまは、それを利用者が表の形式に依存して読むか、ワークフローごとに進み具合の表示を自作するしかない。表の形式に依存しない読み取りの経路と、どのワークフローでも同じように経過を見られる場所が要る。経過を見る場所から承認の signal、要確認の呼び出しの決着、取り消しを行えれば、待っているワークフローを同じ画面で進められる。

## 決定

### 決定項 1（経過を、記録されたイベントだけから読む読み取り専用の経路を 3 つの SDK に設ける）

Go・TypeScript・Python のコードワークフロー SDK に、根の実行の ID を受け取り、その木と、木に含まれる各実行の経過を返す読み取り専用の経路を設ける。

- 木は、根と、親の記録でたどれる子孫の実行からなる。各実行について、子の一覧と同じ情報（種類、名前、状態、入力、結果、作成時刻、最後の更新時刻、親）を返す。
- 経過は、その実行に記録されたイベントを、記録された順に、SDK の公開の型へ写したものとする。写すのは、種類、適用した時刻、試行の番号、失敗の種類・メッセージ・再試行できるか・結果が不明か、signal の名前、決着の内容など、記録にある事実だけとする。
- 公開の型は、表とイベントの符号化から独立させる。コアの内部の番号や、保存先の列の名前を公開の型に出さない。表やイベントの符号化を変えても、公開の型を保てるようにする。
- 記録にないことは推定で補わない。とくに、意図を記録しないステップの試行を始めた時刻、時計の違うプロセスどうしの時刻の補正は返さない。
- 1 回の読み取りは、保存先の 1 つの読み取りのトランザクションで行う。同じ読み取りの中で、実行の状態と経過、親と子が食い違わないようにする。

この経路は状態を一切変えない。駆動の借用を取らず、実行を開始・回復・完了・失敗・取り消しにせず、signal、決着、timer、借用、子の作成を行わない。保存先への操作は、対象の木の行とイベントの読み取りに限る。

保存先の契約には、実行のイベントを読む操作を足す。表とイベントの形式は変えない。この操作を持たない保存先では、経路は「対応していない」として返し、ほかの読み取りで代わりに組み立てない。

### 決定項 2（ビューアは TypeScript の SDK に同梱し、公開の経路だけを使う）

ブラウザで経過を見るビューアを、TypeScript の SDK に同梱する。SDK に外部の依存を足さない。保存先を指定してコマンドとして起動する方法と、利用者のプロセスの中で、すでに開いているランタイムから起動する方法の両方を設ける。PostgreSQL の保存先は、SDK と同じく、利用者が用意したドライバで開く。

ビューアは、保存先の表を直接読まない。読み取りは決定項 1 の経路と、既存の実行の一覧だけを使う。

ビューアは、呼び出しを時刻の上に並べ、並列の呼び出しは並べて示す。実行の状態と、試行ごとの結果を区別して示し、プロセスが止まって中断した試行には印を付ける。記録された時刻の間を区間として描くなど、記録をもとに描いた部分は、記録そのものと見分けられるように示す。入力と結果を読めるようにする。

表示の更新は、ビューアがブラウザとつながっている間だけ、ビューアのプロセスが決定項 1 の経路で読み直して行う。読み直しは、保存先の既存の決着の通知を起こすきっかけとして使えるときは使い、通知はヒントとして扱う。決着しない変化（失敗した試行など）も表示に出すため、つながっている間は一定の間隔でも読み直す。ワークフローを動かすプロセスには、ビューアのための書き込み、通知、常駐の処理を足さない。

### 決定項 3（ビューアからの操作は SDK の公開の操作と同じ意味にし、ビューアは実行を動かさない）

ビューアから、待ちへの signal の送信、要確認の呼び出しの決着（成功・失敗）、ワークフローの取り消しを行えるようにする。どれも、SDK の公開の操作をそのまま呼び、同じ意味、同じ記録、同じ失敗の扱いにする。ビューアのために、状態を変える新しい経路を作らない。

ビューアのプロセスは、ワークフローを動かさない。駆動の借用を取らず、関数を評価せず、ステップを実行しない。操作の結果として進むワークフローは、それを動かしているプロセスが、既存の仕組みで拾って進める。ビューアは、操作が受け付けられたことを返し、その後の進み具合は表示の更新で示す。操作の完了を待つためにビューアの応答を止めない。

### 決定項 4（ビューアは手元の利用者だけに見せる）

入力と結果には、プロンプト、外部のサービスの応答、記事の本文など、利用者のデータが入る。操作は実行の状態を変える。そのため、ビューアの信頼の範囲を、対象の保存先を読み書きできる手元の利用者にそろえる。

- ループバックのアドレスだけで待ち受ける。ほかのアドレスで待ち受ける設定を設けない。外部に公開する用途は、この ADR の範囲に含めない。
- 起動ごとに推測できない鍵を作り、すべての要求にその鍵を求める。鍵は、起動した利用者に表示する URL だけで渡す。
- 想定しない Host や Origin の要求は拒否する。状態を変える操作は、読み取りと分けた要求でだけ受け付ける。
- 画面は、外部の資源（スクリプト、スタイル、フォント、画像）を読み込まない。
- 鍵の寿命はビューアのプロセスの寿命とし、保存しない。ビューアは資格情報を保存先に書かない。

ビューアからの操作は、SDK の操作と同じ記録を残す（決定項 3）。誰がビューアから操作したかを別に記録する仕組みは足さない。

### 決定項 5（適用範囲と費用）

この ADR は、埋め込みランタイムのコードで書くワークフローに、SQLite と PostgreSQL の保存先で適用する。kairod とグラフの実行は範囲に含めない。根の木が保存期間の後に消えた場合（ADR 0054）は、記録がないとして返す。

コアの状態、イベントと命令の種類、IR、ログ、ワーカープロトコル、保存先の表とイベントの形式は変えない。費用は、利用者が経過を読んだとき、またはビューアを開いている間に、その木を読む分だけ発生する。実行ごとの書き込み、常駐の処理、polling を足さない。

### この ADR で決定しないこと

- 3 つの SDK の関数名、公開の型と項目の名前、木と経過を戻り値・iterator のどちらで返すかは、SDK の公開 API 文書と実装に委ねる。
- ビューアのコマンドの名前と引数、画面の構成と見た目、読み直しの間隔、一度に読む量の上限は、TypeScript の SDK の文書と実装に委ねる。
- 試行を始めた時刻を、意図を記録しないステップについても耐久的に記録するかは、その必要が出たときの別の ADR に委ねる。記録を増やすことは、ログの形式と実行ごとの費用に触れる。
- ビューアの外部への公開、複数の利用者による共有、認証と認可、操作した人の監査記録は、その要求ができたときの別の ADR に委ねる。
- kairod とグラフの実行の経過の読み取りとビューアは、kairod の保持の契約を決める別の ADR に委ねる（ADR 0080 の決定項 4 と同じ扱い）。
- 経過を、記録だけのリプレイ（ADR 0080）の結果と同じ画面で重ねて示すかは、ビューアの実装に委ねる。

## 結果

- 良い影響: 表の形式に依存せずに、どのコードワークフローでも、試行の回数、失敗した試行、プロセスが止まって中断した試行、待っている呼び出しを確かめられる。
- 良い影響: 承認の signal、要確認の呼び出しの決着、取り消しを、経過を見ながら同じ画面で行える。
- 良い影響: 3 つの SDK が同じ保存先から同じ経過を返すため、どの言語で書いたワークフローも同じビューアで見られる。
- 良い影響: コア、ログ、表、実行ごとの費用を増やさない。
- 悪い影響: 意図を記録しないステップについては、試行を始めた時刻が分からない。ビューアの区間は記録された時刻から描いたもので、実際に試行していた時間と一致するとは限らない。
- 悪い影響: 時計の違うプロセスが適用したイベントの時刻は、そのまま並べると前後が食い違って見えることがある。
- 悪い影響: ビューアを開いている間は、ビューアのプロセスが保存先を一定の間隔で読み直す。木が大きいと、その読み取りの量も大きくなる。
- 悪い影響: ビューアは手元の利用者だけを想定する。チームで共有する画面としては使えない。
- 悪い影響: 保存先の契約に操作が 1 つ増える。利用者が自前で実装した保存先は、その操作を足すまで経過を読めない。
- 中立な影響: ビューアからの操作は SDK の操作と同じ記録になり、ビューアから行ったことは区別されない。
- 中立な影響: ビューアは TypeScript の SDK に含まれる。Go と Python だけを使う利用者も、同じ保存先を指定すれば、Node.js からビューアを起動して見られる。
- 新しく守る制約: 経過の読み取りは状態を変えず、記録にないことを推定で返さない。公開の型を表とイベントの符号化から独立させる。ビューアは公開の経路と操作だけを使い、ループバックだけで待ち受け、起動ごとの鍵のない要求を受け付けず、ワークフローを動かさない。

## 検討した代替案

- 子の一覧だけで描く: 作成時刻と最後の更新時刻しかなく、プロセスが止まって中断した試行や、試行の回数が見えない。
- ビューアが保存先の表を直接読む: 表とイベントの形式は公開の契約ではなく、変えるたびにビューアが壊れる。Go と Python の利用者が同じ経過を読む方法にもならない。
- 試行の開始をイベントとして新たに記録する: 試行の開始時刻が分かるが、すべてのステップに書き込みが 1 回増え、実行ごとの費用とログの形式に触れる。見るための要求で、実行の費用を増やすことになる。
- まず TypeScript の SDK にだけ読み取りの経路を足す: 早く作れるが、Go と Python の利用者がプログラムから経過を読めない。ADR 0080 と同じく、3 つの SDK で同じ読み取りをそろえる。
- ビューアを別の npm のパッケージ、または Go のコマンドにする: 別のパッケージはリリースするものが増える。Go のコマンドは SQLite のドライバのために別のモジュールが要る。TypeScript の SDK は、依存を足さずに SQLite を開け、PostgreSQL は利用者のドライバで開けるため、同梱する。
- ビューアを表示だけにする: 状態を変えないため安全の扱いは簡単になるが、承認や決着のたびに別の手段に切り替える必要がある。操作は SDK の操作をそのまま使い、待ち受けの範囲と鍵で守る。
- 実行のログを外部の観測基盤（トレース）へ送り、そこで見る: 外部のサービスと依存が要り、送らなかった過去の実行は見えない。保存先に既にある記録を読む方が、追加の費用がない。

## 関連する ADR

- ADR 0080 の決定項 1（記録だけのリプレイを通常の再開から分離する）: 状態を変えない読み取り専用の経路という原則を、経過の読み取りにも適用する。
- ADR 0080 の決定項 4（埋め込みランタイムが木を保持する期間に適用する）: 適用範囲（埋め込み、コードワークフロー）と、kairod を範囲外とする理由をそろえる。
- ADR 0076 の決定項 1（運用指標を非耐久な別の観測面にする）: 運用指標は耐久化しないため、後から経過を読む用途には、耐久化されたイベントを読む。
- ADR 0085 の決定項 1（意図は、上限と受け入れをすべて通ったときに記録する）: 実の作用のステップでは、意図の時刻が、試行を実行器へ渡した時刻として記録に残る。
- ADR 0079 の決定項 3（通知は起床のヒントとし、保存先を正典にする）: ビューアの表示の更新は、既存の通知をヒントとして使い、保存先を読み直して確定する。
- ADR 0079 の決定項 4（通知の信頼境界を SQLite ファイルとそろえる）: ビューアの信頼の範囲も、保存先を読み書きできる手元の利用者にそろえる。
- ADR 0054 の「消す条件」の節: 保存期間が過ぎて消えた木は、経過も読めない。
- ADR 0061 の決定項 3（`Cancel` は、記録された結果を確認して返す）: ビューアからの取り消しも同じ操作を使う。ビューアは、その完了を待って応答を止めない。
- ADR 0064 の決定項 1（埋め込みランタイムに、receipt を返す送信 API を足す）: ビューアからの signal も、同じ送信の操作を使う。
- ADR 0041 の決定項 1（原則）: 経過を見るための費用は、見るときだけ払い、実行ごとの費用を増やさない。
