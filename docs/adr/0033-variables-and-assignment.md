# 0033. 書き換えられる変数（loop 変数と会話変数）を持ち、代入は組み込みの保護ステップで行う

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR1, FR2 / 不変条件 1, 2 / ADR 0015, 0028, 0032

## 背景

kairo の値は、すべて「ノードの出力」で、一度書いたら変わらない。loop の中で自分の前の回の値を参照すれば、追記の累積は表せる（ADR 0015）。

Dify には、書き換えられる変数が 2 種類ある。

- **loop 変数:** loop ごとに、初期値（定数か変数）を持つ。本体の中の Variable Assigner が書き換え、次の回と loop の出力で読む。
- **会話変数**（chatflow）: 会話ごとに永続化し、ターンをまたいで持ち越す（テーブル `workflow_conversation_variables`）。Variable Assigner が書き換える。Dify は、書き換えのたびに DB に保存する。

Variable Assigner（v2）の操作は、over-write、clear、append、extend、set、`+=`、`-=`、`*=`、`/=`、remove-first、remove-last の 11 種類。

## 決定

### 変数の宣言

- loop の定義に `vars`（`{名前: {"type":..., "init": <定数か参照>}}`）を足す。
  - 値は loop の活性化に持ち、`<loop の ID>.<名前>` で参照する。本体の中からも、loop の後からも読める。
  - loop の後から読むと、最後の値になる。
- 計画の定義に `vars`（実行の変数）を足す。Dify の会話変数に使う。
  - 初期値は `SubmitRequest.Vars` で渡す（ホストが会話から読み込む）。省略したものは宣言の既定値になる。
  - `$var.<名前>` で参照する。
  - 実行が終わったら、最後の値を `RunInfo.Vars` で返す。書き換えのたびに、実行イベントの出口（ADR 0034）にも流す。
  - **保存はホスト（Dify）が行う。** kairo は会話をまたいで変数を持たない。

### 代入

- 組み込みの保護アクション `kairo.assign` を足す。
  - 書き換える変数（loop 変数か実行の変数）、操作（上の 11 種類）、値（参照か定数）を受け取る。
  - 1 つのノードで、複数の変数を順に書き換えられる。
  - 保護ステップなので、コアの中で評価し、出力はログに残らない（リプレイで再計算する）。
- 書き換えられるのは、そのノードを囲む loop の変数と、実行の変数だけ。宣言のない変数や型の合わない操作は、コンパイル時に拒否する（型の分かる範囲で）。
- 並列に動く 2 つの枝が同じ変数を書き換えたときは、代入ノードが**完了した順**（コアにイベントが適用された順）に適用する。
  - これはイベントの順序で決まるので、リプレイすれば同じ結果になる。
  - ただし、実行するたびに結果が変わりうる。graphon も、スレッドの完了順で同じことが起きる。
- map の要素の中から実行の変数を書き換えることは、v1 では拒否する。Dify は要素ごとに変数プールを複製するので、書き換えは外に伝わらない（確認が要る。差分ハーネスで決める）。

### 状態

- 変数の値は、状態に持つ。loop 変数は loop の活性化に、実行の変数は `State.Vars` に置く。`codecVersion` を上げる。
- 大きな値は、ほかの出力と同じく、ブロブの参照で持てる（ADR 0008）。

## 結果

- Dify の loop 変数、会話変数、Variable Assigner を表せる。
- 「値は書き換えない」という kairo の性質は、宣言された変数に限って破れる。参照は、読んだ時点の値になる。
- 悪くなること:
  - 状態の中の可変な部分が増え、並列の枝からの書き換えの順序が、イベントの順序に依存する（決定性は保つ）。
  - 会話変数の保存は、ホストの責任になる。
- テスト:
  - 11 種類の操作の表。
  - loop 変数の初期値、更新、最後の値。前判定で 0 回のときは初期値（ADR 0032）。
  - 実行の変数の初期値と最後の値。書き換えのイベント。
  - 並列の書き換えの順序を入れ替えても、リプレイで同じ状態のバイト列になる。
  - `checkReplay`。
  - ADR 0028 の差分ハーネスで、assigner と会話変数を含む fixture が一致する。

## 検討した代替案

- 変数を持たず、DSL の変換器が「前の回の自分を参照する保護ステップ」に書き換える: loop 変数は表せる。しかし、会話変数と、複数の代入ノードが同じ変数を書く形は表しにくく、変換が複雑になる。
- 会話変数を kairo が永続化する: 会話は Dify の概念で、kairo の外にある。kairo に持たせると、会話の削除や移行に追従する必要が出る。

## 実装で詰めた詳細（2026-10-05 追記、ADR 0017）

- **置き場所。** 状態の形式は変えていない。
  - 実行の変数: ルートのスコープの値に、予約した番号（-1）のオブジェクトとして置く。
  - loop 変数: loop のノード自身の値（オブジェクト）として置く。`<loop>.<変数>` は、ほかのノードの出力と同じ仕組みで読める。そのため、loop の中から loop 自身を参照することを、変数に限って許した。
- **定義の形。**
  - 宣言は `{"type": <Dify の型>, "value": <定数>}`。loop 変数は、`"ref"` で外の値から初期化することもできる。
  - 値がなければ、型のゼロ値（graphon の `get_zero_value`）になる。
- **初期値の受け渡し。** `SubmitRequest.Vars` は開始のイベントに入れる（イベントの拡張フィールドの版 2）。回復しても同じ初期値になる。
- **代入の意味論。** graphon 0.7.0 の Variable Assigner v2 に合わせた。
  - 操作と型の組み合わせの検査、入力の種類（変数か定数か）の検査、値の型の検査
  - `set` でオブジェクトの変数に文字列を渡すと、JSON として読む。
  - 入力の変数が null なら、その項目を飛ばす。
  - 項目は順に適用し、前の項目が書いた値を後の項目が読む。1 つでも失敗したら、何も書かない。
  - エラーの種類は、graphon の例外のクラス名（`VariableNotFoundError` など）にした。`on_error` を付ければ `error_type` に入る。
- **数値。** Python の算術（int どうしは int、`/=` は常に float）と、float の表記（`2.0`、`1e+16`）に合わせた。
- **テスト:**
  - `TestAssignOperations`、`TestAssignErrorType`、`TestRunVarsInit`、`TestPyFloatRepr`（core）
  - `TestRunVarsAcrossRestart`（engine）
  - 並列の枝からの書き換えの順序を入れ替える検査は、`TestMapElementErrorModes` と同じ方法で、実行イベントの出口（ADR 0034）のテストと一緒に足す。
- **レビューで直したこと（2026-10-05）:** 代入の結果が有限の数でない（オーバーフロー）ときは `InvalidInputValueError` にする。JSON にできず、変数のオブジェクトごと消えていた。テスト: `TestAssignOverflow`
- **map の中からの実行の変数の書き換え（2026-10-05、差分ハーネスで決めた）。**
  - 拒否するのをやめ、graphon と同じく、その要素の中だけに効くようにした。最初に書いたときに、要素のスコープに写しを作る（`localRunVars`）。
  - 要素の中の参照は写しを読み、外には伝わらない。
  - Dify のテスト用データ `update-conversation-variable-in-iteration` が、この挙動を前提にしている（最後の answer は空文字になる）。
  - テスト: `TestRunVarsWrittenInsideMap`
