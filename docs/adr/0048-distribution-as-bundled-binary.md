# 0048. kairo は、kairod のバイナリを同梱した言語ごとのパッケージとして配る

- 状態: 承認
- 日付: 2026-10-07
- 関連: ADR 0009（ワーカーのプロトコル）、0014（標準ライブラリだけで作る）、0018（依存のある実装は別モジュール）、0037〜0047（Dify・n8n との統合）

## 背景

kairo が目指すのは、Celery などのタスク・ワークフローのランタイムの代わりになることである。

- 想定する利用者は、Python・TypeScript・Go でアプリを書く開発者である。
- 開発者は、アプリから実行を投入し、自分のワーカーでステップを動かす。
- Dify（ADR 0037〜0041）と n8n（ADR 0042〜0047）との統合は、実際の負荷で性能を評価するために作った。これらを配る製品にはしない。

今は、kairo を使うには Go でビルドして kairod を起動し、言語ごとの部品（Python の `kairo-worker`、TypeScript の `@kairo/worker`）を別に入れる必要がある。部品はワーカーの側しかなく、アプリから実行を投入する側は、HTTP の API（`/v1/...`）を直接呼ぶしかない。

目指す形は、uv や ruff と同じである。中身はネイティブの 1 つのバイナリで、利用者は自分の言語のパッケージ管理（pip、npm）から入れるだけで使える。uv や ruff は、ライブラリとしてホストのプロセスに組み込まれているのではない。OS と CPU ごとのバイナリをパッケージに同梱し、薄い入り口から起動している。

呼び出し方として、次の 3 つを比べた。

- **gRPC で呼べるサービスにする:** 依存を足すことになる（ADR 0014 で外している）。今の HTTP の API とワーカーのプロトコル（長さ＋型＋JSON）は、どの言語からも数百行で話せる。gRPC で得られるのは、クライアントの自動生成くらいである。
- **Go のライブラリを、他の言語のプロセスに組み込む（共有ライブラリ）:** Go のランタイムがアプリのプロセスに同居する。kairo が落ちるとアプリごと落ち、同期の書き込みや長く動く処理を、アプリのスレッドやイベントループに抱える。
- **バイナリを同梱して、別のプロセスとして動かす:** uv、ruff、esbuild、biome と同じ形。

## 決定

kairod を OS と CPU ごとの静的なバイナリにし、言語ごとのパッケージに同梱して配る。パッケージには、kairod の起動の入り口、実行を投入するクライアント、ワーカーの部品を入れる。

- **配るもの:**
  - **Python（PyPI の `kairo`）:**
    - kairod のバイナリ（wheel の中）と、起動の入り口（`kairo` のコマンドと、プログラムから起動する関数）
    - クライアント（実行の投入、待ち、信号、取り消し）
    - ワーカーの部品（今の `kairo_worker`）
  - **TypeScript（npm の `kairo`）:**
    - kairod のバイナリ（OS と CPU ごとのパッケージ）と、起動の入り口
    - クライアント
    - ワーカーの部品（今の `@kairo/worker`）
  - **Go:** 今までどおり、`kairo/engine` をライブラリとして使うか、kairod を使う。
- **配らないもの:** `compat/dify` と `compat/n8n`（kairo-dify、kairo-n8n）。性能の評価に使う道具として、リポジトリに残す。Python の部品の graphon（Dify のノード）の対応も、評価用の追加（`extras`）のままにする。
- **使い方の 2 つの形:**
  - **開発の手元:** 言語のパッケージの入り口が、kairod を子プロセスとして起動する（データディレクトリは手元）。ワーカーは同じ手元のプロセスで動かせる。Celery でいえば、ブローカーを別に用意しなくてよい。
  - **本番:** kairod をサービスとして動かす（コンテナ、systemd など）。アプリとワーカーは、URL と合言葉でつなぐ。同じバイナリを使う。
- **クライアントの中身:** 今の HTTP の API（`/v1/plans`、`/v1/runs`、`/wait`、`/signals`、`/cancel` など）を包むだけにする。
  - Celery のような書き方（デコレーターでタスクを宣言するなど）をどう用意するかは、ここでは決めない。別の ADR で決める。
  - この ADR は「どう配るか」だけを決める。
- **ビルド:** `CGO_ENABLED=0` の静的なバイナリにする（本体は標準ライブラリだけ）。glibc と musl の両方の Linux で動く。
- **対象（最初）:** linux-x64、linux-arm64、darwin-arm64、darwin-x64。
  - Windows は最初は外す。ワーカーの口が UNIX ソケット前提で、同期の扱いも確かめていないため。
- **npm の形:** バイナリは OS と CPU ごとのパッケージ（`@kairo/kairod-linux-x64` など）に入れる。`optionalDependencies` と `os`・`cpu` の指定で、合うものだけが入るようにする（esbuild、biome と同じ）。
- **pip の形:** wheel を、OS と CPU ごとに作る。タグは `manylinux_2_17`、`musllinux_1_2`、`macosx` の x86_64・arm64 にする。
- **起動と停止:**
  - 入り口が、バイナリの場所を解決する。
  - 設定（データディレクトリ、待ち受ける口、合言葉）を、環境変数と引数で渡して起動する。
  - 準備ができたことは `/healthz` で確かめる。
  - 止めるときは SIGTERM を送る。kairod は、今の終了処理（耐久化）を済ませてから終わる。
- **版の組み合わせ:**
  - 1 つの言語のパッケージの中では、入り口とバイナリの版をそろえる。
  - 別に動かしている kairod とクライアント・ワーカーの間は、今の決まり（知らない型やフィールドは読み飛ばす）で、前後の版の組み合わせを許す。
- **リリース:**
  - CI（GitHub Actions）で、Go のクロスコンパイルで全部のバイナリを作り、SHA-256 を添えて PyPI と npm に出す。
  - 本番向けに、同じバイナリのコンテナイメージも出す。
- **gRPC:** 足さない。いろいろな言語から直接呼びたいという必要が出たら、別モジュール（ADR 0018）として、今の HTTP の API と並べて足す。

## 結果

- 利用者は `pip install kairo` や `npm install kairo` だけで、手元で kairo を動かせる。Go の環境も、ブローカーも要らない。
- 本番でも、同じバイナリをサービスとして置くだけでよい。
- kairod はアプリと別のプロセスで動く。どちらかが落ちても、もう片方を巻き込まない。耐久化と復旧は、kairod の中で今までどおり働く。
- **増える仕事:**
  - OS と CPU ごとのビルドとリリースの仕組みを持つ。
  - パッケージの数が増える（npm で 1＋4、pip で wheel 4 種類以上）。
  - クライアントを、Python と TypeScript で書いて保つ。
- **テスト（足す）:** CI で各バイナリをビルドし、対象の OS ごとに次を確かめる。
  - 入り口から kairod を起動し、`/healthz` が通ること。
  - 言語のワーカーをつなぎ、クライアントから投入した短い実行が終わること。
  - SIGTERM で正しく止まること。

## 検討した代替案

- **gRPC のサービスにする:** 依存が増え（ADR 0014）、今の HTTP の API とプロトコルで足りている。得られるのは、クライアントの自動生成くらいである。
- **Go の共有ライブラリとして組み込む（`c-shared` と、Node の N-API や Python の ctypes）:** ランタイムの同居、落ちたときの巻き込み、同期の書き込みをアプリのスレッドで抱えることを避けられない。
- **コンテナイメージだけで配る:** 本番では簡単だが、手元の開発には重い。Celery の代わりとして、手元ですぐ動くことを優先する。イメージは、同梱のバイナリと並べて出す。
- **初回の実行時にバイナリをダウンロードする（postinstall でダウンロード）:** オフラインや社内のミラーで失敗しやすく、npm の推奨からも外れる。esbuild も、`optionalDependencies` の形に移った。
- **kairo-n8n・kairo-dify も配る:** これらは性能の評価のための道具で、kairo の目的（Celery などの代わり）の利用者のためのものではない。
