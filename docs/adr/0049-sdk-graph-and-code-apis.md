# 0049. SDK は、グラフの API と、コードで書くワークフローの API の 2 段で用意する

- 状態: 承認
- 日付: 2026-10-07
- 関連: ADR 0003（作用の型）、0023（冪等な Submit）、0026（取り消し）、0027（終わった実行のマーカー）、0033（変数）、0048（配り方）

## 背景

kairo は、ワークフローツールなどを作るための OSS である。Python と TypeScript から使う SDK を配る（ADR 0048）。最初の大きな利用者として、コーディングエージェント KairoCode（opencode のようなもの）を作る。

KairoCode のようなエージェントは、ワークフローの形を実行しながら決める。たとえば Claude Code の動的なワークフローでは、スクリプトの中で `agent()` や `parallel()` を呼ぶ。前の結果を見て、次に何を呼ぶか、いくつ並べるかを決める。途中で止まっても、同じ呼び出しは記録した結果を返して、続きから再開できる。

今の kairo の API（`/v1/plans`、`/v1/runs`）は、実行の前にグラフ（計画）を登録する形である。形の決まったワークフローには速くて軽いが、上のような書き方はできない。

一方、エージェントの実行に要るものの多くは、kairo にすでにある。

- 並列と、同時実行の枠
- 宛先ごとの RPM・TPM と、同時実行の自動調整（ADR 0039）
- 耐久化したログからの復旧と、RunID による冪等性（ADR 0023、0027）
- 作用の型（ADR 0003）: ファイルの書き込みやシェルの実行は「実」にして、二重に実行しない。読み取りや検索は「非保護」にして、やり直してよい。
- 信号の待ち、取り消し、ライブ中継、トレース

## 決定

SDK（Python と TypeScript）に、次の 2 段の API を用意する。コアとエンジンは変えない。

### 1. グラフの API（今の HTTP の API を包む）

形の決まったワークフロー用。

- `client.registerNodes(...)`、`client.registerPlan(definition)`、`client.run(plan, input, {runId})`、`client.wait(runId)`、`client.signal(...)`、`client.cancel(runId)`、`client.stream(runId)` を用意する。
- それぞれ `/v1/...` を呼ぶだけにする。

### 2. コードで書くワークフローの API

動的なワークフローとエージェント用。

- **アクションの宣言:** `defineAction(name, {effect, handler})`。
  - `effect` は `"real"`（外に作用する。既定）か `"unprotected"`（外に作用しない。やり直してよい）にする。
  - SDK は、アクションの仕様を kairod に登録し（`/v1/nodes`）、`handler` をワーカーとして受け持つ。
  - 作用は宣言のとき決まり、実行中には変わらない（AGENTS.md）。
- **ワークフローの宣言:** `workflow(name, async (ctx, input) => {...})`。関数はアプリ（SDK）のプロセスで動く。
- **呼び出し:** `ctx.call(action, input)` は、そのアクションの 1 ステップだけの実行を、kairo に投入して結果を待つ。
  - SDK は、アクションごとに 1 ステップの計画（`kairo.call/<action>`）を 1 度だけ登録する。
  - 並列は、言語の普通の書き方（`Promise.all`、`asyncio.gather`）で書く。`ctx.parallel` は、それを包むだけの補助にする。
- **呼び出しの ID（再開の要）:** 投入する実行の RunID は、`<ワークフローの実行 ID>/<呼び出しの鍵>` にする。
  - 呼び出しの鍵は、アクションの名前と入力（正規化した JSON）のハッシュに、同じ組の呼び出しが何回目かを足したもの。Claude Code が `(prompt, opts)` で結果を引くのと同じ考え方である。呼び出しの前のコードを書き換えても、同じ呼び出しは同じ鍵になる。
  - kairo は RunID を冪等の鍵として扱う（ADR 0023）。同じ ID の投入は、すでにある実行（終わっていればその結果）を返す。
- **再開:** ワークフローの関数を、同じ実行 ID で頭から動かし直す。
  - 終わった呼び出しは、kairo が記録した結果をすぐ返す。実のアクションも、二度は実行されない。
  - 終わっていない呼び出しは、走っている実行を待つ。
- **ワークフローの実行そのもの:** ワークフローの実行も、kairo の実行として 1 つ持つ（計画 `kairo.workflow`）。
  - これは、終わりの信号を待つだけの実行である。
  - 一覧と状態は、これで見える。取り消すと、SDK が子の呼び出しをまとめて取り消す。
  - 関数が戻ったら、SDK が結果を信号で渡して終わらせる。
- **待ちと時刻:**
  - `ctx.waitFor(signal)`、`ctx.sleep(duration)` は、それぞれ待つだけの呼び出し（kairo の `wait` を 1 つ持つ計画）にする。
  - `ctx.now()`、`ctx.random()` も、結果を記録する呼び出しにする。
  - ワークフローの関数は、これらと `ctx.call` 以外で、外の世界や時刻に左右されないように書く（決定的であること）。これは利用者が守る決まりとして文書に書く。
- **記録が消えた後の再開を拒む:** 終わった実行の冪等性は、`IdempotencyTTL`（既定 24 時間、ADR 0027）の間しか保たれない。
  - SDK は、ワークフローの実行の開始がそれより古ければ、再開を拒んでエラーにする。
  - 期限を過ぎてから実のアクションが二度実行されることは、起こさない。
- **KairoCode での使い方（例）:**
  - LLM の 1 回の呼び出しは、`"unprotected"` のアクションにする。外に作用せず、出力は記録される。
  - ファイルの書き込み、シェルの実行、git の操作は、`"real"` のアクションにする。
  - ファイルの読み取り、検索は、`"unprotected"` のアクションにする。
  - サブエージェントは、ワークフローの中のワークフロー（子のワークフローの実行）にする。

## 結果

- KairoCode のようなエージェントや、動的なワークフローを、コアを変えずに kairo の上で書ける。
  - 途中で落ちても、同じ呼び出しはやり直さずに再開できる。
  - 外に作用するツールは、二重に実行しない。
- **費用:** コードで書く API は、呼び出し 1 つが kairo の実行 1 つになる。実行の開始と終わりの耐久化の分だけ、グラフの API より重い。
  - LLM の呼び出しやツールの実行（数十 ms〜秒）に比べれば小さい。
  - 速さが要る、形の決まったワークフローは、グラフの API で書く。
- **利用者が守る決まり:** ワークフローの関数は決定的に書く。これを破ると、再開のときに呼び出しの鍵が変わり、別の呼び出しとして実行される。
  - SDK は、再開のときに鍵が記録と合わない呼び出しを見つけたら、警告を出す。
- **テスト（足す）:**
  - Python と TypeScript で、関数の途中でプロセスを止めて再開したとき、次を確かめる。
    - 終わった呼び出しが再実行されないこと（実のアクションの実行回数を数える）。
    - 並列の呼び出しの結果がそろうこと。
  - 取り消しが子の呼び出しに届くこと。
  - 期限を過ぎた実行の再開を拒むこと。

## 検討した代替案

- **コアに「実行中にグラフへノードを足す」仕組みを入れる:** 1 つの実行の中に呼び出しが全部収まり、1 呼び出しあたりの費用は小さい。ただし、IR とコアの意味論（Act の採番、リプレイ）を大きく変える。また、関数をどこで動かすかという問題は残る。まず SDK だけで作り、費用が問題になってから考える。
- **関数そのものを kairo の中で動かす（JavaScript や Python の処理系を組み込む）:** 本体は標準ライブラリだけで作る（ADR 0014）、コアは純粋である（不変条件 1）、という決まりに反する。
- **Temporal のように、関数の履歴を 1 つの実行のイベントとして記録し、再生する:** 呼び出しの記録を kairo の 1 つの実行に持てる。ただし、コアに「外から命令を足す」イベントの種類が要る。SDK の呼び出し単位の冪等性で、同じ性質（終わった呼び出しをやり直さない）が得られる。
- **グラフの API だけにする:** エージェントのように、実行しながら形が決まるものを書けない。

## 実装で詰めた詳細（2026-10-07 追記、ADR 0017）

- **置き場所:**
  - TypeScript は `sdk/ts/src/client.ts`（グラフの API）と `workflow.ts`（コードで書く API）。
  - Python は `sdk/python/kairo_worker/client.py` と `workflow.py`。
  - Python のパッケージ名（`kairo_worker`）は、配り方（ADR 0048）を実装するときに `kairo` に変える。
- **書き方の違い:**
  - Python のワークフローは `async def`（asyncio）で書く。アクションの処理は、普通の関数でも `async def` でもよい。
  - Python ではデコレーター（`@k.action(...)`、`@k.workflow(...)`）で宣言し、待ちは `ctx.wait_for`、眠りは秒（`ctx.sleep(0.3)`）で渡す。
  - TypeScript は `defineAction`・`workflow`・`ctx.waitFor`・ミリ秒の `ctx.sleep` にした。
- **組み込みのアクション:** `kairo.now`、`kairo.random`、`kairo.sleep` は非保護のアクションとして SDK のワーカーが受け持つ。
  - `kairo.sleep` は、期限まで待つ結果（ADR 0045）を返す。待つのは kairo の中で、SDK のプロセスは止まっていてよい。
- **計画:**
  - アクションごとの 1 ステップの計画は `kairo.call/<action>`（入力は `{"in": ...}`）にした。
  - 信号の待ちは `kairo.wait/<信号名>`、ワークフローの実行は `kairo.workflow` にした。`kairo.workflow` は、終わりの信号 `done` を待つだけの計画で、開始の時刻を実行の変数 `started_at` に持つ。
  - どれも耐久化の段階 `file` で投入する。
- **呼び出しの ID:** `<ワークフローの実行 ID>/<sha256(種類 + "\0" + 正規化した入力) の先頭 24 文字>.<何回目か>`。
  - 種類は `kairo.call/<action>`、`kairo.wait/<信号名>`、`kairo.workflow/<名前>`。
  - 正規化は、オブジェクトのキーを並べた JSON にした。
  - 同じ ID で動かし直す相手は、同じ言語の SDK を前提にしている。数値の表記などが言語で違いうるため。
- **信号:** `signal(ワークフローの ID, 名前, 中身)` は、その名前の待ちを 0 回目から順に見て、まだ終わっていない最初のものに信号を送る。
  - 待ちがまだ始まっていなければエラーにする（TypeScript は `Error`、Python は `LookupError`）。
- **取り消し:**
  - `cancel(ワークフローの ID)` は、ワークフローの実行を取り消す。
  - 駆動している SDK は、その実行の終わり（`/wait` の長い待ち）を見て取り消しを知り、待っている呼び出しの実行も取り消す。
  - 呼び出しの処理には、ワーカーのプロトコルの取り消し（ADR 0026）で届く。
- **`close()`:** プロセスが止まったのと同じ扱いにした。
  - 駆動しているワークフローの待ちをやめるが、ワークフローの実行も呼び出しも取り消さない。kairo の中で続き、後で同じ ID で再開できる。
- **残る制約（別の ADR で扱う）:** 終わった実行の出力は、kairod のメモリにしかない（`RecentRuns`、既定 10 万件）。kairod が再起動すると、終わった実行には、出力のないマーカーだけが残る（ADR 0027）。
  - このため、kairod の再起動をまたいでワークフローを再開すると、終わった呼び出しの結果を取り出せない。
  - SDK は、この場合に呼び出しを動かし直さず、`ResultLostError` で止める。外に作用するアクションを二重に実行することはない。
  - SDK のプロセスが止まって再開する場合（kairod は動いたまま）は、今のままで再開できる。
- **テスト:** 本物の kairod をビルドして起動し、次を確かめた（`sdk/ts/src/workflow.test.ts`、`sdk/python/tests/test_workflow.py`）。
  - 1 つ目の駆動役が止まった後、別の駆動役が同じ ID で再開しても、外に作用するアクションは 1 回しか動かないこと。
  - 並列の呼び出しの結果がそろうこと。
  - 終わったワークフローを動かし直すと、何も動かさずに結果を返すこと。
  - 子のワークフロー。
  - `sleep` が kairo の中で待つこと。
  - 信号で `waitFor` が戻ること。
  - 取り消しが、走っているアクションの処理まで届くこと。
