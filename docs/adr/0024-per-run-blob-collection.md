# 0024. ブロブは実行ごとにまとめて保存し、実行の終了時に消す

- 状態: 承認（2026-10-01）。SQL 側の方法（grp 列）は 0025 により置き換え
- 日付: 2026-10-01
- 関連: ADR 0008, 0016, 0020, 0021, 0022

## 背景

16 KiB を超える出力はブロブに移す（ADR 0008）。ブロブは内容のハッシュを名前にしていて（`sha256:<hex>`）、一度書くと消されない。実行が終わっても残り続けるので、保存先は際限なく大きくなる。

内容アドレス型なので、同じ内容は別の実行からも同じ名前になる。そのため、ある実行が終わっても、そのブロブをほかの実行がまだ参照しているかどうか分からない。消すには、参照の数を数えるか、保存先を走査する必要がある。どちらも、保存先インターフェース（`Put`、`Get`、`Delete`）だけでは安全にできない。

## 決定

- 出力のブロブの名前に、実行 ID を含める: `run/<run id>/sha256:<hex>`。
  - 同じ内容の重複排除は、1 つの実行の中だけで行う。
  - 実行をまたいだ共有はしない。実行の入力が参照するのは、その実行自身の出力だけなので、これで足りる。
- 省略可能なインターフェース `blob.Grouper { DeleteGroup(group string) error }` を設ける。group は `run/<run id>` で、その下の全オブジェクトを消す。
  - `blob.Dir`: グループごとにディレクトリを分け（`<root>/g/<group の SHA-256>/<名前の SHA-256>`）、ディレクトリごと消す。
  - `blob.Mem`: 接頭辞が一致するものを消す。
  - `sqlstore.Store`: 表に `grp` 列を足し、`DELETE ... WHERE grp = ?` で消す。表の形が変わるので、既存の表に列を足す移行を `Migrate` に入れる。
  - `blob.Encrypted`: グループ名も鍵付きのハッシュで隠したうえで、内側の `DeleteGroup` に渡す。保存するときの名前は「グループのハッシュ ＋ 名前のハッシュ」とする。
- 消す時機は、実行が終わり、スナップショットを消すとき（ADR 0016 の削除待ち `s.pins` の流れ）とする。
  - ブロブのグループも、スナップショットと一緒に消し終えてから記録の保持を解く。
  - 削除の前にクラッシュしても、終わった実行の記録が残っているので、再起動後のリカバリで終了を確かめてから消し直す。リカバリで終了済みと分かった実行のブロブも消す。
- `Grouper` を実装しない保存先では、これまでどおり消さない。
- 以前の形式のブロブ（`sha256:<hex>`、実行 ID なし）は消さない。どの実行のものか分からないため。

## 結果

- 終わった実行のブロブが残らなくなり、保存先の大きさが、生きている実行の分に収まる。
- 同じ出力が多くの実行で繰り返されると、実行ごとに 1 つずつ保存される。重複排除の効果は小さくなる。
- `blob.Store` を自分で実装している場合、ブロブを回収させるには `Grouper` の実装が要る。
- SQL の表に列が増える。既存の表への列の追加は、権限のある役割で `DDL` を流すか、`Migrate` に任せる。
- テスト:
  - 共通テストに `DeleteGroup` を足し、全保存先に流す。暗号化した状態でも流す。
  - エンジン: 大きな出力を出す実行が終わると、そのブロブが消えている。終了と削除の間にクラッシュしても、再起動後に消える。生きている実行のブロブは消えない。

## 検討した代替案

- 参照カウント: 増減を、実行の状態の変化と同じ順序で耐久化する必要があり、ログ（0016）と保存先にまたがる整合性の問題が増える。
- 走査して回収する（mark & sweep）: 保存先に一覧の操作が要る。生きている全実行の状態を読む必要もあり、規模に比例して重い。
- 期限で消す（TTL）: 長く待つ実行（承認待ちなど）のブロブを消してしまう危険がある。

## 実装で詰めた詳細（2026-10-02 追記、ADR 0017）

- 名前の形式は `run/<id>/sha256:<hex>`（`blob.PutRunContent`）。グループは `blob.GroupOf` で決まる。
- `blob.Dir` は、グループごとに `<root>/g/<xx>/<group の SHA-256>/` のディレクトリを作り、ディレクトリごと消す。
- `blob.Encrypted` は、グループ名も鍵付きのハッシュで隠す。保存名は `run/<group のハッシュ>/<名前のハッシュ>` とし、内側の保存先でもグループ単位で消せるようにした。
- SQL 側は ADR 0025 の方法（名前の前方一致の範囲、件数を区切って削除）にした。
- **ADR に書いていなかった点。** 最後の出力が大きいと、それ自体がブロブへの参照になっている。終了時にブロブを消すと、結果を取り出せなくなる。そこで終了時の順序を次のようにした（`shard.finish`）。
  1. 出力を、ブロブの中身に置き換える。
  2. 終了済みとして記録し、待っている呼び出し側に通知する。
  3. ブロブとスナップショットを消す。

  置き換えが終わるまでの `Get` は、参照のままの出力を返すが、ブロブはまだ残っているので解決できる。
- 耐久性ティアが file 未満の実行は、スナップショットがないので、終了時にブロブだけを消す。
- テスト:
  - `TestBlobsDeletedWhenRunFinishes`（生きている実行のブロブは残る。最終出力は中身に置き換わる）
  - `TestLeftoverBlobsDeletedOnRecovery`
  - 共通テストの `DeleteGroup` の項目（全保存先。暗号化した状態でも）
