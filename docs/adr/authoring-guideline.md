# ADR 執筆ガイドライン

この文書は、今後作成・置換する ADR の執筆とレビューに使う正典です。既存 ADR の本文へ遡って適用せず、状態変更と置き換えは ADR 0000・0017の運用に従います。

規約は、違反してはならない **MUST** と、外す理由を説明できる場合を除いて従う **SHOULD** に分けます。レビューでは規約IDを使って指摘します。

## A. 情報の置き場所と参照

- **A-1（MUST）:** 背景・決定・結果・代替案の本文に Issue、PR、チケット番号や外部URLを書かない。外部資料は「参照」に集める。
- **A-2（MUST）:** 関係する ADR と置き換え関係は「関連する ADR」に集める。外部資料と混ぜない。
- **A-3（SHOULD）:** 実装仕様、移行手順、検証計画、進捗は、それぞれ仕様書、Issue、PR、検証文書へ置く。ADRはそれらの保管場所を「決定しないこと」または「参照」から辿れるようにする。

## B. 長く有効な参照

- **B-1（MUST）:** 物理行番号で参照しない。ファイル、型、API、節の安定した名前で指す。
- **B-2（MUST）:** 他 ADR の個別判断を参照するときは、`ADR NNNN の決定項 N（章題）` の形で、番号と章題を併記する。
- **B-3（SHOULD）:** リンクテキストだけで参照先の種類と意味が分かるようにする。「こちら」「上記」だけで指さない。

## C. 事実と根拠

- **C-1（MUST）:** 背景、結果、代替案の前提事実は、実コード、要件、計測の生データ、仕様や公式文書など、後から再確認できる一次資料と照合する。外部資料には確認日を添える。
- **C-2（MUST）:** 確認できた事実、そこからの推論、提案する判断を混ぜない。背景は判断を先取りせず、中立に書く。
- **C-3（MUST）:** ADR単体で「実際に何が問題か」「なぜ今決めるか」「どの制約が判断を必要にしたか」を理解できるようにする。参照先を読まなければ問題自体が分からない文章にしない。
- **C-4（SHOULD）:** 会議や口頭確認だけを根拠にしない。再確認できない場合は、確認可能な事実だけを書くか、未決事項として委譲する。

## D. ADRに残す判断の粒度

- **D-1（MUST）:** 移行工程、担当、期限、進捗、チェックリスト、バックログをADRへ書かない。完了すると陳腐化する情報はIssueや計画文書へ置く。
- **D-2（MUST）:** 関数名、環境変数名、内部データ構造、アルゴリズム、個別テスト手順など、長期の設計判断ではない実装詳細を決定に含めない。互換性や安全性を成立させるため方式そのものを固定する必要がある場合は、その理由を書く。
- **D-3（SHOULD）:** 適用範囲、例外とその失効条件、そして「このADRで決定しないこと」を明記する。決定しない事項には、実在する委譲先を示す。
- **D-4（SHOULD）:** 実現方式を同じ性質を満たす別方式へ置き換えたとき、ADR本文の変更が必要かを確認する。必要なら、記述が実装詳細に寄りすぎていないか見直す。
- **D-5（MUST）:** 決定は能動態で明確に書き、複数ある場合は `決定項 N（章題）` として番号を固定する。

## E. ADR間と索引の整合

- **E-1（MUST）:** 新規ADR、状態変更、置き換えを `docs/adr/README.md` と一致させる。
- **E-2（MUST）:** 既存判断を変えるときは古い本文を書き換えず、新しいADRで置き換え、双方の状態と関連を更新する。
- **E-3（MUST）:** 同じ判断が既存ADRにある場合は新しいADRを増やさず、既存判断を参照する。

## F. 表記と保守性

- **F-1（MUST）:** タイトルは実装作業ではなく、決めた性質を一文で表す。
- **F-2（SHOULD）:** 用語は要件、既存ADR、コードの公開概念と揃える。新しい同義語を増やさない。
- **F-3（MUST）:** 「最新」「現在対応中」「最終更新日」など、時間とともに意味が変わる情報を本文へ置かない。日付はADRの日付と、外部資料の確認日に限る。

## G. 承認前の点検

- **G-1（MUST）:** 承認時点で、決定の成立に必要な未確定事項を残さない。未確定なら提案のままにするか、適用範囲から外して委譲先を示す。
- **G-2（MUST）:** 結果には、良い影響、悪い影響、中立な影響と、新しく守る制約を含める。
- **G-3（MUST）:** セキュリティに関わるADRは、資産、信頼境界、脅威、失敗時の扱い、鍵や資格情報の寿命、監査可能性を必要な範囲で確認する。
- **G-4（MUST）:** `scripts/adr-lint.sh` を通し、人が意思決定そのものをレビューしてから承認を求める。

## ADRに置かない情報の行き先

| 情報 | 行き先 |
|---|---|
| 実装の型・関数・アルゴリズム | 仕様書、コード、コードコメント、PR |
| 移行の作業、担当、順番、進捗 | Issue、移行計画 |
| テストケースと実行手順 | テストコード、検証文書、PR |
| 計測の生データと反復結果 | `docs/` の検証文書、ベンチマーク出力 |
| 一時的な回避策 | Issue、運用手順 |

## レビュー時の確認

1. ADR単体で、実際の問題と判断の必要性が分かるか。
2. Decisionは長期に守る性質であり、実装仕様や作業計画になっていないか。
3. 適用範囲と決定しないこと、その委譲先が明確か。
4. 事実を一次資料で再確認できるか。
5. 良い・悪い・中立の結果が書かれているか。
6. 関連ADR、状態、索引、置き換え関係が一致しているか。
7. 未確定のまま承認しようとしていないか。
