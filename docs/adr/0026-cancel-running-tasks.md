# 0026. 中断した手順は、実行中のタスクにも取り消しを届ける

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR3, FR7 / ADR 0004, 0007, 0008

## 背景

コアは、手順の試行を打ち切るときに `CmdAbort{Act, Attempt}` を出す。打ち切るのは、次の場合である。

- 手順のタイムアウト
- 実行の取り消し（`Engine.Cancel`）
- 並列の分岐の失敗

シャードは、これを `Dispatcher.Abort` に渡す。しかし `Abort` が落とせるのは、まだキューにいるタスクだけである。

- すでに実行器に渡ったタスクは、最後まで動き続ける。結果は、古い試行のものとしてコアに無視される。
  - インプロセスの実行器の `ctx` は、エンジンの停止でしか切れない（`RegisterExecutor`）。
  - 外部ワーカーには、取り消しを伝えるメッセージがない。
- その間、LLM 呼び出しなら、トークンと時間を使い続ける。宛先ごとの同時実行の枠（ADR 0008）も、埋まったままになる。タイムアウトで打ち切った手順を再試行すると、古い試行と新しい試行が同時に枠を使う。
- 渡った後の `Abort` では、`Dispatcher.aborted` に印が残り、消えない（小さなメモリリーク）。

## 決定

### ディスパッチャが渡したタスクを覚え、取り消す

- タスクの状態は、すべてディスパッチャの goroutine が持つ（今と同じく、ロックを足さない）。
  - キューにいるタスク: `Abort` で落とす。
  - 渡したタスク（`delivered`: `task.Key` → 取り消し関数）: `Abort` でその `ctx` を取り消す。
  - どちらでもない（もう終わった）: 何もしない。印は残さない。
- そのため、`Abort` が「渡す前」と「渡した後」のどちらに届いても、取りこぼしも漏れもない。
- 渡すときに、タスクごとの `ctx` を作る。
  - 作るのはディスパッチャの goroutine で、シャードのループでは作らない。
  - `Poller.C` の要素を、`*task.Task` から `sched.Delivery{Task *task.Task; Ctx context.Context}` に変える。
- `Done` で `delivered` から外す。
  - 同時実行の枠とトークンの精算は、今までどおり `Done`（実行器が実際に戻った時点）で行う。取り消した時点では枠を返さない。止まらない実行器があっても、同時実行の上限は守られる。
- `Unpoll` で戻ったタスクは、`delivered` からキューに戻す。

### インプロセスの実行器

- `RegisterExecutor` の各 goroutine は、`Delivery.Ctx` で `Execute` を呼ぶ。
  - この `ctx` は、エンジンが止まったときにも切れる。
- 取り消された後に実行器が返した結果は、今までどおり `Complete` に渡す。コアは、古い試行の結果として無視する。結果の意味は変えない。

### 外部ワーカー（プロトコル）

- 新しいメッセージ `Cancel {"seq":17}`（runtime → worker）を足す。
  - サーバは、送ったタスクの `Delivery.Ctx` が切れたら `Cancel` を送る（`context.AfterFunc`）。結果を受け取ったら、その登録を外す。
  - `protocol.Worker` は、`Cancel` を受けたら、そのタスクのハンドラの `ctx` を取り消す。
  - 古いワーカーは、知らない種類のメッセージを読み飛ばす（今の `Worker.Run` もそうしている）。そのため互換性は保たれ、取り消しが効かないだけになる。
- 取り消しは、ワーカーへの依頼にとどまる。ワーカーは結果（エラーでよい）を必ず返す。返すまで、同時実行の枠もクレジットも埋まったままになる。

### 効果の種類との関係

- 取り消しは、資源を節約するためのものであり、結果の扱いは変えない。
  - 実の効果（real）の手順を取り消しても、外部で効果が起きたかどうかの扱い（ADR 0004、`Unknown` と要確認）は今のままである。打ち切りの判断はコアがすでにしており、その後に届いた結果は無視される。
  - 実行器は、取り消されたときに、どこまで進んだかを気にしなくてよい。

## 結果

- タイムアウトや取り消しの後に、実行中の LLM 呼び出しや HTTP 呼び出しが止まる（`ctx` に従う実行器なら）。トークン、時間、同時実行の枠が早く空く。
- `Dispatcher.aborted` のリークがなくなる。
- 悪くなること:
  - ディスパッチャが、渡したタスクごとに `ctx` を 1 つ作る（シャードのループの外で、1 タスクあたり 100 バイト程度）。
  - `sched.Poller.C` の型が変わる（v0 なので互換のための型は残さない）。
- テスト:
  - 手順のタイムアウトで、実行中の実行器の `ctx` が切れる。`Engine.Cancel` でも切れる。
  - `Abort` が渡す前と渡した後のどちらに届いても、タスクは取り消され、ディスパッチャに印が残らない（何万回か繰り返してマップの大きさを見る）。
  - 取り消しを無視して動き続ける実行器がいる間は、同時実行の枠が空かない。
  - 外部ワーカーが `Cancel` を受けて、ハンドラの `ctx` が切れる。古いワーカー（`Cancel` を読み飛ばす）でも、動作が変わらない。

## 検討した代替案

- シャードが、手順を出すときに `ctx` を作って実行の状態に持つ: シャードのループで、タスクごとに割り当てが増える。退避した実行の取り消し関数の扱いも要る。ディスパッチャはもともとタスクごとの状態を持っているので、そこに置く。
- エンジンに、実行中のタスクの表（ミューテックスつき）を別に持つ: キューから渡すまでの間に届いた `Abort` を取りこぼす。防ぐには「取り消し済み」の印が要り、それが残る。ディスパッチャの 1 つの goroutine にまとめれば、この競合はない。
- 取り消した時点で同時実行の枠を返す: 取り消しに従わない実行器がいると、上限を超えて呼び出しが走る。外部の割り当て（レート制限）を守ることを優先する。

## 実装で詰めた詳細（2026-10-02 追記、ADR 0017）

- エンジンの停止時の取り消しは、`Dispatcher.AbortAll`（渡したタスクの `ctx` をすべて切る）で行う。
  - 当初は、実行器のプールの `ctx` とタスクの `ctx` を `runTask` で結び付けていた。しかし、タスクごとに共有の親 `ctx` へ登録が入り（ロックとマップの操作）、`BenchmarkFiveNodeRun/none` の CPU 時間が 1 実行あたり約 10µs（約 17%）増えた。
  - `AbortAll` に変えた後の差は、約 2µs（約 3%。負荷の高い macOS での 6 回の比較で、ばらつきの範囲に近い）。
- 渡したがまだ取られていないタスクが、取り消された後に `Unpoll` で戻った場合は、キューに戻さずに捨てる。
- ディスパッチャが覚えているタスクの数を `Dispatcher.Tracked` で返す。仕事が終われば 0 に戻ることをテストで確かめる。
- プロトコルのサーバは、`Task` のフレームを書いてから `Cancel` の送り手を登録する。そのため、`Cancel` がタスクを追い越すことはない。
- レビューで見つかった点を直した。
  - プロトコルのサーバは、`Task` のフレームを書く前に、送ったタスクの表に登録する（`wmu` を持ったまま）。大きなフレームは `WriteFrame` が返る前にワーカーに届くので、後に登録すると、速い Result を捨ててしまうため。`Cancel` の送り手も `wmu` を待つので、追い越しは起きない。
  - ディスパッチャが止まるとき（`Close`）は、処理されずに残ったメッセージに関係なく、渡したタスクの `ctx` をすべて切る（`AbortAll` が処理されないまま止まることがあるため）。
  - `Done` は、同じタスク（ポインタ）のときだけ `delivered` から外す。同じ `task.Key` が新しい実行で再利用されても、新しいタスクの `ctx` を切らない。
  - サーバは、取った時点ですでに取り消されているタスクを送らない。
- テスト:
  - `TestAbortCancelsDeliveredTask`、`TestAbortLeavesNothingBehind`（sched）
  - `TestStepTimeoutCancelsRunningTask`、`TestRunCancelCancelsRunningTask`、`TestCloseCancelsRunningTask`（engine）
  - `TestWorkerReceivesCancel`、`TestOldWorkerIgnoresCancel`（protocol）
