# 0029. 任意のグラフ（DAG）を実行の基本形にする（木の構成要素はグラフに変換する）

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR1, FR2 / 不変条件 1, 2 / ADR 0001, 0013, 0015, 0028

## 背景

kairo の IR は木構造の構成要素（seq / par / cond / map・loop / wait）で、要件は「構成要素は 5 つのみ」としている。しかし、Dify（ADR 0028）や n8n のワークフローは、利用者が画面で自由につなぐ**任意のグラフ**である。

木では表せない形がよく現れる。

- 分岐した後に、別の分岐と合流する。
- ひし形の依存（A→B、A→C、B→D、C→D で、B だけが分岐の中にある、など）。
- 入口（root）が複数ある（トリガーごとの入口）。
- 失敗したときにだけ通る辺（fail-branch）。

graphon は、これを次の意味論で実行している（`docs/compat/dify.md` の 2 節）。

- 辺の状態は、UNKNOWN / TAKEN / SKIPPED の 3 値。
- ノードは、入ってくる辺がすべて確定してから、TAKEN が 1 本でもあれば実行する（全部の確定を待つ OR 結合）。すべて SKIPPED ならスキップし、出ていく辺を SKIPPED にして再帰的に伝える。
- 分岐ノードは、選んだハンドルの辺を TAKEN、それ以外を SKIPPED にする。分岐でないノードは、出ていく辺をすべて TAKEN にする。

木の構成要素から任意のグラフへ変換することは、一般にはできない。逆に、木の構成要素はすべてグラフで表せる。

## 決定

### 実行の基本形をグラフにする

- IR に構成要素 `graph` を足す。

  ```json
  {"kind":"graph","id":"g",
   "nodes":[{"kind":"step","id":"a","action":"llm"}, {"kind":"step","id":"b","action":"classify"}, ...],
   "edges":[{"from":"a","to":"b"}, {"from":"b","handle":"refund","to":"c"}, ...],
   "entry":["a"],
   "output":{"answer":"c.text"}}
  ```

  - `nodes` には、任意の構成要素を置ける（step、wait、map / loop のコンテナ、入れ子の graph）。
  - 辺の `handle` を省略すると `"source"` になる。
- コアの制御の流れは、グラフだけで扱う。変換の向きは**木からグラフ**だけで、グラフを木に変換することはしない。
  - Dify や n8n のグラフは、そのままの形でグラフとして実行する。
  - 既存の seq / par / cond は、書きやすさのための**コンパイル時の糖衣**として残し、コンパイラがグラフに書き換える。コアが持つ合流の仕組みは 1 つだけになる。
  - seq: 一列につなぐ。
  - par: 分岐させてから合流させる。合流するのは、すべての辺が TAKEN になったとき。
  - cond: 条件のノードを置き、ハンドル `"true"` / `"false"` で分ける。その後で合流させる。分岐しなかった側の辺は SKIPPED になるので、OR 結合で合流する。
  - 既存のテスト（`checkReplay` を含む）は、書き換えた後もそのまま通らなければならない。これを、糖衣の意味が変わらないことの検査とする。
- map と loop はコンテナのままにする。本体には、グラフを含む任意の構成要素を置ける。
  - そのため、全体は「ノードの中にグラフを持てるグラフ」（入れ子のグラフ）になる。入れ子になるのはコンテナの本体だけで、同じ階層の中は木ではなく一般の DAG である。Dify の iteration / loop が、子のグラフを持つのと同じ形。本体の 1 回の実行は、今と同じ子スコープ（`core.Scope`）になる。辺の状態は、スコープごとに持つ。

### 実行の意味論（graphon 0.7.0 に合わせる）

- 辺の状態は UNKNOWN / TAKEN / SKIPPED の 3 値で、スコープごとの状態に持つ（1 辺あたり 2 ビット）。
- ノードの準備判定:
  - 入ってくる辺に UNKNOWN が残っていれば、待つ。
  - すべて確定していて、TAKEN が 1 本以上あれば、実行する。
  - すべて SKIPPED なら、スキップして、出ていく辺をすべて SKIPPED にする（再帰的に伝える）。
- ノードが終わったら:
  - 分岐ノードは、選んだハンドルの辺を TAKEN、それ以外を SKIPPED にする。
  - 分岐でないノードは、`"source"` の辺をすべて TAKEN にする。
- **分岐ノード**は、ノード仕様で、ハンドルを決める出力フィールドを宣言したものとする（`NodeSpec.Branch`）。そのフィールドは enum 型で、候補がハンドルの集合になる（ADR 0013 の型付きの分岐と同じ考え方）。
  - 辺の `handle` は、コンパイル時にその集合に含まれるか検査する。
  - 選ばれたハンドルに辺がなければ、出ていく辺はすべて SKIPPED になる。
  - Dify の if-else と question-classifier をこの形にどう写すかは、別の ADR（条件の扱い）で決める。
- **入口:**
  - `entry` が複数あるときは、`Submit` でどれを使うかを選ぶ。使わない入口から先は、開始時に SKIPPED にする。
  - 省略したときは、入ってくる辺のないノードがすべて入口になる。
- **スキップされたノードの出力**は「ない」として扱う。参照は null に解決する（Dify の variable-aggregator の「最初の null でない値」の意味論に合う）。
- **グラフが終わる条件:** 実行中または準備できたノードがなく、すべての辺が確定したとき。出力は `output` で、ノードの出力から組み立てる。
- **決定性（不変条件 1, 2）:**
  - 1 回の `Apply` で複数のノードが準備できたら、ノードの添字の順に命令を出す。
  - 辺の処理は、辺の添字の順に行う。
  - 同じイベント列からは、同じ状態のバイト列ができる。

### 検証（コンパイル時）

- 閉路は拒否する。繰り返しはコンテナ（loop）で表す。
- 辺の両端は存在するノードでなければならない。ハンドルは送り元が出せるものでなければならない。
- 入口から到達できないノードは拒否する。
- 参照（`input` の ref）は、そのノードの祖先（グラフ上で必ず先に確定するノード）か、外側のスコープのものだけを許す。

### 状態と形式

- `core.Scope` に、辺の状態とノードの状態（未実行 / 実行中 / 完了 / スキップ）を足す。状態の形式が変わるので、`codecVersion` を上げる。v0 の形式のスナップショットとログは、読めるようにする。
- 新しいイベントや命令の種類は足さない。スキップは、コアの状態遷移の結果として起きる。可観測性には `step.skipped` を出す。

## 結果

- Dify と n8n のグラフを、形を変えずにそのまま実行できる。木への変換で失敗することがない。
- コアの合流の仕組みが 1 つにまとまり、par と cond の特別扱いがなくなる。
- 悪くなること:
  - 状態に、辺とノードの状態が増える（1 スコープあたり、辺の数 × 2 ビットとノードの数 × 2 ビット程度）。待っている実行のメモリの予算（20 KiB）の中に収まるかを、`TestWaitingRunMemory` で確かめる。
  - コアの書き換えが大きい。`core/` は純粋性のテストと `checkReplay` で守り、`/core-change` の手順に従う。
- 要件 FR1 の「構成要素は 5 つのみ」を変える。構成要素は「グラフ、コンテナ（map / loop）、待機と、葉のステップ」になり、seq / par / cond は糖衣として残る。README の FR1 の行を書き換える。
- テスト:
  - 既存のコアのテストが、糖衣の書き換えの後もすべて通る。
  - グラフの意味論のテスト: ひし形、分岐の後の合流、すべて SKIPPED の伝播、複数の入口、選ばれたハンドルに辺がない場合。
  - 準備できるノードの順序を入れ替えても、同じ状態のバイト列になる（`TestParallelJoinAnyOrder` のグラフ版）。
  - ADR 0028 の差分ハーネスで、graphon 0.7.0 と、実行・スキップされたノードの集合が一致する。

## 検討した代替案

- Dify のグラフを、木の構成要素に変換する: 分岐の後の合流や、ひし形の依存を一般には表せない。ノードを複製すれば表せる場合もあるが、副作用のあるノードが重複し、冪等キーも変わってしまう。
- グラフを、既存の構成要素と並ぶ 6 つ目の構成要素として足す（seq / par / cond はコアに残す）: 合流の仕組みが 2 つになり、入れ子にしたときの意味論と検査の対象が倍になる。
- 閉路を許して、繰り返しもグラフで表す: 停止の判定と、スキップの伝播の意味論が崩れる。Dify もループはコンテナで表しており、閉路を持たない。

## 実装で詰めた詳細（2026-10-02 追記、ADR 0017）

- **古いログとの互換。** ログのイベントは活性化（Act）の番号を持っているので、糖衣の書き換えで Act の採番を変えてはいけない。
  - cond の条件は、Act を作らないグラフのメンバー（`ir.KTest`）にした。準備できた時点でその場で評価し、`"true"` か `"false"` の辺を通す。
  - KTest のノードは `Plan.Nodes` の末尾に置く。既存のノードの番号（状態とスナップショットが持っている）は、木の時と同じになる。
  - seq / par は、木の時と同じ順に子を始める。準備できたノードは、トポロジカル順（同時に準備できたものは小さい添字から）で始める。
- **状態の場所。** 辺とノードの状態は、ADR では「スコープごと」としていたが、グラフの活性化（`core.Act.G`）ごとに持つことにした。loop の各回は新しい活性化になるので、こちらの方が自然。
- **形式。** `codecVersion` を 2 にした。
  - バージョン 1 のスナップショットも読める。seq / par / cond の進み具合（`Pos`、`Results`、走っている子）は、初めて子が終わったときにグラフの状態へ組み立て直す（`migrateGraph`）。
  - 確認したこと: 変更前のコードで、ログだけのものとスナップショットに退避したものの 2 種類のデータディレクトリを作り、新しいコードで回復して最後まで実行した。どちらも同じ出力で終わった。この確認で、seq / cond の待ち数（`Pending`）を組み立て直していない不具合が見つかったので直した。
- **値のクリア。** 手書きのグラフでは、スキップしたメンバー（とその中のノード）の値を消す。loop の後の回で、前の回の値が読めてしまうのを防ぐため。cond は、木の時の振る舞い（消さない）のままにした。
- **参照の制約。** 「祖先のノードか、外側のスコープだけ」という制約は、手書きのグラフにだけ課す（`graphOrder`）。糖衣（seq / par / cond）は、これまでの参照の規則のままにした。
- **出力。**
  - 手書きのグラフで `output` を省略したときは、出ていく辺がなく、実行されたメンバーの出力を、ID をキーにしたオブジェクトにする。
  - seq は最後のメンバーの出力、par は全メンバーの出力のオブジェクト、cond は実行された枝の出力（どちらも実行されなければ null）。
- **入口の選択。** `SubmitRequest.Entry` で選ぶ。開始のイベント（`EvStart.Name`）に入れてログに残すので、回復でも同じ入口になる。存在しない入口は `ErrUnknownEntry`（HTTP では 400）。
- **分岐の値の検査。** 分岐ノードの出力に宣言の候補にない値が入っていたら、実行を失敗にする（graphon も、ハンドルが選ばれないまま分岐ノードが終わるとエラーにする）。
- **性能。** 1 つのノードが終わるたびに、グラフのメンバーを 1 回走査する。
  - 計測（`BenchmarkGraphWide`。負荷の高い macOS）では、1 遷移あたりの時間は次のとおりだった。予算（20µs）の中に十分収まる。

    | 形 | 10 ノード | 100 ノード | 500 ノード |
    |---|---|---|---|
    | 横に広い（fan-out） | 393 ns | 519 ns | 666 ns |
    | 縦に長い（chain） | 324 ns | 372 ns | 828 ns |

  - 既存のベンチマークは、変更の前後で差がなかった。`BenchmarkTransition` は約 970ns、5 ノードの実行は約 +2µs で、この差には ADR 0026 の分を含む。
  - 待っている実行のメモリは、1850 バイトから 1946 バイトになった。
- **糖衣の中の分岐ノード。** seq / par / cond の中に分岐ノード（`NodeSpec.Branch` を持つステップ）を置いた場合は、分岐の値を見ない。糖衣の辺はすべて `"source"` で、メンバーは木の時と同じくすべて実行する（レビューでの指摘。値を見ると、後ろのメンバーが黙ってスキップされていた）。分岐するのは、手書きのグラフの中だけ。
- **入口の選択は手書きのグラフだけ。** 根が seq / par / cond の計画に `Entry` を指定すると、`ErrUnknownEntry` になる（コアでも、実行を失敗にする）。
- **後回しにしたもの。**
  - 可観測性の `step.skipped`: スキップはコアの中で、命令を出さずに起きるため、エンジンからは見えない。欠落しない実行イベントの出口（ADR 0028 で挙げた後続の ADR）を作るときに、そこで扱う。
  - graphon 0.7.0 との差分ハーネスによる一致の確認: ADR 0028 の作業として作る。
- **テスト:**
  - `TestBranchingActionInSugarRunsEverything`
  - `TestGraphBranchAndMerge`、`TestGraphAnyOrder`、`TestGraphEntries`、`TestGraphBadBranchValue`、`TestGraphSkippedValuesAreCleared`、`TestGraphCompileErrors`、`TestVersion1SnapshotMigrates`（core）
  - `TestGraphEntryAcrossRestart`（engine）
  - 既存のコアのテストは、変更なしですべて通った。
