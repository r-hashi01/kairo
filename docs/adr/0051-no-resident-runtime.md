# 0051. kairo は常駐するサーバーを前提にしない: コアを利用者のプロセスに埋め込み、DB だけを使う

- 状態: 承認
- 日付: 2026-10-07
- 関連: 不変条件 1〜9、ADR 0001（純粋なコア）、0002（シャード）、0005・0016（ログ）、0020（SQL の保存先）、0041（実行 1 回あたりのコスト）、0048（配り方）、0049（SDK）、0050（出力を残す）

## 背景

これまでの kairo は、常駐するサーバー（kairod）を前提にしてきた。

- エンジンは、シャードごとのイベントループ、タイミングホイール、メモリの索引を持ち、プロセスが動き続けることを前提にしている。
- SDK（ADR 0049）も、配り方（ADR 0048）も、kairod につなぐことを前提にしている。

しかし、常駐するサーバーを前提にすると、Dify が抱えている問題と同じ構造になる。

- 使っていない間も、サーバーを動かし続ける費用がかかる。Dify では、API、Celery のワーカー、Redis が常に動いている。
- 動かす・監視する・増やす手間が、利用者の側に残る。
- サーバーレスや、必要なときだけ動く環境（使わないときは 0 台まで縮む環境）に置けない。

kairo はランタイムなので、常に動いていなくても動くべきである。

一方、kairo の中心は、もともと常駐を必要としない。

- 実行は値である。待っている実行の費用は、状態のバイト数だけである。
- コアは純粋な関数 `Apply(計画, 状態, イベント) → 命令` で、I/O・時計・goroutine を持たない（不変条件 1）。
- 常駐が要るのは、コアを回すエンジンの部分（シャードのループ、タイマー、メモリの索引）だけである。

## 決定

kairo の基本の形を、**常駐するサーバーを持たない形**にする。コアを利用者のプロセスに埋め込み、状態とログは DB に置く。利用者が用意するインフラは DB だけにする。

常駐のプロセス（kairod）は前提にしない。ただし、常駐できる環境では、kairod を使うとランタイムをより上手く扱える（下の「常駐する kairod」）。

### 基本の形

- **埋め込むもの:** コア（`core`）とコンパイラ（`ir`）だけを埋め込む。どちらも I/O を持たない。
  - **Go:** そのままライブラリとして使う。
  - **TypeScript・Python:** コアとコンパイラを WASM（`GOOS=wasip1`、`//go:wasmexport`）にして、SDK に同梱する。WASM の側は、純粋な関数だけを出す（例: 計画のコンパイル、`apply(計画, 状態, イベント) → (新しい状態, 命令, トレース)`、状態の符号化）。
  - I/O（DB、HTTP、時計）は、すべてホストの言語の側（SDK）で行う。
- **保存先:** DB に置く。
  - 本番は PostgreSQL を最初の対象にする（MySQL などは後で）。
  - 手元とテストは SQLite（メモリの中でもよい）にする。
  - 表は、実行ごとの状態（コアの符号化そのもの）と、実行ごとのイベント（追記だけ）にする。
  - 1 つのイベントの適用は、1 つのトランザクションで行う: イベントを追記し、状態を置き換え、出てきた命令の記録を書く。
- **起動のきっかけ:** イベントごとに、ホストのプロセスが動く。イベントは次のとおり。
  - 実行の投入
  - アクションの完了
  - 信号
  - タイマーの時刻
  - 取り消し

  ホストは、普通のアプリのサーバー、サーバーレスの関数、CLI のどれでもよい。それぞれ次の順で処理する。
  1. 実行の借用を取る
  2. 状態を読む
  3. `Apply` を適用する
  4. 書き戻す
  5. 命令を実行する
- **借用（シャードの代わり）:** 同じ実行を、同時に 2 つのプロセスが進めないようにする。DB の行ロック（`SELECT ... FOR UPDATE`）か、期限付きの借用（リース）で、実行ごとに 1 つのプロセスだけが適用する。
- **タイマー:** 待ちに入るとき、起こす時刻を DB に書き、外部の仕組みに 1 回だけ「その時刻に起こせ」と頼む。
  - 頼む先: クラウドのスケジューラ（EventBridge Scheduler、Cloud Tasks、QStash など）、またはアプリのプロセスの中のタイマー（常駐しているアプリの場合）。
  - 待ち 1 つにつき登録 1 回で、ポーリングしない。
  - 起こし損ねに備え、起動時とイベントのたびに「時刻を過ぎた待ち」を拾う。
- **アクションの実行:** ホストが次のどれかで行う。
  - 同じプロセスで呼ぶ（既定）
  - HTTP で呼ぶ（サーバーレスの関数）
  - キューに積む
- **コードで書くワークフロー（ADR 0049）:** 呼ばれるたびに関数を頭から動かし直す。
  - 終わった呼び出しは、DB の記録から結果をすぐ返す。
  - 終わっていない最初の呼び出しに来たら、それを投入して戻る。
  - その呼び出しが終わったイベントで、もう一度動かし直す。
  - 常駐しているプロセスでは、戻らずに待ってもよい。

### 不変条件の扱い

- **1（純粋なコア）と 2（リプレイ）:** そのまま守る。埋め込むのはコアだけである。
- **3（適用したイベントはすべて順に記録する）:** 実行ごとのイベントの表に、適用と同じトランザクションで追記する。
- **4（実の命令は、耐久化した状態を根拠に出す）:** 意図を記録したトランザクションをコミットしてから、実の命令を実行する。
- **5（結果がわからない実の命令を、成功扱いしない）:** そのまま守る。
- **6（実行ごとの goroutine を持たない。ポーリングしない）:** プロセスはイベントで動き、タイマーは外部に 1 回だけ頼む。
- **7（書き込みは追記だけ）:** イベントの表は追記だけにする。状態の行の置き換えは、スナップショットの原子的な置き換えに当たる。
- **8（スナップショットは耐久化済みのものだけを含む）:** 状態とイベントを同じトランザクションで書くので、自然に満たす。
- **9（シャードの割り当ては再起動しても変わらない）:** 常駐しない形では、実行ごとの借用に置き換える。常駐する kairod では、今までどおりにする。

### 常駐する kairod

kairod は前提ではないが、常駐できる環境なら、ランタイムとしてより上手く扱える選択肢として残す。常駐のプロセスでしか上手くできないことがあるからである。

- **プロセスをまたぐ制御:** 宛先ごとの RPM・TPM、テナントの公平さ、同時実行の上限、適応的な同時実行（ADR 0039）。
  - 常駐しない形でも、DB で数えることはできる。しかし、サーバーレスの関数が多数並ぶと、正確さと費用（DB の往復）の両方で劣る。
- **速さ:** 遷移あたり µs、まとめた書き込み（group commit）、ステップの受け渡しの p99 1ms 以下。
- **ワーカーの取りに来る形と背圧:** クレジット制で、受け取れる分だけ渡す（ADR 0009）。
- **ライブ中継、精度の高いタイマー、実行イベントの出口（ADR 0034）。**

kairod は、同じコアを使い、同じ計画・同じ SDK の書き方で動く。どちらで動かすかは、SDK の設定で選べるようにする（同じ実行を両方から同時には扱わない）。始めは常駐しない形で使い、負荷が増えたら kairod に移る、という使い方ができるようにする。

### 性能の計測（利用者の依頼、2026-10-07）

WASM を配ることを確かめるため、試作して次を測る。試作はリポジトリに入れず、結果だけをこの ADR に書く。

- **コアの 1 イベントあたりの費用:** 状態の復号、`Apply`、状態の符号化を 1 組にして測る（常駐しない形では、イベントごとに状態を DB から読んで書くため）。
  - 比べるもの: ネイティブの Go、Node の上の WASM、Python の上の WASM。
- **実行 1 つあたりの費用（端から端まで）:** 5 ステップの実行を、SQLite（ファイル）に状態とイベントを書きながら進める。
  - 比べるもの: 常駐の kairod の値（README の実測値）。
- **WASM の大きさと、読み込みにかかる時間（コールドスタート）:** サーバーレスで効く。

#### 結果（2026-10-07、Apple M4 Max、load average 20〜25 で負荷あり）

試作は、`core` と `ir` を `GOOS=wasip1`・`-buildmode=c-shared` でビルドし、`//go:wasmexport` で関数を出したもの。ホストとの受け渡しは、イベントと命令を JSON、状態をコアの符号化のバイト列にした。

**WASM の大きさと読み込み**

| 項目 | 値 |
|---|---|
| 大きさ | 4.4MB（gzip で 1.2MB） |
| 読み込み（Node、`node:wasi`） | 約 21ms |
| 読み込み（Python、wasmtime） | 約 235ms（その場でコンパイルするため。コンパイル済みのものを保存すれば縮む見込み） |

**コアの 1 イベントあたりの費用**（状態の復号 → `Apply` → 状態の符号化。イベントと命令の JSON の変換を含む。5 ステップの実行を 2 万回回した）

| 動かし方 | 1 イベント | 実行 1 つ（6 イベント） |
|---|---|---|
| ネイティブの Go | 約 5µs | 約 30µs |
| Node の上の WASM | 約 20µs | 約 120µs |
| Python の上の WASM | 約 111µs | 約 670µs |

- Python が遅いのは、1 イベントごとに Python と WASM の間を 8 回ほど行き来するためと見ている（確保、書き込み、適用、解放、結果の読み出し）。受け渡しの回数を減らす余地がある。

**端から端まで**（常駐するサーバーなし。1 イベント = 1 トランザクション: 状態を読み、イベントを追記し、状態を書き戻す。1 プロセス）

| 構成 | 同時に流す数 | 1 秒あたりの実行数 | 実行 1 つの時間 |
|---|---|---|---|
| Node の WASM ＋ SQLite（ファイル、`synchronous=FULL`） | 1 | 約 2,400 | 0.42ms |
| Node の WASM ＋ SQLite（`synchronous=NORMAL`） | 1 | 約 4,100 | 0.25ms |
| ネイティブの Go ＋ PostgreSQL（手元の Docker） | 1 | 91 | 11ms（1 トランザクション約 1.8ms） |
| ネイティブの Go ＋ PostgreSQL | 16 | 458 | 35ms |
| Node の WASM ＋ PostgreSQL（`pg`） | 1 | 94 | 11ms |
| Node の WASM ＋ PostgreSQL | 16 | 463 | 35ms |
| Python の WASM ＋ PostgreSQL（psycopg、asyncio） | 1 | 85 | 12ms |
| Python の WASM ＋ PostgreSQL | 16 | 491 | 33ms |

- 比べる値として、常駐の kairod（README の実測値）は、5 ノードの実行あたりの CPU が約 50µs、ステップの受け渡しの p99 が 0.5ms 以下である。

**わかったこと**

- **WASM の費用は、DB の往復に比べて小さい。**
  - Node の上で、1 イベント約 20µs だった。
  - SQLite の 1 トランザクション（約 40〜70µs）とは同じくらい、PostgreSQL（約 1.8ms）の 1% ほどである。
  - WASM を配る形で問題ない。Python は受け渡しを減らす必要がある。
- **PostgreSQL では、ホストの言語によらず速さが同じだった。** Go、Node、Python のどれも、同時 1 で 85〜94 実行/秒、同時 16 で 458〜491 実行/秒だった。WASM の費用（Python でも 1 イベント約 0.1ms）は、トランザクション（約 1.8ms）に隠れる。
- **常駐しない形の速さは、DB で決まる。**
  - PostgreSQL では、遷移 1 つにトランザクションが 1 つ要るので、実行 1 つで数〜十数 ms かかる。
  - 1 プロセス 16 並行で、数百実行/秒にとどまる。
  - 常駐の kairod（まとめた書き込みと、メモリの中の遷移）とは、桁が違う。
  - LLM やツールの呼び出し（数百 ms〜秒）が主のワークフローなら、十分である。
  - 速さや、プロセスをまたぐ制御が要るなら、kairod を使う。これは「常駐する kairod」の位置づけのとおりである。
- **縮める余地（未着手）:**
  - トランザクションの中の文を 1 つにまとめる（CTE）。
  - 同じ実行の連続するイベントを 1 つのトランザクションにまとめる（保護ステップは、もともとイベントにならない）。
  - PostgreSQL を手元の VM でなく、同じネットワークに置く。

### 置き換える ADR

- **ADR 0048（kairod のバイナリを同梱して配る）:** この ADR で置き換える。配るのは「WASM のコアを含む SDK」になり、kairod の同梱は任意の付け足しにする。承認されたら、0048 の状態を「0051 により置き換え」にする。
- **ADR 0050（終わった実行の出力を残す、提案）:** 基本の形では、出力はもともと DB に残る。0050 は、kairod のための対応として位置づけ直す。

## 結果

- 利用者が用意するのは DB だけになる。使っていないときに動いているものはない。
- サーバーレス、普通のアプリ、CLI（KairoCode）のどれにも、同じ書き方で置ける。
- kairod なしでテストできる。テストでは、メモリの中の SQLite と埋め込んだコアで、本物の意味論のまま動かせる。偽物のつなぎ先を別に作る必要はない。
- **悪くなること:**
  - 遷移の速さは、DB の往復（ミリ秒）で決まる。常駐の kairod（µs）より遅い。速さや、プロセスをまたぐ制御が要る場合は kairod を使う。
  - WASM のコアの呼び出しは、ネイティブより遅い（それでも DB の往復よりは十分小さい見込み）。
  - SDK に、DB の保存先、借用、タイマーの登録、動かし直しの実装が入り、言語ごとの作業が増える。
- **形式:** DB の表の形式と、WASM が出す関数の形を、新しく決めて保つ。コアの状態の符号化（`codecVersion`）はそのまま使う。
- **テスト（足す）:**
  - WASM のコアが、Go のコアと同じイベント列から同じバイト列の状態を作ること（リプレイの一致）。
  - SQLite と PostgreSQL の両方で、次を確かめる。
    - 実行が終わること
    - 同じ実行を同時に進めないこと（借用）
    - 再起動（プロセスを捨てる）をまたいで再開すること
    - 実の命令が二重に実行されないこと
    - タイマーが時刻に起きること
  - 同じテストの一式を、常駐の kairod にも流し、2 つの形の振る舞いが一致することを確かめる。

## 検討した代替案

- **常駐する kairod を前提にしたまま、サーバーレスの関数から呼ぶ:** サーバーは常に動いている必要があり、Dify と同じ問題が残る。
- **エンジン全体を、言語ごとに書き直す（TypeScript・Python で）:** コアの意味論が言語ごとに分かれ、リプレイの一致を保てない。純粋なコアを 1 つにして、WASM で共有する方が確かである。
- **Go の共有ライブラリとして埋め込む（`c-shared`）:** Go のランタイムがホストに同居し、プラットフォームごとのビルドが要る。WASM は 1 つの成果物で、どの OS・どの言語でも動き、サンドボックスの中で動く。
- **ホストの側でエンジン全体（goroutine とタイマーを含む）を WASM で動かす:** 常駐が前提の部分まで持ち込むことになる。埋め込むのは純粋なコアだけで足りる。

## 実装で詰めた詳細（2026-10-07 追記、ADR 0017）

### 段階 1: WASM のコア

- **`wasmcore` パッケージ:** 計画のコンパイルとイベントの適用を、バイト列の入出力で包む。I/O を持たない。Go のホストは、これを直接使える。
  - `Register(ノードの仕様の JSON の配列)`
  - `Compile(定義の JSON) → {plan, name, hash, has_real, effects}`
  - `Apply(plan, 実行 ID, 状態, イベントの JSON, traced) → (新しい状態, 結果)`
- **ホストとの取り決め（ABI、`wasmcore.ABIVersion` = 1）:** イベント・命令・トレースは、Go の項目名に依存しない JSON にした。コアの型の名前が変わっても、取り決めは変わらない。
  - 項目は snake_case にした。
  - 種類は名前で表す。イベントは `start`、`step_ok`、`step_err`、`timer`、`signal`、`intent`、`recover`、`resolve`、`cancel`、`step_wait`。命令は `dispatch`、`timer`、`cancel_timer`、`abort`、`review`、`done`。
  - 状態は、コアの符号化（`codecVersion`）そのものを使う。
- **命令に足したもの:** 計画のノードの ID と、ディスパッチのアクションと作用（`effect`）を付けた。ホストは、作用を見て、実の命令を意図の耐久化まで保留する（不変条件 4）。
- **無視されたイベント:** コアが無視したイベント（`ErrIgnored`）は、結果に `ignored: true` を付けて返す。状態はそのまま返す。ホストは、このイベントを記録しない（不変条件 3）。
- **結果のその他の項目:** 実行の状態（`status`、`output`、`error`）と、`quiescent`（動いているものがなく、待っているだけ。ホストがメモリから外してよい）を返す。
- **`cmd/kairo-wasm`:** `wasmcore` を WASM から出す入口。`GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared` でビルドする。
  - 外に出す関数: `kairo_abi_version`、`kairo_alloc`、`kairo_free`、`kairo_register`、`kairo_compile`、`kairo_apply`、`kairo_result`。
  - 答えは 1 つの結果のバッファに書き、長さを返す。負の長さはエラーで、バッファにはその文言が入る。
  - ホストが渡すポインタは、`kairo_alloc` で確保したものに限る（確保したバッファの表から引く。整数をポインタに変えない）。
  - 手元の OS では、空のプログラムとしてビルドされる（vet と build が通るように）。
- **検査:** `scripts/check.sh` に、WASM 向けの vet（`cmd/kairo-wasm`、`wasmcore`、`core`、`ir`）とビルドを足した。
- **テスト（`wasmcore/wasmcore_test.go`）:**
  - `TestApplyMatchesTheCore`: `wasmcore` を通した状態が、コアを直接呼んだ状態とバイト列まで一致すること。終わった実行へのイベントが `ignored` になり、状態が変わらないこと。
  - `TestWASMMatchesNative`: WASM をビルドして Node で動かし、同じイベント列から、ネイティブと同じ状態のバイト列を作ること。Node がない環境と、`-short` では飛ばす。
  - どちらも、map、実のステップ（意図を含む）、待ちの結果（ADR 0045）とそのタイマー、信号を通ることを確かめている。
