# 0027. 終わった実行の記録を期限つきで永続化し、再起動をまたいで冪等にする

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR5, FR6 / ADR 0016, 0021, 0023

## 背景

ADR 0023 で、`RunID` を冪等キーにした。ただし、終わった実行を覚えているのは、メモリ上の終了済みキャッシュ（`Config.RecentRuns`）だけである。

- プロセスが再起動すると、キャッシュは消える。
- 終わった実行のログ記録は、圧縮（ADR 0016）で退役し、スナップショットも消える。
- そのため、再起動の後に同じ `RunID` で `Submit` すると、終わったはずの仕事がもう一度始まる。
  - たとえば、呼び出し側がタイムアウトで再試行していて、その間にデーモンを入れ替えた場合である。
  - 実の効果（メール送信、課金など）を持つプランでは、これは二重実行になる。

## 決定

### 終了マーカーと終了ログ

- 終わった実行ごとに、小さな**終了マーカー**を残す。中身は `RunID`、終了時刻、終了状態（成功・失敗・取り消し）である。出力は含めない。
- マーカーは、シャードごとの**終了ログ**に追記する。
  - 終了ログは、普通のログと同じ `wal.Sink` である。そのため、ファイル、SQL、暗号化（ADR 0021）、フェンシングが、そのまま使える。
  - 既定（ファイル形式）では、`DataDir/shard-NNN/` に、接頭辞 `done` のセグメントとして置く。
  - `Config.DoneLogs func(shard int) (wal.Sink, error)` で差し替えられる。`sqlstore.NewBackend` はこれも埋める（ログ名 `done`）。
  - 耐久性ティアが file 以上の実行だけを対象にする。none と memory の実行は、もともと再起動で消えるので、マーカーも残さない。
- 書く時点は、シャードの終了処理のジョブ（`shard.finish` が I/O プールに出すもの）の最初である。
  - マーカーが耐久化してから、ブロブとスナップショットを消し、実行のピンを外す。
  - ピンがある間は、実行の記録は退役しない。そのため、「記録は退役したがマーカーはない」という状態は起きない。
  - 追記は group commit され、シャードのループは待たない。
- 回復では、終了ログを読んで、期限内のマーカーをメモリの索引に戻す。
  - 普通のログに残っていて、終わっているがマーカーがない実行（終了直後のクラッシュ）にも、マーカーを書き直す。

### 期限と回収

- `Config.IdempotencyTTL`（既定 24 時間）を過ぎたマーカーは、冪等性の判定に使わない。
  - TTL を過ぎた後の同じ `RunID` は、新しい実行として始まる（ADR 0016、0023 の RunID 再利用と同じ扱い）。
  - 負の値を指定すると、終了マーカーを書かない（今の振る舞い）。
- 終了ログは時刻順に追記されるので、古いものから退役できる。
  - 新しいマーカーを追記するときに、TTL を過ぎた接頭辞があれば `Retire` する（ポーリングしない。圧縮と同じく、追記を契機にする）。
  - 追記が止まると古いマーカーが残るが、判定では TTL を見るので害はない。次の追記か次の起動で消える。
- メモリの索引は、`RunID` → (終了時刻, 状態) の小さなマップで、シャードごとに持つ。
  - 上限 `Config.IdempotencyMax`（既定 1,000 万件。1 件あたり 100 バイト程度）を超えたら、古いものから捨てて、警告を出す。捨てた範囲は、冪等性の保証から外れる。

### Submit と Get

- `Submit` は、次の順に調べる。どれかに当たれば、新しい実行を作らず `Existing` を返す。どれもディスクを読まない。
  1. 終了済みキャッシュ（今と同じ）
  2. 終了マーカーの索引
  3. シャードの実行中の実行（今と同じ）
- `Get` は、キャッシュになく、マーカーだけがある実行について、状態と終了時刻だけを返す（`RunInfo.Output` は空、`RunInfo.Trimmed = true`）。
  - HTTP の `GET /v1/runs/{id}` も同じで、`"trimmed": true` を付ける。
  - `POST` が 200（既存）を返したのに `GET` が 404、という食い違いをなくすため。

## 結果

- RunID を決めて再試行する呼び出し側は、再起動をまたいでも、TTL の間は二重実行にならない。
- 悪くなること:
  - 実行の終了ごとに、終了ログへの追記が 1 件増える（group commit される。ファイル形式なら、終了処理で消すスナップショットやブロブの I/O と比べて小さい）。
  - 起動時に、終了ログを読む時間が増える（1 日 100 万実行で 24 時間なら、100 万件、数十 MB）。
  - メモリが、期限内のマーカーの分だけ増える。
  - `Config.Sinks` を自前で差し替えていて `DoneLogs` を渡さない場合は、終了ログをファイル形式で `DataDir` に置く。`DataDir` もなければ、マーカーはメモリだけになり、起動時に警告を出す。
- テスト:
  - 実行を終わらせ、圧縮で記録を退役させてから再起動する。同じ RunID の `Submit` が `Existing` になり、`Get` が状態を返す。
  - 時刻（`Config.Now`）を TTL より進めると、同じ RunID で新しい実行が始まる。終了ログの古い接頭辞が退役している。
  - 終了処理のジョブの途中（マーカーの耐久化の前後）で止めて再起動しても、終わった実行が再び始まらない。
  - SQL バックエンドと暗号化の組み合わせでも、上と同じ結果になる（各バックエンドのテストに足す）。
  - 索引が上限を超えると、古いものから捨てられ、警告が出る。

## 検討した代替案

- マーカーを、スナップショットの置き場（`blob.Store`）に `done/<RunID>` として置く: `Submit` のたびに、キャッシュに外れると 1 回の読み出し（SQL なら往復）が要る。また、ブロブの置き場には列挙がないので、期限切れのものを回収できない。
- マーカーを普通のログに書き、圧縮のチェックポイントで先へ運ぶ: 圧縮は頻繁に走るので、TTL の間に同じマーカーを何千回も書き直すことになる。
- 普通のログの退役を、TTL の間だけ遅らせる: 実行中の実行の記録まで TTL の間残る。ログの大きさと回復時間が、TTL に比例して増える。
- 呼び出し側の責任にする（実行 ID を外部の DB で管理してもらう）: 冪等性は、実の効果を持つ仕事を安全に再試行するための基本の機能である。外部の仕組みに任せると、多くの利用者が同じものを作ることになる。

## 実装で詰めた詳細（2026-10-02 追記、ADR 0017）

- 終了ログの既定の置き場は、普通のログと同じ `DataDir/wal/` で、接頭辞は `done-NNN` にした（`shard-NNN` にすると、普通のログのセグメントの glob に一致してしまうため）。
- 終了ログへの追記は、普通のログと同じく、シャードのループがバッファに積んでコミッタに渡す（I/O プールからは書かない）。耐久化の通知（`mDoneAck`）で、終了処理のジョブを I/O プールに出す。
- 終了ログの書き込みが失敗したら、そのシャードの終了処理のジョブは止まったままになる（スナップショットとログの記録は残るので、終わった実行が忘れられることはない）。`Stats.FailedLogs` に数える。
- 索引への追加は、終了した時点で行う（耐久化を待たない）。メモリの終了済みキャッシュと同じ扱い。
- 同じ RunID で新しい実行が始まったら（TTL を過ぎた後）、古いマーカーを索引から消す。`Get` や `Wait` が、動いている実行について古いマーカーを返さないようにするため。回復でも、生きている実行の ID は索引から消す。
- 回復で、終わっているのにマーカーがない実行を見つけたら、ループを始める前に終了ログへ直接書いて耐久化し、それからスナップショットとブロブを消す。
- 終了ログの退役は、期限切れのマーカーが `markerRetireEvery`（1024）件たまるごとに行う。
- `RunInfo` に `Trimmed` と `FinishedAt` を足した（`finished_at` は `omitzero`）。
- `sqlstore.Backend` に `DoneLogs` と `Configure(*engine.Config)` を足した。`store/sqlite` には `DoneLogs(dir)` を足した。
- `kairod` に `-idempotency-ttl` フラグを足した。
- エンジンの索引は、`doneIndex` だけをロック（`RWMutex`）で守る。シャードのループは、マップの操作の間だけそのロックを持つ。
- レビューで見つかった点を直した。
  - 回復でマーカーを書き直すとき、時刻は再起動の時刻ではなく、その実行の最後のイベントの時刻にする。TTL を過ぎていれば書かない。再起動のたびに TTL が延びないようにするため。
  - 回復で、実行の開始より古いマーカーは、同じ ID の前の実行のものとみなし、マーカーがないものとして扱う。
  - 期限切れのマーカーは、4096 件ずつロックを取り直して捨てる。長く止まった後の最初の終了で、`Submit` などを長く待たせないため。警告のログもロックの外で出す。
- 終了ログが壊れたとき（書き込みが失敗したまま）の影響。決定どおり「忘れずに止める」側に倒している。
  - そのシャードで終わった実行は、ピンと状態を持ったままメモリに残り、普通のログも退役しなくなる。メモリとログは、エンジンを再起動するまで増え続ける。
  - TTL を過ぎた ID の再利用の `Submit` は、ピンが外れるのを待つので、`ctx` が切れるまで返らない。
  - 運用では `Stats.FailedLogs` を監視し、0 でなくなったら原因を直して再起動する。
- テスト:
  - `TestRecoveryKeepsFinishTime`
  - `TestIdempotencyAcrossRestart`、`TestMarkersExpireAndRetire`、`TestMarkerWrittenOnRecovery`、`TestMarkerCap`、`TestEncryptedMarkers`（engine）
  - `TestRunIDReuseSurvivesRestart` は、時計を TTL より進めてから同じ ID を再利用するように変えた。
  - SQL の共通シナリオ（`sqltest`）に、記録が退役した後の再起動で、同じ RunID が既存として扱われ、大文字小文字だけ違う ID は別の実行になることを足した。
