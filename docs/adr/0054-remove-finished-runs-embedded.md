# 0054. 埋め込みのランタイムは、終わった実行を、それを含む実行ごとまとめて、冪等の期間の後に消す

- 状態: 承認
- 日付: 2026-10-08
- 関連: 不変条件 7、ADR 0027（終わった実行のマーカーと冪等の期間）、0041（実行 1 回あたりのコスト）、0049（コードで書く API）、0050（kairod で出力を残す）、0051（常駐しない kairo）、0053（スケジューラーの差し込み口）

## 背景

埋め込みのランタイム（ADR 0051）は、実行ごとに、実行の行（状態・入力・出力）とイベントの行を DB に書く。終わった実行のタイマーと借用は消すが、実行の行とイベントは消さない。

- そのため、DB が際限なく伸びる。サーバーレスで長く動かすほど、表と索引が大きくなり、書き込みも遅くなる。
- kairod は、終わった実行を冪等の期間（`IdempotencyTTL`、既定 24 時間）だけ覚え、その後は忘れる（ADR 0027）。埋め込みには、その対応物がない。

消すときに気をつけることが 2 つある。

1. **コードで書くワークフローは、終わった呼び出しの結果を頼りに再開する（ADR 0049）。**
   - 呼び出し 1 つが、実行 1 つである。ID は `<ワークフローの ID>/<キー>` である。
   - 動き続けているワークフローの呼び出しを先に消すと、再開したときに同じ呼び出しをもう一度動かしてしまう。外に作用するアクションが二重に動く。
   - kairod の側では、これを避けるため、開始から冪等の期間を過ぎたワークフローの再開を `ResultLostError` で止めている。そのため、1 日以上シグナルを待つワークフローは、kairod では再開できない。
2. **消した ID は、新しい実行として受け付けることになる。**
   - ワークフローの実行だけを消して、その呼び出しが残っていると、同じ ID でワークフローを投入し直したときに、前回の呼び出しの結果を拾ってしまう。

## 決定

終わった実行を、**それを含む実行（親）ごとの木の単位で、1 つのトランザクションで消す**。木の根が終わってから冪等の期間が過ぎたら、木の中の実行が終わっているかどうかによらず、木ごと消す。

### 親を記録する

- 実行の行に、列 `parent`（文字列、空を許す）を足す。実行を作るときに、作った側が渡す。
  - `Embedded.run(plan, input, { runId, vars, parent })`。SDK のコードで書く API は、呼び出しと子のワークフローに、それを呼んだワークフローの ID を渡す。
  - グラフの API（`parent` を渡さない実行）は、それだけで木の根になる。
- 列 `parent` の索引を足す。

### 消す条件

次をすべて満たす木を消す。

- 根（`parent` が空か、`parent` の実行がもうない）が、終わっている（`completed`・`failed`・`cancelled`）。
- 根の終わった時刻（`updated_at`。終わった実行の行は、もう書き換わらない）が、`now - keepFinished` より前である。
- 木の中に終わっていない実行（待っているもの、要確認のもの、動いているもの）があっても、根が終わっていれば消す。
  - 根が終わった時点で、その木の仕事は終わっている。待たれずに残った呼び出しや、要確認の呼び出しを残し続けると、木がいつまでも消えない。
  - 要確認の記録が要る利用者は、期間のうちに見るか、期間を延ばす。

消すのは、木の中の実行の行・イベントの行・タイマーの行・借用の行である。

- 終わっていない実行のステップが、別の場所でまだ動いていることがある（借用の持ち主のプロセス、HTTP のアクション）。その結果が後から届いても、実行がもうないので何もしない（結果の適用は、実行の行がなければ捨てる）。

木は、`parent` をたどる再帰の問い合わせ（`WITH RECURSIVE`。SQLite と PostgreSQL の両方にある）で集める。

- 1 つの木を、1 つのトランザクションで消す。途中までしか消えない状態（ワークフローは消えたが呼び出しが残る）は作らない。背景の 2. の問題は、これで起きない。
- 根の行をロックしてから、もう一度、条件を確かめる。並んで消そうとしたプロセスや、同じ ID の投入と、ぶつからないようにする。

### いつ、誰が消すか

- `tick()` と、作業のついでの掃除（ADR 0051 の段階 3a。借用の期間に 1 回まで）で行う。
  - 1 回に消す木の数に上限を置く（既定 100）。残りは、次の `tick()` で消す。
- 常駐するスレッドもポーリングも足さない（ADR 0041）。仕事がなくて DB が伸びないあいだは、消す必要もない。
- 次に起こす時刻（ADR 0053 の `nextWake()`）には含めない。消すことは急がないので、ほかの理由で起きたときについでに行う。

### 期間

- `EmbeddedOptions.keepFinished`（ms、既定 24 時間。Python は `keep_finished`）で指定する。`Infinity`（Python は `None`）なら消さない。
- 設定で渡さなければ、環境変数 `KAIRO_KEEP_FINISHED` を読む。値は `30m`、`24h`、`7d` の形の期間、または `forever` である。サーバーレスでは、コードを変えずに環境ごとに変えられるようにするためである。
  - 優先の順は、設定、環境変数、既定（24 時間）である。読めない値なら、開くときにエラーにする。
- 索引: 終わった実行の `updated_at` に、部分索引（`WHERE status IN ('completed','failed','cancelled')`）を足す。根の候補を、全件を走査せずに探すためである。

### 冪等と `ResultLostError`

- **消した ID の扱い:** ADR 0027 と同じく、新しい実行として受け付ける。
- **埋め込みでは、再開を期間で止めない:** 動き続けているワークフローの呼び出しは、ワークフローが終わるまで消えない。そのため、何日シグナルを待っても、終わった呼び出しの結果を受け取って再開できる。
  - 埋め込みでは、開始から冪等の期間を過ぎたワークフローを `ResultLostError` で止める確認をしない（今もバックエンドが `vars` を返さないので、実際には効いていない）。これを仕様として明記する。
  - kairod をバックエンドにしたときは、今までどおり止める（ADR 0050 で扱う）。

### 費用（ADR 0041）

- 実行 1 回あたりに増えるのは、作るときの `parent` の索引への書き込みと、終わるときの部分索引への書き込みである。どちらも、保存をいつまでも伸ばさないための「状態の耐久化」の仕事の一部とみなす。
- 消すときに、木 1 つあたり 1 つのトランザクションが増える。

### 形式

- 表 `run` に列 `parent` を足し、索引を 2 つ足す。
- SDK はまだ配布していないので、既存の DB の移行は、起動時の `ALTER TABLE ... ADD COLUMN`（列がないときだけ）と `CREATE INDEX IF NOT EXISTS` で行う。移行の前に作られた実行は、`parent` が空なので、それぞれが根として扱われる（呼び出しが、そのワークフローより先に消えることがありうる。開発中の DB に限った話なので、これを許す）。

## 結果

- 埋め込みの DB の大きさが、冪等の期間の中で終わった実行と、動いている実行の分に抑えられる。
- 長く待つワークフロー（何日も人の承認を待つエージェントなど）を、埋め込みでは期間に縛られずに再開できる。
- **新しく守ること:**
  - 木は丸ごと 1 つのトランザクションで消し、部分だけを消さない。
  - 根が終わる前の木は、期間を過ぎても消さない（動き続けているワークフローの呼び出しを守る）。
- **テスト（足す、TypeScript と Python の両方）:**
  - 期間を過ぎて終わったワークフローは、その呼び出しと一緒に消え、イベントも残らないこと。期間の前は残ること。
  - 動き続けているワークフローの、終わった呼び出しは、期間を過ぎても消えず、再開で結果を返すこと（呼び出しは二度動かない）。
- 根が終わっていれば、終わっていない子孫（シグナルを待つもの、要確認のもの）を含む木も、期間の後に、タイマーと借用ごと消えること。消えた実行に後から届いた結果は、何もしないこと。
- `KAIRO_KEEP_FINISHED` で期間を変えられること。設定が環境変数より優先されること。読めない値はエラーになること。
  - 消した ID でワークフローを投入し直すと、新しい実行として最初から動くこと。
  - `parent` を渡さない実行（グラフの API）は、単独で消えること。
  - 1 回の掃除で消す数の上限を守ること。
  - 列のない古い表を開くと、列と索引が足されること。

## 検討した代替案

- **実行ごとに、終わってから期間が過ぎたら消す（木を見ない）:** 動いているワークフローの呼び出しが消え、再開で二重に動く。あるいは、kairod と同じく、期間を過ぎたワークフローの再開を止めることになり、長い待ちができない。
- **ID の `/` から親を求める:** 利用者が渡す ID にも `/` が入りうるので、親子と区別できない。また、SQL で「最後の `/` より前」を求める書き方が、製品ごとに違う。
- **イベントだけ消して、実行の行は残す:** 行は小さくなるが、数は際限なく増える。冪等の期間の後も ID を覚え続けることになり、kairod の約束（ADR 0027）とも合わない。
- **専用の掃除の処理（cron）を利用者に用意させる:** スケジューラーの設定が 1 つ増える。`tick()` はすでに呼ばれるので、そのついでに行えば足りる。
- **消す代わりに別の表（保管庫）へ移す:** 保管が要る利用者は、ADR 0034 の実行イベントの出口のような仕組みで外へ流すほうがよい。この ADR では、残す期間を決めることに絞る。

## 実装で詰めた詳細（2026-10-08 追記、ADR 0017）

TypeScript（`sdk/ts/src/store.ts`、`embedded.ts`、`backend.ts`、`workflow.ts`）と Python（`sdk/python/kairo_worker/` の同名のファイル）に入れた。

- **ストアの操作:** `removeFinished(cutoff, limit)`（Python は `remove_finished`）を足した。消した木の数を返す。
  - 根の候補を古い順に `limit` 件まで選び、木ごとに 1 つのトランザクションで消す。
  - トランザクションの中で、根であることを ID で確かめ直す（SQLite は `BEGIN IMMEDIATE`、PostgreSQL は根の行を `FOR UPDATE` でロックしてから）。
  - 消す順は、イベント・タイマー・借用・実行の順にした。木は `parent` をたどって集めるので、実行の行を最後に消す。
  - 再帰の問い合わせは `UNION`（`UNION ALL` ではない）にした。`parent` が輪になっていても止まる。
- **期間の設定:**
  - TypeScript: `EmbeddedOptions.keepFinished`。値は ms で、`Infinity` なら消さない。
  - Python: `Embedded(..., keep_finished=...)`。値は ms で、`None` なら消さない。省略は `"env"` で表し、そのときは環境変数を読む。
  - 環境変数 `KAIRO_KEEP_FINISHED` は、`ms`・`s`・`m`・`h`・`d` の単位の期間か、`forever` を受ける。それ以外はエラーにする。読む関数は、`keepFinished()` / `keep_finished_ms()` として公開した。
- **掃除の時機:** `tick()` の終わりに 1 回、`REMOVE_PER_TICK`（100）件まで消す。作業のついでの掃除も `tick()` を呼ぶので、同じく消す。
- **移行:**
  - SQLite: `PRAGMA table_info` で列を確かめ、なければ `ALTER TABLE ... ADD COLUMN parent TEXT` を行う。
  - PostgreSQL: `ADD COLUMN IF NOT EXISTS` を使う。
  - 索引は、列を足した後に作る。
- **ワークフローの層:**
  - 呼び出し（`ctx.call`、`waitFor`、`sleep` など）と子のワークフローに、それを呼んだワークフローの ID を `parent` として渡す。
  - バックエンドに `keepsCalls`（Python は `keeps_calls`）を足した。埋め込みでは `true` にし、そのときは開始からの期間で再開を止める確認（`ResultLostError`）をしない。kairod のバックエンドは `parent` を受けても使わない。
- **消えた実行への結果:** 後から届いた結果（`complete`、タイマー、借用の期限切れ）は、実行の行がないので何もしない。今の `process` の振る舞い（行がなく、開始でもない出来事は捨てる）のままでよかった。
- **テスト:** `sdk/ts/src/retention.test.ts` と `sdk/python/tests/test_retention.py`（それぞれ 5 件）。
  - 終わったワークフローが、呼び出しと子のワークフローごと、期間の後に消える。期間の前は残る。消えた ID の投入は、新しい実行として最初から動く。
  - シグナルを 3 日待つワークフローの、終わった実のアクションの呼び出しが残り、再開で二度動かない。
  - 終わった根の下の、待っている実行・動いているステップ（タイマーと借用を持つ）が、木ごと消える。後から届いた結果は何もしない。
  - `parent` のない実行は単独で消える。上限を守る。列のない古い表に列が足される。
  - 期間の設定の優先の順と、読めない値のエラー。
  - PostgreSQL での木ごとの削除と列の追加も、両方の言語で手元で確かめた。
