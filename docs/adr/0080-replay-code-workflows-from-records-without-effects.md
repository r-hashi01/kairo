# 0080. 記録だけのリプレイは保存済みの呼び出しだけを読み、作用も実行状態も変えない

- 状態: 提案
- 日付: 2026-11-13

## 背景

コードで書くワークフローは、停止後に関数を先頭から動かし直し、以前と同じ呼び出し ID にある結果を返すことで再開する。通常の再開は仕事を続けるための処理なので、記録にない呼び出しへ到達すれば新しい子の実行を作り、未完了の呼び出しへ到達すれば借用や timer を回復して完了を待つ。

一方、過去のセッションを調べる用途では、保存された入力と呼び出し結果だけを使って同じコードの経路をたどりたい。アクションをもう一度呼ばず、待ちを進めず、実行の状態を変えずに、どの呼び出しへどの順で到達したかと、記録がどこまで存在するかを知る必要がある。とくに、外へ作用する呼び出しを含むワークフローでは、調査のためのリプレイが通常の再開へ入り、新しい呼び出しを作ることを許せない。

埋め込みランタイムの保存先は、コードワークフローの入力、開始時の版、親子関係、各呼び出しの状態と結果を、根の実行の保存期間が終わるまで保持する。子の一覧を読むだけでも記録は列挙できるが、動的な条件分岐、同じアクションの複数回の呼び出し、並列の枝について、現在登録されている関数がどの記録へ到達するかは復元できない。テスト用の環境には子を呼び出しとして整形する読み取りがあるが、通常の SDK には、利用者の関数を記録だけで評価する経路がない。

kairod の終了記録は、冪等性を守るための印と、指定された場合の出力を保持するが、終了後のコードワークフローについて入力、版、子の結果を一つのリプレイ記録として保持する契約ではない。したがって、実行 ID だけから過去の関数を記録だけで評価できる範囲は、埋め込みランタイムが木を保持している期間と一致しない。

## 決定

### 決定項 1（記録だけのリプレイを通常の再開から分離する）

Go・TypeScript・Python のコードワークフロー SDK に、既存の実行を記録だけでリプレイする読み取り専用の経路を設ける。この経路は、保存されたワークフロー名、入力、開始時の版を読み、その名前と版に登録された関数を先頭から評価する。

記録だけのリプレイは、通常の実行や再開の経路を呼ばない。駆動の借用を取らず、実行を開始・回復・完了・失敗・取り消しにせず、signal、resolve、timer、lease、子の作成を行わない。アクションの handler と子ワークフローの関数も起動しない。保存先に対する操作は、対象の根と、関数が到達した呼び出しの読み取りに限る。

開始時の版の関数が登録されていなければ、現在の版へ置き換えずに停止する。同じ版の関数を後から別の内容へ変えた場合、リプレイはその変更後のコードを評価しうる。版の内容を保存または検証する仕組みは新設せず、版を変えずに関数を変えないという既存の規則を適用する。

この読み取り専用の保証は、SDK を通る呼び出しに適用する。利用者のワークフロー関数そのものを sandbox に入れないため、関数が SDK を介さずファイル、ネットワーク、時計などへ触れれば、その処理までは防げない。ワークフロー関数を決定的に書き、外の作用を型付きの呼び出しへ分ける既存の規則を、記録だけのリプレイにも適用する。

### 決定項 2（呼び出しは同じ ID の終端記録だけから再現する）

リプレイ中のアクション、signal の待ち、sleep、子ワークフローは、通常実行と同じ入力の正規化と出現回数から同じ呼び出し ID を求め、その ID の記録だけを読む。

- 完了した呼び出しは、記録された出力を返す。
- 失敗または取り消しで終わった呼び出しは、通常の再開が同じ記録から作る失敗または取り消しを関数へ返す。関数がそれを扱う分岐も、通常のコードと同じように評価できる。
- 記録がない、まだ終わっていない、要確認で止まっている、または結果がすでに失われた呼び出しでは、新しく実行したり完了を待ったりせず、リプレイの境界として停止する。境界には少なくとも、呼び出し ID、種類、名前、確認できた状態を含める。

リプレイの境界は、ワークフローが扱うアクションの失敗とは分ける。関数が広い例外処理で境界を受け取っても、SDK はそれをリプレイ全体の停止として返し、境界より後を「記録から再現できた」とは扱わない。

並列の枝には、保存された一つの全順序があるとはみなさない。各枝は通常と同じ呼び出し ID で記録へ対応し、複数の枝が境界へ同時に到達したとき、どの境界を先に報告するかは公開上の順序保証にしない。

### 決定項 3（到達した呼び出しと手元の評価結果を診断結果として返す）

記録だけのリプレイは、その評価で到達した呼び出しを、呼び出し ID、種類、名前、記録された状態と結果を含む一時的な列として利用者へ公開する。現在の関数が到達しなかった子を、保存先に存在するという理由だけで列へ加えない。並列の枝の観測順は耐久的な実行順序とはみなさず、順序を必要とする利用者は呼び出し ID と親子関係も使う。

子ワークフローは、親のリプレイでは一つの保存済み呼び出しとして扱い、その記録された結果を親へ返す。子の内部を調べる場合は、その子の実行 ID を対象に別の記録だけのリプレイを行う。これにより、一つのリプレイが同じ子の内部を暗黙に重複して列挙せず、どの実行を調べているかを明確にする。

関数が境界なしで戻るか失敗した場合は、その手元の評価結果も診断結果に含めるが、保存された根の終端結果を置き換えない。保存された実行の状態と出力が正典であり、手元の評価との差は、同じ版のコードや決定性が変わったことを調べる材料にする。リプレイは差を実行の成功・失敗として記録しない。

### 決定項 4（埋め込みランタイムが木を保持する期間に適用する）

記録だけのリプレイは、コードワークフローの根の入力、版、子の状態と結果を一つの木として読める埋め込みランタイムに適用する。メモリの保存先と SQL の保存先で同じ意味にする。根の木が保存期間の後に削除された場合は、記録がないとして返し、同じ ID で新しい実行を作らない。

kairod はこの ADR の適用範囲から外す。kairod で同じ能力を提供するには、終了後も入力、版、親子、各結果を一つの記録として読める保持契約を別の ADR で決める。グラフの実行も、コードの関数と呼び出し ID を再評価する対象ではないため、この経路の対象外とする。

コアの状態、イベントと命令、IR、ログ、ワーカープロトコル、保存先の表は変えない。記録だけのリプレイのための耐久記録、常駐する listener、polling、実行ごとの背景処理を足さない。費用は、利用者が明示してリプレイしたときに、その関数が到達した記録を読む分だけ発生する。

### この ADR で決定しないこと

- 三つの SDK の関数名、診断結果と境界エラーの型、到達した呼び出しを callback・iterator・戻り値のどれで公開するかは、SDK の公開 API 文書と実装に委ねる。
- 記録だけのリプレイを対話的に一呼び出しずつ進める debugger、途中のローカル変数の保存、任意の地点への巻き戻しは、対象とする要求ができたときの別の Issue と ADR に委ねる。
- 保存期間を越える監査用 archive と、削除済みの木の復元は、保存と監査の要件を扱う別の ADR に委ねる。
- ワークフロー関数を任意のファイル・ネットワークアクセスから隔離する sandbox は、SDK の実行環境に関する別の要件に委ねる。
- kairod とグラフの実行の record-only replay は、決定項 4 の保持契約を決める別の ADR に委ねる。

## 結果

- 良い影響: 過去のコードワークフローを、アクションや待ちを進めずに、保存済みの呼び出しへ対応させて調べられる。
- 良い影響: 記録にない呼び出しへ到達しても新しい実の作用を起こさず、その地点を明示して停止できる。
- 良い影響: コア、ログ、表を増やさず、三つの SDK が同じ保存済みの木を読み取れる。
- 悪い影響: 対象の関数を実際に評価するため、利用者が決定性の規則に反して関数へ直接書いた作用までは防げない。
- 悪い影響: kairod と、保存期間を過ぎて削除された埋め込みの実行には使えない。
- 悪い影響: 一回のリプレイで読む量は到達した呼び出し数に比例し、並列の呼び出しに耐久的な全順序を与えない。
- 中立な影響: リプレイで計算した結果は診断用であり、保存済みの実行結果、一覧、親子の状態、保持期限を変えない。
- 新しく守る制約: record-only の経路から実行を開始・回復・決着させない。呼び出しは同じ ID の終端記録だけから返し、記録不足は作用させず境界として返す。開始時の版以外へ黙って切り替えない。

## 検討した代替案

- アクションの handler を、記録した結果を返す handler に差し替えて通常の再開を使う: すべての handler を正しく差し替える必要があり、記録にない呼び出しの開始、未完了の呼び出しの回復、終了状態の更新を通常の経路が行いうる。
- 親の子を一覧し、作成時刻などで並べて表示するだけにする: 保存された子は見えるが、現在の関数がどの条件分岐でどの呼び出しへ到達するか、同じ種類の何回目に対応するかを再現しない。
- 子ワークフローを親から再帰的にすべてリプレイする: 一つの呼び出しの表示が暗黙に木全体へ広がり、同じ子を個別に調べたときと重複する。親では保存済みの一呼び出しとして扱い、内部はその実行 ID で明示して調べる。
- 記録にない非保護の呼び出しだけは実行する: 外に作用しない宣言でも、調査結果が保存記録だけから得られなくなり、待ちや子の開始との境界も複雑になる。作用の型にかかわらず実行しない。
- コアのイベント列を別の状態へ適用してコードワークフローをリプレイする: コアのイベントは各子のグラフ実行を再現できるが、SDK の関数の条件分岐と呼び出し順は記録していない。コードの関数と既存の子の記録を対応させる目的には、SDK 側の読み取りで足りる。

## 関連する ADR

- ADR 0049 の決定項 2（コードで書くワークフローの API）: 同じ呼び出し ID から保存済みの結果を返す既存の再開規則を、読み取り専用の評価にも使う。
- ADR 0041 の決定項 1（原則）: 記録だけのリプレイの費用を、明示して調べたときの読み取りだけに限定する。
- ADR 0054 の決定項 1（親を記録する）と決定項 2（消す条件）: 埋め込みの親子の木が、リプレイで読む記録の範囲と寿命を定める。
- ADR 0060 の決定項 1（ワークフローは、始めたときの版で動かし続ける）: 記録だけのリプレイも開始時の版を選び、別の版へ切り替えない。
- ADR 0061 の決定項 2（SDK は関数の手元の結果でなく、耐久化した終端結果を返す）: 通常実行では保存済み結果を正典とする。記録だけのリプレイの手元の評価は診断結果であり、正典を変えない。
- ADR 0062 の決定項 1（親のある実行は、親のリプレイが同じ呼び出しへ到達したときだけ再開する）: 通常の再開は到達した子を回復するが、記録だけのリプレイは回復せず終端記録だけを読む。
