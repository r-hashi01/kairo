# 0034. 欠落しない実行イベントの出口を、ログから決定的に導いて作る

- 状態: 承認（2026-10-02）
- 日付: 2026-10-02
- 関連: FR6, FR7 / 不変条件 1, 3, 7 / ADR 0005, 0016, 0028, 0029, 0036

## 背景

Dify は、実行とノードごとの記録を DB に書く（`workflow_runs`、`workflow_node_executions`）。SSE でも、`workflow_started`、`node_started`、`node_finished`、`iteration_*` などを流す。これらは欠けると履歴や画面が壊れるので、**欠落してはならない**。

kairo の出口は、今は 2 つある。

- 可観測性のストリーム（obs）: 欠落を許す（バッファがあふれたら捨てる）。
- ライブの中継（live）: 記録しない。

どちらも、この用途には使えない。また、スキップされたノード、辺の状態、分岐で選んだハンドルは、コアの中で起きることで、今はエンジンからも見えない（ADR 0029 で後回しにしたもの）。

## 決定

### トレース: コアが遷移を書き出す

- `core.Apply` が、命令とは別に**トレース**を返す。中身は、何が起きたかの記録である。
  - ノードの開始。入力と、何回目の試行かを含む。
  - ノードの終わり。成功・例外・失敗、出力、選んだハンドルを含む。
  - スキップ
  - リトライの予定
  - 要確認
  - 回（iteration / loop）の開始と終わり
  - 変数の書き換え（ADR 0033）
  - 実行の終わり
- トレースは、適用したイベントだけから決まる（不変条件 1, 2）。時刻はイベントの時刻を使う。
  - **リプレイすれば、同じトレースが同じ順で出る。** そのため、トレース自体をログに書く必要はない。ログが真実で、トレースはそこから導いたものになる。
- 保護ステップ（if-else、assigner など）の開始と終わりも出す。Dify では、これらも 1 つのノードの実行として記録されるので。
- 実行器の結果に付く `process_data` と `execution_metadata`（使ったトークン数など）を、イベントのデータとしてログに書く（`task.Result.Meta` を足す）。ノードの終わりのトレースにも入れる。大きいものは、出力と同じくブロブにする（ADR 0008）。

### 出口: カーソルと ack のある購読

- `Engine.Subscribe(from Cursor) (*Feed, error)`
  - カーソルは、シャードごとの（LSN、その LSN の中の通し番号）の組。
  - `Feed` は、トレースを順に返す。シャードの中では順序を保つ。シャードをまたいだ順序は保証しない（実行は 1 つのシャードにしかないので、実行の中では順序が保たれる）。
- 購読者は、処理を終えたカーソルを `Feed.Ack` で返す。
  - **ack されていない LSN は、ログの退役（ADR 0016）から守る。** 購読者が止まっても、再開したときに続きから読める。
  - ack したカーソルは、終了ログ（ADR 0027）と同じく耐久化する（購読者の名前ごと）。
- 読む場所:
  - 新しいトレースは、シャードがイベントを適用したときに、メモリのリングバッファに積む。
  - 購読者が遅れてバッファから落ちたら、ログを読み直してコアでリプレイし、トレースを作り直して渡す。
  - リプレイはシャードのループの外（I/O プール）で行う。
- 購読者を登録していなければ、トレースを作るだけで（ほぼ）コストはかからない。ログの退役も止めない。

### ライブのチャンクの合流

- ストリームのチャンク（LLM の出力の断片）は、記録しない（今と同じ）。
- 購読中の購読者には、同じ順序の流れの中に、チャンクも挟んで渡す。そのノードの「終わり」のトレースより前に、同じ流れで届く。
- 応答ストリームの順序制御（ADR 0036）は、この順序に依存する。
- 購読者が再接続した後は、チャンクは届かない（終わったノードの出力に、全文が含まれる）。

### obs との関係

- obs は、今の役割（欠落を許す監視用の流れ）のまま残す。トレースから作るように寄せられるが、それは別の判断にする。

## 結果

- Dify の実行履歴と SSE を、欠落なく作れる。kairo が落ちても、購読者が落ちても、ack した位置から続く。
- スキップ、ハンドル、辺の状態が外から見えるようになる（ADR 0029 で後回しにした `step.skipped` は、トレースのスキップで扱う）。
- 悪くなること:
  - `core.Apply` の出力が増える（トレースの割り当て）。購読者がいないときは作らない、という選択肢を `Apply` の引数で持つ。
  - 購読者が ack しない限りログが退役しないので、止まった購読者がディスクを使い続ける。ack が遅れていることを `Stats` に出し、購読の登録を外す API を用意する。
  - イベントのレコードに `Meta` が増える。ログの形式は、後ろに足すので、古いログも読める。
- テスト:
  - リプレイしたトレースが、実行中に出たトレースとバイト列まで一致する。
  - 購読者を止めて再開すると、ack した位置から欠けなく続く。退役の後でも読める。
  - バッファから落ちた購読者は、ログからの作り直しで追いつく。
  - チャンクが、そのノードの終わりより前に届く。
  - ADR 0028 の差分ハーネスで、SSE のイベント列（アダプタが作ったもの）が一致する。

## 検討した代替案

- トレースもログに書く: ログが倍近くに増え、ログとトレースの食い違いを守る仕組みが要る。トレースはログから決定的に導けるので、書く必要がない。
- obs を欠落しないように変える: obs は、監視の流れが詰まっても実行を止めないために欠落を許している（FR7）。両方の役割を 1 本に持たせると、どちらかを損なう。
- 購読者ごとに、kairo がイベントを DB に書く（アウトボックスの表）: 書き込みが倍になる。DB のない構成（ファイル形式が既定）でも同じ仕組みで動かしたい。

## 実装の前に変えたこと（2026-10-05、利用者の承認済み。ADR 0017）

「読む場所」の節にあった「購読者がバッファから落ちたら、ログを読み直してコアでリプレイし、トレースを作り直す」は、そのままでは成り立たなかった。

- ある LSN 以降のトレースを作り直すには、その時点の各実行の状態が要る。
- しかし、退避や圧縮のスナップショットは実行の基点を先へ進め、それより前の記録は退役する。そのため、その時点の状態を復元できないことがある。
- 再起動のときも同じで、ack されていないトレースのうち、スナップショットが覆った範囲は失われる。

代わりに、次のようにする（案 A）。

- **ack より先へ、状態の保存を進めない。** 購読（`Config.Feeds` に名前を書いたもの）がある間は、次のことをしない。
  - シャード×ティアごとに、すべての購読が ack した LSN より先を覆うスナップショットを作らない（退避、圧縮のチェックポイント）。
  - 終わった実行の後片付け（スナップショットの削除とピンの解除）をしない。
  - ログを退役しない。

  ack が進んだら、待たせていたものを進める。
- **再起動では、ack の後のトレースを必ず作り直せる。** スナップショットは ack の位置以前を覆うものしかなく、その後のイベントはログに残っているので、回復のリプレイの中で作り直す。購読者は、カーソルが ack 以下のものを受け取らない。
- **動いている間は、メモリに溜める。**
  - ack されていないトレースは、メモリのバッファに溜める。
  - 溜まった数が上限（`Config.FeedLimit`）を超えた購読は切る。その購読には `ErrLagged` を返し、保持の計算からも外す。切られた購読者は、欠けたことを知ったうえで、つなぎ直しから始める。
- **代償。** 購読者が遅れている間は、退避と退役が止まり、メモリとディスクが増える。遅れの大きさを `Stats` に出す。
- **ack の単位。** カーソルは（シャード、ティア、LSN、その LSN の中の通し番号）。
  - ack はシャード×ティアごとで、そのカーソル以下をまとめて ack する。
  - 保持の境界は、ack した LSN の 1 つ手前にする（同じイベントの残りのトレースを作り直せるように）。
  - 耐久性ティアが none の実行のトレースとライブのチャンクは、LSN を持たない。つながっている購読者にだけ届き、作り直しも保持もしない。

## 実装で詰めた詳細（2026-10-05 追記、ADR 0017）

- **コア。** `core.ApplyTraced` を足した（`Apply` はそのまま残し、購読がなければトレースは作らない）。
  - トレースの種類: 実行の開始と終わり、ノードの開始と終わり（成功・例外・失敗、選んだハンドル、実行器のメタデータ）、スキップ、リトライ、要確認、iteration / loop の回の開始と終わり、変数の書き換え。
  - グラフと cond の条件は構造なので、トレースを出さない。保護ステップ（`kairo.switch`、`kairo.assign` など）は、Dify と同じく 1 つのノードの実行として出す。
  - ノードの開始は最初の試行のときだけ出す。以降はリトライとして出す（graphon と同じ）。
  - テストのシミュレータ（`sim`）は、常にトレースありで適用する。`checkReplay` は、状態のバイト列に加えて、トレースがリプレイで同じ順に同じ内容で出ることも確かめる。これで、既存のすべてのコアのテストが、トレースの決定性の検査になる。
- **実行器のメタデータ。** `task.Result.Meta`（Dify の `process_data` や使用量）を、イベントの拡張フィールド（版 3）に入れてログに残し、そのステップの終わりのトレースに付ける。
- **エンジン。**
  - シャードは、ループの 1 回分のトレースを mpsc のキューで `feedHub` に渡す。シャードのループにロックは足していない。
  - `feedHub` は、購読ごとの ack と、シャードごとの未 ack のエントリを持つ。境界が変わったら、シャードに `mFeedBound` を送る。
  - シャードは、境界より新しい状態のスナップショット（退避、圧縮のチェックポイント）、終わった実行の後片付け、境界より新しい記録の退役を止める。境界が進んだら、待たせていたものを進める。
- **購読の名前は設定で決める（`Config.Feeds`）。** ack は、スナップショットの置き場に `feed/<名前>` として保存する。初めての名前は「今」から始まる（回復の後のログの位置までを ack 済みとみなす）。
- **イベント単位の ack。** 1 つのイベントのトレースは 1 回で届く。そのため、ack したエントリがそのイベントの最後のものなら、イベント全体を ack 済みとして扱う。そうしないと、追いついている購読者がいても、待っている実行が退避されなくなる。
- **ack の頻度は購読者が決める。**
  - ack はそのたびに永続化する（ファイル形式なら 1 回の書き込み）。
  - 計測では、バッチごとに ack すると 1 実行あたり約 37µs 増えた。プロファイルでは、ほぼすべてが ack の書き込みで、エンジン側のトレースの生成と受け渡しは 1% 程度だった。
  - 購読者は、一定の数か時間ごとにまとめて ack する。Dify 側のアダプタもそうする。
- **再起動。** 回復のリプレイの中で、ack より後のイベントにトレースを付けて作り直す。`Next` は、カーソルが ack 以下のエントリを渡さない。
- **テスト:**
  - `TestTraceOfGraph`、`TestTraceOfRetryExceptionAndMeta`、`TestTraceOfMapLoopAndVars`（core）
  - `TestFeedDeliversTracesAndChunksInOrder`、`TestFeedHoldsStateAndReplaysAfterRestart`、`TestFeedLag`、`TestFeedHoldsLogRetirement`（engine）
- **レビューで直したこと（2026-10-05）:**
  - 回復の時点ですでに終わっていた実行も、トレースが ack されていなければ、記録をピンで守り、スナップショットとブロブの削除を ack まで待たせる。以前は回復の中で消していたため、ack 前に 2 回再起動すると、その実行のトレースが作り直せなくなっていた。
  - 待たせていた後片付けを再開するときも、書き込み中のスナップショットの後に回す（不変条件 8）。
  - トレースは、イベントを適用した直後にフィードへ渡す（同じ回で実行器に渡すタスクより先）。以前はループの終わりにまとめて渡していたため、ステップのチャンクがそのステップの開始のトレースより先に届くことがあった。
  - 実行が「最後にトレースを出したイベントの LSN」（`feedLSN`）を持ち、退避と後片付けの可否はそれで判定する。トレースを出さないイベント（意図、回復、メールボックスへの signal など）のせいで、追いついた購読者がいても実行が退避できなくなることを防ぐ。
  - 遅れて切られた購読をつなぎ直すときは、開始の位置を各シャードから受け取る（`mFeedStart`）。シャードは同時に、その位置より先のスナップショットを止める。
  - 位置を持たないエントリ（チャンク、none / memory ティアのトレース）は、つながっていない購読のために溜めず、遅れの判定にも数えない。つなぎ直した後に、前のチャンクは届かない。
  - ack は、永続化してからメモリに反映する。同じ購読の ack は順に処理する（古い ack が新しい ack を上書きしない）。範囲外のカーソルはエラーにする。
  - 境界が変わるたびに圧縮の判定を走らせるのをやめた（退役はログが伸びたときの判定で進む）。
  - `Next` は、毎回始めるシャードを変える（後ろのシャードが待たされ続けないように）。
  - フィードの管理側では、遅れの判定をバッファ全体が上限を超えたときだけ行い、取り除いた分の詰め直しはまとめて行う。
  - `Engine.Unsubscribe(name)` を足した。ack の記録も消すので、次の起動では「今」から始まる。名前を `Config.Feeds` から外すだけだと古い ack が残るので、外す前に `Unsubscribe` する。
  - 実行器のメタデータが `BlobThreshold` を超えたら、ブロブに置いて参照だけをログに残す（決定のとおり）。
  - テスト: `TestFeedFinishedRunAcrossTwoRestarts`、`TestFeedChunksWhileDisconnected`、`TestFeedTracelessEventsDoNotHoldRuns`。チャンクの順序は、race 検出器の下で 50 回続けて確かめた。
