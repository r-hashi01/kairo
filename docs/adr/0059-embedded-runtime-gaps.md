# 0059. 埋め込みのランタイムの不足を埋める: 動かす側の借用で再開し、先に来たシグナルを受け、上限・待ちの期限・一覧・投げっぱなしの開始を足す

- 状態: 承認
- 日付: 2026-10-09
- 関連: ADR 0041（実行 1 回あたりのコスト）、0049（コードで書く API）、0051（常駐しない kairo）、0054（終わった実行の削除）、0058（Go の SDK）

## 背景

Go の SDK（ADR 0058）を作り終えてから、SDK として足りないものを洗い出しました。そのうち次の 2 つは Go だけの不具合だったので、ADR なしで直しました。

- 呼び出し側が待つのをやめただけで（`Run` に渡した ctx が切れた）、kairo の中の呼び出しまで取り消していた。いまは kairo で取り消されたときだけ取り消し、それ以外は `ErrStopped` を返して、ワークフローを再開できるまま残します。
- ワークフローの関数が panic すると、プロセスごと落ちていた。いまはワークフローの失敗として記録します。

残りの 6 つは、3 つの SDK（TypeScript・Python・Go）に共通する不足です。表の形や取り決めに触れるので、ADR で決めます。

1. **常駐するプロセスが落ちると、動かしていたワークフローが止まったままになる。** 待ちモードでワークフローを動かすのは、`Run` を呼んだプロセスだけです。そのプロセスが落ちると、誰かが同じ ID で `Run` をもう一度呼ぶまで、何も進みません。手順の借用（lease）は期限切れで別のプロセスが拾いますが、ワークフロー関数そのものには借用がありません。サスペンドモードも同じで、決着を受けて動かし直している途中に落ちると、次のきっかけが来ません。
2. **待ちができる前に届いたシグナルを捨てる。** `Signal` は、待ちの実行がまだないと「待っていない」というエラーを返します。ワークフローが `WaitFor` に着く前に承認が来ると、送った側がやり直すしかありません。
3. **埋め込みのランタイムに、同時実行と速さの上限がない。** kairod 経由（`HttpBackend`）には `concurrency` がありますが、埋め込みでは、来た手順をすべてすぐに走らせます。LLM の API の RPM を守る手段もありません。
4. **待ちに期限を付けられない。** コアの wait は `timeout` を持っています（`ir.Node.Timeout`、出力の `timed_out`）。それなのに、SDK の `WaitFor` からは指定できません。
5. **実行を一覧できない。** 根の実行を探す方法がなく、`RunInfo` に作成・更新の時刻もありません。どの利用者の実行かといった、利用側の目印も付けられません。
6. **開始だけして待たない API がない。** `Run` は、終わるまで（サスペンドモードなら止まるまで）戻りません。HTTP のハンドラーから受け付けて、すぐに ID を返すといった使い方ができません。

## 決定

3 つの SDK に同じ意味で入れる。表の形と取り決めは 3 つで同じにし、同じ DB を言語をまたいで使えること（ADR 0058 の相互再開）を保つ。

### 1. ワークフローを動かす側にも借用を付ける

- ワークフローの関数を動かしている間、そのプロセスは lease 表に**駆動の借用**を持つ。行は `(run = ワークフローの ID, act = 0)` で、owner と until は手順の借用と同じに扱う。act 0 はコアが手順に振らない番号なので、手順の借用とぶつからない。
- 借用を取るのは、関数を動かし始めるとき（`Run`、`Submit`、決着を受けた動かし直し、下の再開）。外すのは、関数が終わったとき（完了・失敗・取り消し）と、サスペンドモードで止まったとき。外すときは、ワークフローの実行を進めるのと同じトランザクションで外す。
- 更新は、手順の借用と同じ `RenewLeases(owner)` で一緒に延ばす。実行ごとの更新は増えない。
- `tick`（待ちモードでは定期の掃除、サスペンドモードでは外からの `/tick`）で期限切れの駆動の借用を見つけたら、そのワークフローを登録しているプロセスが借用を取り直し、関数を最初から動かす。終わった呼び出しは記録から返る（ADR 0049）ので、作用は繰り返さない。登録していないプロセスは、手順のときと同じく飛ばす（`skipUnknownPlan`）。
- 別のプロセスが動かしている間（借用が生きている間）に同じ ID で `Run` を呼んだら、自分では動かさず、終わるのを待つ。今は 2 つのプロセスが同時に同じ関数を動かせるが、これで 1 つになる。
- 子のワークフローは、親の関数の中で動くので、借用は根だけが持つ。根を動かし直せば、子も記録から順に進む。

### 2. 待ちより先に来たシグナルを、待ちの実行として先に作っておく

- `Signal(id, name, payload)` で、まだない番号の待ちに当たったら、その待ちの実行（ID は `WaitFor` が使うのと同じ `callID(id, "kairo.wait/"+name, "null", n)`、親は `id`）を作り、同じトランザクションでシグナルを適用して完了させる。
- ワークフローが後から `WaitFor` に着くと、同じ ID の実行がすでに完了しているので、その出力を返す。新しい表は要らない。
- 同じ名前のシグナルは、届いた順に 0 番、1 番……の待ちに入る。今の「待っている最も若い番号に入れる」と同じ順になる。
- ワークフロー `id` が存在しない、または終わっているときは、今と同じくエラーを返す。
- 使われなかった先取りの待ちは、ワークフローの木と一緒に消える（ADR 0054）。

### 3. 埋め込みのランタイムに、同時実行と速さの上限を足す

- `Options.Concurrency`（Go）/ `concurrency`（TypeScript・Python）: このプロセスで同時に走らせる手順の数。既定は上限なし（今と同じ）。
- アクションごとの `Limit(n)` と `Rate(perMinute)`: アクション（または `Destination` のキー）ごとの同時数と、1 分あたりの開始数。
- 枠を待つ手順も、借用は取ったまま更新する。プロセスが落ちれば期限が切れ、別のプロセスが拾う。待っている手順のために、ポーリングもスレッドも足さない（枠が空いたときに次を始める）。
- 上限はプロセスごとに数える。複数のプロセスで合わせた上限は、この ADR では扱わない（代替案を参照）。

### 4. 待ちに期限を付ける

- `WaitFor(ctx, name, Timeout(d))` のように期限を指定できるようにする。コアの wait の `timeout` を使う。期限が来ると、結果は `TimedOut` の値（Go は `ErrTimedOut`、TypeScript・Python は例外）になる。
- 期限の有無で呼び出しの ID は変えない（`canonical` は今のまま `null`）。プランは期限ごとに分け、名前を `kairo.wait/<name>@<ミリ秒>` にする。期限なしは今の `kairo.wait/<name>` のまま。
- 「いくつかの待ちのうち先に来たもの」を選ぶ API（select）は、この ADR では足さない（代替案を参照）。

### 5. 実行の一覧と目印

- run 表に 2 列を足す。`workflow`（根のワークフローの名前。呼び出しの実行では空）と `meta`（利用側が開始時に付ける JSON のオブジェクト。後から変えない）。足し方は ADR 0054 の `parent` 列と同じく、起動時の移行で行う。
- `List(ctx, Filter{Workflow, Status, Since, Until, Limit, After})` で、根の実行（`parent` が空）を作成順に返す。`meta` は返すが、絞り込みには使わない。
- `RunInfo` に `Created` と `Updated`（ミリ秒の時刻。表にすでにある列）と `Meta` を足す。
- 開始時の目印は、`WithMeta(map)`（Go）、`meta`（TypeScript・Python）で付ける。

### 6. 開始だけして待たない

- `Submit(ctx, k, name, in, WithID(...)) (id, error)`: 開始を耐久化してから戻る。関数は、このプロセスが借用を取って裏で動かす（待ちモード）。サスペンドモードでは、止まるまで動かしてから戻る。
- `Await[O](ctx, k, id)`: 終わるのを待って結果を返す。どのプロセスからでも呼べる（決着の通知で起きる。ポーリングしない）。ctx が切れたら `ErrStopped` を返し、ワークフローには触らない。
- 同じ ID の `Submit` を重ねても、実行は 1 つ（今の `Run` と同じ冪等さ）。

## 結果

- 常駐するプロセスが落ちても、残ったプロセス（または次の `tick`）がワークフローを続ける。同じワークフローを 2 つのプロセスが同時に動かすこともなくなる。
- 実行 1 回あたりのコストは、根のワークフローごとに lease 表の行が 1 つ（挿入と削除）増える。これは「状態の耐久化」のための仕事（どこまで動かしたかを、落ちても引き継げるようにする）に当たる（ADR 0041）。更新は owner ごとにまとめて行うので、実行の数に比例しない。先取りのシグナル、上限、期限、一覧は、使ったときにだけコストを払う。
- 表の形が変わる（run 表の 2 列、lease 表の act 0）。古い版（0.1.x）の SDK は act 0 の借用を手順として拾おうとして、失敗する。同じ DB を使うプロセスは、すべてこの版以上にそろえる必要がある。リリースノートに書く。
- 新しく守ること:
  - 駆動の借用は、ワークフローの実行を進めるのと同じトランザクションで取り、外す。
  - 先取りの待ちは、待ちの実行と同じ ID・同じ親で作る。
- テスト（`kairotest` と、TypeScript・Python の同じ内容のテストに足す）:
  - 待ちモードのプロセスを、ワークフローの途中で落とす。別のプロセスの掃除で、ワークフローが最後まで進み、作用は 1 回だけになる。
  - 生きている借用があるうちは、別のプロセスの `Run` が関数を動かさない。
  - 待ちより先に送ったシグナルを、後から着いた `WaitFor` が受け取る。2 つ送れば、2 つの待ちが順に受け取る。
  - 上限を超えた手順が待ち、枠が空くと走る。走っている数が上限を超えない。
  - 期限の来た待ちが `ErrTimedOut` になる。
  - `List` の絞り込みと並び順、`Submit` と別プロセスの `Await`。
  - Go と TypeScript の相互再開（`storetest/xlang_test.go`）に、駆動の借用と先取りの待ちを含める。

## 検討した代替案

- **待ちモードの再開を、起動時に「終わっていない根を全部動かす」で行う:** 複数のプロセスが同じ DB を使うと、全員が同じワークフローを動かしてしまう。生きているプロセスが動かしているものまで奪う。借用なら、落ちたものだけを拾える。
- **先に来たシグナルを、別の表（受信箱）に置く:** 表が 1 つ増え、`WaitFor` のたびにその表を見る必要がある。待ちの実行を先に作れば、今の表と今の `WaitFor` のまま動く。
- **複数のプロセスで合わせた速さの上限（DB の表で数える）:** すべての手順の開始に DB の書き込みが 1 つ増える（ADR 0041 の、全実行が払う常駐のコスト）。必要になったら、`Destination` のキーごとに選んで使える形で、別の ADR にする。
- **select を今入れる:** 選ばれなかった側の待ちを、リプレイで同じように取り消す決まりが要る。期限付きの待ちで、多くの使い方（承認か期限か）はまかなえる。必要がはっきりしてから決める。
- **`meta` で絞り込めるようにする:** JSON の中を検索する書き方が、SQLite と PostgreSQL で違う。索引も要る。まずは返すだけにし、絞り込みが要るなら列として足す。

## 実装で詰めた詳細（2026-10-09 追記、ADR 0017）

### Go（sdk/go）

- **待ちモードの `Run` は、駆動を裏に回す。** `Run` は「開始（新しければ駆動の借用を同じトランザクションで設定）→ 裏で駆動 → 結果を待つ」になった。呼び出し側の ctx が切れても、待つのをやめるだけ（`ErrStopped`）で、ワークフローはこのプロセスが動かし続ける。このプロセスがすでに裏で動かしている ID は、二重に動かさない。サスペンドモードの `Run` は、今までどおりその場で止まるまで動かす。ctx が切れたら借用を期限切れで残し、次の `Tick` が拾う。
- **サスペンドモードでは、借用を「次に動かすワークフロー」が持つ。** 決定 1 では「借用は根だけが持つ」としたが、サスペンドモードで決着を受けて動かし直すのは、その呼び出しを作ったワークフロー（子のこともある）なので、決着のトランザクションでは直接の親に借用を付ける。待ちモードでは、子は親の関数の中で動くので、借用は根だけが持つ（決定のとおり）。決定からの逸脱で、利用者が 2026-10-09 に了承した。
- **待ちモードの掃除は、借用の期間ごと（既定 30 秒）にプロセスで 1 つ。** `Start` の直後にも 1 回走る。通知の仕組み（`Notifier`）がない保存先では、掃除のたびに、このプロセスで待っている実行を読み直す。別のプロセスで終わった実行を待つ `Await` は、通知がなければ最大で借用の期間だけ遅れて戻る。
- **期限切れで残す借用は、持ち主を空にする。** 持ち主が自分のままだと、同じプロセスがほかの借用を延ばすとき（owner ごとの更新）に一緒に延びて、いつまでも拾われないため。
- **`Close` は、持っていた駆動の借用を期限切れにして渡す。** 正しく閉じたプロセスのワークフローは、ほかのプロセスの次の掃除（または次の `Run`）ですぐに続く。閉じずに落ちたときは、借用の期間が過ぎてから続く。
- **サスペンドモードの `Await` は待たない。** 終わっていなければ `ErrSuspended` を返す（関数を待たせ続ける常駐のプロセスがないため）。
- **古い版との共存の結果を訂正する。** 0.1.x の SDK は、期限切れの act 0 の借用を手順の結果不明として適用しようとし、コアに無視されたうえで借用を消す。失敗はしないが、引き継ぎが黙って失われる。同じ DB のプロセスをそろえる必要があることは変わらない。
- **`Signal` は、存在しないワークフロー、または終わったワークフローには、エラーを返す。** 先取りの待ちを作れるのは、終わっていないワークフローだけ。
- **同じ ID の実行を 2 つのプロセスが同時に作ったとき、負けた側は「既存」として扱う**（開始のエラーのあとに行があれば、それを見つけたことにする）。先取りの待ちと、ワークフローが着いた待ちが競ったときに要る。
- **待ちのプランは、使う前に登録していなくても、処理するときに名前から作る**（`kairo.wait/<name>` と `kairo.wait/<name>@<ms>`）。期限付きの待ちのタイマーを、そのプランを使ったことのないプロセスが発火させるときに要る。
- **上限を待つ順番は、宛先の同時数 → 宛先の速さ → プロセスの同時数。** 宛先の枠を待つ手順が、プロセスの枠をふさがないようにするため。速さは壁時計で数える（`Options.Now` には従わない）。
- **実行あたりの書き込み。** 待ちモードの根は、借用の行の挿入（開始と同じトランザクション）と削除（終わりと同じトランザクション）が増えるだけで、文は増えない。サスペンドモードでは、決着した呼び出しごとに、親の借用の書き込み（決着と同じトランザクション）と、止まったときの削除が 1 つずつ増える。
- **Go の API の名前。** `Options.Concurrency`、`Limit(n)`、`Rate(perMinute)`、`WaitTimeout(d)`（`Timeout` はアクションの設定で使っているため）、`ErrTimedOut`、`ErrStopped`、`(*Kairo).Submit`、`Await[O]`、`WithMeta`、`(*Kairo).List(Filter)`。`RunInfo` に `Workflow`・`Meta`・`Created`・`Updated` を足した。保存先（`Store`）には `ClaimDrive`・`EndDrive`・`List` を足した。
- **テスト。** `kairotest` に、StoppedDriverIsTakenUp・LiveDriverIsNotDoubled・SignalBeforeTheWait・WaitTimesOut・Limits・SubmitAwaitAndList を足した（メモリと SQLite で流れる）。StoppedDriverIsTakenUp は、引き継ぎ（`lostDrive`）を外すと落ちることを確かめた。

### TypeScript（sdk/ts）

- **API。** `k.run(name, input, { id, meta, signal })`、`k.submit(name, input, { id, meta })`、`k.result(id, { signal })`、`k.list({ workflow, status, since, until, after, limit })`、`ctx.waitFor(name, { timeout })`（ミリ秒）、アクションの `limit`・`rate`、`concurrency`。例外は `StoppedError`・`TimedOutError`。結果を待つ API は、Python の `await` が予約語なので、両言語で `result` にそろえた（Go は `Await`）。
- **打ち切れない関数は置いていく。** TypeScript では関数を外から止められないので、中止されたら関数の Promise を待たずに戻る。そうしないと、永久に待つ関数があるとき `close` が終わらない。置いていった関数が後で失敗しても、未処理の reject にはしない。
- **掃除のタイマーは `unref()` する。** `close` を呼ばないスクリプトでも、プロセスが終われるようにするため。
- **kairod（`HttpBackend`）では、借用・先取りのシグナル・一覧はない**（一覧はエラー）。待ちモードの `run` は、従来どおり呼び出したところで動かす。kairod の保持期間を過ぎたときの `ResultLostError` を、呼び出し側に届けるため。期限付きの待ちと `limit`・`rate` は kairod でも効く。
- **待つのをやめると取り消していた不具合**は TypeScript にもあったので、直した。
- **テスト。** `src/driving.test.ts` に、Go と同じ 9 件を SQLite で足した。Go と TypeScript の相互再開のテストも通る。

### Python（sdk/python）

- **API。** `Kairo(..., concurrency=)`、`@k.action(..., limit=, rate=)`、`await k.run(name, input, id=, meta=)`、`await k.submit(...)`、`await k.result(id)`、`await k.list(workflow=, status=, since=, until=, after=, limit=)`、`await ctx.wait_for(name, timeout=)`。例外は `StoppedError`・`TimedOutError`。
- **待ちの期限の単位は、言語ごとの `sleep` に合わせる。** Go は `time.Duration`、TypeScript はミリ秒、Python は秒（`ctx.sleep` が秒のため）。プラン名の `@<ms>` はどれもミリ秒。
- **中止は asyncio の取り消しで伝える。** 待ちモードの `run` と `result` は、取り消し（`asyncio.timeout` を含む）を `StoppedError` に変えて投げる。close や取り消しのときは、関数を動かしているタスクを取り消し、終わりを待たずに置いていく。
- **上限は、手順のスレッドに入る前に、イベントループの上で待つ。** 待っている手順が既定のスレッドプールを塞いで、ほかの宛先の手順を止めないようにするため。枠を待っている手順の打ち切りは、`TaskContext.cancelled` に足したフックで知らせる（ポーリングしない）。
- **`signal` で、ワークフローがない、または終わっているときは `LookupError` を投げる**（既存の「待っていない」と同じ型）。kairod での `list` は `RuntimeError` を投げる。
- **借用の更新ループは、保存先のエラーで止まらない。** 次の周期にまた更新する。以前は 1 回のエラーで止まっていた。
- **close の後に待っていた `run` は、`asyncio.CancelledError` ではなく `StoppedError` になる。** 既存のテストの期待を、この振る舞いに合わせて変えた。
- **テスト。** `tests/test_driving.py` に、Go・TypeScript と同じ 9 件を SQLite で足した。

### 3 言語の PostgreSQL

TypeScript と Python にも、PostgreSQL で流すテストを足した。中身は、止まったプロセスからの引き継ぎ、先取りのシグナル、`submit`・`result`、`list` で、`KAIRO_SDK_PG_DSN` があるときだけ流れる。2026-10-09 に、PostgreSQL 17 で Go・TypeScript・Python のすべてが通った。
