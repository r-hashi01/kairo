# 0038. Dify のワークフローの実行から Celery をなくし、仕事の配布は kairo が担う。枠の単位は実行ではなくノードの実行にする

- 状態: 承認（2026-10-05）
- 日付: 2026-10-05
- 関連: ADR 0008, 0034, 0036, 0037（0037 の第 1 段階の「1 実行 1 Celery タスク」と、第 2 段階の検討を置き換える）, 0039

## 背景

ADR 0037 の第 1 段階では、1 つの実行が Celery のタスクを 1 つ占める。タスクの中では、kairo のイベントを読み、graphon のイベントに組み立てて Dify の下流に流す。比較（0037 の追記）でわかったことは次のとおり。

- エンジンの時間は 1/5〜1/20 になった。それでも処理量は、Celery の同時実行数（既定 4）で頭打ちになる。
- Celery のプロセスの CPU が張りついていた。kairo-dify とノードのワーカーは、ほぼ空いていた。
- 第 1 段階の限界: タスクが落ちると、Dify の記録が止まる。デーモンが再起動すると、まだ読まれていないイベントが失われる。

勿体ないのは、Celery が「1 つの実行を丸ごと 1 つの仕事」として扱うことにある。LLM の応答を待つ間も、人の入力を待つまでも、実行は枠を占める。そのため、処理量は「枠の数 ÷ 1 実行の長さ」で決まる。本来、処理量を決めるべきものは、外部の上限（LLM の提供元）、ノードの実行に要る資源、保存の書き込みの速さである（ADR 0039）。

役を 3 つに分けて考える。Dify と n8n（queue モード）では、どちらも ②③ を 1 つの仕組みが担っている。

| 役 | 中身 | Dify の今 | n8n の今 |
|---|---|---|---|
| ① プロセスを生かしておく | 起動、再起動、台数の増減 | Docker / Kubernetes | Docker / Kubernetes |
| ② プロセスの中の枠を束ねる | 同時に進める仕事の数 | Celery の親プロセス（gevent、`-c 4`） | Bull のワーカー（既定 10） |
| ③ 仕事を配る | どの実行をどこで進めるか、取りこぼしの防止 | Celery（Redis） | Bull（Redis） |

検討の途中で、kairo を常駐させず、実行のときにだけ動く実行器にする案も考えた（「検討した代替案」）。しかし、次の役は実行をまたいで共有され、常に起きている必要がある。

- 状態の耐久化
- 期限での起こし
- 公平さと上限の数え上げ
- 受け持ちの決定

これらは 1 か所に集めるのが、速くて正しい。

## 決定

### 1. 役の分担

- **① は今のまま、Docker や Kubernetes が行う。** kairo はプロセスを管理しない。
- **③ は kairo（kairo-dify）が行う。** Celery の役である。
  - kairo は、実行の状態を預かる部品として常駐する。データベースと同じ位置づけ。
  - 待っている実行は、状態のバイト列でしかない。常駐して動いているのは、イベントを受けて次を決める部分（1 回の遷移が µs 単位）と、仕事の配布である。
- **② はホストのワーカーが行う。枠の単位は「ノードの実行」にする。**
  - ワーカーが受け取るのは、ノードの実行と、イベントの下流（次項）の 2 種類の仕事。どちらも、終わったら枠を返す。
  - 実行が枠を占めることはない。人の入力や時間の待ちは、枠を使わない。
  - 枠の大きさは固定値で決めない（ADR 0039）。

### 2. 構成

```
Client ─SSE─ Dify API ──(Redis topic)── Dify のワーカー（Python、状態を持たない、N 台）
                │                          │ ▲            │ ▲
                │ 投入・signal・取り消し    │ │ イベント    │ │ ノードの仕事
                ▼                          ▼ │（区画、ack） ▼ │（pull）
             kairo-dify ───────────────────┴──────────────┘
```

Celery のワーカーと同じく、1 種類の Python のプロセス（`flask kairo-worker`）が、ノードの実行と実行の下流の両方を受け持つ。グラフの実行は kairo が行う。ワーカーは、必要なときに仕事とイベントを受け取るだけで、実行をまたぐ状態を持たない。

- **API のプロセス。** 実行を kairo-dify に直接投入する（Celery のタスクを作らない）。
  - SSE は今と同じく、Redis の topic を購読して流す。クライアントから見た API は変わらない。
  - 停止は kairo-dify の取り消しを、human-input のフォームが送信されたら kairo-dify の signal を、直接呼ぶ。
- **Dify のワーカー。** 0037 の `flask kairo-worker` を広げて、2 つの役を持たせる。
  - **ノードの実行。** ワーカープロトコルで仕事を pull して実行する（今と同じ）。
  - **イベントの下流。** kairo のイベントを読み、ADR 0036 の合成と Dify の下流を動かす。下流とは、キュー、タスクパイプライン、レイヤー（保存、会話変数、トレース）、Redis の topic への publish のこと。
    - 実行ごとの下流のオブジェクトは、その実行の最初のイベントで作り、終わったときか一時停止したときに捨てる。待っている実行（human-input）は、ワーカーの中に何も持たない。
  - 2 つの役が同じプロセスの資源を分け合う。上限の決め方は ADR 0039 に従う。詰まるようなら、起動の引数で役を分けて動かせるようにする。
- **イベントの区画と ack（kairo-dify）。**
  - kairo-dify は、実行を区画（partition）に分けて配る。区画は実行 ID のハッシュで決まり、区画数はデータディレクトリごとに固定する。
  - ワーカーは「区画をいくつか受け持ちたい」と言ってつなぐ（`GET /v1/feed`）。kairo-dify が空いている区画を割り当て、ワーカーの増減に応じて配り直す。1 つの区画を受け持つ接続は、常に 1 つだけ。
  - ワーカーは、Dify の記録を DB に書き終えてから ack する。kairo-dify は、区画ごとの耐久の購読（ADR 0034）として ack を保存し、ack より後のイベントを、再接続や配り直しのときに渡し直す。
    - これで、0037 の第 1 段階の限界（ワーカーやデーモンが落ちたときの欠け）がなくなる。
    - 渡し直したイベントは、ワーカーが実行ごとの番号で重複を捨てる。
  - 0037 の「実行ごとのメモリのバッファ」と `GET /v1/runs/{id}/events` は、区画の購読に置き換える。
- **一時停止と再開。**
  - 一時停止したら、ワーカーは一時停止の状態（0037 と同じ）を Dify の DB に保存し、その実行の下流のオブジェクトを捨てる。
  - 再開のイベント（kairo の待機の終わり）が届いたら、そのとき区画を受け持っているワーカーが、保存した状態から下流を作り直して続ける。
- **human-input の期限切れ。**
  - kairo の待機の期限（タイミングホイール）で表す。beat の定期的な検査は使わない。
  - 期限切れのイベントが届いたら、ワーカーが Dify のフォームを期限切れにして、`__timeout` の分岐に進める。
- **実行記録の保存。** ワーカーの中で書く。保存のタスクには回さない。

### 3. 範囲

- **対象:** ワークフローと chatflow の実行の経路。実行の開始、実行、停止、human-input の再開と期限切れ、実行記録の保存。
- **対象外:** ナレッジのインデックス作成、メール、プラグインなど、実行と関係しない Celery のタスク。human-input のメールの通知は、今のまま `mail` の queue に出す。

### 4. 実装の段階

1. kairo-dify: 区画ごとの耐久のイベントの API、ack、区画の割り当てと配り直し。
2. Dify: ワーカーにイベントの下流の役を足す。0037 の合成器を使い、Celery のタスクの中でしていたこと（生成器から下流まで）を、ワーカーの中のイベント駆動の処理に移す。
3. Dify: API の投入、停止、signal を kairo-dify に直接向ける。期限切れを kairo に移す。
4. 比較を取り直す。条件は 0037 の 4 節と同じで、Celery は止める。

## 結果

- ワークフローの実行の経路から Celery がなくなる。運用するプロセスは、kairo-dify、Dify のワーカー、API の 3 つ。
- 処理量は、実行の数ではなく、ノードの実行に要る資源と外部の上限で決まる（ADR 0039）。
- ワーカーやデーモンが落ちても、ack の後から続けられる。Dify の記録が欠けない。
- 待っている実行は、ワーカーの資源を使わない。
- 悪くなること・確かめること:
  - Dify のコードのうち「1 実行 1 タスク」を前提とした部分（生成器、パイプライン、キュー）を、イベント駆動に直す必要がある。直す量は、段階 2 で調べて追記する。
  - ワーカーの中で、実行中の実行ごとに下流の状態を持つ。状態の大きさ（実行中の数に比例する）を測る。
  - kairo-dify が 1 台だと、そこが止まると実行も止まる（状態は失われない）。複数台にして、シャードの持ち主をリースで決め、落ちた台のシャードを引き継げるようにするのは、別の ADR で決める。
  - Celery のワーカーの設定（同時実行数、キューの名前）で運用していた環境は、ワーカーの台数で調整することになる。
- テスト:
  - kairo-dify: 区画の購読、ack、渡し直し、配り直し。1 つの区画を同時に 2 つの接続が受け持たないこと。
  - ワーカー: 渡し直しでの重複の除去、一時停止の後の下流の作り直し、期限切れ。
  - 実際の Dify で、0037 と同じ SSE と DB の比較を、Celery を止めた状態で取り直す。

## 検討した代替案

- **0037 の第 1 段階のまま、Celery の同時実行数を増やす。** 頭打ちの位置が動くだけで、1 実行 1 タスクの構造、タスクが落ちたときの欠け、待っている実行の扱いは残る。
- **kairo を常駐させず、実行のときにだけ動く実行器にする。** 状態の置き場、受け持ち、起こす仕組みは、ホスト（Dify の Postgres と Redis、n8n の DB と Redis）が実装する案。
  - 1 歩進めるたびに、DB や Redis との往復（数 ms）が何度も要る。kairo のエンジンの中なら、1 回の遷移は約 1µs。
  - リース、起こす仕組み、公平さを、Python と TypeScript でそれぞれ作り、正しさを保つ必要がある。いちばん間違えやすい部分を二重に持つことになる。
  - 参考: n8n 2.42.0 は、待ちの境い目でだけ状態を DB に保存する。実行中にプロセスが落ちた実行は `crashed` の印を付けるだけで、続きからは再開しない。
- **下流（保存、SSE）を Go で作り直し、kairo-dify が直接書く。** ADR 0036 で捨てた案と同じ。
- **下流だけを受け持つ常駐のプロセスを、ノードのワーカーとは別に置く。** 役ごとに増減できるが、運用するプロセスの種類が増える。1 種類にまとめ、必要なら起動の引数で役を分ける。
- **API のプロセスがイベントを直接読んで、SSE を流す。** クライアントが切れた実行や、API を通らない実行（トリガー）の記録を、誰も書かなくなる。

## 確認したこと（2026-10-05）

- human-input のメールの通知は、今のまま Celery の `mail` の queue に出す（この ADR の範囲外）。
- トリガーと非同期の実行も、kairo-dify への直接の投入に移す（この ADR の範囲）。

## 実装で詰めた詳細（2026-10-05 追記、ADR 0017）

### kairo 側（`compat/dify/daemon/feed.go`）

- **区画はシャード。**
  - 1 つの実行のイベントは、すべて同じシャードに、順に入る。エンジンのイベントの出口（ADR 0034）の ack もシャードごとである。そこで、区画をシャードそのものにした。
  - 区画の数はシャードの数で、データディレクトリごとに固定される（不変条件 9）。`kairo-dify` の `-shards` の既定は 64。ワーカーの台数の上限は区画の数になる。
  - エンジンの購読は 1 つ（`dify`）。デーモンが、エントリをシャードで区画に振り分ける。
- **ack。**
  - ワーカーはエントリを 1 つずつ（ID で）ack する。ID は `シャード.ティア.LSN.通し番号` で、再起動しても変わらない。
  - デーモンは、区画の先頭から続けて ack されたところまで、エンジンの出口を ack する。
  - ログの位置を持たないエントリ（チャンク）は、そのとき受け持っている接続にだけ送り、ack は要らない。
  - 受け持ちの割り当てには世代を付ける。古い世代の ack は無視する。
- **受け持ち。**
  - ワーカーは `GET /v1/feed?want=N` でつなぐ。デーモンは、空いている区画を割り当てる。
  - 新しい接続が分け前より少ない区画しか持てないときは、分け前を超えて持っている接続から取り上げる（`revoked`）。
  - 閉じた接続の区画は、ほかの接続に割り当て直す。割り当てられた接続には、その区画で ack されていないエントリを、先頭から送る。
- **計画の準備（`dify.Options.Prepare`、`PUT /v1/plans/{name}?prepare=1`）。**
  - 実行の先頭に、signal `dify.prepare` を待つ待機（`__prepare`）を置く。会話変数があるときは、その payload から会話変数を設定する assign（`__vars`）も置く。実行の入力への参照は、待機の payload の `input` を読む。
  - API は、Celery のタスクに渡していた引数だけを入力（`__host`）にして投入する。変数を作るのは、区画を受け持つワーカーである（`POST /v1/runs/{id}/prepare`）。
  - 待機の期限は 1 時間。それまでにどのワーカーも準備しなければ、実行は失敗する。
- 0037 の「実行ごとのメモリのバッファ」と `GET /v1/runs/{id}/events` は削除した。
- エンジンに `Engine.Shards()` を足した。
- テスト: `TestRunEventsAndHumanInput`、`TestUnacknowledgedEntriesAreDeliveredAgain`、`TestPartitionsAreShared`、`TestAcknowledgementsReachTheEngine`、`TestPreparedRun`、`TestCancel`、`TestPlansPersist`

### Dify 側（ブランチ `feat/kairo-engine`）

- **API（`services/app_generate_service.py`、`core/workflow/kairo/start.py`）。**
  - ストリーミングの実行の `on_subscribe` で、Celery のタスクの代わりに、計画の登録（`?prepare=1`）と実行の投入を行う。投入は、開始が耐久化してから返る。
  - 引数（`AppExecutionParams`）は、実行の入力 `__host` に入れる。
- **ワーカー（`core/workflow/kairo/feed.py`、`flask kairo-worker`）。** ノードの実行と、イベントの下流の両方を 1 つのプロセスで受け持つ。
  - 区画のイベントを、実行ごとに振り分ける。
  - 実行の最初のイベントが `run_start` なら、Celery のタスクの本体（`_AppRunner.run()`）を動かす。それ以外（一時停止の後に続いた実行）なら、再開のタスクの本体（`_resume_app_execution`）を動かす。
  - どちらも、`KairoGraphEngine` がこの実行に「付いた」状態で動く。付いた状態では、実行を投入せず、変数を送る（prepare）。イベントは、ワーカーが振り分けたものを読む。
  - 下流が終わったら（実行の終わり、または一時停止）、読んだエントリを ack する。下流が終わった後に届いたイベントは、次の下流を始める（一時停止の直後に続いた場合）。
  - 下流は、動いている実行ごとにスレッドで動く。待っている実行は何も持たない。スレッドの数を予算で抑えるのは ADR 0039 で行う。
- **human-input（`core/workflow/kairo/human.py`、`services/human_input_service.py`）。**
  - フォームが送信されたら（期限切れも同じ経路）、API が、一時停止の保存した状態からノードを実行して選択と入力を求め、kairo に signal で送る。Celery の再開のタスクは使わない。
  - kairo が実行を続けると、そのイベントを受け持つワーカーが、再開の処理で下流を作り直す。このときは signal を送らない（API が送った）。
- **エンジンの選び方。** `KairoGraphEngine` を使うのは、その実行がワーカーに付いているときだけ。付いていない実行（ブロッキングの実行は API のプロセスで動く、単体のデバッグの実行）は graphon のまま動く。
- **まだのもの:**
  - ブロッキングの実行（`response_mode=blocking`）を kairo で動かすこと。
  - トリガーと非同期の実行を、直接の投入に移すこと。
  - human-input の期限切れの検査を、beat から kairo の待機の期限に移すこと（kairo の待機の期限は効いているが、Dify のフォームを期限切れにする処理は beat のまま）。
  - 受け持ちが移ったときに、前の持ち主がまだ処理中の実行を止めること（両方が同じ実行を処理しうる。記録はノードの実行 ID で上書きになるが、SSE は重複しうる）。

### 負荷試験で見つかって直したこと（2026-10-06）

- **実行時間の上限を kairo に渡さない（`start.py` の `_limits`）。**
  - 直す前は、`WORKFLOW_MAX_EXECUTION_TIME` を kairo の `MaxDuration` として渡していた。kairo の期限は待ちの時間も数える（ADR 0030）。そのため、human-input で止まった実行は、既定の 1 時間で失敗した。graphon では、時間は開始か再開のたびに数え直す（`ExecutionLimitsLayer`）ので、待ちは数えない。
  - 時間の上限は、graphon と同じ Dify の `ExecutionLimitsLayer` に任せる。kairo に渡すのは手順の数の上限（`max_steps`）だけにした。
- **上限による中止は、その場で受け取る（`engine.py` の `_LayerChannel`）。**
  - 直す前は、中止の命令をスレッドで 0.1 秒ごとに Redis から読んでいた。その間に kairo が実行を最後まで進めてしまい、graphon なら止まるところが成功になった。
  - 層（`ExecutionLimitsLayer`）には、Redis ではなくプロセスの中の命令の口を渡す。層が中止を送ると、イベントを処理しているその場で kairo の実行を取り消す。外からの停止（API の stop）は、これまでどおりスレッドで Redis から読む。
    - 最初は、イベントを 1 つ処理するたびに Redis を読んで確かめた。iter（1 実行で約 100 のイベント）で、Redis への往復が 1 実行あたり約 100 回増え、8 プロセスの処理量が 18.9 回/秒から 12.4 回/秒に落ちた。そのためやめた。
  - 中止したら、そのとき動いていたノードの終わりだけを処理し、それより後に始まったノードは記録しない。実行は中止で終える（graphon と同じ「Aborted: Maximum execution time exceeded: …」）。
- **一時停止から再開した下流は、届いているイベントを先に読む（`EventSource.pending`）。**
  - 直す前は、フォームが開いたままなら、何も読まずに一時停止し直した。一時停止中に kairo 側で実行が終わった場合（上限、取り消し）、その `run_end` が読まれず ack もされなかった。区画の先頭が詰まり、背圧で全体が止まった。詳しくは ADR 0040 の背景。
- **調べるための道具。**
  - kairo-dify は SIGUSR1 で、エンジンの数（`Stats`）と、ack されていないエントリを持つ区画の先頭（`Daemon.FeedState`）をログに出す。
  - Dify のワーカーは、SIGUSR1 で全スレッドのスタックを出す（`faulthandler`）。
- **一時停止中の停止（stop）は、graphon と同じに扱う。** 一時停止中の実行を Dify で停止しても、kairo には伝えない。graphon でも、停止は何もしない。実行は一時停止のまま残り、フォームを送信すれば続きを実行して成功する（両方で確かめた）。
