# 0082. 永続レジストリは版付きカタログとして耐久化し、現行計画を明示する

- 状態: 承認（2026-11-18）
- 日付: 2026-11-18

## 背景

kairod は、HTTP API で受け取ったノード仕様と計画を、実行に利用できる状態にしてデータディレクトリへ保存する。状態遷移を適用している間はコンパイル済みの計画が必要だが、実行の開始記録には計画の正確な名前とハッシュが残るため、再起動後のリカバリに必要な永続的な正典は、その組に対応する `ir.Frozen` である。使われていない過去の計画まで常にコンパイルしてメモリへ置く必要はない。

既存の保存では、ノードの action と計画の名前に含まれる `/`、`:`、`@` をすべて `_` に置き換えてファイル名を作る。この変換では異なる正確な名前が同じパスになり、後の登録が前のファイルを置き換えうる。ファイルは一時ファイルから置き換えるが、ファイル本体と親ディレクトリの同期を完了条件にしていない。そのため、成功応答の後に電源断が起きると、登録した計画を失い、耐久化済みの実行を復元できない可能性がある。

また、登録はメモリを先に変更してから保存する。保存に失敗して HTTP がエラーを返しても、そのプロセスでは失敗した登録が利用できる。起動時には保存された計画を更新時刻の順に読み、同名で最後に読んだ版を現行にする。更新時刻はコピーや復元で変わり、同じ値にもなりうるため、同じファイル集合から同じ現行版を選べるとは限らない。

既存ファイルには、保存された各計画の正確な名前とハッシュは入っているが、「どの版が現行か」という記録はない。同名の版が複数ある場合、元の現行版をファイル内容だけから復元することはできない。したがって、登録の耐久化境界、正確な名前の表現、現行版の選択、既存形式からの移行を一つの判断として決める必要がある。

## 決定

### 決定項 1（正確な名前と現行版を版付きカタログに記録する）

永続化するノード仕様、すべての凍結済み計画、計画名ごとの現行版を、一つの版付き JSON カタログに記録する。action と計画名はファイル名へ不可逆変換せず、正確な文字列としてカタログ内に保存する。計画の現行版はハッシュへの明示的な参照とし、ファイルの更新時刻、列挙順、パス名から推測しない。

同じ正確な計画名とハッシュに異なる凍結内容が対応した場合は、どちらかを選ばず登録または起動を失敗させる。過去の実行を復元するための計画版は、現行版が変わってもカタログに残す。

### 決定項 2（耐久化したカタログを公開より先に確定する）

永続レジストリへの変更は直列化し、変更後の完全なカタログを原子的かつ耐久的に置き換える。ファイルの内容と置き換えを含むディレクトリのメタデータが耐久化してから、実行、コンパイル、登録に伴う通知へ変更を公開し、成功を返す。

置き換え前に確定した通常の保存失敗では、永続カタログと実行から見える登録のどちらも直前に確定した状態に保つ。置き換え後のディレクトリ同期が失敗した場合は、旧版と新版のどちらが電源断後に残るかを確定できないため、変更を実行へ公開せず、新しい登録と新しい実行を再起動まで受け付けない。耐久化の後、応答より前にプロセスが停止した場合も結果が不明になりうるため、再起動後に同じ内容の登録を安全に再試行できるようにする。

カタログを永続レジストリの正典とし、メモリ上の登録は破棄して再構築できる作業集合として扱う。現行計画と、実行中または復元中の run が参照するコンパイル済み計画はメモリに置けるが、参照されていない過去の凍結済み計画を常駐させることは要件にしない。必要な読み込みとコンパイルはシャードのイベントループ外で行い、実行中の状態遷移にストレージ I/O を持ち込まない。

起動時はカタログの参照、計画ハッシュ、重複を検証してから登録を公開する。カタログが不完全または矛盾している場合は、一部だけを利用可能にせず起動を失敗させる。検証や登録のために一時的にカタログ全体を読むことと、すべての計画を常駐させることは区別する。

### 決定項 3（旧形式の曖昧な現行版を推測しない）

版付きカタログがなく旧形式のファイルがある場合は、ファイル内の正確な action、計画名、ハッシュ、凍結内容を読み、カタログへ移す。パス名と更新時刻は識別や順序の根拠にしない。移行したカタログを耐久化してから、その内容を利用可能にする。

同じ計画名の有効な版が一つだけなら、その版を現行にする。複数ある場合は、すべてを過去の実行の復元に利用できる状態で残すが、現行版は推測しない。利用者が既存の登録経路で使う版を明示的に再登録するまで、その名前では新しい実行を開始できない。旧形式で既に同じパスへ上書きされ、残っていない登録は復元できない。

### この ADR で決定しないこと

- カタログのフィールド名、ロック、I/O 補助関数、エラー応答などの実装詳細は、実装とテストで定める。
- 過去の計画版を削除できる条件と回収方法は決めない。必要になった場合は、リカバリ中または保存中の実行との関係を別の ADR で決める。
- 計画ハッシュの長さと、開始記録に保存する計画識別子の形式は変えない。同じ名前とハッシュに異なる内容が現れた場合に拒否する範囲に留め、識別子自体の変更は別の ADR に委ねる。
- メモリ上の作業集合から使われていない計画を外す時機と上限は決めない。必要になった場合は、実行中の参照を保ったまま回収する方針を別の性能・資源管理の判断で定める。
- 永続化を無効にした埋め込み利用のメモリ内登録は対象にしない。

## 結果

- 良い影響: 登録成功後に開始した耐久実行は、電源断後も同じ凍結済み計画で復元できる。異なる正確な名前は互いを上書きせず、コピーや復元後も現行版は変わらない。
- 良い影響: 通常の保存失敗で、エラーを返した登録だけが実行から見える状態をなくせる。起動時も、壊れたレジストリを部分的に公開しない。
- 良い影響: 過去の凍結済み計画はカタログだけに保持でき、登録履歴の総量を常駐メモリ量に直結させずに済む。
- 悪い影響: 登録のたびにカタログ全体を置き換えるため、登録数に応じて書き込み量が増える。登録は実行のホットパスではないが、大きなレジストリでは登録遅延が増える。
- 悪い影響: 旧形式に同名の計画が複数ある場合、移行後に利用者が現行版を明示するまで、その名前の新しい実行を開始できない。誤った版を自動選択しない代わりに、移行時の操作が必要になる。
- 悪い影響: カタログの置き換え後にディレクトリ同期が失敗すると、進行中の実行は続けられるが、新しい登録と新しい実行にはプロセスの再起動が必要になる。
- 中立な影響: 既存の計画ハッシュと WAL の開始記録は変わらない。旧形式のファイルは移行入力として読めるが、カタログの耐久化後はカタログが正典になる。
- 新しく守る制約: 永続登録は、耐久カタログ、実行への公開、成功応答の順で確定する。現行計画を更新時刻やファイル列挙順から決めてはならない。カタログからの読み込みをシャードのイベントループで行ってはならない。

## 検討した代替案

- 正確な名前を可逆に符号化した個別ファイルと、現行版を示す別ファイルを使う: 名前の衝突は防げるが、計画本体と現行版の複数ファイルを一つの登録として確定する順序と、クラッシュ後の中間状態の扱いが必要になる。
- 登録を追記ログとして保存する: 登録順と現行版を復元でき、全体の置き換えも避けられるが、リプレイ、破損境界、圧縮、退役という別の永続ログの規約が必要になる。実行ログとは異なる低頻度の設定変更には複雑さが大きい。
- 不可逆なファイル名にハッシュの接尾辞を足す: 実用上の衝突確率は下げられるが、正確な名前を識別子にできず、現行版の原子的な更新も解決しない。
- 旧形式の更新時刻またはハッシュ順で現行版を自動選択する: 操作なしで移行できるが、更新時刻はコピーや復元で変わり、ハッシュ順には登録順の意味がない。誤った計画で新しい実行を始める危険を避けられない。

## 関連する ADR

- ADR 0006 の決定項 3（永続化では `ir.Frozen` を保存する）: カタログに保持する計画の正典と、リカバリで同じハッシュへ戻す要件を定めている。
- ADR 0017 の決定項 1（ADR を承認してから実装する）: この永続形式の変更は、本 ADR の承認後に実装する。
- ADR 0023 の決定項 1（開始記録の耐久化後に `Submit` が返る）: 成功した耐久実行を復元するには、開始より前に対応する計画が耐久化されている必要がある。
- ADR 0060 の決定項 1（ワークフローは始めたときの版で動かし続ける）: 実行中の版を保持し、新しい実行にだけ明示した現行版を使う性質を共有する。
