# 0061. コードで書くワークフローの完了と取り消しは、先に記録された結果だけを返す

- 状態: 承認
- 日付: 2026-11-04
- 関連: 不変条件 2・3・5 / ADR 0023（耐久化した開始）、0049（コードで書く API）、0058（Go の SDK）、0059（埋め込みのランタイム）/ GitHub Issue #3

## 背景

コードで書くワークフローは、関数を最初から動かし直し、終わった呼び出しの結果を記録から返すことで再開する（ADR 0049）。ワークフロー自身は `kairo.workflow` の実行であり、関数が返ると、SDK が `done` のシグナルを送って成功または失敗を記録する。取り消しは、同じ実行へ `cancel` のイベントを送る。

コアは、完了した実行へ後から届いたイベントを無視する。そのため、`done` と `cancel` のうち先に適用されたものだけがログに残り、記録の結果は一意になる。一方、SDK は、関数が返した値と、`done` を送ったときのエラーだけを見てライブの呼び出し元へ結果を返している。`done` が、先に記録された `cancel` のために無視されても、それを区別していない。失敗を記録する経路では、`done` を送ったエラーも捨てている。

この競合で、次の順になることがある。

1. ワークフローの関数が値を返す。
2. 別の処理からの `cancel` が先に適用され、実行は `cancelled` になる。
3. SDK の `done` は、終わった実行へのイベントとして無視される。
4. ライブの `Child` は関数の値を返すが、再開した `Child` は記録から `ErrCancelled` を返す。

親のワークフローは、ライブと再開で違う枝へ進みうる。後の呼び出しの入力や ID が変わると、記録にない実の呼び出しとしてもう一度動くことがある。個々の実行の記録は決定的でも、記録と異なる結果を SDK が返すことで、リプレイ可能性を利用するコードで作用が重なる。

同じ形の実装は Go・TypeScript・Python の 3 SDK にある。kairod をバックエンドにした場合も、`done` と `cancel` は非同期に同じ実行へ届くので、同じ規則が要る。

## 決定

### 1. 完了と取り消しは、先に記録されたものだけが有効になる

ワークフローの成功、失敗、取り消しは排他的な終端結果とする。`done`（成功または失敗）と `cancel` のうち、実行が終わる前に先に適用されたイベントだけが有効になる。後から届いたイベントは、これまでどおりコアが無視し、ログには書かない。

「先」は呼び出しを始めた壁時計の順ではなく、保存先が直列化した順とする。

- 埋め込みのランタイムでは、実行の行を更新するトランザクションの順。
- kairod では、シャードがイベントを適用し、同じ順でログに書いた順（不変条件 3）。

コアの状態、イベントの種類、ログと表の形式は変えない。すでにコアが持つ「終わった実行へのイベントを無視する」という規則を、SDK が返す結果にも反映する。

### 2. SDK は関数の手元の結果でなく、耐久化した終端結果を返す

3 SDK の、コードで書くワークフローを動かす処理（Go の `runAs`、TypeScript と Python の対応する処理）を、次の規則にする。

1. 関数が成功または失敗で戻ったら、これまでどおり `done` を送る。
2. その実行の終端結果が耐久化するのを待ち、記録された状態と出力を読む。
3. ライブの呼び出し元にも、再開時に記録から読むものと同じ結果を返す。

記録が `cancelled` なら、関数が値を返していても取り消しを返す。記録が `completed` または `failed` なら、その記録の値または失敗を返す。`done` が先なら、その後の取り消しは結果を変えない。

`done` の送信または終端結果の確認に失敗したときは、関数の手元の値やエラーを確定した結果として返さない。保存先のエラーまたは「ここではもう駆動していない」というエラーを返し、次の駆動が記録から結果を決める。失敗を記録する経路でも、`done` のエラーを握りつぶさない。

kairod の `Wait` は、終了が耐久化してから返す。埋め込みの保存先では、終端結果を適用したトランザクションの commit 後に結果を確かめる。このため、SDK が結果を返した後にプロセスが落ちても、再開時の結果は同じになる。

### 3. `Cancel` は、記録された結果を確認して返す

SDK の `Cancel` は、取り消しの送信を受け付けただけでは成功を返さない。対象の実行が耐久化した終端状態になるまで待ち、次のように返す。

- 終端状態が `cancelled`: 成功。すでに取り消されていた場合も成功とし、取り消しは冪等にする。
- 終端状態が `completed` または `failed`: `ErrRunSettled`（TypeScript・Python は `RunSettledError`）。この呼び出しの取り消しは結果を変えなかったことを知らせる。
- 実行がない: 既存の「実行がない」エラー。
- 呼び出し側の待ちが打ち切られ、どちらが記録されたか確認できない: 成功とはせず、既存の停止または context のエラー。

Go の `(*Kairo).Cancel`、TypeScript の `Kairo.cancel`、Python の `Kairo.cancel` に同じ意味を持たせる。生の kairod HTTP API がイベントを非同期に受け付ける形は変えず、SDK は取り消しを送った後に既存の wait API で耐久化した結果を確認できる。ワーカープロトコルとログの形式は変えない。

### 4. 費用

ワークフローが終わるとき、SDK は耐久化した終端結果を確認する。これは、利用者へ返す結果を記録と一致させるための「結果の記録」の仕事であり、ADR 0041 の実行 1 回に要る仕事に当たる。

埋め込みのランタイムでは、イベントを適用した処理が持つ終端状態を使える場合は、余分な DB の読み取りをしない。別プロセスが競合に勝った場合と kairod では、既存の wait/get の経路で記録を読む。確認のためのポーリング、実行ごとの goroutine、常駐する対応表は足さない。

## 結果

- `Child` とトップレベルの `Run` が返す結果は、ライブ実行と再開で一致する。
- 完了と取り消しが競合しても、親は記録と同じ枝へ進み、競合だけを理由に後の実の呼び出しを別の ID で動かさない。
- 取り消しを呼んだ側は、完了に負けた取り消しを成功と誤認しない。
- `Cancel` は、これまでの「送信を受け付けたら戻る」より長く待つことがある。利用者が待つのを打ち切っても、実行の終端結果そのものは変えない。
- コア、状態の符号化、ログ、保存先の表、ワーカープロトコルには変更がない。
- 3 SDK で、成功対取り消しと、失敗対取り消しの意味を同じに保つ。

次のテストを足す。

- 関数が成功で戻った直後、`done` を送る前に取り消しを入れる決定的な hook をテスト内に置く。取り消しが先なら、ライブと再開の両方が取り消しになる。
- `done` を先に記録してから取り消す。ライブと再開の両方が同じ成功値になり、`Cancel` は `ErrRunSettled` / `RunSettledError` になる。
- 関数の失敗と取り消しについても、どちらが先かの両方を確かめる。
- 親が結果の違いで別の入力の呼び出しへ進む形の回帰テストを置き、ライブと再開で呼び出しの ID と回数が変わらないことを確かめる。
- 埋め込みの保存先と kairod 経由の両方で確かめる。Go の共通の振る舞いは `kairotest` に置き、TypeScript・Python にも同じ競合のテストを置く。

## 検討した代替案

- **`done` の前に取り消されていないかを読む:** 読み取りと `done` の間に取り消せるので、競合をなくせない。
- **関数が戻った時点からは、常に完了を取り消しより優先する:** 関数が戻ることと保存先への記録を原子的にできない。別プロセスは関数が戻ったことを知らず、取り消しが成功したかも判断できない。
- **ライブでは関数の値を返し、再開時だけ記録に従う:** 現状の不具合を残し、リプレイで親の経路が変わる。
- **取り消しを、呼び出しの間でだけ調べるシグナルにする:** 実行中の呼び出しをその場で止められず、ADR 0026 の取り消しとも合わない。
- **SDK のプロセス内のロックで `done` と `cancel` を直列化する:** 別のプロセスや kairod からの取り消しとは直列化できない。保存先またはシャードがすでに持つ順を使うほうが、記録と一致する。

## 実装で詰めた詳細（2026-11-04 追記、ADR 0017）

- 3 SDK とも、`done` を送った後に、既存の backend の `wait` で終端結果を読む形にした。kairod では `Wait` が終了の耐久化後に返る。埋め込みでは `signal` / `cancel` のトランザクションが終わった後の行を読む。backend の契約を増やさず、同じ経路で意味をそろえた。
- 埋め込みで増えるのは、ワークフロー終了時の主キーによる読み取り 1 回である。ポーリングはせず、別プロセスが競合に勝った場合は既存の通知で起きる。これは記録された結果を利用者へ返すための確認として扱う。
- 関数の失敗をこのプロセスが記録したときの原因（Go の `WorkflowError.Err`、TypeScript の `cause`、Python の `__cause__`）は、記録されたエラーメッセージと手元の原因が同じ場合だけ残す。別の駆動が先に違う失敗を記録した場合に、負けた側の原因を付けない。
- `Cancel` は、取り消しを送った後に同じ `wait` を使う。最終状態が `cancelled` なら、先に取り消されていた場合を含めて成功する。`completed` または `failed` なら、Go は `ErrRunSettled`、TypeScript と Python は `RunSettledError` を返す。
- テストでは backend を包み、`done` の直前に `cancel` を適用して、その耐久化を待ってから `done` を通す。関数の成功と失敗の両方で、ライブと再開がともに取り消しになることを確かめる。Go はメモリと共通の保存先テスト、TypeScript は kairod と SQLite、Python は同じ workflow suite で確かめる。
