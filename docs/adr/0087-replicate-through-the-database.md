# 0087. kairod の複製は、自前で作らず、SQL の保存先のデータベースの複製に任せる

- 状態: 承認（2026-11-27）
- 日付: 2026-11-27

## 背景

kairod は、既定では、ログ（WAL）とスナップショットとブロブを、データディレクトリのファイルに書く。耐久性のティア `file` は、ログをそのファイルに fsync してから確定とする。複製はないので、データを置いたディスクが壊れると、確定した実行も失われる。

エンジンには、もう 1 つのティア `replicated` がある。これは「複製が ack したログ」を表すティアで、エンジンには、そのための Sink を差し込む口（`Config.Sinks`）だけがある。kairo 自身の、複製する Sink の実装はない。`docs/runtime.ja.md` も、複製は v0 に含めていないとしている。

一方、エンジンは、ログとスナップショットとブロブを SQL のデータベースに保存できる（ADR 0020）。PostgreSQL・MySQL（TiDB を含む）・Oracle・SQLite の実装があり、書き手の排他（フェンシング）も持つ。保存先の書き込みは、そのデータベースのコミットで確定する。PostgreSQL などは、データベースとして複製を持つ。たとえば PostgreSQL のストリーミングレプリケーションで同期コミットを使えば、コミットはスタンバイが受け取ってから返る。

ただし、SQL の保存先を使えるのは、Go のプログラムにエンジンを組み込んだときだけである。配っている `kairod` のコマンドには、保存先を選ぶ指定がなく、ファイルにしか書けない。

そのため、`kairod` をそのまま使う利用者には、ディスクが 1 つ壊れても確定した実行を失わない構成がない。

## 決定

### 決定項 1（kairo は、ログの複製を自前で作らない）

kairo は、ログ・スナップショット・ブロブを複製の相手へ送る仕組みを、自前では作らない。複製は、保存先のデータベースの複製に任せる。

### 決定項 2（kairod は、保存先に SQL のデータベースを選べる）

`kairod` は、耐久性のあるティアのログ・スナップショット・ブロブを、ファイルの代わりに SQL のデータベースに保存できるようにする。使える製品とその実装は、ADR 0020 のとおりとする。

- 選んだデータベースのコミットが、そのティアの確定になる。複製の構成（同期か非同期か、スタンバイの数）は、データベースの側で決める。
- 書き手の排他は、ADR 0020 のフェンシングのとおりとする。複製の切り替え（フェイルオーバー）のあとに、古い kairod が書き続けることはない。

### 決定項 3（ディスクが壊れても失わない構成を、利用者向けに示す）

ディスクが 1 つ壊れても確定した実行を失わない構成として、同期の複製を持つデータベースを保存先にする構成を、文書に示す。そのとき、何が守られるか（どの時点で確定とするか）と、守られないこと（非同期の複製では、切り替えのときに最後の確定を失いうる）を書く。

### この ADR で決定しないこと

- `kairod` で保存先を選ぶ指定の形（フラグか、環境変数か、設定ファイルか）と、接続の資格情報の受け取り方。実装の PR で決める。資格情報は、ログやエラーに出さない。
- 埋め込みのランタイム（SDK）。もともと SQLite か PostgreSQL に保存するので、その複製はデータベースの側で構成できる。
- ティア `replicated` の扱い。利用者が Sink を差し込む口として、そのまま残す。
- ファイルの保存先を、ほかのマシンやオブジェクトストレージへ送る仕組み。必要になれば、別の ADR で決める。

## 結果

- 良い影響
  - `kairod` の利用者が、データベースの複製で、ディスクが 1 つ壊れても確定した実行を失わない構成を取れる。
  - kairo は、複製・切り替え・追いつきの仕組みを持たなくて済む。それらは、データベースが長く磨いてきたものを使う。
- 悪い影響
  - ディスクの故障に耐えるには、利用者が複製を持つデータベースを用意する必要がある。ファイルだけの構成では、これまでどおり耐えない。
  - SQL の保存先の書き込みは、ファイルより遅い（ADR 0020 の計測）。同期の複製では、確定までの時間に、スタンバイまでの往復が加わる。
  - `kairod` のコマンドが、データベースのドライバを含む分だけ大きくなる。
- 中立な影響
  - エンジン、ログの形式、ティアの意味は変わらない。
  - ファイルの保存先の振る舞いは変わらない。
- 新しく守る制約
  - 資格情報は、ログ・エラー・観測に出さない。

## 検討した代替案

- **ティア `replicated` の Sink を kairo が作る（ログを別のノードへ送り、ack を待つ）:** 複製の相手の選び方、切り替え、追いつき、分断のときの扱いを、すべて kairo が持つことになる。データベースの複製で同じ性質が得られるので、採らなかった。
- **スナップショットとブロブだけを、オブジェクトストレージへ写す:** ログを失えば、最後のスナップショットのあとの確定が失われる。ディスクの故障に耐える性質にならないので、採らなかった。
- **何もしない（文書に、複製はないと書くだけ）:** `kairod` の利用者に、ディスクの故障に耐える構成がないまま残る。採らなかった。

## 関連する ADR

- ADR 0020（指定があれば SQL データベースに保存できるようにする）: SQL の保存先の実装とフェンシング。この ADR は、それを `kairod` から選べるようにし、複製の手段として位置づける。
- ADR 0016（ログはチェックポイントとセグメント単位の退役で圧縮する）: 保存先が SQL でも、退役の規則は変わらない。
