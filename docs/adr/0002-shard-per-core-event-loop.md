# 0002. 1コア1シャードのイベントループが実行を所有し、ロックを持たない

- 状態: 承認（2026-10-01）
- 日付: 2026-09-30
- 関連: FR2 / 不変条件 6, 9

## 背景

待機中の実行 100 万件を 1 台で保持するには、実行ごとに goroutine やタイマーを持てない。また、実行の状態にロックをかけると、外部 I/O の間ロックを保持しない、という不変条件を守りにくい。

## 決定

- シャードは 1 つの goroutine（`engine/shard.go` の `loop`）で、担当する実行の状態を排他的に所有する。ロックはない。
- 外からの入力は、ブロックしない MPSC キュー（`mpsc.Queue`。Push は短いクリティカルセクションだけ）で届ける。対象は、Submit、ワーカーの結果、シグナル、ログの ack、スナップショットの読み書き完了。ループはこのキューと、シャード自身の OS タイマー（→ 0010）の 2 つだけを待つ。タイマーが鳴ったら、発火したものを `wheel.Advance` で取り出す。1 回の起床で溜まった入力はまとめて処理し、ログもまとめて渡す（→ 0005）。
- 実行はその ID の FNV-1a ハッシュでシャードに割り当てる。シードをランダムにすると再起動後に別シャードへ振られるため使わない。シャード数はデータディレクトリごとに固定する（`SHARDS` ファイルで検査）。
- I/O はコミッタの goroutine か、固定数（16）の I/O ワーカーで行い、結果はメッセージで返す。`e.doIO` はジョブを無制限の MPSC キューに積むだけで、ブロックも goroutine の起動もしない。

## 結果

- goroutine の数は実行数によらない（`TestNoGoroutinePerRun`、`TestEvictionBurstUsesFixedIOPool`）。1 つの実行は 1 つのシャードの中で完結する。
- 当初の `doIO` は、プールのバッファ（4096）が満杯になると 1 件ごとに goroutine を起動していた。大量の退避が一度に起きるとこの不変条件を破るので、ADR の照合で見つけてキュー方式に直した。
- シャード数を変えるには移行手順が要る（v0 では拒否するだけ）。
- ホットな実行が 1 つあると、そのシャードに偏る。実行の粒度が小さい前提の設計である。

## 検討した代替案

- 実行ごとの goroutine: 待機中に数 KB のスタックと、スケジューラの負荷がかかる。
- 共有の map ＋ ロック: 競合し、ロック保持中の I/O が入り込みやすい。
- `maphash`（ランダムシード）: 実装した後、再起動後の再ルーティングの不具合として発見し、置き換えた。
