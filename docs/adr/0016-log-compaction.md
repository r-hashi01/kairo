# 0016. ログはチェックポイントとセグメント単位の退役で圧縮する

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: FR6 / 不変条件 7, 8 / ADR 0005 を一部置き換え、ADR 0011

## 背景

v0（ADR 0005）のログは増え続け、リカバリではログ全体をメモリに読み込む。長く動かすと、ディスク使用量と再起動時間が際限なく増える。

0005 では LSN を「読み込み時に数えた通し番号」としていた。この方式では、古いセグメントを消すと番号がずれるので、そのままでは圧縮できない。

## 決定

### セグメントと LSN（0005 の一部を置き換え）

- セグメントのファイル名に先頭の LSN を入れる（`shard-NNN.L<20桁の LSN>.wal`）。セグメント内の LSN は、先頭からの通し番号で決まる。
- v0 形式のファイル（`shard-NNN.<8桁>.wal`）も読める。v0 と同じく、前のセグメントからの続き番号として数える。
- `FileSink` は次のときに新しいセグメントを作る。
  - 起動したとき（v0 と同じ）
  - 現在のセグメントが `SegmentSize`（既定 64 MiB）を超えたとき
- `wal.Sink.ReadAll` のコールバックは `fn(lsn, rec)` とし、LSN は Sink が渡す。

### 退役

- 省略可能なインターフェース `wal.Retirer { Retire(lsn uint64) error }` を設ける。
  - Sink は「すべての記録の LSN が `lsn` 未満のセグメント」を丸ごと削除してよい。
  - セグメントの中身を書き換えたり切り詰めたりはしない。
- `wal.Sink` に `Next()`（次に振る LSN）を足す。記録をすべて退役した後でも、再起動したエンジンの LSN が Sink と食い違わないようにするため。
- `Retire` は `Committer.Retire` でキューに積み、コミッタの goroutine 上で実行する。シャードのループは待たない。`Append` によるセグメントの切り替えも同じ goroutine で行うので、両者は競合しない。
- 実行ごとに、まだ必要な最小の LSN（`run.pin()`）を持つ。
  - 最初のチェックポイントが耐久化する前は: 開始記録の LSN
  - それ以降は: 次の 2 つの小さい方
    - 最新のチェックポイント記録の LSN（`cpRec`）。開始記録が消えた後、リカバリがこの実行を見つけるのに要る。
    - スナップショット後にこの実行自身が書いた最初の記録の LSN（`postSnap`）。まだなければ考えない。
  - スナップショットより後に他の実行の記録しかなければ、それらは引き止めない。
- 境界は、シャード×ティアごとに `min(生きている実行の pin, 削除待ちの終了済み実行の pin, 耐久化済み LSN + 1)` とする（`shard.maybeCompact`）。
- 終了した実行は、スナップショットの削除が完了する（`mSnapDeleted`）までは記録を保持する（`s.pins`）。
  - 削除より先に記録を退役させると、クラッシュ後に古いスナップショットだけが残り、終わった実行が生き返ってしまうため。
  - 書き込み中のスナップショットがあるときは、その完了を待ってから削除する（`deleteSnap`）。
  - 同じ RunID で新しい実行が来たら、古い実行のスナップショットの削除が終わるまで、新しい実行の開始を遅らせる（`run.starts`）。古い削除が新しい実行のスナップショットを消すのを防ぐため。リカバリでは、開始記録が来たら同じ ID の以前の記録を捨てる。

### チェックポイント

- スナップショットをストアに書き終えたら、そのティアのログにチェックポイント記録 `recCheckpoint` を足す。中身は、実行のメタデータ（計画、テナント、ティア）とスナップショットの LSN。
- 実行の `cpLSN` / `cpRec` / `postSnap` は、このチェックポイント記録が耐久化してから更新する（`hCheckpoint`）。
  - スナップショットの対象 LSN（`pendSnap`）以降に書いた自分の記録は、エンコードした時点から追跡する（`pendFirst`）。チェックポイントが耐久化するまでの間に書いた記録も取りこぼさないため。
- チェックポイント記録はイベントではない。状態には適用せず、`lastLSN` も進めない。
- 圧縮の判定は ack のときに行う（イベント駆動。ポーリングはしない）。前回の判定から、ワークロードによるログの伸びが `CompactEvery`（既定 65,536 記録）以上あったら、次の 2 つを行う。
  - 境界を計算して `Retire` する。
  - pin が `compactStale`（4）判定分より古い実行を前に進める。
    - メモリにある実行: その場でスナップショットを取る（`checkpointLive`）。ファイルティア以上で、`lastLSN` まで耐久化済みのものに限る。
    - 退避済みでスナップショットがディスクにある実行: 同じスナップショットのチェックポイント記録を、もう一度書くだけでよい。
- 圧縮が自分の判断で書いたチェックポイント記録（`own`）は、「ログの伸び」に数えない。
  - 数えると、待機中の実行が `2 × CompactEvery` 件を超えたとき、書き直した記録だけで次の判定が起き、アイドル中も書き込みと起床が止まらなくなる（実装後のレビューで見つかった）。
  - 書き直しは、ワークロードが `compactStale × CompactEvery` 記録伸びるたびに、実行あたり約 1 回に収まる。
- ログが伸びていない間は判定しない。退役を急ぐ理由もないので、これでよい。
- Sink への追記が一度でも失敗したら、そのログでは退役しない（`l.failed`）。`FileSink` は失敗の後、すべての追記を拒否する。どこまで書けたか分からないので、LSN を Sink とエンジンで揃えたまま続けられないため。
- スナップショットの書き込み（`blob.Dir.Put`）は、リネームの後にディレクトリも fsync する。チェックポイントで開始記録を消す以上、スナップショットは電源断でも残っていなければならないため。

### リカバリ

- 実行は、開始記録かチェックポイント記録のどちらかから見つける。
- 状態は、スナップショット（あれば）にその LSN より後のイベントを適用して作る。上の境界の規則により、生きている実行（と削除待ちの終了済み実行）のこれらの記録は必ず残っている。
- 開始記録もスナップショットもない実行は、終了済みとみなして読み飛ばし、ログに残す。
- `postSnap` は、残っているイベントから計算し直す。

### 不変条件 7 の解釈

不変条件 7 の「書き込みは追記のみ」は、「セグメントの中身は書き換えも切り詰めもしない」という意味とする。すべての記録が不要になったセグメントを丸ごと消すことは、これに反しない。

## 結果

- ログに残るのは、生きている実行のためのものだけになり、リカバリで読む量も同じ範囲に収まる。
- 長く動く実行は定期的にスナップショットされ、待ち続ける実行はチェックポイント記録を書き直される。そのぶん書き込みが増える。
- 終了した実行は、スナップショットの削除が終わるまで記録を残す。I/O が遅いと、そのぶん退役も遅れる。
- `Sink` の `ReadAll` のシグネチャが変わり、`Next` も加わるので、自前の Sink がある場合は対応が要る（v0 では外部実装はない）。
- メモリティアの `MemSink` も `Retirer` を実装する。
- テスト:
  - `TestLogCompaction`: 多数の実行が終わると古いセグメントが消える。圧縮後に再起動しても、退避中の待機実行と実行中だった実行が再開し、終わった実行は生き返らない。
  - `TestFileSinkSegmentsAndRetire`: セグメントのローテーション、LSN の連続性（再起動・全退役の後も）、v0 形式のファイルの読み込み、`Retire` が丸ごとのセグメントしか消さないこと。
  - `TestMemSinkRetire`。
  - `TestCompactionDoesNotWakeIdleEngine`: 待機中の実行が `2 × CompactEvery` を超えても、アイドル中のシャードが起きない（退避あり／なし）。
  - `TestRunIDReuseSurvivesRestart`: 終わった実行の ID を再利用しても、再起動後に新しい実行が正しく復元される。
  - 既存の `TestFileSinkAppendOnly` は「既存セグメントの中身が変わらない」ことを引き続き検証する。

## 検討した代替案

- 生きている記録を新しいセグメントへコピーし、古いものを消す（copy-forward）: 書き込み量が増え、ログの記録を書き直すことにもなる。スナップショットで基点を進める方が単純。
- 各記録に LSN を保存する: 記録ごとに 8 バイト程度増える。番号のずれはセグメント先頭の LSN だけで防げる。
- 圧縮しない: 現状の問題そのもの。
- 一定時間ごとに圧縮を判定する: ポーリングになる（不変条件 6）。ack の進み具合で判定すれば十分。
- 実行の基点を「スナップショットの LSN + 1」にする（最初の設計）: 実装して試したところ、スナップショット後に自分の記録がない待機中の実行が、境界をその位置に固定したまま進まなかった。
- 削除待ちの終了済み実行を引き止めない: スナップショットの削除前にクラッシュすると、古いスナップショットから終わった実行が生き返りうる。
