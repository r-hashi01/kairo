# 0050. kairod では、指定した実行は、終わった後も出力を冪等の期間のあいだ残す

- 状態: 承認
- 日付: 2026-10-07
- 関連: 不変条件 7・8、ADR 0023（冪等な Submit）、0024（実行のブロブ）、0027（終わった実行のマーカー）、0041（実行 1 回あたりのコスト）、0049（SDK）、0051（常駐しない kairo）

## 位置づけ（2026-10-08 見直し）

この ADR は、ADR 0051（常駐しない kairo）より前に書いた。ADR 0051 の後は、次のように位置づける。

- **対象は kairod だけにする。** SDK が kairod をバックエンドにしたとき（`HttpBackend`）の問題である。
  - 埋め込みのランタイム（ADR 0051）では、終わった実行の出力は DB の実行の行（`run.output`）に残る。再起動しても消えないので、この問題は起きない。
  - 基本の形は埋め込みなので、この ADR は急がない。kairod を使う利用者が、再起動をまたいだ再開を必要としたときに進める。
- **埋め込みには、逆向きの問題がある（この ADR では扱わない）。** 埋め込みのランタイムは、終わった実行の行もイベントも消さない。結果は失われないが、DB が際限なく伸びる。
  - 冪等の期間（`idempotencyTTL`）を過ぎた実行を消す仕組みが要る。消し方（いつ、誰が、どの単位で）は保存の形式と冪等の約束に触れるので、別の ADR で決める。
- 下の「決定」から「検討した代替案」までは、kairod についての提案として、そのまま残す。

## 背景

SDK のコードで書く API（ADR 0049）は、呼び出し 1 つを kairo の実行 1 つにする。ワークフローを同じ ID で動かし直すと、終わった呼び出しは kairo が覚えている結果を返す。これで「終わった呼び出しをやり直さない」を実現している。

ところが、終わった実行の出力は、kairod のメモリ（`RecentRuns`、既定 10 万件）にしかない。

- kairod が再起動すると、終わった実行には終了のマーカー（ADR 0027。実行 ID、終わった時刻、状態）だけが残り、出力は消える。
- そのため、kairod の再起動をまたいでワークフローを再開すると、終わった呼び出しの結果を取り出せない。
- 今の SDK は、この場合に `ResultLostError` で止める（外に作用するアクションを二重に実行しないため）。

エージェント（KairoCode）や長いワークフローでは、kairod の再起動（更新、障害）をまたいで再開できることが要る。

## 決定

投入のときに `keep_output` を指定した実行は、終わった後も、出力を冪等の期間（`IdempotencyTTL`、既定 24 時間）のあいだ残す。指定しない実行は、今までどおりにする。

- **指定のしかた:** `SubmitRequest.KeepOutput`（JSON は `keep_output`）。耐久化の段階が `file` 以上の実行に限る（マーカーがそうであるのと同じ）。
  - SDK のコードで書く API は、呼び出しとワークフローの実行に、これを付けて投入する。
- **出力の置き場所:** ブロブの保存先（`blob.Store`）に、キー `kept/<実行 ID>` で置く。
  - 実行のブロブのグループ（ADR 0024、`run/<id>/`）とは別にする。そうしないと、実行の終わりに消えてしまう。
  - ブロブは原子的な置き換えで書く（不変条件 7）。
  - 出力がブロブの参照（`$blob`）を含むときは、中身に置き換えてから置く（終わった実行の結果を中身に置き換えるのと同じ）。
- **順番（不変条件 8 と ADR 0027 に合わせる）:**
  1. 出力をブロブに置く。
  2. マーカーを書く。
  3. マーカーが耐久化したら、スナップショットと実行のブロブを消し、ログの記録を退役に回す（今までどおり）。
  - マーカーより先に出力が耐久化しているので、マーカーがあって出力がない、という状態にはならない。
  - 出力を置いた後、マーカーの前に落ちた場合は、実行の記録が残っているので、再起動で実行を終わらせ直し、同じキーに置き直す。
- **マーカーの形式:** 版を 2 にして、「出力を残した」という印（1 バイト）を足す。版 1 のマーカーも、今までどおり読む（印なしとして扱う）。
- **読み方:** `Get`・`Wait`・`Submit`（既にある ID）で、メモリに結果がなく、マーカーに印がある実行は、ブロブから出力を読んで返す。
  - このときの `RunInfo` は `Trimmed` にせず、`Output` を持たせる。読みは、呼んだ側の goroutine で行う（シャードのループでは読まない）。
- **消し方:** マーカーが期限切れになったとき（`IdempotencyTTL`）、そのブロブも消す。
  - 消すのは、マーカーの期限切れと同じ処理（シャードのループから I/O の goroutine へ）で行う。
  - 消し損ねたブロブは、起動時に、マーカーのない `kept/` のブロブとして見つけて消す（ADR 0024 の後片付けと同じ考え方）。
- **費用（ADR 0041）:**
  - 指定しない実行には、何も増えない。
  - 指定した実行には、終わりにブロブの書き込みが 1 回（耐久化を含む）、期限切れに削除が 1 回増える。これは「結果の記録」の仕事である。
  - メモリには出力を持たない（マーカーの索引に 1 バイトの印が増えるだけ）。

## 結果

- SDK のワークフローは、kairod の再起動をまたいでも、終わった呼び出しの結果を受け取って再開できる。`ResultLostError` になるのは、冪等の期間を過ぎたときだけになる。
- **形式の変更:**
  - 終了のマーカーの版が 2 になる。古いマーカーは読める。
  - 古い kairod は版 2 のマーカーを読めないので、古い版に戻すことはできない（ADR 0027 と同じく、戻すことは約束しない）。
- **新しく守ること:**
  - 出力のブロブは、マーカーより先に耐久化する。
  - マーカーの期限切れでブロブも消し、際限なく残さない。
- **テスト（足す）:**
  - `engine`: `keep_output` の実行が、再起動の後も `Get`・`Wait`・同じ ID の `Submit` で出力を返すこと。
  - `engine`: 期限切れでブロブが消えること。マーカーの前に落ちた場合も、再起動で出力が置き直されること。
  - `engine`: 指定しない実行は、今までどおり出力のないマーカーになること。
  - SDK: kairod を再起動してから同じ ID でワークフローを再開し、終わった呼び出しが動かずに結果を返すこと。

## 検討した代替案

- **すべての実行の出力を残す:** 指定しない実行にも、ブロブの書き込みと削除の費用がかかる（ADR 0041 に反する）。
- **出力をマーカーの中に入れる:** マーカーのログは、番号を指定して 1 件だけ読むことができない（`wal.Sink` は先頭から読むだけ）。出力をメモリの索引に持つことになり、冪等の期間のあいだ、メモリが出力の大きさだけ増える。
- **SDK の側で結果を保存する:** 保存先と耐久化を、アプリの側に持ち込むことになる。kairo を使う意味が薄れる。
- **RecentRuns を大きくする:** メモリにしかないので、再起動で消えることは変わらない。

## 実装で詰めた詳細（2026-10-08 追記、ADR 0017）

- **`keep_output` の記録:** 開始の記録とチェックポイントの記録の「tier のバイト」の上位ビット（`keepBit`）に入れた。
  - 古い記録は、印なしとして読める。
  - この形式の変更も、マーカーの版 2 と同じく、古い kairod に戻せなくする。古い kairod は、印の付いたバイトを知らない tier として読む。
- **出力のキー（決定の範囲内で変えた）:** `kept/<実行 ID>` ではなく、`kept/<実行 ID>/<世代>` にした。
  - 世代は、その実行を終わらせたイベントのログの位置（LSN）で、マーカーにも書く（版 2 のマーカーは、印のあとに世代を持つ）。
  - I/O のワーカーは 16 個が並列に動くので、同じ ID の古い出力を消す処理が、新しい実行の書き込みより後に終わることがある。キーが同じだと、新しい出力が消えて、マーカーだけが残る。世代でキーを分ければ、この入れ替わりが起きても新しい出力は消えない。
  - 世代は、落ちたあとの再起動でも同じ値が求まる（そのイベントの LSN）。マーカーの前に落ちて置き直すときも同じキーに書くので、残骸が出ない。
  - 実装の途中では「`doIO` は順に処理される」と思い込んで、キーを分けていなかった。`invariant-reviewer` の指摘で直した。
- **消し損ねの拾い方（決定から外れる。2026-10-08 に利用者と合意）:** 決定の「起動時に、マーカーのない `kept/` のブロブを見つけて消す」は、ブロブの保存先に一覧を取る手段がないので、次の方式に置き換えた。
  - 期限切れのマーカー、または同じ ID の新しいマーカーに置き換えられたマーカーの出力を、`doIO` で消す。
  - 消し終わるまで、そのマーカーの LSN を `doneLog.deleting` に置き、終了ログをそこより先へ退役させない（`markerBound`）。
  - 落ちたり削除に失敗したりしても、マーカーがログに残るので、次の起動の `recoverMarkers` が見つけて消し直す。起動時の削除も、失敗すればまたマーカーを残す。
  - これで、出力を指すものが何もないまま、出力だけが残ることはない。残るのは、削除が失敗し続けている間だけで、その間はマーカーも残り、起動のたびに消し直す。
- **出力を置くのに失敗したとき:** 書き込みが失敗した実行には、「出力を残していない」マーカーを書いて、今までどおり後片付けに進む。出力は残らず、結果を忘れた扱い（Trimmed）で読まれる。
  - 実行の記録を残して書き込みを繰り返す、という選択はしなかった。保存先が壊れている間に、記録と後片付けが際限なく溜まるのを避けるためである。
- **SDK:** kairod をバックエンドにしたときは、呼び出しとワークフローの実行を、すべて `keep_output` 付きで投入する（TypeScript と Python）。
- **一緒に見つかって直したもの（TypeScript の SDK）:** プロセスを閉じる（`Kairo.close()`）と、待っていた呼び出しまで kairo の側で取り消していた。そのため、閉じたプロセスのワークフローを後から再開すると失敗していた。埋め込みのランタイムでも同じだった。閉じている最中は取り消さないようにした（Python の SDK には、もとからこの区別があった）。
- **テスト:**
  - `engine/kept_test.go`（7 件）:
    - 再起動の後に `Get`・`Wait`・`Submit` が出力を返す。ブロブに移った出力も、中身で返る。残さない実行は、今までどおり Trimmed になる。
    - 期限切れで出力が消える。止まっている間に期限が切れた出力も、起動のときに消える。
    - 同じ ID を期限切れの直後に 20 回走らせ直しても、マーカーが指す出力は毎回ある。
    - 出力の削除が失敗している間はマーカーが退役せず、次の起動で消える。このテストは、退役を後回しにする処理を外すと落ちることも確かめた。
    - マーカーの前に落ちても、再起動で出力を置いてからマーカーを書く。
    - 版 1 のマーカーと、印のない開始の記録を読める。
  - `sdk/ts/src/workflow.test.ts`: kairod を止めて立て直し、待っていたワークフローを再開すると、終わった実のアクションの呼び出しが二度動かずに結果を返す。`keep_output` を外すと `ResultLostError` で落ちることも確かめた。
