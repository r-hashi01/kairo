# 0041. 実行 1 回あたりのコストは、その実行に要る仕事だけにする

- 状態: 承認
- 日付: 2026-10-06
- 関連: 不変条件 6 / ADR 0037、0038、0039

## 背景

kairo の目標は「ランタイム自身がボトルネックにならないこと」で、不変条件 6（実行ごとに goroutine を持たない、ポーリングしない）もそのためにある。ところが、Dify との統合（ADR 0037、0038）では、kairo の外側に、同じ種類のコストが入り込んでいた。2026-10-06 に、次のことがわかった。

- **停止。** Dify のワーカーは、実行ごとに監視のスレッドを持ち、0.1 秒ごとに Redis から停止の命令を読んで、kairo の実行を取り消していた。
  - 全実行が、まれにしか起きない停止のために、スレッドとポーリングのコストを払う。
  - 停止を受け付けてから kairo に届くまでの最大 0.1 秒の間、kairo は次のノードを始めることも、実行を終えることもできる。止まったと返しているのに、止まっていない。
  - 直す案として「開始時に、タスク ID → 実行 ID の対応を Redis に書く」も考えた。しかしこれも、全実行が停止のために書き込みを 1 回払う。
- **上限による中止。** 中止をイベントごとに Redis で確かめるように直したところ、iter の処理量が 18.9 回/秒から 12.4 回/秒に落ちた。プロセスの中で受け取るように直して、元に戻した。
- **1 実行あたりの CPU（native、1 プロセス）。** Dify のワーカーが 28〜40 ms、DB が約 20 ms、API が約 7 ms、kairo-dify が約 3 ms だった。記録を書く DB の仕事より、ワーカーの仕事のほうが大きい。

個々の修正では、その場の不具合は直せる。しかし、何を基準に「重い」と判断するかが決まっていなかった。そのため、同じ種類のコストが繰り返し入り込んだ。

## 決定

### 1. 原則

実行 1 回が本当に必要とする仕事は、次の 3 つだけとする。

- ノードを実行する
- 状態を耐久化する（kairo のログ）
- 結果を記録する（Dify では DB）

これ以外の、実行ごとのコストは、次の原則で削る。

1. **まれなことのコストは、起きたときにだけ払う。** 停止、human-input、タイムアウト、障害への備えに、全実行が常駐のコスト（スレッド、ポーリング、対応表の書き込み）を払わない。
2. **データの経路と制御の経路を分け、どちらも 1 本にする。**
   - データ（kairo → ワーカー → DB）は 1 回だけ流す。
   - 制御（停止、human-input の送信）は、指示を出す側（API）から、状態を持つ側（kairo）へ直接届ける。データの経路を制御に使わない。
3. **1 つの実行の ID は 1 つにする。** ID の対応表を作らない。

kairo の本体だけでなく、統合の側（`compat/`、Dify のブランチ）にも同じ原則を当てる。

AGENTS.md の「作業の進め方」に、この原則を 3 行で加える。変更が実行ごとのコストを増やすなら、それが上の 3 つの仕事のどれのためかを示す。どれでもないなら、ADR で理由を書く。

### 2. 停止への適用

- **ID を 1 つにする（Dify のブランチ）。** kairo で動かす実行は、Dify のタスク ID を `workflow_run_id` と同じ値にする。開始のときも、再開のときも同じにする。
  - Dify がタスク ID で引く鍵は、どれも接頭辞つき（`generate_task_belong:`、`generate_task_stopped:`、`workflow:{id}:commands`）で、実行 ID と同じ値にしても衝突しない。
- **停止は、API から kairo に直接届ける（Dify のブランチ）。** `AppTaskService.stop_task` は、kairo の実行なら、kairo-dify の取り消しを直接呼ぶ。graphon の実行のために、Redis への停止の命令もこれまでどおり送る。
- **取り消しは、適用されてから返す（kairo-dify）。** `POST /v1/runs/{id}/cancel` は、取り消しをシャードに渡したあと、同じシャードに状態を問い合わせる。シャードの受信箱は順に処理されるので、応答が返った時点で取り消しは適用済みである。エンジンは変えない。
  - 応答には、実行の状態を入れる（`cancelled`、または、すでに終わっていたなら、その状態）。
  - 応答の後に、その実行のノードが新しく始まることはない。動いていたノードには、取り消しが伝わる（ADR 0026）。
- **下流の監視スレッドをなくす（Dify のブランチ）。** `KairoGraphEngine` は、停止のためのスレッドもポーリングも持たない。停止は、kairo の取り消しの `run_end` として届き、下流はそれを中止として記録する。
  - 上限による中止は、これまでどおりプロセスの中で受け取る（`_LayerChannel`）。

### 3. ワーカーのコストの見直し

Dify のワーカーの 1 実行あたりのコストを、プロファイルで分解する。上の原則に反しているもの（3 つの仕事のどれのためでもないもの）を一覧にして、直すかどうかを利用者と決める。プロファイルを取ることは、コードを変えない計測なので、この ADR の承認に含める。

## 結果

- 停止は、受け付けた時点で kairo に適用済みになる。応答の後にノードが始まらない。止まったと返しているのに止まっていない時間がなくなる。
- 実行ごとの監視スレッドと Redis のポーリングがなくなる。停止のコストは、停止したときの呼び出し 1 回だけになる。
- Dify では、kairo で動かす実行のタスク ID と実行 ID が同じ値になる。両者が別の値であることに依存した利用者側のコードがあれば、影響を受ける（Dify の中には見当たらない）。
- 新しい作業の原則が増える。自動では守らせられないので、レビューで確かめる（`invariant-reviewer` の観点に加える）。
- テスト:
  - kairo-dify: 取り消しが適用されてから返ること、終わった実行への取り消しはその状態を返すこと（`compat/dify/daemon` に足す）。
  - Dify: 実際の Dify で、停止を graphon と比べる（既存の停止の比較）。停止の後にノードが始まらないことを、長いノードの後に続くノードがある定義で確かめる。

## 検討した代替案

- 監視スレッドのまま、ポーリングをやめて Redis の購読（pub/sub、BLPOP）にする: 実行ごとに待ち受けの接続が要る。データの経路（ワーカー）を通るので、遅れも残る。
- kairo-dify が Dify の Redis を読む: kairo が Dify の Redis に依存する。
- 開始時に、タスク ID → 実行 ID の対応を Redis に書く: 全実行が停止のために書き込みを払う（原則 1 に反する）。
- 対応を kairo-dify のメモリに持つ: デーモンの再起動で消える。消えないように保存するなら、デーモンの保存形式に手が入る。
- 押した時刻を基準に、その後に動いたノードを記録しない: 実際に動いたノード（外部への作用）が記録から消える。遅れより悪い嘘になる。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

- **原則:** AGENTS.md の「作業の進め方」と、`invariant-reviewer` の観点に加えた。
- **ID（Dify のブランチ）:** `core/workflow/kairo/ids.py` の `task_id_for`。ワークフローとチャットフローの生成で使う。再開は、保存した生成の内容（タスク ID を含む）を使うので、同じ値のままになる。Dify の中にも、`workflow_run_id` をタスク ID に使う箇所がすでにある（`workflow_execute_task.py`）。
- **停止（Dify のブランチ）:** `core/workflow/kairo/stop.py` の `send_stop_command`。Dify の中で停止の命令を送っていた 9 か所（コントローラ 7、`AppTaskService`、`execution_coordinator`）を、この関数に置き換えた。kairo の実行でなければ、kairo-dify は 404 を返し、何もしない。
- **取り消し（kairo-dify）:** `POST /v1/runs/{id}/cancel` は 200 と `{"status"}` を返す（以前は 202）。テストは `TestCancelAnswersOnceApplied`。
- **下流:** `KairoGraphEngine` の監視スレッドと `_watch_commands` を削除した。`request_abort` は、プロセスの中の中止（`_abort_run`）にした。
- **実際の Dify での確認:**
  - 6 秒かかるノードの途中で停止すると、kairo は停止の応答から 0.01 秒で「Aborted: User requested stop」で終わった。停止の応答の後に始まったノードはなかった。
    - graphon は、停止の仕組みが 2 つ（古い停止のフラグと命令）あり、どちらが先に効くかで「Aborted: User requested stop」と「Stopped by user.」が入れ替わる。kairo は前者になる。
  - 停止が届く前に kairo が実行を終えていた場合（iter を 0.03 秒で停止）、kairo は `completed` を返し、記録も成功になった。画面へのイベントは kairo の実行より遅れて届くので、画面ではまだ動いているように見えても、実際には終わっている。
  - 回帰の比較: SSE は 24 件中 19 件、DB は 22 件中 21 件、ブロッキングの応答は 23 件中 22 件が一致した。残りは、並列の枝の順序、サンドボックスの一時ファイル名、フォームの ID と期限だけが違う（以前と同じ）。

### 3 節: Dify のワーカーのコストの見直し（2026-10-06）

プロファイル（py-spy、1 プロセス、同時実行数 16）で、ワーカーの CPU を分けた。kairo との連携（prepare、ack、イベントの組み立て）は 3〜6% だった。残りは Dify がもともと持つ記録の書き方である。

| 内訳 | native | iter |
|---|---|---|
| ノードの記録の書き込み（persistence 層 → SQLAlchemy） | 65% | 79% |
| SSE のイベントを Redis に流す | 15% | 14% |
| inspector への通知を Redis に流す（聞き手がいなくても全実行で送る） | 8% | 8% |
| kairo との連携 | 約 6% | 約 3% |
| 停止フラグの問い合わせ | 約 1% | 約 1% |

直したこと（Dify のブランチ。記録の中身は変えない）:

1. **ノードの記録（`sqlalchemy_workflow_node_execution_repository.py`、`persistence.py`）。** ノード 1 つの終わりで、`save` と `save_execution_data` が別々に「SELECT してから書く」をしていた（SQL 4 回、コミット 2 回）。このリポジトリが書いた行なら、読まずに UPDATE 1 回で書く（`save_with_execution_data`）。データの退避（大きな入出力をストレージに移す）が要るときと、このリポジトリが書いていない行（再開した実行）は、これまでの経路で書く。
   - テスト: 2 回書いた行と 1 回で書いた行が同じになること、SQL が UPDATE 1 回だけであること、書いていない行では元の経路に戻ること。
2. **停止フラグの問い合わせ（`base_app_queue_manager.py`）。** kairo に付いた実行では、停止フラグを見ない。停止は kairo に直接届く。
3. **ウォッチドッグ（`execution_coordinator.py`）。** 実行ごとに `threading.Timer`（スレッド 1 本）を作っていた。プロセスに 1 本のタイマーのスレッドが、全実行の期限を持つ形にした（`_Timers`）。
   - テスト: 期限の順に呼ばれること、期限を増やしてもスレッドが増えないこと。
4. **停止（2 節）は、Dify の既存の停止の呼び出しを残し、その後に `cancel_on_kairo` を 1 行足す形にした。** 既存のテスト（`GraphEngineManager` に停止が送られること）をそのまま使える。

結果（kairo、同時実行数 128、8 プロセス、load average 約 20 のときに比べた）:

| ワークフロー | 直す前 | 直した後 | 1 実行あたりのワーカーの CPU | 1 実行あたりの DB の CPU |
|---|---|---|---|---|
| native | 39.1 回/秒 | 46.0 回/秒 | 52 → 36 ms | 20.5 → 18.9 ms |
| iter | 17.3 回/秒 | 20.9 回/秒 | 177 → 145 ms | 66 → 53 ms |
| code | 43.3 回/秒 | 42.5 回/秒 | 40 → 39 ms | 14 → 16 ms |

- load average が 30〜45 のときの計測では、どの値も悪く出た（DB と Redis の CPU まで 2〜3 倍になった）。マシンの他の負荷による。比べるのは、負荷が近いとき同士にした。
- 直した後のプロファイルでは、ノードの終わりの書き込みの割合が半分になった（native 42% → 21%、iter 55% → 28%）。次に大きいのは、ノードの始まりの書き込み（「行があるか」を SELECT してから INSERT）と、SSE のイベントの Redis への送信である。

5. **inspector（`persistence.py`、`inspector_events.py`、`workflow_node_output_inspector.py`）。** 全実行が、ノードが変わるたびに inspector 用のチャンネルに通知を送っていた（聞き手がいなくても）。実行は、画面に届けるためのイベントを、実行ごとのチャンネル（`channel:{app_mode}:{run_id}`）にすでに流している。kairo の実行では、inspector はそのチャンネルを読み（`subscribe_run_events`）、persistence 層は inspector 用の通知を送らない。graphon の実行は、これまでどおり。
   - 「聞き手がいるときだけ送る」案も考えた。開いている実行の一覧を、各プロセスが 1 秒ごとに読む形になり、ポーリング（原則 1）になるので採らなかった。同じ情報を 2 本の経路で送っていたこと（原則 2）が、もとの無駄だった。
   - DB への書き込みは、イベントを流すより先に終わっている（persistence 層が先に動く）。イベントを受けて読み直せば、書いた後の行が読める。
   - テスト: イベントから inspector の通知への変換、kairo の実行では通知を送らないこと。実際の Dify で、実行の途中から開いて、ノードの変化と終わりを受け取れること、inspector 用のチャンネルへの送信が 0 件であることを確かめた。

続けて直したこと（2026-10-06）:

6. **ノードの始まりの書き込み（`save_new`）。** persistence 層は、再開した実行では、それまでのノードの記録を読み込んでいる。そこにないノードは、行がまだない。そのときは、「行があるか」を読まずに INSERT する。再開した実行の、すでにあるノードは、これまでどおり読んでから書く。ID の衝突（重複キー）のときに ID を作り直す扱いは変えていない（既存のテストのとおり）。
   - 最初は「まず INSERT し、重複キーなら読んで更新する」形を試した。重複キーを ID の衝突として扱う既存の約束（テスト）と、トランザクションの数が合わなかったので、persistence 層が新しいノードだと知っているときだけ INSERT する形にした。
7. **SSE のイベントの送信（`core/workflow/kairo/publish.py`）。** kairo の実行のイベントは、プロセスに 1 本の送信のスレッドに渡す。スレッドは、たまっている分を取り、実行のチャンネルごとに、Redis のパイプラインで 1 往復で送る（順序は保つ）。たまるのを待たないので、遅れは増えない。負荷が高いと、自然にまとまる。受け取る側の形式は変えていない。実行の下流は、終わる前に、自分のイベントが送られたことを確かめる（`flush`）。
   - 送信に失敗したときは、ログに残して続ける（以前は、下流の失敗になった）。SSE は耐久ではなく、記録は DB にある。

1 プロセス（ワーカーが上限のとき。同時実行数 16、プロファイルを取った計測）の処理量:

| ワークフロー | 直す前 | 1〜4 の後 | 5〜7 の後 |
|---|---|---|---|
| native | 24.8 回/秒 | 30.9 回/秒 | 37.8 回/秒 |
| iter | 5.0 回/秒 | 10.0 回/秒 | 14.2 回/秒 |

8 プロセス（同時実行数 128）: native 44.5 回/秒、iter 25.7 回/秒（1 実行あたりのワーカーの CPU 95 ms、DB 41 ms）、code 45.5 回/秒。8 プロセスでは、ワーカー以外（マシンの CPU、DB）が先に効いていて、伸びは小さい。

残っている大きなもの: SQLAlchemy の ORM（ワーカーの CPU の 6 割）。ノード 1 つの書き込みは INSERT 1 回と UPDATE 1 回まで減った。これより減らすには、記録する内容（たとえば、実行中のノードを DB に出さない）を変えることになる。

レビュー（`invariant-reviewer`）で直したこと（2026-10-06）:

- **退避した実行の取り消し。** 待っている間に退避した実行では、取り消しは、状態を読み込んでから適用される。そのため、問い合わせの答えが「running」のまま返っていた。いまは、まだ終わっていなければ、終わるのを待ってから答える（`Engine.Wait`）。取り消しは実行を終わらせるので、終わりを待てば、適用を待ったことになる。テストは `TestCancelAnswersOnceApplied` に足した。
- **投入を待っている実行の取り消し。** 背圧などで、まだ始まっていない実行への取り消しは、以前は 404（kairo の実行ではない）になっていた。そして、後でその実行が始まっていた。いまは、その投入を取り下げる。投入は 409 で終わり、実行は始まらない。取り消しは「cancelled」を返す。テストは `TestCancelWithdrawsAQueuedRun`。
- **計画の問い合わせ。** kairo-dify は、実行のノードに名前を付けるため、実行ごとに 1 回、エンジンに計画を問い合わせる（記録のための仕事）。もう消えた実行について、エントリのたびに問い合わせ直していたので、答えがなかったことも覚えるようにした。
