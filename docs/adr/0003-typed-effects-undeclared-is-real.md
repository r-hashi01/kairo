# 0003. 作用に型を付け、宣言のないものは「実」として扱う

- 状態: 承認（2026-10-01）
- 日付: 2026-09-30
- 関連: FR3, FR6 / 不変条件 5, 10

## 背景

耐久化・リトライ・冪等性の扱いを全体一律にすると、LLM 呼び出しのように再実行してよいものまで重く扱うか、送信や決済のように取り消せないものを軽く扱うことになる。

## 決定

- 作用の型は非保護 / 保護 / 実 / 待機の 4 種（`ir.Effect`）。ノードの実装が `ir.NodeSpec` で宣言し、計画のコンパイル時に確定する。
- `ir.Effect` のゼロ値を `EffectReal` にする。レジストリにないアクションも実として扱う（`Registry.Lookup`）。
- 実の命令は既定で試行 1 回。結果が不明なとき（タイムアウト、接続断、再起動）は、`IdempotentRetry` の宣言があれば同じ冪等キーで再試行する。なければ `blocked`（要確認）で止め、`EvResolve` で人が決着させる。
- 冪等キーは `run_id/step_id` とする。`step_id` はノード ID に map の添字と loop の回数を付けたもので、試行をまたいでも変わらない。
- 実の作用を含む計画は、アドミッション時に耐久性ティアを `RealMinTier` 以上に引き上げる。既定値は、ファイルティアが使えれば（`DataDir` か Sink の指定があれば）file、使えなければ memory。
  - つまり `DataDir` なしで組み込むと、実の作用も memory ティアで動く。この場合、プロセスごと落ちると意図の記録も失われる。

## 結果

- 宣言漏れは安全側（重い側）に倒れる。
- 要確認の状態を扱う運用手段（API の resolve）が要る。

## 検討した代替案

- 既定を非保護にする: 宣言し忘れた送信処理が、クラッシュ後に二重実行される。
- 実行時に作用の型を変えられるようにする: 耐久化の判断がコンパイル時に確定しなくなる。
