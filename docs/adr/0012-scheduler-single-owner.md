# 0012. スケジューラは宛先ごとのトークンバケットとテナント間ラウンドロビンで、単一 goroutine が所有する

- 状態: 提案（v0 実装済み）
- 日付: 2026-09-30
- 関連: FR5

## 背景

希少な資源は CPU ではなく、外部のクォータ（RPM / TPM）である。テナント間の公平性と、宛先ごとのレート制御が要る。

## 決定

- ディスパッチャ（`sched.Dispatcher`）は 1 つの goroutine が状態をすべて所有する。入力は MPSC キューで受ける。
- 宛先ごとに RPM と TPM のトークンバケットを持つ。容量は既定で 10 秒分。TPM は見積もりで差し引き、完了時に実際の使用量で精算する。
- 宛先の中ではテナントをラウンドロビンで回す。テナントごとの同時実行数にも上限を設ける。
- トークンが足りないときは、足りる時刻にタイマーを 1 本だけ張る。
- 実行のアドミッション（`sched.Admission`）は、mutex で守った小さな構造にする。I/O はせず、クリティカルセクションは map の操作だけ。上限を超えたらテナント間ラウンドロビンのキューに入れ、キューも満杯なら `ErrOverloaded`（HTTP 429）を返す。

## 結果

- 公平性、レート制限、同時実行数の上限をテストで確認している（`sched_test.go`）。
- ディスパッチャが 1 つなので、全宛先の割り当てがその goroutine に集中する。v0 の規模では問題ないが、将来は宛先ごとに分ける余地がある。

## 検討した代替案

- シャードごとにレート制御する: 宛先のクォータはシャードをまたいで共有されるので、分割すると不公平か超過になる。
- アドミッションもアクターにする: 呼び出し側が応答を待つことになる。mutex の短い区間で十分と判断した。
