# 0077. 実行時に選んだ宛先へ、完了後の重みと再試行待ちを共有して適用する

- 状態: 提案
- 日付: 2026-11-11

## 背景

kairo の作用は、アクションの宣言時に決まる宛先をレート制御のキーにする。中央のディスパッチャは宛先ごとのリクエスト数とトークン数を制御できるが、埋め込みのランタイムが制御できるのは、宣言時に決まる宛先ごとの同時実行数と開始数だけである。

一つのアクションが複数の外部提供元を扱う場合、実際の宛先は各ステップの入力または呼び出し時の指定で決まる。宣言時の固定値では、別々の割り当てを持つ提供元が同じ上限を共有するか、上限を作用の内側で重ねて実装することになる。後者では、ランタイムのテナント間公平性と worker の配布順を使えず、同じ制御を利用側ごとに持つことになる。

外部提供元が数える使用量は、開始前には正確に分からないことがある。テキストの長さからの推定では、画像、言語、キャッシュの読み書き、提供元固有の数え方を再現できない。正確な入力・出力の使用量は応答で初めて分かるため、その一件が上限を越えることを許し、以後の仕事を待たせる必要がある。

また、実行器は失敗が再試行可能であることと、宛先が上限を拒否したことを返せるが、宛先が求めた待ち時間を返せない。コアはアクションに固定された backoff から次の試行時刻を決めるため、外部提供元が数十秒待つよう求めても、短い間隔で再試行して再び拒否される。同じ宛先へ向かう別の仕事も、その拒否を知らずに開始する。

この判断では、コアの決定的なリプレイ、実の命令を耐久化後にだけ解放する不変条件、実行ごとの goroutine と polling を持たない不変条件を変えない。レート制御の状態は実行結果ではなくアドミッションの状態であり、実行ごとの耐久書き込みを増やしてはならない。

## 決定

### 決定項 1（ステップの宛先を実行時の入力から決定する）

アクションは、固定の宛先に加えて、解決済みのステップ入力から宛先を選ぶ規則を宣言できるようにする。コードで書くワークフローは、呼び出し時の宛先指定をこの規則へ渡せるようにする。宛先は作用を worker へ渡す前に確定し、同じ試行の途中では変えない。

呼び出し時の宛先は、呼び出しの決定的な入力と識別に含める。リプレイで同じ呼び出しへ到達したときは同じ宛先になり、別の宛先を指定した呼び出しを既存の呼び出しとして取り違えない。宛先が空、不正な型、または公開された大きさの上限を超える場合は、外部作用を始める前の確定した失敗にする。

宛先の指定がなければ、既存どおり、宣言時の宛先、その指定もなければアクション名を使う。グラフの定義と Go・TypeScript・Python のコード API は、同じ宛先選択の意味を持つ。

### 決定項 2（宛先ごとの上限を仕事の受付時に解決する）

kairod は中央の宛先別設定を使い、埋め込みのランタイムは process が与える宛先別の上限を使う。埋め込みでは、上限を仕事の受付時に解決し、設定変更を次に受け付ける仕事から反映できるようにする。すでに開始した作用は、後から上限が変わっても取り消さない。

同じ宛先へアクションの宣言と宛先別設定の両方が上限を与える場合は、各種類について厳しい方の正の値を使う。上限を解決する処理の失敗では作用を始めず、無制限として続けない。

複数 process の埋め込みランタイムを合わせた上限は扱わない。各 process の上限であり、process をまたぐ一つの上限が必要な配置では、中央のディスパッチャを持つ kairod を使う。

### 決定項 3（完了後に分かる非負の重みを宛先の分単位の上限へ精算する）

宛先の上限に、リクエスト数とは別の「重み/分」を持たせる。トークン数は重みの代表的な用途であり、ランタイムは重みの単位や提供元固有の数え方を解釈しない。作用は結果とともに、実際に消費した非負の整数の重みを報告できる。

開始前に見積りがある仕事は、その値を予約し、完了時に実績との差を精算する。見積りがない仕事はゼロとして開始でき、その実績によって残高が負になり得る。残高が戻るまで、同じ宛先の後続の仕事を待たせる。したがって、同時に進んだ仕事の実績によって一時的に上限を越えることはあるが、正確でない見積りを必須にはしない。

重みはアドミッションだけに使い、コアの出力、実行の成功・失敗、耐久ログへ加えない。結果を失った試行の重みを推測して成功扱いせず、結果不明な実の作用の扱いも変えない。

### 決定項 4（再試行可能な拒否の待ちを、試行と宛先で共有する）

作用の結果は、確定した再試行可能な失敗に、外部提供元が求めた非負の待ち時間を付けられるようにする。この指定は、作用が受け付けられなかったと実行器が判断できる場合だけに使い、結果不明の作用には使わない。

コアは、結果を適用した時刻と待ち時間から「次に試してよい最短時刻」を決め、アクションに宣言された backoff と比べて遅い方まで待つ。この最短時刻をイベントと耐久ログに含め、再起動後のリプレイでも同じ試行時刻を再現する。

ディスパッチャと埋め込みのアドミッションは、同じ結果を受けた時点から、その宛先の新しい仕事も指定時間以上待たせる。複数の拒否が重なった場合は、最も遅い時刻を使う。待機中も固定間隔で確認せず、一つの次時刻への通知と、取消・停止の通知で起こす。

宛先全体の停止は process 内のアドミッション状態であり、再起動をまたいで耐久化しない。拒否された試行自身の最短時刻は耐久化する。外部提供元ごとの最大試行回数、総待ち時間、待ち時間がない拒否の既定値は、アクションと利用側のポリシーに委ねる。

### 決定項 5（形式の互換性と宛先状態の有界性を保つ）

worker と HTTP アクションの結果形式には、実績の重みと再試行待ちを省略可能な値として加える。値を送らない既存実装の意味は変えず、新しいランタイムは過去のログと結果形式を読み続ける。新しい待ちを記録したログを古いランタイムが読む前方互換性は約束しない。

実行時の宛先名を運用指標の属性にしない。宛先ごとのキュー、実行中の仕事、分単位の残高、または停止時刻のいずれにも影響しなくなった状態は退役できるようにし、過去に一度現れた宛先を process の寿命中ずっと保持しない。個別宛先の診断には既存の詳細観測と process の統計を使う。

### この ADR で決定しないこと

- Go・TypeScript・Python の公開 API の具体的な名前、入力から宛先を選ぶ表記、worker protocol のフィールド名は、Issue 20 の実装仕様へ委ねる。
- 提供元のエラー本文やヘッダーから、再試行可能か、結果不明か、待ち時間はいくつかを判定する規則は各 executor と provider adapter に委ねる。
- 提供元ごとの最大試行回数、総待ち時間、待ち時間がない拒否の既定値、利用者設定と project 設定の統合は、利用側の要件とアクション設定へ委ねる。
- process をまたぐ埋め込みランタイムの上限、課金台帳、監査用の使用量保存は、この ADR の範囲外とする。

## 結果

- 良い影響: 一つのアクションを使ったまま、実際の外部提供元ごとにリクエストと重みの上限を分けられる。
- 良い影響: 応答で初めて分かる正確な使用量を後続のアドミッションへ反映でき、画像やキャッシュを不正確な文字数換算へ寄せずに済む。
- 良い影響: 一件の拒否が求めた待ちを、その再試行と同じ宛先の別の仕事が共有し、短い再試行の集中を避けられる。
- 悪い影響: 重みが開始後に分かる仕事は、同時に進んだ件数ぶんだけ上限を一時的に越え得る。
- 悪い影響: 実行時の宛先、動的な上限、重み、再試行待ちを三つの SDK と二つの作用経路で同じ意味に保つ必要があり、公開契約が増える。
- 中立な影響: レート制御と宛先全体の停止は再起動で失われる process-local な状態のままであり、個々の試行の最短時刻だけがリプレイ可能になる。
- 新しく守る制約: 宛先は外部作用の前に決定し、呼び出しの識別へ含める。重みは非負とする。再試行待ちは結果不明に使わない。動的な宛先を運用指標の非有界な属性にせず、不要になった宛先状態を退役可能にする。

## 検討した代替案

- 提供元ごとに別のアクションを宣言する: 利用側の設定で増減する提供元が、ワークフローに記録する作用名と計画を変えてしまう。同じ作用の実装も提供元の数だけ登録する必要がある。
- 待ちと再試行を作用の handler 内で行う: worker の credit と実行中の枠を待ちの間も占有し、別の process と同じ宛先の仕事へ拒否を共有できない。利用側ごとに公平性と取消の実装も重複する。
- 開始前の重み見積りを必須にする: 画像、言語、キャッシュ、提供元固有の数え方では正確にならず、応答にある実績と二重の基準を持つ。
- 完了した重みを一分間の個別履歴としてすべて保持する: 厳密な移動窓にはなるが、宛先の処理量に比例する保持と掃除が増える。既存のトークンバケットへ実績を精算し、一定量の状態で後続を待たせる。
- 宛先の停止を耐久化する: すべての拒否と上限状態を実行ログまたは別の共有保存へ書くことになり、作用の結果に不要な書き込みを実行ごとに増やす。再起動後は外部提供元からの次の拒否と通常の上限で再学習する。

## 関連する ADR

- ADR 0012 の決定（宛先ごとのトークンバケットと単一 goroutine）: 中央のリクエスト数と重みの残高は、引き続きディスパッチャが単独で所有する。
- ADR 0039 の決定項 1（外部の制約: 宛先ごとの同時実行数を、観測から決める）: 再試行待ちは、上限拒否による同時実行数の調整と同じ宛先へ適用する。
- ADR 0041 の決定項 1（原則）: レート制御を耐久記録へ増やさず、待ちのための実行ごとの goroutine と polling を持たない根拠。
- ADR 0059 の決定項 3（埋め込みのランタイムに、同時実行と速さの上限を足す）: 固定宛先の開始数から、実行時の宛先と完了後の重みへ埋め込み側の制御を広げる。
- ADR 0076 の決定項 5（観測は実行経路を待たせず、無効時の費用を持たせない）: 実行時の宛先名を運用指標の属性にしない根拠。
