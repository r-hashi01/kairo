# 0000. 設計判断を ADR として記録する

- 状態: 承認（2026-10-01）。承認を得る時機は 0017 で補足
- 日付: 2026-09-30

## 背景

kairo の設計は、少数の強い原則（実行は値、作用に型、書き込みを3本に分ける、ストレージは外側）と、それを守るための不変条件でできている。コードとテストは「どうなっているか」を示すが、「なぜそうしたか」「何を捨てたか」は残らない。人もコーディングエージェントも、理由を知らずに不変条件を緩めてしまう危険がある。

## 決定

- 設計判断は `docs/adr/NNNN-slug.md` に1判断1ファイルで記録する。書式は `template.md` に従う。番号は連番とし、再利用しない。
- 状態は 提案 / 承認 / 却下 / 廃止 / 置き換え のいずれか。判断を変えるときは既存の ADR を書き換えず、新しい ADR を書く。古い ADR の状態は「NNNN により置き換え」にする（ADR 自体も追記のみ）。
- 次の変更には ADR が要る:
  - 不変条件（AGENTS.md）を追加・変更・緩和する
  - IR の構成要素、作用の型、イベント・命令の種類を増やす
  - ログ・スナップショット・ワーカープロトコルの形式を変える
  - 外部依存を足す
  - 要件定義から外れる、または要件の未決事項を決める
- 索引は `docs/adr/README.md` に置く。`scripts/adr-lint.sh`（`scripts/check.sh` から呼ぶ）で番号の重複と索引漏れを検査する。

## 結果

- 判断の理由と、捨てた代替案が残る。v0 の判断は、後からまとめて起票したもの（0001〜0015）で、状態は「提案」。利用者のレビューを経て「承認」にする。
- ADR を書かないと通らない変更が増える。軽い変更は対象外（上の一覧にないもの）。

## 検討した代替案

- README に設計の説明をまとめて書く: 現在の姿は書けるが、判断の経緯と却下した案が残らない。
- コードコメントに理由を書く: 局所的な理由には向くが、横断的な判断（出力コミット等）の置き場にならない。
