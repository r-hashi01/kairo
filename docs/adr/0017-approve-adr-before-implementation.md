# 0017. ADR は実装に入る前に承認を得る

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: ADR 0000 の運用を補う

## 背景

ADR 0000 は、判断を ADR に記録することと、状態の付け方を決めていた。しかし、いつ承認を得るかは決めていなかった。ADR 0016（ログ圧縮）は「提案」のまま実装・テスト・レビューまで進み、承認はその後に求める形になった。

実装してから承認を求めると、判断は事実上もう済んでいる。利用者が別の案を選ぶ余地がなくなり、ADR が後追いの記録になってしまう。

## 決定

- ADR が要る変更（ADR 0000 と AGENTS.md の一覧）は、ADR を「提案」で起票し、利用者の承認を得てから実装に入る。
- 判断に計測や試作が必要なら、そのこと自体（何を、どの範囲で、何を基準に判断するか）を ADR に書いて、承認を得てから行う。結果を受けて決定を変えるときは、承認前なら ADR を直し、承認後なら新しい ADR を書く。
- 実装中に、承認済みの決定から外れる必要が出たら、実装を止めて利用者に相談する。黙って変えない。
  - 承認済みの決定の範囲内で詳細を詰めること（関数名や内部の手順など）は、相談なしでよい。その内容は、実装と同時に ADR に追記して報告する。
- 起票した担当者（人またはエージェント）が、自分で「承認」にしてはいけない。

## 結果

- 決めるのは利用者で、エージェントは選択肢と根拠を出す、という役割分担がはっきりする。
- 承認を待つあいだ、実装は止まる。ADR が要らない変更は、これまでどおり進めてよい。
- 守らせる仕組み:
  - AGENTS.md と `/adr` スキルに手順として書く。
  - `invariant-reviewer` が、差分の根拠になっている ADR が「承認」かを確認する。
  - 機械的に止める hook はない。どの変更に ADR が要るかは、hook では判定できないため。
- ADR 0016 はこの規則ができる前に実装された。承認は事後に求める。

## 検討した代替案

- 実装と同時に起票し、マージ前に承認を得る: 0016 で実際にこうなり、承認が追認になった。
- 小さな判断は承認不要にする: どこからが小さいかで揉める。ADR が要る変更の一覧（0000）で線を引いているので、それで足りる。
