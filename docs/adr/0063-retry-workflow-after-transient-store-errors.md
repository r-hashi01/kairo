# 0063. 一時的な保存先エラーではワークフローを失敗にせず、駆動を譲ってリプレイする

- 状態: 承認（2026-11-06）
- 日付: 2026-11-06
- 関連: 不変条件 2・6 / ADR 0041（実行 1 回あたりのコスト）、0049（コードで書く API）、0051（常駐しないランタイム）、0059（駆動の借用）、0061（記録された終端結果）/ GitHub Issue #5

## 背景

コードで書くワークフローでは、関数が返したエラーを、そのワークフローの失敗として `done` に記録する。利用側の業務エラーや、アクションが確定して失敗した結果には、この扱いが必要である。

一方、`Call`、`Child`、`WaitFor` などが、埋め込みランタイムの保存先から一時的なエラーを受けることがある。たとえば SQLite の busy、PostgreSQL の一時的な切断、トランザクションの競合である。ワークフロー関数がそのエラーを返すと、今は同じく失敗を記録する。一度失敗を記録すると、保存先が回復しても同じ ID のワークフローは再開できない。数時間から数日続くセッションでは、短い DB 障害がセッション全体の永久的な失敗になる。

アクション用の `Retryable` / `RetryableError` は、この用途には使えない。これは 1 つのアクションの試行が「作用しなかったので再試行してよい」と示す印で、コアが試行回数と backoff を管理する。今回やり直すのは、ワークフロー関数を先頭からリプレイする駆動である。終わった呼び出しは記録から返し、未完了の地点だけを続ける（ADR 0049）。2 つを同じ印にすると、アクションの再試行とワークフローの再駆動を区別できない。

駆動をすぐ繰り返すと、保存先が回復しない間に busy loop になる。新しい定期ポーリングや実行ごとのタイマーを足すことも、不変条件 6 と ADR 0041 に反する。埋め込みランタイムには、プロセスが落ちた駆動を lease の期限切れで引き継ぐ経路がすでにある（ADR 0059）。

## 決定

3 つの SDK（Go・TypeScript・Python）に、アクションの再試行とは別の、**現在のワークフロー駆動を記録せずに譲る印**を同じ意味で入れる。

### 1. 保存先の操作エラーを、ワークフロー再駆動の印にする

- 組み込みの SQLite・PostgreSQL の保存先と Go の `SQLStore` は、実行中のクエリ、トランザクションの開始・確定・取り消し、接続で起きたエラーを、ワークフロー再駆動の印を持つエラーとして返す。
- `Store` のトランザクションへ渡した関数が返す Kairo の意味上のエラー（実行がない、プランが違う、作用を弱めた等）は、保存先の操作エラーではないので印を付けない。context / task の取り消しも、保存先の障害として包まない。
- 利用者が独自の `Store` を実装するときも、一時的または運用上回復可能な保存先のエラーには同じ印を付ける。組み込みの保存先は、ドライバ固有の型へ SDK から依存しないため、実行中に DB から返った操作エラーを回復可能として扱う。設定やスキーマの恒久的な誤りだった場合は、ワークフローを誤って失敗にする代わりに未完了のまま残し、ログを繰り返す。利用者が設定を直すか、明示して取り消す。
- 保存先の初期化に失敗した場合と、ワークフローの開始をまだ耐久化できていない場合は、譲れる実行がないので、これまでどおり呼び出し元へエラーを返す。

公開する名前は、Go が `kairo.RetryWorkflow(err)`、TypeScript が `WorkflowRetryError`、Python が `WorkflowRetryError` とする。保存先が付ける印と、利用者が明示して付ける印は同じである。これにより、保存先以外でも「この試みでは終端を記録せず、後で同じ ID をリプレイする」と利用者が明示できる。Go は `errors.Is` / `errors.As`、TypeScript と Python は例外の cause の鎖をたどるので、文脈を加えて返しても印を失わない。

### 2. 印の付いたエラーでは、成功も失敗も記録しない

ワークフロー関数、子のワークフロー、呼び出し、または関数が戻った後の子孫の片付けと `done` の送信が、印の付いたエラーで止まった場合、SDK は次のようにする。

- 親のワークフローへ失敗の `done` を送らない。成功の終端処理中だった場合も、成功を記録しない。
- ワークフロー関数またはその呼び出しから印が返った場合は、ADR 0062 の終端処理へ入らず、未完了の子孫を取り消さない。これは終端ではなく、同じ実行を後で続けるためである。
- 子のワークフローから来た印は親へそのまま伝わる。根の駆動まで伝わった時点で、木全体の現在のリプレイを止める。
- 通常の業務エラー、アクションの確定した失敗、印のない例外は、これまでどおり失敗として記録する。

すでに終わった呼び出しは耐久化した結果から返るので、リプレイしても作用を繰り返さない。未完了の実の試行については、既存の lease 回復と不変条件 5 の規則を変えない。

### 3. 埋め込みランタイムでは、駆動 lease を残して期限切れから再開する

根の駆動まで印が伝わったら、通常の停止時に行う `EndDrive(..., resume=true)` を呼ばない。駆動 lease を、プロセスが突然落ちた場合と同じ形で残す。その駆動を数える処理からは外れるため、lease の更新は止まり、記録済みの期限に失効する。

- 待ちモードでは、既存の掃除が期限切れの駆動を引き継ぎ、関数を先頭から動かす。`Run` / `Await` の呼び出し元は、停止を要求しない限り、耐久化した終端結果を待ち続ける。
- サスペンドモードでは、現在の呼び出しは通常の待ちと同じ `ErrSuspended` / `Suspended` で戻る。`NextWake` は残した lease の期限を返し、その時刻以後の `Tick` が再開する。
- lease の既定の長さ（現在 30 秒）が再駆動までの上限になる。専用の retry timer、固定 `Sleep`、実行ごとの goroutine、ポーリングは足さない。
- エラーと次に再開できる時刻を warn のログへ出す。耐久ログには、成功・失敗の終端も、この一時的なエラーそのものも記録しない。

lease を取る前に保存先が失敗した場合は、期限切れの既存 lease があれば従来の掃除が拾う。新しい実行の開始を耐久化できなかった場合は、決定 1 のとおり呼び出し元へ返す。

実装では、同じ owner の lease をプロセス単位でまとめて延長する。ほかの実行が動いていると、再駆動を待つ lease まで延長されるため、印を受けた駆動の lease は owner を空にして、現在から lease 期間後へ引き渡す。行は削除せず、期限切れを拾う既存の経路と `NextWake` を使う。

関数がすでに成功または失敗で戻り、ADR 0062 の終端処理を始めた後で保存先エラーになった場合は、その前に耐久化できた子孫の取り消しを戻さない。ADR 0062 の途中停止と同じく、親の終端だけを記録せず、次のリプレイが終端処理を続ける。

### 4. kairod 経由は未完了のまま停止し、同じ ID の再呼び出しで続ける

kairod はワークフロー関数の駆動 lease を保存していないため、SDK のプロセスが消えた後に関数を自動で再駆動できない。kairod 経由で明示した `RetryWorkflow` / `WorkflowRetryError` が根まで伝わった場合も、失敗の `done` は送らず、既存の停止エラー（Go の `ErrStopped`、TypeScript・Python の `StoppedError`）を呼び出し元へ返す。利用者が同じ実行 ID で `Run` を呼ぶと、記録済みの呼び出しを使って続く。

HTTP や worker の一時的なエラーを自動でこの印へ変えることと、kairod に駆動 lease を持たせることは、この ADR には含めない。今回、自動で印を付けるのは埋め込みランタイムの保存先だけである。

## 結果

- SQLite の busy など短い保存先障害で、長く動くワークフローを永久に失敗として記録しない。保存先が回復すれば、同じ ID と同じ呼び出しの記録から続く。
- アクションの `Retryable` と、ワークフロー駆動のやり直しは、API と実装の両方で分かれる。
- 保存先が回復しない場合、実行は失敗にならず未完了のまま残る。ログと一覧から運用者が見つけ、保存先を直すか取り消す必要がある。
- 表、コアの状態、イベント、命令、WASM ABI、ワーカープロトコルは変えない。保存先エラーの型と SDK の制御だけを変える。
- 通常の実行が払う永続化の回数は増えない。一時的なエラーが起きた場合だけ、既存の lease 回復の費用を払う（ADR 0041）。

次のテストを 3 つの SDK に同じ意味で足す。

- 1 つ目の実の呼び出しを終えた後、次の `Call` / `Child` の保存先操作を 1 回だけ失敗させる。親は失敗を記録せず、lease の期限後に完了し、1 つ目の作用を繰り返さない。
- 明示した `RetryWorkflow` / `WorkflowRetryError` でも同じく、終端を記録せず再開する。
- 印のない業務エラーは、これまでどおり失敗として記録する。
- 一時的なエラーの時点で、未完了の子孫を ADR 0062 の終端処理として取り消さない。
- サスペンドモードは `Suspended` で戻り、`NextWake` より前には再駆動せず、期限後の `Tick` で続く。
- kairod 経由は失敗を記録せず `StoppedError` で戻り、同じ ID の `Run` で続く。

## 検討した代替案

- **すべてのワークフローエラーを再試行する:** 業務上の失敗、入力の誤り、コードの不具合まで永久に再試行する。明示した印と Kairo の保存先エラーだけに限る。
- **アクションの `Retryable` / `RetryableError` を流用する:** アクションの 1 試行を再試行する印と、ワークフロー関数のリプレイを譲る印の意味が違う。実行場所と backoff の所有者も違う。
- **SQLite の busy など、ドライバ固有のエラーコードだけを選ぶ:** SDK 本体が任意の Go SQL ドライバや利用者から渡された PostgreSQL pool を受ける設計なので、各ドライバの型へ依存できない。未知の一時障害を永久的な失敗にするより、DB 操作のエラーを未完了として残す。
- **一時的なエラーを `done` の失敗として記録し、同じ ID の再実行で覆す:** 終わった実行へのイベントは無視され、ADR 0061 の「先に記録した終端だけが結果」に反する。失敗を記録する前に駆動を譲る必要がある。
- **専用の retry timer と指数 backoff を保存する:** 表かイベントの形式を増やし、一時障害のたびに新しい耐久化が要る。まずはすでに耐久化されている駆動 lease の期限を使えば、クラッシュ回復と同じ安全性で busy loop を防げる。頻度を独立して調整する必要が出たら別の ADR で扱う。
- **印の付いたエラーでも子孫を取り消す:** これはワークフローの終端ではない。再開に必要な未完了の呼び出しを消し、実の試行の意味も変えてしまう。
