# 0089. 関数が呼び出しの取り消しを捕まえずに終わったら、ワークフローは失敗でなく取り消しとして終える

- 状態: 提案
- 日付: 2026-11-28

## 背景

コードで書くワークフローの取り消しは、木として行う（ADR 0062 の決定項 3）。SDK の `cancel` は、見つかった未完了の子孫を深いものから取り消し、最後に根のワークフローを取り消す。順番がこうなっているのは、ワークフローの終端（成功・失敗・取り消し）を記録する前に、子孫がすべて終わっていなければならないためである（ADR 0062 の決定項 2）。保存先も、未完了の子孫が残るワークフローへ終端を書くことを拒む。

ワークフローの関数は、取り消された呼び出し（アクション、待ち、子のワークフロー）を、取り消しを原因に持つ呼び出しのエラーとして受け取る。関数がこれを捕まえずに終わると、SDK は関数の失敗としてワークフローの失敗を記録する。完了と取り消しは、先に記録されたものだけが有効になる（ADR 0061 の決定項 1）。

`cancel` を呼んだプロセスと、そのワークフローを動かしているプロセスが同じなら、問題は起きない。`cancel` は子孫を取り消す前に、そのプロセスの駆動を止め、取り消しの要求を覚えておく。このため、関数が受け取った取り消しは、失敗としてではなく、ワークフローの取り消しとして扱われる。

別のプロセスから `cancel` を呼ぶと、次の順になる（2026-11-28、TypeScript の SDK の埋め込みのランタイムで確認）。

1. `cancel` を呼んだプロセスが、待ちの子を取り消す。
2. ワークフローを動かしているプロセスの関数が、取り消された待ちをエラーとして受け取り、捕まえずに終わる。
3. 動かしている側の SDK が、ワークフローの失敗を記録する。
4. `cancel` を呼んだプロセスが根を取り消そうとするが、根はすでに終わっている。`cancel` は `RunSettledError` を返し、ワークフローは失敗のまま残る。

Go と Python の SDK も、取り消しの順番（子孫が先、根が後）と、同じプロセスでだけ取り消しの要求を覚える作りが同じである。動かしているプロセスは、根の取り消しがまだ記録されていない時点で、子の取り消しを見る。その時点では、取り消しが木全体へのものか、その呼び出しだけへのものかを、記録から区別できない。

埋め込みのランタイムでは、ワークフローを動かすプロセスと、運用の操作（承認、取り消し）をするプロセスが別であることが普通にある。複数のプロセスが同じ保存先を共有する構成や、実行の経過を見るビューア（ADR 0088）からの取り消しがそうである。どのプロセスから取り消しても、ワークフローが「取り消し」で終わる必要がある。

## 決定

### 決定項 1（捕まえられなかった取り消しは、ワークフローの取り消しにする）

ワークフローの関数が、呼び出しの取り消しを原因とするエラーを捕まえずに終わったら、SDK はワークフローの失敗を記録しない。代わりに、そのワークフローを木として取り消す（ADR 0062 の決定項 3 と同じ手順：未完了の子孫を取り消し、根を取り消し、記録された終端を確かめる）。ライブの呼び出し元へは、ADR 0061 の決定項 2 のとおり、記録された終端（取り消し）を返す。

「捕まえずに終わった」とは、関数が送出したエラーの原因をたどると、呼び出しの取り消しに行き着くことをいう。関数が取り消しを捕まえて、値を返した場合や別のエラーを送出した場合は、今までどおり、その成功または失敗を記録する。

この規則は、取り消しがどのプロセスから来たか、木全体へのものか呼び出し 1 つへのものかによらず適用する。呼び出し 1 つ（たとえば子のワークフロー）だけが取り消され、親の関数がそれを捕まえなかった場合も、親は取り消しで終わる。

### 決定項 2（取り消しを呼んだプロセスと動かしているプロセスは、同じ終端へ収束する）

`cancel` を呼んだプロセスと、ワークフローを動かしているプロセスの両方が、同じワークフローを木として取り消しうる。どちらの取り消しも冪等であり、記録される終端は「取り消し」の 1 つになる。`cancel` を呼んだプロセスは、根がすでに取り消されていれば、ADR 0061 の決定項 3 のとおり成功として返す。

関数が取り消しを捕まえて成功または失敗を先に記録した場合は、ADR 0061 の決定項 1 のとおり、その結果が残り、`cancel` は `RunSettledError` を返す。これは利用者のコードが取り消しを別の結果に変えたものであり、この ADR はその判断を変えない。

### 決定項 3（記録とリプレイ）

コアの状態、イベントと命令の種類、ログ、保存先の表、ワーカープロトコルは変えない。取り消しの要求を表す新しい記録も足さない。ワークフローの終端は、既存の取り消しのイベントとして記録する。

関数を記録からリプレイしたときも、取り消された呼び出しは同じエラーを返すので、同じ規則で同じ終端になる。ワークフローが終端を記録する前にプロセスが止まった場合は、次の駆動が同じ規則で取り消しを記録する。

Go・TypeScript・Python の 3 つの SDK に、同じ規則を適用する。埋め込みのランタイムと kairod のどちらをバックエンドにしても同じにする。

### この ADR で決定しないこと

- 取り消しの原因を判定するエラーの型と、原因のたどり方は、各 SDK の公開 API の文書と実装に委ねる（TypeScript・Python は `CancelledError`、Go は `ErrCancelled` を原因に持つ呼び出しのエラーを想定する）。
- 取り消しの理由（誰が、なぜ取り消したか）を記録して利用者に見せる仕組みは、その要求ができたときの別の ADR に委ねる。
- 呼び出し 1 つだけを取り消したときに、親へ伝えずに失敗として扱いたい利用者は、関数の中で取り消しを捕まえて失敗を送出する。これを SDK の設定で切り替える仕組みは設けない。必要になったら別の ADR で決める。
- グラフの実行（コードで書くワークフローでないもの）の取り消しの意味は変えない。

## 結果

- 良い影響: どのプロセスから `cancel` しても、関数が取り消しを捕まえない限り、ワークフローは「取り消し」で終わる。運用の操作をする別のプロセスやビューアから、安全に取り消せる。
- 良い影響: 記録とイベントを増やさず、既存の取り消しの手順と ADR 0061 の「先に記録されたものが有効」という規則の上に成り立つ。
- 悪い影響: これまで、子のワークフローや呼び出し 1 つを取り消し、親が捕まえなかった場合、親は失敗で終わっていた。この ADR の後は、親も取り消しで終わる。親の失敗を前提にした利用者のコードや監視は、取り消しも扱う必要がある。
- 悪い影響: 取り消しが別のプロセスから来たときは、動かしているプロセスも子孫の取り消しと根の取り消しを行う。取り消しの書き込みが、2 つのプロセスで重なることがある（冪等なので結果は変わらない）。
- 中立な影響: 同じプロセスの中での取り消しは、今までどおり先に駆動を止める経路で処理され、結果は変わらない。
- 新しく守る制約: SDK は、取り消しを原因とするエラーで関数が終わったワークフローの失敗を記録しない。3 つの SDK で同じ判定をする。

## 検討した代替案

- 取り消しの要求を、子孫を取り消す前に根へ記録する（新しいイベント、または待ちへのシグナル）: 動かしているプロセスが、子の取り消しを見たときに根の要求を確かめられる。ただし、記録とイベントの種類を増やし、ログと保存先の形式に触れる。この ADR の規則は、新しい記録なしで同じ収束を得られる。
- 根を先に取り消し、子孫を後から取り消す: 動かしている側は根の取り消しを先に見られる。しかし、終わったワークフローの下に未完了の子孫が残る間ができ、ADR 0062 の決定項 2 と、保存先の「未完了の子孫がある終端は書かない」という守りを崩す。
- 根と子孫の取り消しを 1 つのトランザクションで行う: 競合はなくなるが、埋め込みの保存先の操作は実行 1 つごとのトランザクションであり、木の大きさに比例する長いロックが要る。kairod ではシャードをまたぐため同じ形にできない。
- 動かしているプロセスが、子の取り消しを見たら記録せずに駆動を手放し、根の終端を待つ: 呼び出し 1 つだけが取り消された場合、根の終端は誰も書かず、ワークフローは止まったまま残る。
- 取り消しを、`cancel` を呼んだプロセスが、動かしているプロセスへ直接伝える: プロセス間の通知（ADR 0079 の通知、PostgreSQL の通知）はヒントであり、届かないことがある。正しさを通知に頼れない。

## 関連する ADR

- ADR 0061 の決定項 1（完了と取り消しは、先に記録されたものだけが有効になる）: この ADR は、取り消しを捕まえなかった関数が、失敗を先に記録しないようにする。先に記録されたものが有効という規則は変えない。
- ADR 0061 の決定項 3（`Cancel` は、記録された結果を確認して返す）: 動かしているプロセスが先に取り消しを記録した場合も、`cancel` は成功を返す。
- ADR 0062 の決定項 2（ワークフローは、未完了の子孫を片付けてから成功または失敗を記録する）と決定項 3（明示した取り消しも、子孫の終端を確認してから返す）: 取り消しの順番（子孫が先）を保ち、動かしている側も同じ手順で取り消す。
- ADR 0088 の決定項 3（ビューアからの操作は SDK の公開の操作と同じ意味にし、ビューアは実行を動かさない）: ビューアからの取り消しは別のプロセスからの取り消しであり、この ADR で「取り消し」で終わるようになる。
