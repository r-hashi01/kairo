# 0078. 埋め込みランタイムは宛先の要求数・重み・再試行待ちを保存先でプロセス間共有できる

- 状態: 承認（2026-11-13）
- 日付: 2026-11-12

## 背景

埋め込みランタイムは、同じ保存先を使う複数の process でワークフローを引き継げる。一方、宛先ごとの同時実行数、要求数/分、重み/分、再試行待ちは、それぞれの process のメモリにある。複数の process が同じ外部提供元の割り当てを使うと、各 process が割り当て全体まで仕事を始められるため、process 数に応じて外部の上限を越え得る。

中央のディスパッチャを持つ配置では、一つの kairod が worker process をまたいで宛先の上限を所有できる。しかし、埋め込みランタイムは常駐するサーバーを必要とせず、SQLite または PostgreSQL だけを共有する配置も対象にしている。その配置で一つの上限を守るには、外部作用を始める前の許可と、完了後に分かる重み、上限拒否が求めた待ちを、process 間で直列化できる場所が要る。

すべての作用について保存先へ問い合わせると、共有を必要としない利用者にも外部作用ごとの読み書きが増える。共有する上限は実行結果や課金記録ではなく、一時的なアドミッション状態である。また、同時実行数まで process 間で共有するには、作用を実行中の process が停止した場合に枠を返す借用と結果不明の扱いが必要になり、時間で回復する要求数・重み・再試行待ちとは障害時の意味が異なる。

この判断では、コアの決定的なリプレイ、実の命令を耐久化後にだけ解放する不変条件、実行ごとの goroutine と固定間隔の polling を持たない不変条件を変えない。

## 決定

### 決定項 1（共有を明示した宛先だけ、速度の状態を process 間で共有する）

埋め込みランタイムの宛先別上限には、process 内だけで数える既定の範囲と、同じ保存先の名前空間で数える共有範囲を設ける。共有範囲は宛先ごとに明示し、指定のない宛先は従来どおり process 内だけで数える。

共有範囲では、要求数/分、完了後に報告された重み/分、確定した再試行可能な拒否が求めた待ちを process 間で共有する。同時実行数と process 全体の上限は process 内のままにする。kairod の中央ディスパッチャの意味は変えない。

共有を要求した宛先に、process 間を直列化できる保存先の能力がなければ、作用を始める前に設定の誤りとして拒否する。process 内の上限へ黙って弱めない。

### 決定項 2（外部作用の直前に保存先から許可を得て、失敗時は閉じる）

共有範囲の外部作用は、保存先が一貫して与える時刻と原子的な状態更新によって、同じ宛先の要求間隔、重みの残高、停止時刻を確認してから始める。まだ始められない場合、保存先は次に確認できる時刻を返し、ランタイムはその時刻または取消・停止の通知まで待ってから確認し直す。固定間隔では確認しない。

許可を得る保存先操作に失敗した場合は作用を始めず、一時的な保存先エラーとしてワークフローを譲ってリプレイする。無制限または process 内だけの上限へ切り替えて続けない。許可を得た後の取消または process 停止では、その要求の容量を返さない。外部作用を始めたかどうかを別の process から確定できないため、安全側で消費済みとして扱う。

### 決定項 3（実績の重みと再試行待ちを共有状態へ精算する）

作用の完了後に分かった非負の重みは、共有する宛先の残高へ精算する。実績によって残高が負になった場合は、時間で回復するまで、どの process からの後続の仕事も待たせる。

確定した再試行可能な拒否に待ちがある場合は、その宛先の共有する停止時刻を遅い方へ延ばす。結果不明の作用には適用しない。共有状態は作用の成功・失敗やコアの出力を変えず、個々の試行が再び始められる時刻は、引き続き耐久ログから決定的に再現する。

作用の結果が分かった後は、その結果の記録と、重みおよび再試行待ちの共有状態への精算を、同じ保存先の一つのトランザクションで確定する。トランザクションが失敗しても、保持している結果を再度記録して精算し、精算のために作用をもう一度始めない。結果を確定する前に process が停止した場合は、既存の結果不明の扱いに従い、重みを推測しない。

同じ宛先について process ごとの宣言が異なる場合、共有状態がアドミッションへ影響している間は、各種類で最も厳しい正の値を使う。緩い設定の process が共有上限を引き上げることを許さない。状態が中立になって退役した後は、次の仕事がその時点の宣言から新しい状態を作る。

### 決定項 4（共有状態を一時的かつ有界に保つ）

共有状態はワークフローの記録、使用量の台帳、監査ログに含めない。要求間隔、重みの残高、停止時刻のいずれにも影響しなくなった宛先の状態は削除できるようにする。期限を過ぎた状態の掃除は、既存の保存先操作または既存の tick に便乗して件数を区切って行い、宛先ごとの常駐処理や新しい polling を設けない。

保存先への追加の操作は、共有範囲を明示した宛先の許可と精算だけに課す。process 内の上限だけを使う宛先と、上限のない宛先の経路には追加しない。実行時の宛先名を運用指標の属性にしない。

### 決定項 5（三つの SDK で同じ共有範囲と信頼境界を使う）

Go・TypeScript・Python の埋め込みランタイムは、同じ保存先の名前空間を使うとき、共有状態の意味と形式を一致させる。保存先の共通契約には、共有する許可、精算、停止、退役を原子的に扱う任意の能力を加える。SQLite と PostgreSQL の保存先はこの能力を提供し、独自の保存先は共有範囲を使う場合だけ実装を必要とする。

同じ名前空間へ書ける process は、外部提供元の割り当てを消費したり、宛先を待たせたりできるため、同じ信頼範囲に置く。共有状態へ提供元の資格情報、作用の入力・出力、課金の明細は保存しない。共有状態は監査の根拠にはしない。

共有範囲を使う名前空間では、その宛先へ作用を出すすべての process を、この能力に対応した版へそろえる。対応していない古い process は共有状態を見ずに作用を始められるため、混在時の上限は保証しない。形式の追加は、共有範囲を使わない古い process が既存のワークフロー記録を読むことを妨げない。

### この ADR で決定しないこと

- 公開 API の具体的な名前は各 SDK の API 文書へ、保存先の型・表・SQL・移行手順と待機を組み立てる内部アルゴリズムは各保存先の実装と保守文書へ委ねる。
- process 間で共有する同時実行数と、その枠を process 停止時に回収する借用は、この ADR の範囲外とする。
- 厳密な移動窓、提供元ごとの課金台帳、使用量の監査と請求、外部提供元のエラーを分類する規則は扱わない。
- process 間の仕事の公平な順序は保証しない。各 process 内の待ち順と、共有する速度上限だけを扱う。
- kairod の中央ディスパッチャ、利用側の provider 設定を配布する方法、複数の保存先の名前空間にまたがる上限は変更しない。

## 結果

- 良い影響: 常駐する中央サービスを足さずに、同じ SQLite または PostgreSQL を使う埋め込み process が、一つの外部提供元の要求数・重み・再試行待ちを共有できる。
- 良い影響: 保存先エラーや設定不足で上限を黙って弱めず、外部の割り当てを越えるより作用を始めない側へ倒せる。
- 良い影響: 共有を必要としない宛先には保存先操作を増やさず、動的な宛先の状態も不要になれば退役できる。
- 悪い影響: 共有する作用は、開始前と、重みまたは再試行待ちを返した完了時に保存先の競合と遅延を受ける。保存先が停止すると、その宛先の作用も始められない。
- 悪い影響: process ごとの設定が異なる間は厳しい値が残るため、上限を引き上げる変更は、古い状態が中立になるまで反映されないことがある。
- 中立な影響: 同時実行数は process 内のままであり、process 数を増やすと同時に進む作用の数は増え得る。要求数・重み・再試行待ちの共有とは別の判断として残る。
- 中立な影響: 共有状態は保存先に置くが、ワークフローのリプレイ結果や課金・監査の記録にはならない。
- 新しく守る制約: 共有範囲の作用は保存先の許可前に始めない。保存先の失敗時に上限を弱めない。既知の作用結果と共有状態への精算を原子的に確定する。結果不明の作用から重みや再試行待ちを推測しない。共有状態を不要になった後も無期限に残さない。同じ名前空間で共有する process を同じ信頼範囲と対応版にそろえる。

## 検討した代替案

- 埋め込みでも kairod を必須にする: 一つのディスパッチャで共有できるが、DB だけで引き継げる埋め込み配置に常駐サービスを追加し、障害点と運用対象を増やす。すでに kairod を使う配置では引き続き中央ディスパッチャを使う。
- process 数で上限を割って各 process に設定する: process の増減、停止、負荷の偏りで割り当てがずれ、使い切れないか全体の上限を越える。完了後の重みと再試行待ちも process 間へ伝わらない。
- すべての宛先を常に保存先で数える: 共有を必要としない一つの process の配置にも外部作用ごとの保存先操作が増え、保存先障害が外部作用の可用性へ広がる。
- 作用の結果を記録した後、別のトランザクションで共有状態を精算する: process 停止で実績が共有状態へ反映されない期間ができる。逆の順では、精算後に結果だけ失敗し、同じ作用を再び始める危険がある。
- process に要求や重みのまとまりを前払いする: 保存先の往復は減るが、別の process が記録した再試行待ちを、前払い分を持つ process が知らずに作用を始め得る。停止した process の未使用分を安全かつ速やかに戻す借用も要る。
- 完了した使用量を一分間の明細として保存する: 厳密な移動窓を作れるが、処理量に比例する行と掃除が増え、共有アドミッションの一時状態を使用量台帳へ変えてしまう。

## 関連する ADR

- ADR 0012（宛先ごとのトークンバケットと単一 goroutine）: kairod の中央ディスパッチャは変更せず、埋め込み process だけが保存先で速度の状態を共有する。
- ADR 0041 の決定項 1（原則）: 追加の保存先操作を共有範囲の外部作用だけに限定し、使わない実行へ常駐の費用を加えない根拠。
- ADR 0051（常駐するサーバーを前提にしない）: DB だけを共有する埋め込み配置で process 間の上限を扱う根拠。
- ADR 0059 の決定項 3（埋め込みのランタイムに、同時実行と速さの上限を足す）: process ごととしていた速度の上限に、宛先ごとの任意の共有範囲を加え、この範囲を一部置き換える。同時実行数は process ごとのままにする。
- ADR 0063（保存先エラーではワークフローを譲ってリプレイする）: 共有する許可の保存先エラーを、作用の結果にせず安全にやり直す根拠。
- ADR 0077 の決定項 2（宛先ごとの上限を仕事の受付時に解決する）: process 内としていた埋め込みの上限に、明示した宛先だけの共有範囲を加え、この範囲を一部置き換える。
- ADR 0077 の決定項 3（完了後に分かる非負の重みを宛先の分単位の上限へ精算する）: 実績による負の残高を、同じ保存先の process 間でも共有する。
- ADR 0077 の決定項 4（再試行可能な拒否の待ちを、試行と宛先で共有する）: process 内だった宛先の停止を、共有範囲では同じ保存先の process へ広げる。
- ADR 0077 の決定項 5（形式の互換性と宛先状態の有界性を保つ）: 共有状態にも、動的な宛先を無期限に保持しない制約を適用する。
