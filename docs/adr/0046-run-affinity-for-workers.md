# 0046. 実行ごとの状態を持つワーカーには、同じ実行の仕事をなるべく同じ接続に渡す

- 状態: 承認
- 日付: 2026-10-07
- 関連: 不変条件 6、ADR 0009（ワーカーのプロトコル）、0039（適応的な同時実行）、0041（実行 1 回あたりのコスト）、0042（n8n との統合）、0044（実行の終わりの知らせ）

## 背景

ディスパッチャ（`sched.Dispatcher.match`）は、仕事を受け取れるワーカーの接続（ポーラー）を順に回して渡す。仕事を広く分けるためである。

n8n との統合（ADR 0042）で、kairo-worker は式のサンドボックスを実行ごとに 1 つ持つようにした。しかしワーカーを増やすと、1 つの実行のステップが複数のワーカーに分かれる。サンドボックスはワーカーごとに作り直しになり、1 実行あたりの CPU が増えた。2026-10-07 の計測では、ワーカー 1 で約 29ms、2 で約 52ms、4 で約 73ms だった。スループットは、ワーカーを増やすと下がった。

実行ごとの状態を持つワーカーは、`RunEnd` を申し出る（ADR 0044）。どの接続が実行ごとの状態を持つかは、すでにわかっている。

## 決定

`RunEnd` を申し出た接続（実行ごとの状態を持つワーカー）には、同じ実行の仕事を、なるべく同じ接続に渡す。

- **渡し方（`sched.Dispatcher.match`）:**
  - 渡そうとする仕事の実行に、前に仕事を渡した接続（なじみの接続）があり、その接続にまだクレジットが残っていれば、その接続に渡す。
  - なじみの接続がない、クレジットがない、もう切れている場合は、今までどおり順に回して渡し、渡した接続をその実行のなじみにする。
  - なじみを持つのは、`RunEnd` を申し出た接続に渡した実行だけ。申し出ない接続には、今までどおり順に回して渡す。
- **なじみの表:** 実行 ID → 接続。ディスパッチャのループだけが持つので、ロックは要らない（ADR 0039 と同じ）。
  - 実行が終わったら消す。エンジンが `Dispatcher.RunEnded(runID)` を呼ぶ（`OnRunEnd` と同じ時点）。
  - 接続が切れたら（`Unpoll`）、その接続をなじみに持つ項目を消す。
- **公平さと上限は変えない。** テナントの順番、同時実行の上限（ADR 0039）、RPM/TPM は、今までどおり仕事を選ぶ段階で効く。なじみは「選んだ仕事をどの接続に渡すか」だけを変える。
- **費用（ADR 0041）:** 申し出ない接続の仕事には何も増えない。申し出た接続では、仕事ごとに表を 1 回引き、実行ごとに 1 項目を持つ。タイマーもポーリングも使わない。

## 結果

- 実行ごとの状態（kairo-worker のサンドボックス）が、ワーカーを増やしても 1 実行に 1 つで済むようになる（なじみの接続にクレジットがある限り）。
- 偏りが出うる。長い実行が多い接続には仕事が寄る。ただし、クレジットが尽きればほかの接続に渡るので、止まることはない。
- **新しく守ること:** なじみは、クレジットを超えて渡す理由にならない。表は、実行の終わりと接続の切断で必ず消す（際限なく伸びない）。
- **テスト（足す）:**
  - `sched`: 申し出た接続が 2 つあるとき、同じ実行の仕事が同じ接続に渡ること。クレジットが尽きたらほかに渡ること。実行の終わりと切断で表が消えること。申し出ない接続には、今までどおり順に回すこと。
  - 実機（n8n）: ワーカー 2・4 で、1 実行あたりの kairo-worker の CPU が、ワーカー 1 のときと同じくらいに戻ること。

## 検討した代替案

- **ワーカーの側でサンドボックスを共有する。** ワーカーは別のプロセスで、サンドボックス（isolated-vm）はプロセスをまたげない。
- **ワーカーを 1 プロセスにして、同時実行の数を増やす。** ワーカー 1 では c=64 で 105 rps まで伸びた。しかし、1 プロセスのメインスレッドが頭打ちになれば、それ以上は広げられない。
- **すべての接続でなじみを持つ。** 実行ごとの状態を持たないワーカー（Dify の Python ワーカーなど）にも表の費用がかかり、分け方が偏るだけで得がない。

## 実装で詰めた詳細（2026-10-07 追記、ADR 0017）

- **入口:** `Dispatcher.NewAffinePoller`。`protocol.Server` は、Hello で `run_end` を申し出た接続をこれで作る。エンジンは、実行が終わったときに `Dispatcher.RunEnded` を呼ぶ（`OnRunEnd` と同じ `e.finish` の中）。
- **選び方（`match`）:** なじみの接続が切れておらず、クレジットがあり、その仕事のアクションを受けるなら、そこに渡す。このときは接続の並びを回さない。そうでなければ今までどおり先頭に渡して並びを回し、その接続が申し出た接続なら、その実行のなじみを付け替える。
- **知らせの費用（レビューで直した）:** 最初の実装では、申し出た接続が 1 本でもあると、すべての実行の終わりにディスパッチャへの知らせを 1 件積んでいた。なじみの表の実行 ID を、ほかの goroutine からも読める写し（`sync.Map`）にも持ち、表にある実行の終わりだけを知らせるようにした。申し出た接続がない間は、写しも読まない。
- **テスト:** `sched/affinity_test.go`
  - 同じ実行が同じ接続に渡ること。
  - クレジットが尽きたらほかに移り、移った先がなじみになること。
  - 接続が切れたら残った接続に渡ること。
  - 実行の終わりと切断で表が空になること。
  - 申し出ない接続は順に回すこと。
- **実機（n8n、kairo-n8n は Linux のコンテナ、同期あり）:** kairo-worker の 1 実行あたりの CPU は次のとおり。ワーカーを増やしても、ほぼ変わらなくなった。

| ワーカーの数 | 直す前 | 直した後 |
|---|---|---|
| 1 | 約 29ms | 約 33ms |
| 2 | 約 52ms | 約 34ms |
| 4 | 約 73ms | 約 37ms |
