# 0084. コードで書くワークフローのリプレイが記録から外れたら、作用のある新しい呼び出しを起こす前に止める

- 状態: 提案
- 日付: 2026-11-26

## 背景

コードで書くワークフローは、再開のたびに関数を頭から動かし直す。関数が作る呼び出しは、位置ではなく中身で記録と照らし合わせる。呼び出しの ID は、ワークフローの実行 ID と、呼び出しの種類と正規化した入力のハッシュと、同じ組の呼び出しが何回目かから決まる。同じ種類・同じ入力の呼び出しをすれば、記録された結果が返る。呼び出しの前のコードを書き換えても、同じ呼び出しは同じ ID になる。

この照合のしかたのため、関数が決定的でないと、再開したときに記録とは別の呼び出しを作る。たとえば、時計の値や乱数を `ctx` を通さずに読み、それを入力に入れると、ID が変わる。その呼び出しは新しい呼び出しとして動き、実の作用を持つアクションなら、外への作用がもう一度起きる。いまの 3 つの SDK（Go・TypeScript・Python）には、これを見つける仕組みがない。決定的に書くことは利用者が守る決まりとして文書にあるだけで、破ったときは何も知らされない。

この問題は、不変条件 5 と同じ種類の害を生む。不変条件 5 は、結果が不明な実の命令を成功扱いせず、再実行もしない。しかし、関数が記録から外れて作った新しい呼び出しは、kairo から見れば新しい実行なので、何も止めない。

見つける方法は、SDK が呼び出しをどう同時に動かすかで変わる。

- Go の SDK は、同時に動かす呼び出しを `Parallel` に限っている（自前の goroutine で呼び出すことは、決まりで禁じている）。`Parallel` の枝ごとに名前（lane）があり、枝の中の呼び出しの ID はその名前を含む。1 つの枝の中では、呼び出しは順番に作られる。
- TypeScript と Python の SDK には、枝の名前がない。同時に動かすときは、`Promise.all` や `asyncio.gather` で呼び出しをそのまま並べる。どの呼び出しが先に作られるかは、先に返った呼び出しの順で変わる。
- 枝の名前を TypeScript と Python に足すと、呼び出しの ID が変わる。すでに記録された実行の ID と合わなくなり、走っている実行を再開できなくなる。

リプレイが記録へ「到達した」ことは、すでに定義がある。関数が同じ ID の呼び出しを作り、既存の実行を開くことが到達である。到達したことを、保存先には記録しない。

## 決定

コードで書くワークフローを、Go・TypeScript・Python の SDK で動かすとき（埋め込みのランタイムでも kairod でも）に、次のとおりにする。

### 決定項 1（作用のある新しい呼び出しは、記録から外れていないと確かめてから作る）

リプレイの途中で、関数が記録にない呼び出しを作ろうとしたとき、その呼び出しが作用を持つなら、作る前に確かめる。

- 作用を持つ呼び出しとは、アクションの呼び出しのうち、そのアクションが「非保護」でないもの（実の作用、冪等な実の作用を含む）と、子のワークフローである。
- 確かめる内容は、「このワークフローが作った作用のある記録のうち、今回のリプレイがまだ到達していないものが、その新しい呼び出しより前にあるはずなのに残っていないか」である。残っていれば、関数は記録から外れている。
- 作用を持たない呼び出し（非保護のアクション、待ち、sleep）は、確かめずに作る。作り直しても外への作用が起きないからである。

### 決定項 2（「その新しい呼び出しより前にあるはず」を、SDK ごとに確かに決められる範囲で判定する）

判定が呼び出しの順番の揺れに左右されないよう、次の範囲で判定する。

- **Go:** `Parallel` の枝ごとに判定する。新しい呼び出しを作る枝に、まだ到達していない作用のある記録が残っていれば、外れている。1 つの枝の中では呼び出しが順番に作られるので、この判定は順番の揺れに左右されない。
- **TypeScript・Python:** 作用のある新しい呼び出しを、すぐには作らずに待たせる。待たせるあいだも、ほかの呼び出しは記録から答える。関数が、待たせている呼び出しのほかには、記録から答えられる呼び出しをもう作らなくなった時点（それ以上進めない時点）で判定する。そのとき、まだ到達していない作用のある記録が残っていれば、外れている。残っていなければ、待たせていた呼び出しを作る。

枝の名前を TypeScript と Python に足すことはしない。呼び出しの ID の形（ADR 0049 の決定項 2（コードで書くワークフローの API））を変えないためである。

### 決定項 3（外れたら、作用を起こさずに止め、名前のあるエラーで知らせる）

記録から外れたと判定したら、次のとおりにする。

- 待たせていた呼び出しも、判定した呼び出しも作らない。何も記録しない。
- その駆動をやめ、ワークフローを「先へ進めない」状態として扱う。ワークフローを失敗にはしない。扱いは、ADR 0060 の決定項 2（実行中の呼び出しは、今の設定で続ける。ただし作用は弱めない）と決定項 3（1 つの実行の失敗で `tick` を止めない）と同じにする。ログと観測（`run.stuck`）に出し、借用の期限を 1 回分先へ延ばして、ほかの実行は続ける。
- 知らせる内容には、3 つの SDK で共通の名前のあるエラーの種類と、到達しなかった記録の呼び出しと、作ろうとした新しい呼び出しを含める。
- 決定的なコードを配り直せば、次の駆動のリプレイが記録へ到達し、そのまま続く。利用者は、版を分ける（ADR 0060 の決定項 1（ワークフローは、始めたときの版で動かし続ける））か、`Cancel` で終わらせることもできる。

### 決定項 4（判定に使う記録の範囲）

判定に使う「このワークフローが作った作用のある記録」は、直接の子のうち、作用を持つ呼び出しと子のワークフローに限る。

- 待ちと sleep は含めない。待ちは、先に届いたシグナルが作ることがある（ADR 0059 の決定項 2（待ちより先に来たシグナルを、待ちの実行として先に作っておく））。また、作り直しても作用が起きない。
- 外から親へ付けたワークフロー（ADR 0065）は含めない。親の関数が作ったものではないからである。
- 非保護の呼び出しの記録は含めない。時刻を含むログのような、害のない非決定性で止めないためである。

### この ADR で決定しないこと

- エラーの種類の名前、待たせ方、「それ以上進めない時点」の具体的な見つけ方。各 SDK の実装と、その PR で決める。
- グラフで書くワークフロー（ADR 0049 の決定項 1（グラフの API（今の HTTP の API を包む）））。リプレイしないので、この判定の対象にならない。
- 作用を持たない呼び出しの非決定性を知らせる仕組み。必要になれば、別の ADR で決める。
- 関数が `ctx` を通さずに I/O で待つなど、決まりを破るコードでの判定の正しさ。そのようなコードでは、TypeScript と Python の判定が早すぎて誤って止まることがある。その扱いは、SDK の文書に書く。

## 結果

- 良い影響
  - 関数が決定的でないために、実の作用がもう一度起きることがなくなる。外れたことが、名前のあるエラーとして知らされる。
  - ワークフローは失敗にならないので、コードを直して配れば、そのまま続けられる。
- 悪い影響
  - リプレイのある駆動ごとに、直接の子の一覧を 1 回読む。子の数に比例する読み取りで、ワークフローを動かし直すたびに払う。いまのリプレイも記録された子を 1 つずつ開いているので、量の桁は変わらない。ADR 0041 の決定項 1（原則）が求める「実行に要る仕事」には、作用を二度起こさないための確かめとして含める。
  - TypeScript と Python では、リプレイの途中の作用のある新しい呼び出しが、関数がそれ以上進めなくなるまで待たされる。待つのは、記録から答える読み取りが終わるまでの時間である。
  - 版を上げずに関数を書き換え、作用のある呼び出しの前に別の作用のある呼び出しを足すと、走っている実行は止まる。いままでは、別の呼び出しとして動いていた。
- 中立な影響
  - 呼び出しの ID、記録の形式、保存先の形式は変わらない。
  - 決定的な関数の振る舞いは変わらない。
- 新しく守る制約
  - 作用を持つ呼び出しをリプレイの途中で新しく作るときは、この判定を通す。
  - 3 つの SDK で、判定の結果とエラーの種類をそろえる。

## 検討した代替案

- **駆動が終わったときに見つけて知らせるだけにする:** 3 つの SDK で同じにでき、簡単に作れる。しかし、もう起きた作用は防げない。不変条件 5 と同じ種類の害を残すので、採らなかった。
- **Go だけで止め、TypeScript と Python は知らせるだけにする:** SDK によって保証が違うことになる。3 つの SDK を同じ取り決めで動かすという方針（ADR 0058）に反するので、採らなかった。
- **TypeScript と Python にも枝の名前を足し、Go と同じ判定にする:** 呼び出しの ID が変わり、すでに記録された実行を再開できなくなる。採らなかった。
- **呼び出しを位置で照合する:** 呼び出しの前のコードを書き換えても同じ ID になる、という ADR 0049 の性質を失い、同時に動かす呼び出しでは順番が揺れる。採らなかった。
- **外れたらワークフローを失敗にする:** 取り返しがつかない。コードを直しても続けられないので、採らなかった。

## 関連する ADR

- ADR 0049 の決定項 2（コードで書くワークフローの API）: 呼び出しの ID の決め方と、決定的に書く決まり。この ADR は、ID の形を変えずに、決まりを破ったときの作用を止める。
- ADR 0058（Go の SDK）: 3 つの SDK を同じ取り決めで動かす方針。判定の結果とエラーの種類をそろえる根拠。
- ADR 0059 の決定項 2（待ちより先に来たシグナルを、待ちの実行として先に作っておく）: 待ちを判定の範囲から外す理由。
- ADR 0060 の決定項 1（ワークフローは、始めたときの版で動かし続ける）: 関数を書き換えるときの正しい道。
- ADR 0060 の決定項 2（実行中の呼び出しは、今の設定で続ける。ただし作用は弱めない）、決定項 3（1 つの実行の失敗で `tick` を止めない）: 「先へ進めない」の扱いをそろえる。
- ADR 0062 の決定項 1（親のある実行は、親のリプレイが同じ呼び出しへ到達したときだけ再開する）: 「到達」の定義をそのまま使う。
- ADR 0065（外から始めるワークフローを、未完了の親の木へ原子的に加える）: 外から付けた子を判定の範囲から外す理由。
- ADR 0041 の決定項 1（原則）: 駆動ごとに子の一覧を読む費用の位置づけ。
