# 0042. n8n との統合は、n8n の engine v2 の「データプレーン」を kairo で置き換える形で行う

- 状態: 承認
- 日付: 2026-10-06
- 関連: ADR 0029（グラフの実行モデル）、0037・0038（Dify との統合）、0041（実行 1 回あたりのコスト）

## 背景

Dify の次の対象は n8n（2.42.0）である。n8n の実行は次のようになっている（2026-10-06 の調査。根拠は `packages/` 以下のコード）。

- **今の実行エンジン（v1）は、1 つのプロセスの中で完結する。** `WorkflowExecute`（`packages/core`）が、実行の全状態（`IRunExecutionData`）をメモリに持ち、ノードを 1 つずつ実行する。
  - queue モードでは、Bull のジョブで実行を丸ごとワーカーに渡す。
  - 状態の保存は、待ちに入るときと終わったときだけ。進捗の保存を有効にすると、ノードが終わるたびに全体を上書きする。
  - 実行中にプロセスが落ちると、`crashed` の印を付けるだけで、続きからは再開しない。
  - 時刻での再開は、leader が 60 秒ごとに DB を読む `WaitTracker` が行う（ポーリング）。
- **ノードは、実行の履歴全体を同期的に読める前提で書かれている。** `$('Name')` や `.item` などの式は、祖先のノードの出力（`runData`）と `pairedItem` を、その場でたどる。
- **n8n 自身が、実行エンジンを外に出す作り直し（engine v2、`packages/@n8n/engine` v0.22.0）を進めている。** 設計は kairo とよく似ている。
  - 純粋な中核に、外部の作用を注入する形。状態は Postgres に耐久化する。
  - 本体（コントロールプレーン、`packages/cli`）と実行エンジン（データプレーン）は、同じプロセスで動くときも HTTP の契約でつながる（`EngineDataPlaneProvider`）。
    - 本体 → エンジン: `POST /executions`（開始）、`GET /executions/:id`（取得）、`POST /executions/search`（一覧）
    - エンジン → 本体: ライフサイクルイベント（`execution:started/completed/failed`、`step:started/completed/failed`）。本体はこれを v1 の画面向けの push に変換するので（`EngineLifecycleEventPushRelay`）、画面は変えなくてよい。
  - v1 のノードは、本体が渡すステップ実行器（`IStepExecutor`、実装は `V1StepExecutor`）で動かす。祖先の出力から v1 の `runData` を組み立て直して、ノードの `execute()` を呼ぶ。
  - ワークフローの JSON をエンジンのグラフに変える変換器（`V1WorkflowConverter`）もある。v1 と意図的に違う点（分岐は並列で動かす、値は JSON を往復する、など）と、まだ扱わない機能（`continueErrorOutput`、Merge の `chooseBranch`、ピン留めしたデータ、途中からの実行など）が書かれている。
  - 使うかどうかは、ワークフローごとの設定（`settings.engineType === 'v2'`）と、モジュール（`N8N_ENABLED_MODULES` の `engine-v2`）で決まる。対象は manual / webhook / trigger の実行。

Dify では、差し込む場所（`WorkflowEntry` の差し替え）と、合わせる相手（graphon）を、こちらで決めた。n8n では、n8n 自身が差し込み口と、新しい実行の意味論（engine v2）を用意している。

## 決定

### 1. 差し込む場所: engine v2 のデータプレーンを kairo で置き換える

n8n の本体（コントロールプレーン）と画面は変えない。engine v2 のデータプレーンが果たしている役を、kairo が引き受ける。

| 役 | engine v2 | kairo での置き換え |
|---|---|---|
| 実行の開始・取得・一覧（HTTP） | `@n8n/engine` の server | 新しいデーモン `kairo-n8n`（`compat/n8n`）が同じ契約を話す |
| グラフの実行、待ち、耐久化 | engine v2 の中核と Postgres | kairo のエンジン（ADR 0029 のグラフ） |
| v1 のノードの実行 | 本体のプロセスの中の `V1StepExecutor` | n8n 側のワーカーが、kairo のワーカープロトコルで仕事を受け取り、`V1StepExecutor` で動かす |
| 本体へのライフサイクルイベント | engine v2 の publisher | `kairo-n8n` が、kairo の実行イベント（ADR 0034）を同じ形に変えて送る |

- **グラフ:** n8n の `V1WorkflowConverter` がワークフローを engine v2 のグラフにする。`kairo-n8n` は、そのグラフを kairo の計画に変える（Go、`compat/n8n`）。n8n のワークフローの JSON を、kairo が直接は読まない。v1 との違いの決め方を、n8n と同じにするためである。
- **ノードの実行:** n8n の TypeScript のコードを動かすので、kairo のワーカープロトコルの TypeScript の SDK を作る（`sdk/ts`）。n8n 側のワーカーは、本体のプロセスの中で動かす形と、別のプロセスで動かす形のどちらでも動くようにする。
- **ノードが読む履歴:** `V1StepExecutor` は、祖先のノードの出力を読む（`loadStepData`）。`kairo-n8n` は、実行ごとのノードの出力を返す API を持つ。

### 2. 合わせる相手: engine v2

- 比べる相手は、n8n の engine v2 とする（Dify での graphon にあたる）。v1 とは比べない。v1 と engine v2 の違いは、n8n が意図して決めたものだからである。
- 同じワークフローを engine v2 と kairo で動かし、本体に届くライフサイクルイベントと、`GET /executions/:id` の結果を比べる仕組み（ハーネス）を作る。
- 最初に扱う範囲は、engine v2 と同じにする。
  - 実行の種類: manual / webhook / trigger
  - ステップ: v1 のノード（`execute` を持つもの）、待ち、バッチ、サブワークフロー
  - engine v2 が断る機能は、kairo-n8n も同じ理由で断る。

### 3. 段階

1. **調べて決める:** engine v2 の HTTP の契約、イベントの形、ステップの種類（待ち・バッチ・サブワークフロー）と、そのグラフの表し方を読み、kairo の計画への対応表を作る。足りない構成要素や作用があれば、別の ADR で決める。
2. **比べる仕組み:** engine v2 を、n8n の外で単体で動かす（`serve.ts`）。同じグラフを kairo でも動かし、結果を比べる。
3. **kairo-n8n:** 開始・取得・一覧の API、イベントの送信、ノードの出力の API。
4. **TypeScript の SDK と n8n 側のワーカー:** `V1StepExecutor` を kairo の仕事として動かす。
5. **実際の n8n で:** engine v2 の代わりに kairo-n8n につないで、画面での実行、webhook、trigger、待ち、停止を確かめる。性能を、engine v2 と、v1（regular / queue モード）と比べる。

## 結果

- n8n 本体と画面に手を入れずに済む見込みがある。n8n が自分で用意した境い目を使うからである。
- 実行中にプロセスが落ちても、続きから再開できるようになる（kairo の耐久化）。待ちの再開に、ポーリングが要らなくなる（kairo のタイマー）。
- 悪くなること・新しく負うもの:
  - engine v2 はまだ若い（v0.22.0）。契約が変われば、kairo-n8n も追う必要がある。
  - v1 を使っている既存のワークフローは、対象にならない。engine v2 に切り替えたワークフローだけが kairo で動く。
  - TypeScript の SDK を、Python の SDK と並べて保守する。
  - 実行の一覧（検索）は、kairo の得意な形ではない。終わった実行の要約をどこに置くか（kairo-n8n の索引、または Postgres）は、段階 1 で決める。
- テスト: 段階 2 の比較のハーネス。ほかは、段階ごとに足す。

## 検討した代替案

- **v1 の `WorkflowExecute` を置き換える（Dify と同じ形）。** 今使われているワークフローがそのまま対象になる。しかし、v1 の意味論（深さ優先の順次実行、キャンバスの位置による並び、legacy の親の強制実行、`waitingExecution` など）を、kairo の外で再現し続けることになる。差し込み口も、こちらで本体に作り込む必要がある。n8n が v2 に移ろうとしている中で、古い方に合わせることになる。
- **engine v2 の中で、ステップを配る部分だけを kairo にする。** engine v2 の中核と Postgres は残し、ステップの実行先だけを kairo に向ける。状態を持つのが engine v2 のままなので、耐久化・待ち・再開で kairo の利点が出ない。
- **n8n のワークフローの JSON を、kairo が直接読む。** n8n の変換器と結果がずれる。v1 との違いの決め方を、n8n と別に持つことになる。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

### 段階 1: engine v2 と kairo の対応

engine v2（`@n8n/engine` 0.22.0、互換層 `@n8n/node-engine-compatibility` 0.10.0）を読んだ結果。

**engine v2 の今の状態（置き換えの判断に効くもの）**

- 停止の API がない。リクエストによる待ちの再開（フォームなど）もない。再開は期限によるものだけ。
- リトライがない。変換器は `retryOnFail`・`alwaysOutputData`・`executeOnce` を何も言わずに捨てる。
- 1 プロセスの中で、ステップを 1 つずつ順に動かす（並列にしない）。キューはメモリの中にあり、耐久化しない。書き込みの途中で落ちたときの回復も、まだない。
- 本体なしでは、v1 のノードのステップが動かない（`running` のまま止まる）。v1 のノードを動かすのは、本体の中（in-process）か、`n8n engine` コマンド（remote）。
- ライフサイクルイベントは、届かなくてもよいもの（at-most-once）として送る。正しさは `GET /executions/:id` で読み直す前提。

**対応表**

| engine v2 | kairo |
|---|---|
| グラフのノード（`trigger` / `v1-node` / `batch`） | trigger は実行の入力。`v1-node` は n8n 側のワーカーが動かすステップ。`batch` は kairo の loop（下の「足りないもの」2） |
| 辺 `{from, to, outputIndex, inputIndex}` | kairo のグラフの辺。どの出力の口から出るかを区別する必要がある（下の「足りないもの」1） |
| 辺が生きている = 元が成功し、その出力の口が `null` でない | 辺の 3 値（未定・通過・スキップ、ADR 0029） |
| 入ってくる辺がすべて決まってから、生きた辺が 1 本でもあれば動く。全部死んでいれば skip | 同じ（graphon 0.7.0 と同じ決まり、ADR 0029） |
| 入力が複数のノードは 1 回だけ動き、死んだ入力の口には `null` が入る | 入力の参照。スキップしたノードの出力は `null` |
| 分岐の順序は決まっていない | 並列に動かしてよい |
| `iteration`（ループの何回目か。ループの外は 0） | loop の回 |
| 待ち（`resumeAt` と `outputsAtDeadline`） | wait の期限。期限が来たら、宣言された出力で進む |
| 失敗したら、実行はすぐ failed。待っているステップは cancelled | ステップの失敗で実行が失敗する（ADR 0030 の既定） |
| `continueOnFail` | n8n 側のワーカーで処理する（engine v2 と同じ） |
| ステップの出力（`StepSlots`）と、`loadStepData`（実行の全ステップの出力を読む） | kairo-n8n が、実行ごとのステップの出力を返す API を持つ |
| ライフサイクルイベント（6 種類） | kairo の実行のトレース（ADR 0034）から作り、kairo-n8n が本体の `/internal/status-callback` に送る |
| レスポンスチャンネル（webhook の応答、実行の終わりの `ended`） | 応答はワーカー（n8n のコード）が送る。`ended` は kairo-n8n が Redis に PUBLISH する |
| 開始・取得・一覧の HTTP、JWT（HS256）の認証 | kairo-n8n が同じ契約を話す |

**足りないもの（kairo の IR に足す必要がある）**

1. **出力の口が複数あり、同時に複数が生きるノード。** n8n のノードは、出力の口ごとに通る・通らないが決まる（Switch で複数の口に同時に流すなど）。kairo の分岐は「ハンドルを 1 つ選ぶ」形だけ（ADR 0031）。
2. **SplitInBatches のループ。** 回ごとに入力を `batchSize` ずつ切り出し、本体の出力を回をまたいで貯め、切り出すものがなくなったら貯めたものを出す。本体が何も返さなければ、そこでループを終える。kairo の loop と `kairo.assign`（append）で、貯めることと終わることは表せる。しかし、切り出すことを表す組み込みのステップがない。

この 2 つは IR の構成要素を増やすことになるので、別の ADR（0043）で決める。

**実行の記録の置き場所（利用者と決めた、2026-10-06）**

- 実行の記録（`GET` と一覧で返すもの: 実行の行とステップの行）は、Postgres に置く。kairo は、終わった実行の状態を消すからである。
  - engine v2 自身が Postgres を必須にしている（`N8N_ENGINE_DATABASE_URL`）。そのため、engine v2 で n8n を動かす環境には、もともと Postgres がある。
  - 一覧の絞り込み（ワークフロー・状態・時刻）とページングは、DB に任せる。DB が全体の上限になる、という方針（ADR 0039）にも合う。
  - kairo-n8n は別モジュール（`compat/n8n`）にし、Postgres のドライバへの依存はそこに閉じる（ADR 0018）。SQL は、`store/sqlstore` と同じく、準備した文だけを使う（ADR 0020）。
  - kairo のエンジン自身の保存先（ログとスナップショット）は、これまでどおり既定でファイルにする。
- 退けた案: kairo-n8n がファイルに置き、検索用の索引をメモリに持つ。終わった実行が増えるほどメモリを使い、絞り込みとページングも自前で作ることになる。

### 段階 2・3: 変換器と kairo-n8n（2026-10-06）

- **変換器（`compat/n8n/convert.go`）。** engine v2 のグラフを kairo の計画にする。
  - v1 のノードは `n8n.node` のステップ（実の作用、口を持つ、ADR 0043）。入力は `in0`、`in1`、... で、それぞれ元のノードの口を参照する。
    - engine v2 と同じく、リトライしない（`max_attempts: 1`）。
    - 結果が不明なときは、レビューで止めずに失敗にする（`on_unknown: fail`、ADR 0035）。
  - トリガーは、実行の入力（`trigger`）の口を出す `kairo.pass`。
  - `batch` は、ADR 0043 の形の loop。
  - engine v2 が断る形（トリガーが 1 つでない、待ちとサブワークフロー、1 つの入力に 2 本の辺、入れ子のループ、本体の途中からの出入り）は断る。
  - テスト: engine v2 の結合テストと同じ場面（直列、合流、条件のひし形、SplitInBatches のループ、本体が何も返さないループ）を、同じ偽のステップ実行器で kairo 上で動かし、engine v2 が期待する入力と結果になることを確かめた（`convert_test.go`）。
- **kairo-n8n（`compat/n8n`、`cmd/kairo-n8n`）。**
  - **HTTP:** engine v2 と同じ契約（開始・取得・一覧・`/healthz`）。
    - 認証は HS256 の JWT（`auth.go`）。
    - エラーの形（`{error, reason}`）と状態コード（400・401・404・409・501）も合わせた。
    - engine v2 は、同じ ID の 2 回目の開始に 500 を返す。kairo-n8n は 409 を返す。
  - **記録:** Postgres の 2 つの表（実行とステップ、`views.go`）。
    - 接続は `store/postgres` の `Open` を使う（検証付きの TLS 以外は断る）。新しいライブラリは足していない（ドライバは `store/postgres` と同じ pgx）。
    - SQL は、用意した文だけを使う。一覧の絞り込みは、引数が null なら条件を外す形の 1 つの文にした。
  - **イベント:** エンジンのイベントの出口を読み、トレースを 1 つのトランザクションで記録してから ack する。
    - ステップの行の ID は、実行・ノード・回から作る UUID。同じトレースを読み直しても、同じ行になる。
    - 記録の後に、ライフサイクルイベントを本体に送る。engine v2 と同じく、50ms ごと・500 件までまとめ、届かなければ捨てる。
    - 実行が終わったら、`ended` の応答を Redis に PUBLISH する。Redis の通信（RESP）は、`AUTH` と `PUBLISH` だけを自分で書いた。
  - **計画:** グラフの中身のハッシュで名前を付け、データディレクトリに残す（再起動したときに、続きの実行が計画を見つけられるように）。
  - **ブロブ:** 出力をブロブに移さない（ADR 0043 の制約）。
  - テスト: 本物の Postgres（`KAIRO_N8N_PG_DSN`）と、偽の本体・偽の Redis で、次を確かめた（`daemon_test.go`）。
    - 開始から記録までの流れ、イベント、`ended` の応答、一覧
    - 失敗した実行
    - エラーの応答と認証
- **段階 4 に残したこと:** n8n 側のワーカーが、祖先のノードの出力を読む方法（engine v2 の `loadStepData`）。
  - ステップの行は、kairo-n8n がイベントを読んでから書く。そのため、次のステップが配られた時点で、前のステップの行がまだないことがある。
  - engine v2 は、ステップの行を書いてから次を配るので、この問題がない。

### 段階 4: n8n 側のワーカー（2026-10-06）

- **祖先の出力の読み方（利用者と決めた）。** ワーカーは、ステップを動かす前に、kairo-n8n の `POST /internal/step-data` に問い合わせる。
  - kairo-n8n は、そのステップの開始を記録し終えるまで待ってから答える。実行のイベントは順に届くので、開始を記録した時点で、それより前のステップの記録はそろっている。
  - 答えは engine v2 の `StepData`（グラフと、終わったステップの出力をノード・回ごとに）。これに、ステップの文脈に要る実行の情報（ワークフロー ID、モード、呼び出し元）を足した。
  - 待ちはメモリの中で、ステップの開始を記録したときに起こす。kairo-n8n が再起動した後は、記録（Postgres）を見て判断する。
  - 認証は、ワーカーの合言葉（`KAIRO_WORKER_TOKEN`、Bearer）。
  - 退けた案: 祖先の出力を仕事の入力に入れる。kairo はループの回が進むと出力を上書きするので、過去の回の出力を渡せない。
- **TypeScript の部品（`sdk/ts`、`@kairo/worker`）。** kairo のワーカーの決まりごと（ADR 0009）を、Node.js の標準の機能だけで話す。実行時の依存はない。
  - Python の部品と同じ働き（Hello と合言葉、仕事、結果、出力の流し、取り消し）。
  - 取り消しは `AbortSignal` で、仕事の処理に渡す。
  - テスト: 偽のランタイムとの単体テスト（`node --test`）。本物のプロトコルの口（Go）と TypeScript のワーカーをつなぎ、ひし形のグラフを最後まで動かす結合テスト（`compat/n8n/interop_test.go`）。
- **n8n の `kairo-worker` コマンド（n8n のブランチ `feat/kairo`、`packages/cli/src/commands/kairo-worker.ts`）。** `n8n engine`（engine v2 のデータプレーン）と同じ部品で組み立てる。
  - ノードの型、付加データ（`EngineAdditionalDataBuilder`）、認証情報（`RemoteCredentialsHelper`、本体に問い合わせる）、webhook の応答（Redis）は、`n8n engine` と同じものを使う。
  - engine v2 の実行器（`V1StepExecutor`）を、kairo の仕事ごとに呼ぶ。祖先の出力は、上の問い合わせで読む。
  - 認証情報の問い合わせには、ステップごとの取り消しの信号を渡す。engine v2 は、プロセスで 1 つの信号を共有している（TODO CAT-4526）。
  - 待つノード（Wait など）は、まだ扱わない（段階 5）。

### 段階 5: engine v2 との比較（2026-10-06）

本物の n8n（ブランチ `feat/kairo`）の本体を、データプレーンだけ差し替えて動かし、同じ呼び出しを流して比べた。データプレーンは engine v2（`n8n engine`）と kairo-n8n ＋ `n8n kairo-worker` の 2 つ。Postgres も Redis も同じものを使った。

- **比べたワークフロー:** 4 種類。
  - If で分かれるもの（n=42 と n=3）
  - SplitInBatches のループ（5 件を 2 件ずつ）
  - 途中のノードが失敗するもの（Stop and Error）
- **一致したもの:**
  - **記録:** 実行とステップの状態・出力・エラーが、4 つの実行すべてで一致した。比べたのは、データプレーンの API（`GET /api/workflow-executions/:id?includeSteps=true`）から読んだ記録。ID・時刻と、Webhook の出力に入る HTTP ヘッダーは除いた。
  - **ライフサイクルイベント:** 種類・順番・中身が一致した。データプレーンと本体の間に記録用の中継を挟んで比べた。
  - **webhook の応答:** n=42 以外は一致した。失敗した実行は、どちらも `500 {"message":"Error in workflow"}` を返す。
- **比べて直したこと:**
  - **ループの最後の周回。** engine v2 は、ループの最後の周回（バッチノードが done 側に出した回）に本体のステップを作らない。スキップとしても作らない。kairo-n8n は、この回の本体を「スキップ」として記録していた。
    - 直し方: その回の本体のスキップを記録しないようにした（`trace.go`）。最後の周回は、バッチノードの `kairo.slice` が loop 側を空にした回で見分ける。
    - テスト: `TestDaemonBatchLoopSteps`。
    - 再起動: 最後の周回の判定はメモリに持ち、再起動の後は記録から復元する（バッチノードのステップの行のうち、loop 側の口が null で完了したもの）。最後に確定したステップ（`ended` の `lastStep`）も、同じく記録から復元する。記録を読むのは、再起動の前にトレースを読んでいた実行だけ（ADR 0045 の追記と同じ）。テスト: `TestRunInfoRestore`。
  - **オブジェクトのキーの順番。** `kairo.assign` は値を Go の map に戻してから書くので、キーが辞書順に並び替わっていた。ループで集めた項目が、ノードの出した順番と違う並びで返っていた。
    - これは Dify でも同じで、Python の dict は挿入順を保つ。
    - 直し方: 値を動かすだけの操作（over-write、append、extend、remove-first、remove-last）では、元のバイト列から結果を組み立てるようにした（`core/vars.go` の `spliceAssign`）。検証と意味はこれまでどおり、デコードした値で行う。
    - テスト: `TestSliceLoopKeepsKeyOrder`。
    - 状態の符号化と、ログの形式は変わらない。数値の表記と有限でない数の扱いは、これまでどおり（詳しくは ADR 0033 の追記）。
- **残った違い（kairo-n8n の方が v1 に近い）:**
  - **`lastNode` 応答のデータの揺れ。** engine v2 は、`ended` の `lastStep` に「最後に確定して実行を終わらせたステップ」をそのまま入れる。そのステップがスキップだと、応答は「最後のノードがデータを返さなかった」になる。
    - n=42 では、スキップされた Small の確定が Big の完了より後になることがある。順に呼ぶとたいていデータが返るが、起動直後の 1 回目と、同時に呼んだとき（16 並列で 64 回）はすべて「データなし」になった。
    - kairo-n8n は、トレースの順に最後に確定したステップを返す。If の時点で Small のスキップが確定するので、Big の出力が毎回返る（16 並列で 64 回とも）。
  - **キーの順番。** engine v2 は、応答の出力を jsonb から読み直すので、キーが jsonb の順（短い順、同じ長さはバイト順）に並ぶ。例: `{"from":42,"size":"big"}`。kairo-n8n は、ノードが出した順のまま返す。例: `{"size":"big","from":42}`。v1 の n8n と同じ並び。
    - 記録（jsonb）のキーの順番は、どちらも jsonb の順になる。
- **画面からの手動実行（2026-10-06）:** 画面の「Execute workflow」と同じ API（`POST /rest/workflows/:id/run`、`triggerToStartFrom`）で、手動トリガーから始まる If のワークフローを動かした。本体が持つ結果（各ノードの状態と出力、最後に動いたノード、モード）は、kairo-n8n と engine v2 で完全に一致した。
- **待つノード（2026-10-06、ADR 0045）:** ステップの結果として「期限まで待ってから、この出力で終わる」を返せるようにした。70 秒待つ Wait ノードで、待機中も終わった後も、記録は engine v2 と一致した。再開の要求で抜ける待ち（期限のないもの）は、engine v2 と同じく扱わない。

#### 性能（2026-10-06、macOS、14 コア）

ほかの作業でマシンの負荷が高かった（load average 14〜44）。そのため値は目安で、同じ時間帯に続けて測ったものだけを比べる。

- **測り方:**
  - n=42 の If のワークフロー（Webhook、Set、If、Set の 4 ノード）の webhook を、`ab` で呼んだ。
  - 応答は `lastNode`。1 回の呼び出しが、実行の終わりまで待つ。
  - v1 は、同じワークフローを engine v1 で、本体のプロセスの中で動かした（regular モード）。

まず、既定の設定で測ったときの、1 実行あたりの CPU（c=8、2000 回）。

| 構成 | 1 実行あたりの CPU |
|---|---|
| kairo-n8n（Go） | 約 6ms |
| kairo-worker（Node） | 約 113ms |
| engine v2（Node、1 プロセス） | 約 82ms |
| v1（本体の中） | 約 36ms |

- **CPU の大半は n8n の式の評価器だった。** kairo-worker の CPU プロファイルでは、メインスレッドの時間の半分以上が、式の評価器（isolated-vm）だった。
  - 内訳は、サンドボックスの生成・破棄と評価。CPU 時間が経過時間の約 6 倍になるのも、isolated-vm のスレッドが使うためだった。
  - 評価器は、式を持つ呼び出し側（Workflow オブジェクト）ごとにサンドボックスを 1 つ取り、使い終わると捨てる。
  - v1 は 1 実行で 1 つ使う。engine v2 の実行器（`V1StepExecutor`）は、ステップごとに 1 つ使う。
  - 用意しておく数（`N8N_EXPRESSION_ENGINE_POOL_SIZE`）は既定で 1。同時に動くステップが多いと、生成を待つことになる。
- **kairo 自身の取り分:** 1 実行あたり約 6ms で、Postgres への記録、イベント、`ended` を含む。

次の表は、`N8N_EXPRESSION_ENGINE_POOL_SIZE=16` で 3 つの構成を続けて測ったもの。

| 構成 | c=1 | c=8 | c=32 |
|---|---|---|---|
| kairo-n8n ＋ kairo-worker | 40 rps（p50 24ms） | 97 rps（p50 77ms） | 101 rps（p50 309ms） |
| engine v2 | 21 rps（p50 47ms） | 28 rps（p50 225ms） | 35 rps（p50 891ms） |
| v1（本体の中） | 148 rps（p50 7ms） | 158 rps（p50 49ms） | 163 rps（p50 195ms） |

- **v1 の queue モード（2026-10-06）:** 本体と `n8n worker`（1 プロセス、同時実行 10）で、同じ webhook を測った。本体の保存先は SQLite で、n8n は queue モードを SQLite では正式にはサポートしない（警告が出る）。値は目安。
  - c=1 で 32 rps（p50 33ms）、c=8 で 41 rps（p50 191ms）、c=32 で 46 rps（p50 784ms）。
  - 1 実行あたりの CPU は、ワーカーが約 39ms、本体が約 8ms。
  - 同じくワーカー 1 プロセスの kairo-n8n（ADR 0044 の後、c=8 で 144 rps、c=32 で 162 rps）の方が、3 倍ほど多くこなした。queue モードは、ワーカーの同時実行の数（既定 10）で頭打ちになる。
- **engine v2 との比較:** 同じ実行器（`V1StepExecutor`）を使い、kairo-n8n は engine v2 の 2〜3 倍のスループットだった。
  - engine v2 は 1 プロセスで、ステップごとに Postgres を読み書きしながら次のステップを決める。
  - kairo は、次のステップを決めて配るまでを Go の中で行い、記録は後から書く。
- **v1 との比較:** v1 との差は、ほぼステップごとのサンドボックスの費用。これは engine v2 の実行器の性質で、kairo のランタイムの費用ではない。
- **式のサンドボックスは 1 実行に 1 つ（2026-10-06、利用者と決めた）。** v1 と同じ単位にした。engine v2 はステップごとに 1 つ使う。
  - n8n 側（ブランチ `feat/kairo`）の変更:
    - `Expression` に、サンドボックスの持ち主を差し替える口を足した（`shareIsolateWith`、`acquireIsolateFor`、`releaseIsolateFor`）。持ち主を指定しなければ、これまでどおり自分が持ち主になる。
    - `V1StepExecutor` の依存に `isolateOwner` を足した。ステップごとに作る Workflow の式に、実行ごとの持ち主を渡す。
  - kairo-worker は、実行ごとに持ち主を 1 つ作り、最初のステップでサンドボックスを取って持ち続ける。
    - ワーカーには実行の終わりがわからない。そこで、最近使った実行の分を最大 64（`KAIRO_WORKER_ISOLATES`）まで持つ。超えたら、ステップが動いていない一番古い実行の分を手放す。全部でステップが動いているときは、engine v2 と同じくステップごとに取る。
    - ステップが失敗したら、その実行の分を手放す。タイムアウトでサンドボックスが壊れていることがあり、実行は失敗で終わるため。
    - タイマーもポーリングも使わない（ADR 0041）。
    - 実行の終わりは、kairo から知らせる（ADR 0044 の `RunEnd`）。受けたら、その実行のサンドボックスを手放す。上の「最大 64」は、知らせが届かなかったとき（再起動やつなぎ直しの前に渡された実行）の安全弁になった。
  - 評価は同期的（`evalClosureSync`）なので、同じ実行の並列の枝が 1 つのサンドボックスを使っても、評価が混ざることはない。
  - 正しさ: 4 種類のワークフローで、記録は engine v2 と一致したまま。
  - 性能（同じ条件で測り直した。load average 25〜38 と高い）: kairo-worker の CPU は、1 実行あたり約 86ms から約 29ms になった。v1 の本体の中での実行（約 36ms）と同じくらい。

    | プール | c=1 | c=8 | c=32 |
    |---|---|---|---|
    | 16 | 24 rps（p50 21ms） | 136 rps（p50 57ms） | 100 rps（p50 209ms） |
    | 1（既定） | 23 rps（p50 26ms） | 105 rps（p50 68ms） | 87 rps（p50 243ms） |

### 横に広げたときの計測（2026-10-07）

ワーカーの数を変えて、n=42 の If のワークフロー（4 ノード）の webhook を測った（各 2000 回）。式のサンドボックスのプール（`N8N_EXPRESSION_ENGINE_POOL_SIZE`）は、どの構成も 16 にした。

マシン（macOS、14 コア）は、ほかの作業で常に load average 18〜30 だった。プロセスを増やすほど CPU を取り合うので、値は目安にとどめる。

- **先の計測の訂正:** 段階 5 の性能の表（kairo-n8n の 40〜162 rps）は、kairo-n8n を `-nosync`（耐久化の書き込みを省く）で動かしていた。engine v2 は Postgres に同期して書くので、条件がそろっていなかった。
- **macOS の同期:** 同期ありで macOS の上で動かすと、kairo-n8n は c=8 で 17 rps（p50 432ms）だった。
  - n8n のノードは作用が「実」のステップなので、意図の記録が耐久化するまで仕事を渡さない（不変条件 4）。4 ノードの実行は、同期を 5 回ほど順に待つ。
  - macOS の同期は `F_FULLFSYNC` で、1 回に十数 ms かかる（p99 17ms）。
  - Postgres（engine v2 と v1 の保存先）は Linux のコンテナの中で、同期が安い。そこで、kairo-n8n も Linux のコンテナで動かして測り直した（データはコンテナの中）。
- **結果（同期あり、rps と p50）:**

| 構成 | c=8 | c=32 | c=64 |
|---|---|---|---|
| kairo-n8n（Linux）＋ kairo-worker 1 | 77（94ms） | 97（313ms） | 105（570ms） |
| kairo-n8n（Linux）＋ kairo-worker 2 | 36（133ms） | 93（338ms） | 87（701ms） |
| kairo-n8n（Linux）＋ kairo-worker 4 | 53（134ms） | 64（479ms） | 70（892ms） |
| v1 queue（Postgres）＋ n8n worker 1 | 103（76ms） | 100（311ms） | 92（679ms） |
| v1 queue（Postgres）＋ n8n worker 2 | 109（70ms） | 112（284ms） | 117（547ms） |
| v1 queue（Postgres）＋ n8n worker 4 | 73（75ms） | 123（254ms） | 113（542ms） |
| engine v2（1 プロセス） | 24（264ms） | 5（1468ms） | 5（2927ms） |

- **わかったこと:**
  - **engine v2 は横に広げられない。** `@n8n/engine` 0.22.0 の待ち行列はプロセスの中にしかなく（`InMemoryWorkQueue`）、仕事を 1 件ずつ順に処理する。`n8n engine` を増やしても仕事を分け合わない。c=32 以上では、応答が 300 秒の時間切れになるものが出た。
  - **kairo-n8n はワーカーを増やすと遅くなった。** kairo-worker の 1 実行あたりの CPU が、ワーカー 1 で約 29ms、2 で約 52ms、4 で約 73ms と増えた。
    - 原因: 1 つの実行のステップが、複数のワーカーに分かれて渡る。式のサンドボックスは各ワーカーの中で実行ごとに作るので、ワーカーごとに作り直しになる。
  - **v1 queue は、1 実行のノードを 1 つのワーカーがまとめて動かす。** サンドボックスは 1 つで済み、ノードごとの耐久化もない。ワーカー 1 では、c=8 で kairo-n8n より速かった（103 対 77 rps）。
  - **kairo 自身の費用は小さい。** macOS で測ったとき、kairo-n8n の CPU は 1 実行あたり約 4〜6ms だった（記録、イベント、応答を含む）。差を生んでいるのは、ワーカーの側の費用と、ノードごとの耐久化の待ちである。
- **次の候補（利用者と決める）:**
  1. **同じ実行のステップを、なるべく同じワーカーに渡す。** スケジューラの渡し方を変えるので、ADR が要る。
  2. **作用のない n8n ノードを「実」として扱わない。** Set・If・Switch・Merge などは外に作用しないので、再実行してよい。変換のときに、ノードの型で作用を決める。耐久化の待ちは、外に作用するノード（HTTP、DB、メールなど）だけになる。作用の宣言の決め方なので、ADR が要る。
  3. **負荷のない Linux のマシンで測り直す。**

### ADR 0046・0047 の後の計測（2026-10-07）

同じ条件で測り直した（kairo-n8n は Linux のコンテナ、同期あり）。値は rps（p50）。計測のワークフローの 4 ノード（Set、If、Set、Set）は、どれも ADR 0047 で非保護になった型である。

| 構成 | c=8 | c=32 | c=64 |
|---|---|---|---|
| kairo-n8n ＋ kairo-worker 1 | 46（116ms） | 95（327ms） | 101（607ms） |
| kairo-n8n ＋ kairo-worker 2 | 55（123ms） | 71（413ms） | 98（640ms） |
| kairo-n8n ＋ kairo-worker 4 | 60（124ms） | 76（396ms） | 105（599ms） |

- kairo-worker の 1 実行あたりの CPU は、ワーカーの数によらず 33〜37ms になった（ADR 0046）。
- スループットは、まだ v1 queue（c=8 で 103 rps、p50 76ms）に届かない。
  - ワーカーを増やしても伸びないので、ワーカーの CPU ではないところで頭打ちになっている。
  - 疑っているのは、ステップごとの step-data の待ちである。ステップの開始が Postgres に記録されるまで答えを待つので、1 ステップごとに、フィードの配送と Postgres のコミットを順に待つ。
  - マシンの負荷（load average 18〜25）の影響も残る。

### ステップデータをメモリから答える（2026-10-07、利用者と決めた）

- **原因を測った:** kairo-worker の中で、ステップごとの時間を測った。同時 8 で、ステップデータの待ちは p50 で 17〜23ms だった。ノードの実行は 1ms 未満だった。kairo-n8n の側の内訳（トレース約 21 件のまとまりごとの平均）は次のとおり。
  - トレースが出てから届くまで: 10〜17ms。ほとんどは、前のまとまりの書き込みを待つ時間。
  - Postgres への書き込み: 約 5ms。コミット: 約 2ms。
  - ステップデータは、ステップの開始が Postgres にコミットされるまで答えないので、ステップごとにこれを順に待っていた。
- **変えたこと（段階 4 の「ステップの開始を記録し終えるまで待ってから答える」を置き換える）:**
  - **メモリから答える。** kairo-n8n は、実行ごとに、始まったステップと、終わったステップの出力（ノードと回ごと）をメモリに持つ（`runInfo.started`、`outputs`）。フィードからトレースを読んだ時点で更新し、待っているステップデータの問い合わせを起こす。トレースは kairo のログで耐久化した後に届くので、Postgres より先に答えても、耐久化していない出力を渡すことはない。
  - **トリガーの出力:** 実行の始まりのトレース（`TrRunStart`）の入力から取る。
  - **読み取りと記録を分けた。** フィードを読む goroutine がトレースを読み解き（`read`）、記録の goroutine が Postgres に書く（`record`）。記録の側は、たまっているまとまりを 1 つのトランザクションにまとめて書く。ライフサイクルイベント、`ended` の応答、kairo への ack は、今までどおりコミットの後に出す。
  - **再起動の後:** 記録から作り直した実行は、ステップの行から、始まったステップと出力を復元する。再起動の前に始まったステップは、記録（`HasStep`）で確かめる。始まりから追っている実行は、記録を引かない（ステップごとの Postgres の問い合わせはない）。
  - テスト: `TestDaemonStepDataAfterRestart`（再起動の後に、記録から作り直した実行でも、前のステップとトリガーの出力が読めること）。既存の `TestDaemonRunsAndRecords` は、メモリからの答えを確かめる。
- **結果:**
  - ステップデータの待ちは、同時 8 で p50 3.6ms、同時 1 で 0.7ms になった（もとは 17ms と 5.4ms）。
  - 同じ条件の計測（kairo-n8n は Linux のコンテナ、同期あり、load average 20〜29）の値は rps（p50）。

| 構成 | c=8 | c=32 | c=64 |
|---|---|---|---|
| kairo-n8n ＋ kairo-worker 1 | 92（76ms） | 130（231ms） | 124（503ms） |
| kairo-n8n ＋ kairo-worker 2 | 136（56ms） | 145（198ms） | 139（459ms） |
| kairo-n8n ＋ kairo-worker 4 | 98（61ms） | 68（285ms） | 136（497ms） |

  - v1 queue（ワーカー 1 で c=8 が 103 rps、ワーカー 2 で 109〜117 rps）を上回った。
  - ワーカー 4 の c=32 の落ち込み（p99 3.5 秒）は、マシンの負荷が高かった時間帯のもので、測り直していない。
- **残る時間:** データプレーンの中の実行の時間（作成から終了まで）は p50 で約 45ms。同時 8 の応答の p50 との差（約 30〜50ms）は、n8n の本体が webhook を受け、Redis で終わりを受け取るまでの時間である。
