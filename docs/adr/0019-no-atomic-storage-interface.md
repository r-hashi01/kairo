# 0019. 保存先インターフェースは変えない（SQLite の第 2 段階は行わない）

- 状態: 承認（2026-10-01）
- 日付: 2026-10-01
- 関連: ADR 0016, 0018

## 背景

ADR 0018 の第 1 段階で、SQLite 版の Sink と Store は既存のインターフェースのまま動いた。性能の基準も満たした（ack p99 はファイル版の 1.03〜1.16 倍、スループットは 0.89〜0.96 倍）。

0018 は、基準を満たしたら第 2 段階を提案するとしていた。第 2 段階とは、「スナップショット＋チェックポイント＋退役」を 1 回の原子的な操作にする保存先インターフェースを足し、ADR 0016 の順序制御を簡単にすることである。

ところが、既定の保存先はファイル形式のままと決まっている（0018）。ファイル版には複数の保存先にまたがるトランザクションがないので、エンジンは 0016 の順序制御を捨てられない。

## 決定

- 保存先インターフェース（`wal.Sink`、`wal.Retirer`、`blob.Store`）は変えない。第 2 段階は行わない。
- SQLite 版は、既存のインターフェースの実装として提供を続ける。耐久化の順序制御は、ファイル版と同じエンジンの仕組み（0016）に任せる。
- 次のどれかが起きたら、改めて第 2 段階を検討する。
  - 既定の保存先をトランザクションのあるものに変える判断をしたとき
  - 0016 の順序制御に起因する不具合が、繰り返し見つかったとき
  - SQLite 版でしか実現できない要件（例: 複数の実行をまたぐ原子的な更新）が出たとき

## 結果

- エンジンの耐久化の経路は 1 本のまま。保存先ごとに分岐しない。
- SQLite を選んでも、0016 の順序制御は簡単にならない。SQLite 版の利点は、運用面（1 ファイル、`sqlite3` で中身を見られる、Litestream などの複製）に限られる。
- 新しく守らせることはない。

## 検討した代替案

- 原子的な操作を任意のインターフェースとして足し、対応する保存先だけ簡単な経路を使う: エンジンに経路が 2 本でき、検証すべき組み合わせが増える。既定のファイル版で使われない経路を保守することになる。
- ファイル版にもトランザクション相当を実装する（例: 統合ログにスナップショットも書く）: スナップショットがログに入ってログが肥大し、0011・0016 の設計を作り直すことになる。
