# 0060. 実行中のワークフローの下でコードと設定が変わるとき: ワークフローは版で固定し、呼び出しは今の設定で続ける（作用は弱めない）

- 状態: 承認
- 日付: 2026-10-09
- 関連: 不変条件 4・5 / ADR 0049（コードで書く API）、0051（常駐しない kairo）、0058（Go の SDK）、0059（埋め込みのランタイムの不足）

## 背景

コードで書くワークフロー（ADR 0049）は、再開のたびに関数を最初から動かし直します。終わった呼び出しは、呼び出しの ID（種類と入力のハッシュ、何番目か）で記録から返ります。このやり方は、関数とアクションの設定が変わらないことを前提にしています。実際には、ワークフローが動いている間（数日待つ承認もある）にデプロイが入ります。変わり方は 3 つあり、どれも今は扱えていません。

1. **ワークフローの関数が変わる。** 呼び出しを足す・消す・入力を変えると、その呼び出しの ID が変わります。記録にない呼び出しとして実行されます。実のアクションでも同じで、前の版で済ませた支払いの入力が少し違えば、新しい呼び出しとして支払いがもう一度走ります。ADR 0049 では「関数は決定的に書く」を利用者の決まりにしただけで、関数を変えたいときの手段がありません。
2. **アクションの設定が変わる。** タイムアウトやリトライ回数を 1 つ変えると、そのアクションのプラン（`kairo.call/<action>`）のハッシュが変わります。ハッシュはプランの定義とアクションの仕様から作るためです。すると、再試行を待っている呼び出しは「plan changed since it started」で処理できなくなり、二度と進みません。2026-10-09 に Go の SDK で確かめました。
   - SDK を上げただけでも起こりえます。アクションの仕様（`ir.NodeSpec`）に項目が増えると JSON が変わり、すべてのプランのハッシュが変わるからです。
3. **1 つの実行の失敗が、`tick` 全体を止める。** 上の失敗で `tick` がエラーを返して途中で止まります。同じ回に処理するはずだった、ほかの実行のタイマーや借用まで進まなくなります。

## 決定

3 つの SDK（Go・TypeScript・Python）に同じ意味で入れる。表の形は変えない。

### 1. ワークフローは、始めたときの版で動かし続ける

- ワークフローを宣言するときに、版を付けられるようにする。
  - Go: `kairo.Workflow(k, "refund", fn, kairo.Version("2"))`
  - TypeScript: `k.workflow("refund", fn, { version: "2" })`
  - Python: `@k.workflow("refund", version="2")`
- 版は、ワークフローの実行の入力に `"version"` として記録する（今の `{"workflow", "input"}` に足す）。版を付けなければ `""` で、今と同じに動く。
- **プロセスが動かすのは、その名前と版の両方を登録している実行だけ。** ほかの版の実行は、借用の引き継ぎ（ADR 0059）でも `Run` でも動かさない。そのワークフローが登録されていないときと同じに、ほかのプロセスに任せる。
- 1 つの名前に、いくつかの版を同時に登録できる。新しく始める実行には「今の版」を使う。前の版は、走っている実行を終わらせるためだけに残す。
  - Go: `kairo.Draining()`
  - TypeScript: `{ version: "1", draining: true }`
  - Python: `draining=True`
  - 1 つの名前に、今の版はちょうど 1 つ。2 つ以上あれば `Start` がエラーを返す。
- 子のワークフローは、それを始めたときの、その名前の今の版で動く。その後は、その版で動き続ける。
- `RunInfo` に `Version` を足す。どの版の実行が残っているかは `List` で見られるので、前の版を消してよいかを判断できる。

### 2. 実行中の呼び出しは、今の設定で続ける。ただし作用は弱めない

- `kairo.call/`・`kairo.wait/`・`kairo.workflow` のプランは SDK が作るもので、どれも 1 つのノードしかない。記録されたハッシュと今のハッシュが違っても、エラーにせず、今のプランで続ける。続けたら、記録されたハッシュを今のものに置き換える。
  - アクションの設定の変更（タイムアウト、リトライ、間隔、上限）は、その時点から、実行中の呼び出しの次の試行にも効く。
- **例外は 1 つだけ：結果のわからない実の試行を、実でない設定で扱わない（不変条件 5）。**
  - 対象は、呼び出しに実の試行が出ていて、その意図が耐久化済みで、結果がまだ来ていないとき。
  - そのとき、今の設定が「実で、`IdempotentRetry` もない」でなければ、今の設定には切り替えない。
  - そのイベントは適用せず、ログと観測に出す。その呼び出しは止まったままになる。
  - 切り替えないのは、もし切り替えると、結果が不明になったときに再試行され、実の作用が二度起こりうるため。
  - 利用者は、設定を戻すか、`Resolve` / `ResolveFailed` / `Cancel` で決着させる。この 3 つは、どの設定でも安全に適用できるので、上の場合でも今のプランで適用する。
- コアに、活性化が耐久化済みの意図を持つかを返す読み取りの関数を 1 つ足す（`core.Act` の `IntentDurable()`）。純粋な読み取りで、状態の形式は変えない。

### 3. 1 つの実行の失敗で `tick` を止めない

- `tick` が実行ごとに処理するもの（期限切れの借用、期限の来たタイマー、駆動の引き継ぎ）で 1 つが失敗しても、ログと観測に出して次に進む。
- `tick` がエラーを返すのは、保存先の読み取りそのものが失敗したときだけにする。

## 結果

- 走っている実行を止めずに、ワークフローの関数を書き換えて出せる。前の版を残しておけば、前の版の実行は前の関数で終わる。
- 実行中の実の呼び出しは、前の版の関数で始めたものとして記録どおりに扱われる。新しい版の関数の入力で、もう一度走ることはない。
- タイムアウトやリトライを変えても、実行中の呼び出しが止まらない。SDK を上げてハッシュが変わっても止まらない。
- 実行 1 回あたりのコストは増えない。版は入力の中の数バイト。ハッシュの比較は今もしていて、置き換えは違うときにだけ起こる。
- 新しく守ること:
  - 前の版を消すのは、その版の実行が残っていないことを確かめてから。残っている実行は、その版を登録したプロセスが現れるまで進まない。
  - 版を付けずに関数を変えたときの振る舞いは、今と同じ（ADR 0049 の決まり）。
- テスト（3 つの SDK に同じものを足す）:
  - 版 1 で始めて止めた実行を、版 1（`Draining`）と版 2 を登録したプロセスで再開する。版 1 の関数で終わる。新しい実行は版 2 で動く。
  - 版 1 を登録していないプロセスは、版 1 の実行を動かさない。
  - 再試行を待っている呼び出しのアクションの設定を変えて再開すると、今の設定で終わる（今は止まる）。
  - 実の試行が結果待ちのまま、そのアクションを `Unprotected` に変えて再開すると、切り替えずに止まる。`ResolveFailed` で決着できる。
  - 1 つの実行が処理できなくても、同じ `tick` で、ほかの実行のタイマーが発火する。
  - コアの `IntentDurable()` に、`checkReplay` を通るテストを足す。

## 検討した代替案

- **関数の中で版を分ける（Temporal の `GetVersion` / `patched`）:** 関数の中に「この地点で変えた」という目印の呼び出しを置き、古い実行と新しい実行で枝を分ける。1 つの関数で両方を扱えるが、古い実行かどうかを見分けるには、その地点より後の記録があるかを知る必要がある。kairo の呼び出しの ID は内容から作るので、記録の順番が取れない。また、関数が古い枝を抱え続ける。版ごとに関数を分けるほうが、分かりやすく、消すときも版ごとに消せる。
- **ハッシュが変わったら、古い定義で続ける:** 安全だが、古い定義を実行ごとに保存する必要がある（表の形が変わる）。また、設定を直したくて出したデプロイが、実行中の呼び出しに効かなくなる。作用以外は今の設定で続けるほうが、利用者の意図に合う。
- **関数の書き換えを検知して止める:** 再開のときに、記録にない呼び出しが現れたら止める。ただ、新しい呼び出しは正しい書き換えでも現れるので、誤りかどうかを判断できない。版での固定を先に入れ、検知は必要になってから考える。
- **前の版を残さず、走っている実行を新しい版で続ける（今の振る舞い）:** 関数の変更が呼び出しの ID を変えるかどうかを、利用者が毎回考えることになる。実の呼び出しが二度走る事故が起こりうる。

## 実装で詰めた詳細（2026-10-09 追記、ADR 0017）

### コアと WASM

- **`core.Act.IntentDurable()` は「試行が出ていて、その意図が耐久化済み」を返す。** 意図の印は、次の試行を出すまで消えない。そのため、試行が出ていること（dispatched）も条件に入れた。
- **`EvResolve` は、`Unknown` を付けたときに限り、`IntentDurable()` の活性化も決着させる。** 決定 2 では「`Resolve` / `ResolveFailed` / `Cancel` で決着させる」としたが、作用を弱めたために止めた呼び出しは要確認になっていない。結果不明のイベントを適用できず、試行が出たままになるからである。そこで、コアの resolve の受け付けを広げた。
  - 広げた経路は、イベントに `Unknown` を付けたときだけ通る。kairod（エンジンの `Resolve`）は付けないので、これまでどおり要確認の活性化しか決着させない（レビューの指摘による）。
  - SDK の resolve が付けるのは、その呼び出しが「作用を弱めたために止まった」ときだけである。つまり、プランのハッシュが違い、今の設定では結果不明の試行を実として扱えないときに限る。ふつうに実行中の実の試行は、これまでどおり決着させない。
  - 決着させるとき、コアは出ている試行の中止（`CmdAbort`）を出し、タイマーを片付けて、試行を引っ込める。元の試行の結果が後から届いても、活性化はもう決着しているので無視される。
  - 状態の形式は変えていない。コアのテスト `TestResolveRealAttemptOut` と `TestIntentDurable` で確かめ、どちらも `checkReplay` を通る。
  - エンジンでは、意図の印は記録を適用した時点で立つ。耐久化はその記録のログが確定した時点で、印のほうが先になる。名前との違いは、コードのコメントに書いた。
- **TypeScript と Python のために、WASM に `kairo_inspect` を足した。** 結果は `wasmcore.Inspection`（`intent_durable`、`review`、`intents`）である。`kairo_compile` の結果にも `idempotent` を足した。どちらも足しただけなので、ABI の版（1）は変えない。

### Go（sdk/go）

- **版の指定の名前は `kairo.WorkflowVersion("2")` にした。** 決定の例の `kairo.Version` は、0.2.0 で SDK の版の定数として公開済みだったため、名前がぶつかった。
- **版を付けない実行の入力は、これまでと同じバイト列にした。** 版は、付けたときだけ入力に `"version"` を足す。TypeScript・Python の SDK と、以前の版で始めた実行との互換のためである。
- **版の確かめは、借用を取る前に行う。** その版を持たないプロセスは、駆動の借用を取らずに飛ばす（未登録のプランと同じ扱い）。待ちモードの `Run` は、ほかのプロセスが動かすのを待つ。
- **止まった実行は、ログ（warn）と、観測の新しい種類 `run.stuck` に出す。** 作用を弱めたときのエラーは `ErrEffectWeakened` とした。
- **止まった実行は、借用の期間だけ後回しにする**（レビューの指摘による）。期限切れの借用は、持ち主を空にして期限を延ばす。タイマーは、発火の時刻を延ばす。止まったものが毎回の `tick` の取得の枠（1,000 件）の先頭を占め続けて、ほかの実行に届かなくなるのを防ぐためである。ほかのプロセスのもの（未登録のプランや版）は、これまでどおり黙って飛ばす。
- **版のない子のワークフローに当たっても、親を失敗で記録しない**（レビューの指摘による）。親の駆動の借用を手放し、両方の版を持つプロセスに任せる。
- **そのまま適用してよいイベント**：作用を弱めた判定でも、再試行を生まないイベントは適用する。中身は取り消し、resolve、試行の確定した成功、待ちである。
- **テスト**：`kairotest` に、VersionsArePinned、SettingsChangeUnderACall、EffectIsNotWeakened、ChildVersionNotHere を足した。ChildVersionNotHere は、上の修正を外すと落ちることを確かめた。
  - EffectIsNotWeakened では、もう 1 つのことも確かめる。作用を弱めて止まった呼び出しと同じ `Tick` で、ほかの実行のタイマーが発火することである。

### TypeScript・Python（sdk/ts、sdk/python）

- **API**
  - 版：TypeScript は `k.workflow(name, fn, { version, draining })`、Python は `@k.workflow(name, version=..., draining=...)`。
  - 手で決着させる：TypeScript は `k.resolve(callId, output)` / `k.resolveFailed(callId, message)`、Python は `await k.resolve(...)` / `await k.resolve_failed(...)`。この 2 つは、これまで TypeScript と Python になかったので、今回足した。
  - エラー：`EffectWeakenedError`。
  - 観測：`run.stuck`。
  - WASM の包み：`Core.inspect(state)`。
- **kairod（`HttpBackend`）では、版による固定が効かない。** kairod の実行の情報は入力を返さないので、既存の実行の版を読めないためである。入力が報告されないときは、今の版で動かす。`resolve` は埋め込みのランタイムだけで使え、kairod ではエラーを投げる。
- **版のない子に当たったとき、親を失敗で記録しないのは、その場合（`NotHere`）だけにした。** Go はプランが未登録のエラー全般を対象にしている。TypeScript・Python は保存先のエラーが 404 として届くので、404 全体を対象にすると「実行がない」なども含んでしまうためである。
- **`tick` の打ち切りは、「ランタイムが閉じたら抜ける」にした。** TypeScript・Python には Go の ctx にあたるものがないためである。
- **TypeScript と Python には、アクションに `IdempotentRetry` を宣言する手段がまだない。** 判定で `idempotent` を読む処理は入れたので、宣言の手段を足せば、そのまま効く。
- **テスト**：Go と同じ 4 つ（VersionsArePinned、SettingsChangeUnderACall、EffectIsNotWeakened、ChildVersionNotHere）を、両方に足した。
  - EffectIsNotWeakened では、止まったことの観測も待つ条件に入れた。Go のテストも同じ形に直した。

### kairod が実行の入力を返す（2026-10-09 追記）

上の「kairod では版による固定が効かない」は、次の変更で解消した。

- **ランタイムは版を知らないままにした（利用者の方針）。** 版を読んで、どの関数で動かすかを決めるのは、実行させる側（SDK）である。kairod は、SDK が書いた入力を、中身を見ずに返すだけにした。
- **`engine.Engine.GetInput` を足した。**
  - 終わっていない実行について、投入されたときの入力を `RunInfo.Input` に入れて返す。
  - 退避されている実行は、そのために読み込む。読み込みは、尋ねた人の分だけ払う（ADR 0041）。
  - 尋ねられたときだけ使う対応表をシャードに置き、実行ごとの構造体やメッセージには項目を足していない。そのため、待機中の実行のメモリは増えない。
  - `Get` は、これまでどおり入力を返さない。
- **HTTP API は `GET /v1/runs/{id}?input=true` で入力を返す。** ブロブに置かれた大きな入力も、中身に戻して返す。
- **TypeScript・Python の kairod 経由（`HttpBackend`）は、ワークフローを再開するときに入力を尋ねて、版を読む。** 入力を返さない古い kairod では、今の版で動かす。
- **テスト**
  - エンジン：`TestGetInput`。退避された実行の入力を返すこと、`Get` は返さないことを確かめる。
  - TypeScript・Python：kairod と埋め込みの両方で「始めたときの版で続く」テストを足した。入力を尋ねないようにすると、kairod の側が落ちることも確かめた。
