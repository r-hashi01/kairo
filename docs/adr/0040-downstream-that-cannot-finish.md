# 0040. Dify の記録を書けない実行は、やり直したうえで失敗として記録し、ack する

- 状態: 承認
- 日付: 2026-10-06
- 関連: ADR 0038（区画と ack）、ADR 0039（背圧）、ADR 0034（イベントの出口）

## 背景

ADR 0038 では、Dify のワーカーは、実行のイベントを Dify の DB に書き終えてから ack する。kairo-dify は、区画（シャード）ごとに、先頭から続けて ack されたところまで、エンジンの出口を ack する。

この規則では、Dify の記録をどうしても書けない実行が 1 件あると、次のことが起きる。2026-10-06 の負荷試験で実際に起きた。

1. human-input の待ちが kairo 側でタイムアウトし、実行が終わった（`run_end`）。
2. Dify のワーカーは、その `run_end` を受けると、Dify の一時停止の状態から実行を再開した。再開した実行はまた一時停止し、`run_end` を読まずに終わった。そのため、その `run_end` は ack されなかった。区画の割り当てが変わるたび、またはデーモンが再起動するたびに、同じことを繰り返した。
3. その区画（64 のうち 2 つ）に入った後続の実行は、ワーカーが ack しても、先頭が詰まっているためエンジンまで ack が届かず、すべて未確認として残った。
4. 未確認が 8,750 件まで溜まり、背圧（ADR 0039、`-feed-hold 10000`）がかかった。新しい実行を受け付けなくなり、再起動しても戻らなかった。

2 のタイムアウトの扱いは、ADR 0038 の範囲のバグとして別に直す。ただし、記録を書けない原因はほかにもありうる（Dify 側のバグ、壊れたデータ、消された行など）。原因によらず、1 件の実行がその区画を、そして背圧を通して全体を、止めないようにしたい。

ADR 0038 には、「ack は Dify の DB に書き終えてから」という規則しかない。書けない場合をどう扱うかは決めていない。

## 決定

Dify のワーカー（`core/workflow/kairo/feed.py` の `FeedWorker`）で、1 つの実行の下流の処理（`_downstream`）が、何度やり直しても完了しない場合を扱う。

1. **完了しなかった試行。** 次のどちらかを、その実行の下流の試行の失敗とする。
   - 例外で終わった。
   - 終わったが、渡されたエントリを 1 つも読まなかった。そのため、未読のエントリが残っている（今回の例。進展がない）。
2. **やり直し。** 失敗した試行は、間をあけてやり直す。回数は最大 3 回、間隔は 5 秒、30 秒とする。
   - やり直しを待つ間も、その実行の新しいエントリは受け取って溜める。
   - 回数はワーカーのプロセスのメモリに持つ。再起動したり、区画がほかのワーカーに移ったりしたら、数え直しになる。
3. **あきらめる。** 3 回失敗したら、次の順で処理する。
   - その実行を、Dify の DB で失敗として記録する。`workflow_runs` の状態を `failed` にし、エラーに「kairo: 実行の記録中にエラーが起きたため、記録を打ち切りました: <最後の原因>」を入れ、終了時刻を入れる。一時停止の行が残っていれば消す。チャットフローなら、メッセージにも同じエラーを入れる。
     - 実行の行がまだない（開始の記録の前に失敗した）なら、記録はせずに、ログにエラーとして残す。
   - その実行について受け取ったエントリを、読んだかどうかによらず、すべて ack する。
   - ログに、実行 ID、試行の回数、最後の原因を、エラーとして残す。
4. **それより後に届いた、同じ実行のエントリ。** すでにあきらめた実行のものは、下流を始めずに ack する。あきらめた実行の ID は、プロセスのメモリに有限の数だけ覚える。

kairo-dify とエンジンの側は変えない。ack の規則（区画の先頭から続けて）と背圧の規則（ADR 0039）もそのまま。区画の先頭が詰まるのは、やり直しの間（最長で数十秒）に限られる。

## 結果

- 記録を書けない実行が 1 件あっても、その区画は数十秒で流れ始める。背圧が全体を止めるのは、ワーカー全体が遅れている、または落ちているとき（ADR 0039 で確認した場合）だけになる。
- あきらめた実行は、Dify の画面に「失敗」として残る。記録の一部（あきらめた後のノードの記録など）は欠ける。黙って消えるのではなく、欠けたことが画面とログでわかる。
- 一時的な障害（DB の切断など）で 3 回とも失敗すると、本来は書けたはずの記録をあきらめてしまう。やり直しの間隔の合計（約 35 秒）より長い障害では、そうなる。
  - DB が止まっているなら、ほかの実行も書けないので、ワーカー全体が遅れて背圧がかかる。新しい実行は止まるが、記録は失われない。あきらめるのは、1 件だけが繰り返し失敗する場合に限られる。
- 下流が終わらずに止まり続ける場合（デッドロックなど）は、この ADR では扱わない。必要になったら、別に決める。
- テスト（Dify のブランチに足す）:
  - 例外で失敗し続ける下流が、3 回で打ち切られ、実行が失敗として記録され、エントリがすべて ack されること。
  - エントリを読まずに終わる下流が、同じように打ち切られること。
  - 2 回失敗して 3 回目で成功した下流は、普通に ack されること。
  - あきらめた後に届いたエントリが、下流を始めずに ack されること。
- 実際の Dify で、今回止まった環境（タイムアウトした human-input の実行 2 件）で、背圧が解けることを確かめる。

## 検討した代替案

- 失敗したら、やり直さずにすぐ ack する: 一時的な障害でも記録が黙って消える。採らなかった。
- 詰まったままにし、詰まった区画の後ろのエントリを背圧の数から除く: 全体は止まらないが、その区画に入る実行は永久に詰まり続ける。採らなかった。
- kairo-dify の側で、一定時間 ack されない先頭を飛ばす: Dify の記録がどうなったかを kairo-dify は知らない。失敗として記録できず、黙って欠ける。採らなかった。

## 実装で詰めた詳細（2026-10-06 追記、ADR 0017）

- 実装: Dify のブランチ `feat/kairo-engine` の `core/workflow/kairo/feed.py`（`FeedWorker._failed`、`_retry`、`_give_up`、`record_failure`）。
  - やり直しでは、前の試行が読んだものも含めて、その実行の受け取ったイベントを最初から渡し直す。区画を配り直したときと同じ扱いになる。
  - 失敗の記録の文言は「kairo: recording the run stopped after an error: <原因>」にした（Dify の他のエラーと同じく英語）。
  - やり直しを待つ間に区画がほかのワーカーに移ったら、やり直さない（新しい持ち主が最初から受け取る）。
- テスト: `tests/unit_tests/core/workflow/kairo/test_feed.py` の 4 件（失敗し続ける、何も読まない、3 回目で成功、あきらめた後のエントリ）。
- 実際の Dify での確認: 止まった環境では、背景の 2 件が ADR 0038 の修正（再開した下流が `run_end` を読む）で記録され、ack された。背圧が解け、新しい実行を受け付けた。あきらめる経路は、実機では起きていない（テストだけで確かめた）。
