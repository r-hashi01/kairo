# kairo 検証マップ（TS SDK・埋め込み実行）

利用者に見える kairo の振る舞いを確かめるための、保守される一覧です。駆動の前に読み、該当する機能ファイルを手順として使います。

## 前提

- `kv.sh doctor` が `doctor: ok` を出す。
- 手順ごとに、使い捨ての作業ディレクトリと、このチェックアウトから作った `kairo.wasm` を使う（`kv.sh journey` が用意する）。
- 自分の手順が起こしたプロセスとデータベースだけを扱う。利用者の `kairo.db` や、ほかで動いているプロセスには触れない。

## 駆動の約束

- 1 つの役割（実行・シグナル・決着・状態の読み取り）は 1 つの Node プロセス。利用者のアプリと同じく、プロセスどうしは同じ SQLite ファイルだけを共有する。
- クラッシュは SIGKILL で起こす。
- 待ちは、条件（ファイルの出現、プロセスの観測イベント、プロセスの終了）を見て待つ。固定の sleep で待つのは、借用の期限切れを待つときだけ。
- 同じデータベースを第三のプロセスで繰り返し開いて様子を見ない（利用者のアプリにはない競合を足すことになる）。

## 証明と省略の報告

- 操作（どのプロセスに何をさせたか）と、結果の状態（戻り値、`inspect-*.json`、`markers/`）の両方を残す。
- 作用の回数は `markers/` の `<order>.done` で数える。
- 各チェックの `PASS`/`FAIL` と `RESULT` を、証拠のディレクトリとともに報告する。
- 流せなかった手順は、試したコマンドと満たせなかった前提を書いて報告する。別の手順で代わりに確かめたことにしない。

## 機能ファイルの約束

各ファイルは H1 と、利用者に見える振る舞いを述べる 1 段落で始め、次の 4 つの H2 をこの順に持ちます：`Sub-features`、`How to get to it (user POV)`、`Driving it with kv.sh`、`Gotchas`。

## 機能

- [ワークフローを実行する](./run-a-workflow.md)：1 回の実行、結果、作用 1 回、保存状態。
- [クラッシュのあとで再開する](./resume-after-crash.md)：SIGKILL、同じ ID での再実行、作用 1 回、耐久タイマー。
- [別のプロセスからシグナルを送る](./signal-from-another-process.md)：`waitFor` と `k.signal`。
- [結果不明の実の作用を確認に回す](./unknown-outcome-review.md)：`blocked`、再実行しないこと、`k.resolve`。
